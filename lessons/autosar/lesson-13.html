Bài 13: Chi tiết Tầng Application Software

Trong các bài trước, chúng ta đã tìm hiểu Application Software ở mức tổng quan và hiểu được vị trí của nó trong kiến trúc AUTOSAR Classic. Từ bài này, chúng ta bắt đầu đi sâu vào từng thành phần bên trong Application Software và cách chúng phối hợp với nhau.

Application Software là nơi chứa phần lớn logic chức năng của ECU. Thay vì trực tiếp điều khiển phần cứng, Application Software được tổ chức thành các Software Component (SWC) và tương tác với phần còn lại của hệ thống thông qua RTE.

Phạm vi của phần này: Từ Bài 13 trở đi, nội dung sẽ đi sâu hơn so với phần tổng quan. Tuy nhiên, mục tiêu vẫn là hiểu bản chất và cách các thành phần liên kết với nhau trước khi đi vào các cấu hình AUTOSAR hoặc ARXML chuyên sâu.

1. Application Software là gì?

Application Software là tầng chứa các chức năng nghiệp vụ của ECU. Đây là nơi triển khai các logic liên quan trực tiếp đến chức năng mà ECU cần thực hiện.

Ví dụ, đối với một Body ECU, Application Software có thể chứa các chức năng như:

  • Điều khiển khóa cửa.
  • Điều khiển cửa sổ.
  • Điều khiển đèn ngoại thất.
  • Điều khiển cần gạt nước.
  • Xử lý trạng thái ignition.
  • Giám sát một số điều kiện của ECU.

Một đặc điểm quan trọng của Application Software trong AUTOSAR là nó không nên phụ thuộc trực tiếp vào phần cứng cụ thể. 

Application Software
        │
        │  RTE
        ▼
Basic Software
        │
        ▼
Hardware

Ví dụ, logic "nếu điều kiện A xảy ra thì bật đèn" thuộc Application Software. Application Software không cần trực tiếp thao tác thanh ghi GPIO để bật đèn.

2. Software Component - SWC

Thành phần quan trọng nhất của Application Software là Software Component (SWC).

Có thể hiểu SWC là một đơn vị phần mềm đại diện cho một chức năng hoặc một nhóm chức năng có liên quan. 

Application Software
│
├── Door Control SWC
├── Window Control SWC
├── Exterior Light SWC
├── Wiper Control SWC
└── Ignition Control SWC

Mỗi SWC có thể chứa:

  • Logic xử lý.
  • Các Runnable.
  • Input và Output thông qua Port.
  • Các Interface mà SWC sử dụng.
  • Các Event kích hoạt Runnable.

Việc chia Application Software thành các SWC giúp hệ thống có cấu trúc rõ ràng và các chức năng có thể được phát triển, kiểm thử và tái sử dụng độc lập hơn.

3. Một SWC gồm những thành phần nào?

Ở mức khái niệm chi tiết hơn, có thể hình dung một SWC như sau: 

                 Software Component
        ┌─────────────────────────────────┐
        │                                 │
        │        Runnable(s)              │
        │            │                    │
        │            ▼                    │
        │      Application Logic          │
        │                                 │
        │   ┌───────────┐ ┌───────────┐   │
        │   │   Input   │ │  Output   │   │
        │   │   Port    │ │   Port    │   │
        │   └───────────┘ └───────────┘   │
        │                                 │
        │        Events / Interfaces      │
        │                                 │
        └─────────────────────────────────┘

Các thành phần này có quan hệ với nhau. Ví dụ, một Event có thể kích hoạt một Runnable, Runnable đọc dữ liệu từ Input Port, thực hiện logic và gửi kết quả thông qua Output Port.

4. Runnable là gì?

Runnable là một đơn vị thực thi bên trong SWC. Có thể hiểu đơn giản rằng đây là phần code thực hiện một công việc cụ thể của Application Software.

Một SWC có thể có một hoặc nhiều Runnable. 

Exterior Light SWC
│
├── ExtLight_Init
│
├── ExtLight_Control
│
└── ExtLight_Shutdown

Mỗi Runnable có thể đảm nhiệm một nhiệm vụ khác nhau. Ví dụ:

  • ExtLight_Init: xử lý khởi tạo.
  • ExtLight_Control: xử lý logic điều khiển đèn.
  • ExtLight_Shutdown: xử lý khi ECU chuyển trạng thái.

Tuy nhiên, Runnable không tự chạy một cách tùy ý. Việc một Runnable được thực thi phụ thuộc vào Event liên kết với nó.

5. Event và việc kích hoạt Runnable

Event xác định điều kiện khiến một Runnable được kích hoạt. Đây là một phần quan trọng để hiểu cách Application Software thực sự được thực thi.

Một cách đơn giản có thể hình dung: 

Event
  │
  │ kích hoạt
  ▼
Runnable
  │
  │ thực thi
  ▼
Application Logic

Có nhiều kiểu điều kiện kích hoạt khác nhau. Ở mức cơ bản, chúng ta có thể gặp:

  • Timing Event: kích hoạt theo chu kỳ thời gian.
  • Data Received Event: kích hoạt khi có dữ liệu mới.
  • Operation Invoked Event: liên quan đến việc một operation được gọi.
  • Init Event: dùng cho quá trình khởi tạo.

Ví dụ một Runnable được thực thi mỗi 100 ms: 

Time
 │
 ├── 0 ms     → Runnable
 │
 ├── 100 ms   → Runnable
 │
 ├── 200 ms   → Runnable
 │
 ├── 300 ms   → Runnable
 │
 └── ...

Điều này rất quan trọng trong hệ thống embedded vì Application Software thường phải xử lý dữ liệu theo thời gian xác định.

6. Port của Software Component

SWC không giao tiếp trực tiếp với các SWC khác bằng cách truy cập trực tiếp vào code hoặc biến nội bộ của nhau. Thay vào đó, AUTOSAR sử dụng Port để định nghĩa điểm giao tiếp của SWC.

Có thể hình dung Port giống như một "cổng giao tiếp" của SWC: 

        SWC A                       SWC B
   ┌──────────────┐            ┌──────────────┐
   │              │            │              │
   │    Output    ├────────────┼─── Input     │
   │     Port     │            │     Port     │
   │              │            │              │
   └──────────────┘            └──────────────┘

Port giúp tách biệt logic bên trong SWC với cách SWC giao tiếp với bên ngoài.

Đây là một trong những ý tưởng quan trọng của AUTOSAR: Application Software tập trung vào chức năng, còn cơ chế giao tiếp được xử lý thông qua kiến trúc AUTOSAR và RTE.

7. Sender/Receiver và Client/Server

Trong AUTOSAR, hai kiểu giao tiếp quan trọng giữa các Software Component là Sender/Receiver và Client/Server.

7.1. Sender/Receiver

Sender/Receiver phù hợp với việc trao đổi dữ liệu hoặc trạng thái. Một SWC gửi dữ liệu và SWC khác nhận dữ liệu. 

SWC A
  │
  │ gửi dữ liệu
  ▼
RTE
  │
  │ truyền dữ liệu
  ▼
SWC B
  │
  │ đọc dữ liệu
  ▼
Application Logic

Ví dụ: 

Door Status SWC
       │
       │ DoorOpen = TRUE
       ▼
      RTE
       │
       ▼
Interior Light SWC
       │
       ▼
Bật đèn nội thất

7.2. Client/Server

Client/Server phù hợp khi một SWC yêu cầu một chức năng được thực hiện bởi SWC hoặc Service khác. 

Client SWC
    │
    │ Request
    ▼
  RTE
    │
    ▼
Server SWC
    │
    │ Execute operation
    ▼
  Result
    │
    ▼
Client SWC

Có thể hình dung Sender/Receiver thiên về trao đổi dữ liệu, trong khi Client/Server thiên về gọi một chức năng hoặc operation.

8. Interface là gì?

Port xác định điểm giao tiếp của SWC, còn Interface định nghĩa nội dung và cách thức giao tiếp đó.

Ví dụ về mặt ý tưởng: 

SWC A
 │
 │ Output Port
 │
 ▼
Data Interface
 │
 ▼
Input Port
 │
 ▼
SWC B

Interface giúp hai SWC hiểu được chúng đang trao đổi loại thông tin nào hoặc cung cấp operation nào.

Vì vậy, khi phân tích một SWC, chúng ta thường cần xem xét ít nhất:

  • SWC cung cấp dữ liệu gì?
  • SWC nhận dữ liệu gì?
  • SWC sử dụng Interface nào?
  • Port nào kết nối với Interface đó?

9. RTE đứng giữa Application Software như thế nào?

RTE là lớp trung gian giúp Application Software giao tiếp với các thành phần khác mà không cần Application Software biết chi tiết cách giao tiếp được triển khai bên dưới. 

        Application Software
        ┌───────────────────┐
        │      SWC A        │
        │                   │
        │    Runnable       │
        └─────────┬─────────┘
                  │
                  │ RTE API
                  ▼
        ┌───────────────────┐
        │        RTE        │
        └─────────┬─────────┘
                  │
          ┌───────┴────────┐
          ▼                ▼
       SWC khác          BSW

Ví dụ, nếu Application cần dữ liệu từ một SWC khác, Application không cần biết dữ liệu đó cuối cùng được truyền bằng CAN, LIN hay một cơ chế nội bộ nào.

RTE cung cấp phần giao tiếp phù hợp để Application Software sử dụng.

10. Ví dụ: Điều khiển đèn ngoại thất

Hãy xét một ví dụ đơn giản về chức năng điều khiển đèn.

Giả sử hệ thống có:

  • Input: trạng thái công tắc đèn.
  • Application: logic quyết định bật/tắt đèn.
  • Output: yêu cầu điều khiển đèn.

Có thể tổ chức Application Software như sau: 

Exterior Light SWC
│
├── Input Port
│      └── LightSwitchStatus
│
├── Runnable
│      └── ExtLightControl_Run
│
└── Output Port
       └── LightCommand

Luồng xử lý: 

LightSwitchStatus
       │
       ▼
     Input
      Port
       │
       ▼
ExtLightControl_Run()
       │
       │ Application Logic
       ▼
 LightCommand
       │
       ▼
    Output
      Port

Nếu công tắc chuyển sang trạng thái ON, Runnable có thể xử lý: 

if (LightSwitchStatus == ON)
{
    LightCommand = ON;
}
else
{
    LightCommand = OFF;
}

Đây mới là logic Application. Việc tín hiệu cuối cùng đi đến GPIO, CAN, LIN hoặc phần cứng nào không thuộc trách nhiệm trực tiếp của đoạn logic này.

11. Từ Application đến Hardware

Khi kết hợp kiến thức từ các bài trước, chúng ta có thể mở rộng ví dụ trên thành toàn bộ luồng: 

Physical Input
      │
      ▼
   Hardware
      │
      ▼
     MCAL
      │
      ▼
    BSW / Abstraction
      │
      ▼
      RTE
      │
      ▼
Application SWC
      │
      │ Application Logic
      ▼
      RTE
      │
      ▼
    BSW / MCAL
      │
      ▼
   Hardware
      │
      ▼
Physical Output

Điểm cần chú ý là Application Software nằm ở phía trên của kiến trúc và tập trung vào what: ECU cần thực hiện chức năng gì.

Các tầng bên dưới chịu trách nhiệm nhiều hơn về how: dữ liệu được truyền như thế nào, phần cứng được truy cập ra sao, driver nào được sử dụng và thiết bị nào thực hiện thao tác.

12. Ví dụ chi tiết hơn: Door Lock

Hãy xem xét một chức năng khóa cửa đơn giản. 

                  Door Lock System

       ┌─────────────────────────────┐
       │     Door Lock Control SWC   │
       │                             │
       │ Input:                      │
       │  - LockRequest              │
       │  - VehicleSpeed             │
       │                             │
       │ Runnable:                   │
       │  - DoorLockControl_Run      │
       │                             │
       │ Output:                     │
       │  - LockCommand              │
       └──────────────┬──────────────┘
                      │
                      ▼
                     RTE
                      │
                      ▼
                 BSW / MCAL
                      │
                      ▼
               Door Lock Hardware

Runnable có thể thực hiện logic ở mức khái niệm:

  1. Đọc yêu cầu khóa cửa.
  2. Kiểm tra các điều kiện liên quan.
  3. Quyết định có cho phép khóa hay không.
  4. Tạo yêu cầu điều khiển khóa.

Điều quan trọng là logic này có thể được phát triển độc lập tương đối với loại microcontroller cụ thể.

13. Internal Behavior của SWC

Khi đi sâu hơn vào SWC, chúng ta không chỉ quan tâm SWC giao tiếp với bên ngoài như thế nào mà còn phải quan tâm đến Internal Behavior.

Internal Behavior mô tả cách SWC hoạt động bên trong, bao gồm những thành phần như:

  • Runnable.
  • Event kích hoạt Runnable.
  • Data được sử dụng bởi Runnable.
  • Quan hệ giữa Runnable và các Port.
  • Các thông tin liên quan đến việc thực thi.

Có thể hình dung: 

SWC
│
├── Ports
│
├── Interfaces
│
└── Internal Behavior
      │
      ├── Runnable 1
      ├── Runnable 2
      ├── Events
      └── Data / Execution information

Đây là một khái niệm quan trọng khi sau này chúng ta bắt đầu đọc và phân tích AUTOSAR configuration hoặc ARXML.

14. VFB - Virtual Functional Bus

Một khái niệm quan trọng khi tìm hiểu Application Software là Virtual Functional Bus (VFB).

VFB cung cấp một mô hình giao tiếp ở mức trừu tượng cho các Software Component. 

        SWC A                         SWC B
          │                             │
          │                             │
          └─────────── VFB ─────────────┘
                        │
                        │
                 Communication
                  abstraction

Nhờ cách tiếp cận này, SWC có thể được thiết kế dựa trên chức năng và giao tiếp cần thiết thay vì ngay lập tức phụ thuộc vào cách hệ thống được triển khai trên một ECU cụ thể.

Khi triển khai thực tế, các kết nối logic này sẽ được ánh xạ thông qua RTE và các tầng bên dưới.

15. Application Software trong một ECU

Một ECU thực tế thường không chỉ có một SWC. Nhiều SWC có thể cùng tồn tại và phối hợp với nhau. 

                    ECU
                     │
          ┌──────────┴──────────┐
          │ Application Software│
          │                     │
          │ ┌─────────────────┐ │
          │ │ Door Control    │ │
          │ │ SWC             │ │
          │ └─────────────────┘ │
          │                     │
          │ ┌─────────────────┐ │
          │ │ Window Control  │ │
          │ │ SWC             │ │
          │ └─────────────────┘ │
          │                     │
          │ ┌─────────────────┐ │
          │ │ Light Control   │ │
          │ │ SWC             │ │
          │ └─────────────────┘ │
          │                     │
          └──────────┬──────────┘
                     │
                     ▼
                    RTE
                     │
                     ▼
                    BSW
                     │
                     ▼
                  Hardware

Các SWC có thể trao đổi dữ liệu với nhau hoặc sử dụng các Service do BSW cung cấp thông qua kiến trúc AUTOSAR.

16. Tại sao Application Software không truy cập Hardware trực tiếp?

Đây là một trong những điểm quan trọng nhất cần ghi nhớ.

Nếu Application Software truy cập trực tiếp thanh ghi hoặc peripheral của microcontroller, code sẽ phụ thuộc mạnh vào hardware cụ thể. 

Application
     │
     │ Direct register access
     ▼
Microcontroller A

Khi thay đổi microcontroller, phần Application có thể phải thay đổi rất nhiều.

AUTOSAR cố gắng tách các phần này: 

Application
     │
     ▼
    RTE
     │
     ▼
    BSW
     │
     ▼
    MCAL
     │
     ▼
Hardware

Nhờ đó, Application Software có mức độ độc lập cao hơn đối với hardware và có thể được tái sử dụng trong những hệ thống tương tự.

17. Cách phân tích một Application SWC

Khi gặp một SWC trong tài liệu thiết kế AUTOSAR, có thể phân tích theo thứ tự sau:

  1. SWC này thực hiện chức năng gì?
  2. SWC nhận những dữ liệu nào?
  3. SWC cung cấp những dữ liệu nào?
  4. SWC có những Runnable nào?
  5. Runnable nào được kích hoạt bởi Event nào?
  6. SWC sử dụng loại Interface nào?
  7. SWC giao tiếp với SWC nào khác?
  8. Dữ liệu đi qua RTE như thế nào?
  9. Cuối cùng dữ liệu được kết nối tới BSW hoặc Hardware nào?

Đây là cách tiếp cận rất hữu ích khi đọc một architecture diagram hoặc thiết kế AUTOSAR thực tế.

18. Ví dụ tổng hợp

Giả sử chúng ta có chức năng: "Tự động khóa cửa khi xe đạt tốc độ nhất định". 

Vehicle Speed
      │
      ▼
  Input Port
      │
      ▼
Door Lock Control SWC
      │
      ▼
Runnable
DoorLockControl_Run()
      │
      ├── Read vehicle speed
      │
      ├── Check lock condition
      │
      └── Generate LockCommand
                  │
                  ▼
             Output Port
                  │
                  ▼
                 RTE
                  │
                  ▼
             BSW / MCAL
                  │
                  ▼
           Door Lock Hardware

Trong ví dụ này:

  • Vehicle Speed là dữ liệu đầu vào.
  • Door Lock Control SWC chứa logic chức năng.
  • Runnable thực hiện việc xử lý.
  • Input/Output Port định nghĩa giao tiếp.
  • RTE cung cấp cơ chế giao tiếp giữa Application và phần còn lại của hệ thống.
  • BSW/MCAL đảm nhiệm phần triển khai phía dưới.

19. Những khái niệm cần nhớ

Khái niệm Ý nghĩa

20. Tóm tắt

Application Software là nơi chứa logic chức năng của ECU trong AUTOSAR Classic. Application Software được tổ chức thành các Software Component (SWC).

Mỗi SWC có thể chứa nhiều Runnable. Runnable được kích hoạt bởi các Event và thực hiện application logic.

SWC giao tiếp với bên ngoài thông qua Port và Interface. Hai kiểu giao tiếp quan trọng là Sender/Receiver và Client/Server.

RTE đóng vai trò trung gian giữa Application Software và các thành phần khác của hệ thống. Nhờ đó, Application Software có thể tập trung vào chức năng thay vì trực tiếp phụ thuộc vào Hardware.

Có thể ghi nhớ chuỗi chính:

SWC → Runnable → Event → Port/Interface → RTE → BSW/Hardware
