Bài 14: Chi tiết tầng Runtime Environment

Trong Bài 5, chúng ta đã tìm hiểu RTE ở mức tổng quan và biết rằng RTE nằm giữa Application Software và Basic Software. Trong bài này, chúng ta sẽ đi sâu hơn vào cách RTE thực hiện vai trò trung gian đó và cách Application Software sử dụng RTE để giao tiếp với các thành phần khác.

RTE là một trong những thành phần quan trọng nhất của AUTOSAR Classic vì nó tạo ra lớp giao tiếp giữa Software Component (SWC) và phần còn lại của hệ thống.

Ý tưởng chính: Application Software tập trung vào logic chức năng, trong khi RTE cung cấp cơ chế để logic đó giao tiếp với các SWC khác, với Basic Software và với các Service mà hệ thống cung cấp.

1. RTE là gì?

Runtime Environment (RTE) là lớp phần mềm nằm giữa Application Software và Basic Software trong AUTOSAR Classic. 

┌──────────────────────────────┐
│     Application Software     │
│                              │
│   SWC A     SWC B     SWC C  │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│             RTE              │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│      Basic Software (BSW)    │
└──────────────┬───────────────┘
               │
               ▼
            Hardware

RTE không phải là nơi chứa toàn bộ application logic. Logic chức năng vẫn nằm trong SWC.

RTE chủ yếu cung cấp cơ chế giao tiếp và kết nối để các thành phần Application Software có thể hoạt động trong kiến trúc AUTOSAR.

2. Tại sao AUTOSAR cần RTE?

Nếu không có lớp trung gian, Application Software có thể phải biết rất nhiều chi tiết về cách dữ liệu được truyền hoặc cách Service bên dưới được triển khai.

Ví dụ, một Application SWC cần dữ liệu tốc độ xe. Nếu Application phải tự biết dữ liệu đó đến từ CAN, LIN hay một nguồn khác thì Application sẽ bị phụ thuộc vào cơ chế truyền thông. 

Application SWC
      │
      ├── Biết CAN?
      ├── Biết LIN?
      ├── Biết Driver?
      └── Biết Hardware?
           │
           ▼
       Phức tạp hơn

Với RTE, Application có thể tập trung vào dữ liệu và chức năng mà nó cần: 

Application SWC
      │
      │ yêu cầu / trao đổi dữ liệu
      ▼
     RTE
      │
      │ xử lý kết nối
      ▼
BSW / SWC khác / Service

Vì vậy, RTE giúp tách Application Software khỏi cách giao tiếp và triển khai phía dưới.

3. RTE không phải là một lớp "logic chức năng"

Một hiểu nhầm phổ biến là coi RTE như nơi xử lý logic của ECU. Thực tế, logic chức năng vẫn thuộc về Application Software. 

Application SWC
      │
      │ "Nếu tốc độ > X thì khóa cửa"
      │
      ▼
   Application Logic

      │
      ▼

      RTE
      │
      │ Cung cấp cơ chế giao tiếp
      ▼

      BSW

RTE không quyết định xe có nên khóa cửa hay không. Application SWC mới là nơi chứa quyết định đó.

RTE giúp đưa dữ liệu cần thiết đến SWC và đưa kết quả của SWC đến nơi cần sử dụng.

4. RTE và Software Component

RTE được thiết kế dựa trên các giao tiếp được mô tả giữa các Software Component. 

             Application Software

      ┌──────────────┐
      │    SWC A     │
      └──────┬───────┘
             │
             │
             ▼
      ┌──────────────┐
      │     RTE      │
      └──────┬───────┘
             │
             │
             ▼
      ┌──────────────┐
      │    SWC B     │
      └──────────────┘

Nếu SWC A cần gửi dữ liệu cho SWC B, Application code không cần trực tiếp gọi code nội bộ của SWC B.

Thay vào đó, giao tiếp được định nghĩa thông qua các Port và Interface, sau đó RTE cung cấp cơ chế thực hiện kết nối đó.

5. RTE và Port

Trong bài trước, chúng ta đã biết Port là điểm giao tiếp của SWC. RTE sử dụng các định nghĩa giao tiếp đó để kết nối các thành phần. 

SWC A
┌──────────────┐
│              │
│ Output Port  ├──────┐
│              │      │
└──────────────┘      │
                      ▼
                     RTE
                      │
                      ▼
               Input Port
┌──────────────┐      │
│              │◄─────┘
│    SWC B     │
│              │
└──────────────┘

Vì vậy, khi phân tích một kết nối trong AUTOSAR, có thể suy nghĩ theo chuỗi: 

SWC
 ↓
Port
 ↓
Interface
 ↓
RTE
 ↓
Port
 ↓
SWC

6. RTE và Sender/Receiver

Một trong những trường hợp phổ biến nhất RTE xử lý là giao tiếp Sender/Receiver.

Ví dụ SWC A gửi trạng thái cửa: 

Door Status SWC
       │
       │ DoorStatus
       ▼
     RTE
       │
       ▼
Interior Light SWC
       │
       │ DoorStatus
       ▼
Application Logic

SWC gửi dữ liệu được gọi là Sender, còn SWC sử dụng dữ liệu được gọi là Receiver.

Application không cần trực tiếp quản lý toàn bộ cơ chế truyền dữ liệu giữa hai SWC. RTE thực hiện phần kết nối theo kiến trúc đã được định nghĩa.

7. RTE và Client/Server

RTE cũng hỗ trợ giao tiếp theo mô hình Client/Server.

Trong mô hình này, một SWC yêu cầu một operation và một SWC khác cung cấp operation đó. 

Client SWC
     │
     │ Request Operation
     ▼
    RTE
     │
     ▼
Server SWC
     │
     │ Execute
     ▼
  Result
     │
     ▼
    RTE
     │
     ▼
Client SWC

Ví dụ, một SWC có thể yêu cầu một Service kiểm tra một điều kiện hoặc thực hiện một chức năng.

Điểm quan trọng là Client không cần biết chi tiết bên trong Server được triển khai như thế nào.

8. RTE và Runnable

RTE không chỉ liên quan đến việc trao đổi dữ liệu mà còn liên quan đến cách các Runnable trong SWC được kích hoạt và tương tác với môi trường. 

Event
  │
  ▼
RTE / Runtime mechanism
  │
  ▼
Runnable
  │
  ▼
Application Logic

Ví dụ một Runnable cần chạy định kỳ: 

100 ms
   │
   ▼
Runnable A
   │
   ▼
Read Data
   │
   ▼
Process
   │
   ▼
Write Result
   │
   ▼
Wait for next activation

Nhờ cơ chế Runtime của AUTOSAR, Application Software được tổ chức thành những đơn vị thực thi rõ ràng thay vì tự xây dựng toàn bộ cơ chế scheduling và giao tiếp.

9. RTE và Timing Event

Một Runnable có thể được kích hoạt theo chu kỳ. Ví dụ một Runnable xử lý dữ liệu nhiệt độ có thể được yêu cầu thực thi mỗi 100 ms. 

Time
 │
 ├── 0 ms      → Runnable
 │
 ├── 100 ms    → Runnable
 │
 ├── 200 ms    → Runnable
 │
 ├── 300 ms    → Runnable
 │
 └── ...

Application developer quan tâm đến việc Runnable cần được thực thi theo chu kỳ nào và xử lý dữ liệu gì.

Các cơ chế bên dưới của hệ thống chịu trách nhiệm đảm bảo việc thực thi phù hợp với cấu hình và kiến trúc của ECU.

10. RTE và Data Received Event

Không phải mọi Runnable đều phải chạy theo chu kỳ. Một Runnable có thể được kích hoạt khi dữ liệu mới xuất hiện. 

New Data
   │
   ▼
Input Port
   │
   ▼
  RTE
   │
   │ Data Received Event
   ▼
Runnable
   │
   ▼
Process Data

Ví dụ: 

CAN Data
   │
   ▼
Communication Stack
   │
   ▼
   RTE
   │
   ▼
Data Received Event
   │
   ▼
VehicleSpeed_Run()
   │
   ▼
Application Logic

Như vậy, RTE tạo cầu nối giữa dữ liệu được cung cấp cho Application và việc thực thi Runnable tương ứng.

11. RTE API ở mức khái niệm

Trong mã nguồn Application, việc giao tiếp với môi trường thường được thực hiện thông qua các cơ chế truy cập do RTE cung cấp.

Ở mức khái niệm, có thể hình dung Application thực hiện: 

Runnable
   │
   ├── Đọc dữ liệu từ môi trường
   │
   ├── Xử lý dữ liệu
   │
   └── Ghi kết quả ra môi trường
          │
          ▼
         RTE

Tùy vào kiểu giao tiếp, RTE cung cấp các cơ chế phù hợp cho việc đọc, ghi dữ liệu hoặc gọi operation.

Ở giai đoạn này, điều quan trọng cần nhớ là: Application sử dụng giao diện do RTE cung cấp thay vì trực tiếp truy cập các tầng bên dưới.

Lưu ý: Các API RTE cụ thể, cách đặt tên API, tham số, return value và code được sinh tự động sẽ được tìm hiểu ở phần chuyên sâu hơn. Trong bài này chỉ cần hiểu vai trò của chúng trong kiến trúc.

12. RTE và Basic Software

Một trong những vai trò quan trọng nhất của RTE là kết nối Application Software với Basic Software. 

Application SWC
      │
      ▼
     RTE
      │
      ▼
Service / BSW
      │
      ▼
ECU Abstraction
      │
      ▼
MCAL
      │
      ▼
Hardware

Ví dụ, Application cần một dịch vụ nào đó của ECU. Application không nhất thiết phải biết Service đó được thực hiện bằng module BSW nào hoặc module đó cuối cùng truy cập hardware ra sao.

RTE tạo ra lớp kết nối cần thiết giữa hai phía.

13. RTE và Service

Ngoài việc kết nối các SWC với nhau, Application Software còn có thể sử dụng các chức năng được cung cấp bởi BSW Service. 

Application SWC
      │
      │ Request service
      ▼
     RTE
      │
      ▼
BSW Service
      │
      ▼
Underlying BSW modules

Điều này giúp Application Software không phải tự triển khai những chức năng hệ thống đã được AUTOSAR hoặc BSW cung cấp.

Có thể hiểu đơn giản:

  • Application: "Tôi cần chức năng này."
  • RTE: "Tôi cung cấp đường kết nối."
  • BSW Service: "Tôi thực hiện chức năng đó."

14. RTE trong giao tiếp giữa các SWC cùng ECU

Một trường hợp đơn giản là hai SWC nằm trên cùng một ECU. 

                    ECU
 ┌─────────────────────────────────────┐
 │                                     │
 │   SWC A                 SWC B       │
 │    │                      ▲         │
 │    │ Output               │ Input   │
 │    ▼                      │         │
 │   ┌────────────────────────┐        │
 │   │          RTE           │        │
 │   └────────────────────────┘        │
 │                                     │
 └─────────────────────────────────────┘

RTE xử lý kết nối logic giữa hai SWC dựa trên các giao tiếp được thiết kế.

Đây là một trong những trường hợp thể hiện rõ nhất vai trò "middleware" của RTE.

15. RTE và giao tiếp giữa các ECU

Một điểm quan trọng là RTE không trực tiếp thay thế Communication Stack.

Nếu dữ liệu cần đi từ một ECU sang ECU khác, luồng tổng quát sẽ có nhiều tầng hơn: 

ECU A

Application SWC
      │
      ▼
     RTE
      │
      ▼
Communication Stack
      │
      ▼
CAN / LIN / Ethernet
      │
      │ Network
      ▼
CAN / LIN / Ethernet
      │
      ▼
Communication Stack
      │
      ▼
     RTE
      │
      ▼
Application SWC

ECU B

RTE nằm ở phía Application của mỗi ECU, còn việc truyền dữ liệu qua mạng được thực hiện bởi Communication Stack và phần cứng truyền thông.

Vì vậy, cần phân biệt:

  • RTE: kết nối Application với môi trường runtime.
  • Communication Stack: xử lý việc truyền thông.
  • MCAL/Driver: giao tiếp với phần cứng.

16. Ví dụ: CAN đến Application

Giả sử ECU nhận tốc độ xe thông qua CAN. 

CAN Bus
   │
   ▼
CAN Controller
   │
   ▼
CAN Driver
   │
   ▼
Communication Stack
   │
   ▼
   RTE
   │
   ▼
Vehicle Speed SWC
   │
   ▼
Runnable
   │
   ▼
Application Logic

Application SWC không cần trực tiếp đọc CAN Controller. Nó chỉ cần nhận dữ liệu theo giao diện mà Application đã được thiết kế.

Đây là một ví dụ điển hình cho việc RTE giúp tách Application khỏi cơ chế truyền thông bên dưới.

17. Ví dụ: Application đến CAN

Luồng ngược lại cũng có thể xảy ra khi Application muốn gửi một dữ liệu ra mạng. 

Application SWC
      │
      ▼
    Runnable
      │
      ▼
     RTE
      │
      ▼
Communication Stack
      │
      ▼
CAN Driver
      │
      ▼
CAN Controller
      │
      ▼
CAN Bus

Application chỉ tập trung tạo ra dữ liệu hoặc trạng thái cần gửi. Các tầng bên dưới đảm nhiệm việc biến yêu cầu đó thành dữ liệu truyền thông thực tế.

18. RTE và tính độc lập của Application

Một trong những lợi ích lớn của RTE là hỗ trợ tính độc lập của Application Software.

Ví dụ một Application SWC có thể sử dụng dữ liệu VehicleSpeed.

Ở cấp Application, điều quan trọng là: 

VehicleSpeed
     │
     ▼
Application Logic

Application không nhất thiết phải quan tâm dữ liệu này đến từ:

  • CAN.
  • LIN.
  • Một SWC khác.
  • Một Service.
  • Một nguồn dữ liệu khác được hệ thống thiết kế.

Chính sự tách biệt này giúp kiến trúc AUTOSAR có khả năng tái sử dụng Application Software tốt hơn.

19. RTE không hoàn toàn giống một Middleware thông thường

Có thể gọi RTE là một lớp trung gian hoặc middleware ở mức khái niệm, nhưng cần hiểu rằng RTE trong AUTOSAR được tạo ra dựa trên kiến trúc và cấu hình cụ thể của ECU.

Nó không phải một phần mềm middleware chung được viết hoàn toàn độc lập rồi chạy giống nhau trên mọi ECU. 

System Design
      │
      ▼
SWC / Ports / Interfaces
      │
      ▼
ECU Mapping
      │
      ▼
RTE
      │
      ▼
Generated / Configured Runtime Connections

Do đó, RTE của một ECU cụ thể phụ thuộc vào cách các SWC, giao tiếp và các thành phần hệ thống được thiết kế và ánh xạ.

20. RTE và ECU Mapping

Trong hệ thống AUTOSAR, một Software Component ở mức thiết kế chức năng có thể được ánh xạ vào một ECU cụ thể. 

Software Architecture
        │
        ├── SWC A
        ├── SWC B
        └── SWC C
                │
                │ ECU Mapping
                ▼
              ECU 1
                │
                ▼
               RTE

RTE của ECU sẽ cung cấp các kết nối cần thiết cho những SWC được triển khai trên ECU đó.

Vì vậy, khi tìm hiểu RTE, cần phân biệt hai góc nhìn:

  • Thiết kế chức năng: SWC cần giao tiếp với ai và trao đổi gì.
  • Triển khai ECU: các SWC đó được đặt ở ECU nào và kết nối thực tế ra sao.

21. RTE và Virtual Functional Bus

Ở mức kiến trúc, VFB cung cấp mô hình giao tiếp trừu tượng giữa các Software Component. 

        SWC A                    SWC B
          │                        │
          │                        │
          └──────── VFB ───────────┘
                    │
                    │
              Logical connection

Khi triển khai trên một ECU cụ thể, RTE giúp hiện thực hóa các kết nối cần thiết trong môi trường runtime của ECU. 

Logical Design
      │
      ▼
     VFB
      │
      ▼
 ECU Deployment
      │
      ▼
     RTE
      │
      ▼
Actual Runtime Communication

Vì vậy có thể xem VFB và RTE là hai khái niệm có quan hệ rất gần với nhau nhưng phục vụ các góc nhìn khác nhau.

22. Một ví dụ hoàn chỉnh về hoạt động của RTE

Xét chức năng: tự động bật đèn nội thất khi cửa mở.

Giả sử hệ thống có hai SWC:

  • Door Status SWC
  • Interior Light SWC

Door Status SWC cung cấp trạng thái cửa: 

Door Status SWC
       │
       │ DoorOpen
       ▼
     RTE
       │
       ▼
Interior Light SWC
       │
       ▼
Runnable
       │
       ▼
Check DoorOpen
       │
       ├── TRUE  → Light ON
       │
       └── FALSE → Light OFF

Nếu dữ liệu DoorOpen thay đổi, Runnable của Interior Light SWC có thể được kích hoạt bởi cơ chế Event phù hợp.

Sau đó Runnable xử lý logic và tạo ra kết quả: 

DoorOpen = TRUE
       │
       ▼
InteriorLightControl_Run()
       │
       ▼
LightCommand = ON
       │
       ▼
RTE
       │
       ▼
BSW / MCAL
       │
       ▼
Interior Light Hardware

Đây là ví dụ thể hiện khá đầy đủ vai trò của RTE:

  • Cho phép Runnable xử lý dữ liệu.
  • Đưa kết quả của SWC ra môi trường.
  • Kết nối Application với các tầng bên dưới.

26. Những điểm dễ nhầm lẫn

RTE không phải Application Software

Application Software chứa logic chức năng. RTE cung cấp cơ chế kết nối và giao tiếp runtime.

RTE không phải Communication Stack

RTE có thể kết nối Application với Communication Stack, nhưng việc xử lý giao tiếp mạng thuộc về các module Communication Stack bên dưới.

RTE không phải Hardware Driver

RTE không trực tiếp điều khiển GPIO, CAN Controller hoặc các peripheral. Những chức năng đó thuộc các tầng thấp hơn.

Runnable không phải SWC

SWC là đơn vị chức năng ở mức component, còn Runnable là đơn vị thực thi bên trong SWC.

Port không phải Interface

Port là điểm giao tiếp của SWC, còn Interface mô tả nội dung hoặc kiểu giao tiếp được sử dụng tại Port.

29. Tóm tắt

RTE (Runtime Environment) là lớp trung gian quan trọng giữa Application Software và Basic Software trong AUTOSAR Classic.

Application Software được tổ chức thành các SWC. Các SWC giao tiếp thông qua Port và Interface, còn các Runnable thực hiện logic chức năng.

RTE cung cấp cơ chế để:
- SWC trao đổi dữ liệu với nhau.
- SWC gọi operation của thành phần khác.
- Runnable tương tác với dữ liệu và môi trường runtime.
- Application sử dụng các Service của BSW.
- Application giao tiếp với Communication Stack.

RTE không thay thế Application Software, Communication Stack hay Hardware Driver. Nó đóng vai trò kết nối và trừu tượng hóa môi trường runtime để Application Software có thể tập trung vào logic chức năng.

Có thể ghi nhớ chuỗi chính:

SWC → Port / Interface → RTE → BSW / SWC khác

Và với giao tiếp mạng:

Application → RTE → Communication Stack → Driver → Network
