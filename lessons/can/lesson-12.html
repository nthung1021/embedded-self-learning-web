Bài 12: AUTOSAR_SWS_CANDriver

Ở Bài 11, chúng ta đã tìm hiểu AUTOSAR_SRS_CAN và cách AUTOSAR mô tả các software requirements liên quan đến CAN. Bước tiếp theo là đi sâu hơn vào AUTOSAR_SWS_CANDriver.

Nếu SRS trả lời câu hỏi "CAN software cần đáp ứng những requirement gì?", thì SWS CAN Driver đi sâu vào việc đặc tả CAN Driver module, interfaces, APIs, behavior và configuration.

Có thể nhớ ngắn gọn: SRS nói CAN software cần làm gì; SWS CAN Driver đặc tả CAN Driver phải cung cấp interface và behavior như thế nào.

1. AUTOSAR_SWS_CANDriver là gì?

SWS là viết tắt của Software Specification. AUTOSAR_SWS_CANDriver là tài liệu đặc tả module CAN Driver trong AUTOSAR Classic Platform.

CAN Driver thuộc nhóm Microcontroller Drivers trong Basic Software (BSW), nằm rất gần CAN Controller hardware. AUTOSAR Classic Platform phân biệt Application, RTE và BSW; trong BSW có các nhóm abstraction và driver để tách phần mềm khỏi hardware cụ thể. :chatgpt-content-reference{index="1"}

SWS không phải implementation cụ thể của một vendor. Nó định nghĩa interface và behavior chuẩn để các implementation khác nhau có thể tuân theo cùng một AUTOSAR architecture.

2. SRS và SWS khác nhau thế nào?

SRS CAN SWS CAN Driver
Software Requirements Specification Software Specification
Tập trung vào requirements Tập trung vào specification của CAN Driver
CAN software cần đáp ứng điều gì? CAN Driver cung cấp interface/behavior nào?
Mức requirement Mức module/interface specification

Hãy nhớ theo chuỗi: SRS → SWS → Vendor Implementation → Integration → Test.

3. CAN Driver cung cấp những loại interface nào?

Có thể nhìn CAN Driver từ hai hướng: interface với module phía trên và interface với hardware/controller.

Ở phía trên, CAN Driver cung cấp các service/function được AUTOSAR specification định nghĩa. Ở phía dưới, implementation của driver phải truy cập CAN Controller cụ thể của MCU.

4. Các API quan trọng của CAN Driver

Khi học SWS CAN Driver, một trong những phần quan trọng nhất là hiểu các API chính và vai trò của chúng.

API Mục đích
Can_Init Khởi tạo CAN Driver với configuration.
Can_SetControllerMode Thay đổi mode của CAN Controller.
Can_GetControllerMode Đọc mode hiện tại của CAN Controller.
Can_Write Yêu cầu transmission thông qua Hardware Transmit Handle.
Can_GetControllerErrorState Đọc error state của controller.
Can_GetVersionInfo Lấy thông tin version của module khi được hỗ trợ/cấu hình.
Can_MainFunction_Write Thực hiện phần processing liên quan đến TX khi dùng polling.
Can_MainFunction_Read Thực hiện phần processing liên quan đến RX khi dùng polling.
Can_MainFunction_BusOff Xử lý bus-off polling khi cấu hình theo cơ chế này.
Can_MainFunction_Wakeup Xử lý wake-up polling khi được cấu hình.
Không phải mọi API đều được sử dụng giống nhau trong mọi project. Một số function có thể phụ thuộc configuration, controller capability hoặc feature được enable.

5. Can_Init

Can_Init() là một trong những API nền tảng của CAN Driver. Nó được sử dụng để initialize driver dựa trên configuration được cung cấp. 

Can_Init(&CanConfig);

        |
        +-- Controller configuration
        |
        +-- Hardware Objects
        |
        +-- Bit timing
        |
        +-- RX/TX configuration
        |
        +-- Interrupt / polling configuration
        |
        v
   CAN Driver initialized

Sau initialization, driver có configuration cần thiết để quản lý CAN Controller và các Hardware Object.

Một điểm quan trọng là Can_Init không đồng nghĩa với việc CAN Controller đã bắt đầu truyền message trên bus. Initialization và controller mode là hai khái niệm cần phân biệt.

6. Controller Mode

CAN Driver cần quản lý mode của CAN Controller. Trong AUTOSAR CAN Driver, controller có các trạng thái như STOPPED, STARTED và SLEEP.

Việc chuyển mode được yêu cầu thông qua: 

Can_SetControllerMode(
    Controller,
    Transition
);

Ý tưởng quan trọng là upper layer không nên truy cập trực tiếp các register của CAN Controller để thay đổi mode. CAN Driver cung cấp abstraction để thực hiện việc này.

7. Can_GetControllerMode

Sau khi yêu cầu thay đổi controller mode, phần mềm phía trên có thể cần biết controller hiện đang ở mode nào. 

Can_GetControllerMode(
    Controller,
    &ControllerMode
);

Đây là ví dụ đơn giản nhưng rất quan trọng về abstraction: application/upper layer không cần đọc trực tiếp register của MCU. Nó sử dụng interface của CAN Driver.

Không nên Nên
Upper layer đọc CAN register trực tiếp Upper layer sử dụng AUTOSAR interface
Phụ thuộc MCU cụ thể Phụ thuộc standardized driver interface
Khó portability Dễ thay đổi hardware implementation hơn

8. Can_Write và Transmission

Một API đặc biệt quan trọng trong CAN Driver là Can_Write(). Đây là điểm mà transmission request đi vào CAN Driver. 

Std_ReturnType Can_Write(
    Can_HwHandleType Hth,
    const Can_PduType* PduInfo
);

Về mặt tư duy, có thể hiểu: 

CanIf
  |
  | Can_Write()
  v
CAN Driver
  |
  +-- Check HTH
  +-- Check controller/resource
  +-- Prepare TX hardware object
  +-- Write to CAN Controller
  |
  v
CAN Controller
  |
  v
CAN Bus

Driver không cần biết payload đang biểu diễn VehicleSpeed, EngineSpeed hay BrakeStatus. Nó chủ yếu xử lý thông tin cần thiết để đưa PDU tới CAN hardware.

Can_Write là ranh giới rất quan trọng: CanIf đưa transmission request xuống CAN Driver, còn CAN Driver chịu trách nhiệm thực hiện request ở mức hardware.

9. Can_PduType

Để hiểu Can_Write, cần hiểu cấu trúc dữ liệu mà driver nhận được. Một PDU truyền CAN thường chứa các thông tin như identifier, length, data và software handle. 

typedef struct
{
    Can_IdType       id;
    PduInfoType      sdu;
    PduIdType        swPduHandle;
} Can_PduType;

Tùy AUTOSAR version, typedef và thành phần liên quan có thể được định nghĩa theo specification tương ứng. Điều quan trọng về mặt kiến trúc là driver nhận được CAN identifier + payload information + handle/context cần thiết cho transmission.

Thông tin Vai trò
Identifier CAN ID của message.
Length Số byte dữ liệu cần truyền.
Data pointer Địa chỉ vùng dữ liệu.
Software handle Giúp liên kết request với context của upper layer.

10. HTH và Hardware Object

HTH là Hardware Transmit Handle. Nó đại diện cho một transmit hardware object mà upper layer sử dụng khi yêu cầu CAN Driver truyền message. 

CanIf
  |
  | HTH_0 + PDU
  v
CAN Driver
  |
  +-- HTH_0
        |
        +-- TX Mailbox 0
        |
        +-- CAN Controller

HTH không nhất thiết tương ứng một cách đơn giản với một CAN ID. Mapping giữa HTH và hardware resource phụ thuộc configuration và CAN Controller.

Khi transmission không hoạt động, đừng chỉ kiểm tra CAN ID. Hãy kiểm tra cả HTH → Hardware Object → TX resource → Controller.

11. Return value của Can_Write

Can_Write không đơn giản có nghĩa là "message đã xuất hiện trên CAN bus". Return value chủ yếu cho biết request có được driver chấp nhận hay không tại thời điểm gọi API. 

ret = Can_Write(HTH, &Pdu);

if (ret == E_OK)
{
    /* Transmission request accepted */
}
else
{
    /* Transmission request rejected */
}

Một request có thể bị từ chối nếu resource hoặc điều kiện cần thiết cho transmission chưa phù hợp.

Đây là một điểm rất quan trọng khi debug: E_OK của Can_Write không nên được hiểu đơn giản là "CAN frame đã được ACK trên bus". Request acceptance và transmission completion là các sự kiện khác nhau.

12. Transmission Confirmation

Sau khi hardware xử lý transmission, upper layer cần nhận được thông tin confirmation theo architecture.

Transmission confirmation là một event khác với việc upper layer gọi Can_Write(). Điều này đặc biệt quan trọng trong hệ thống asynchronous, nơi request và completion xảy ra ở những thời điểm khác nhau.

14. HRH và Receive Hardware Object

HRH là Hardware Receive Handle. Nó đại diện cho receive hardware object được CAN Driver quản lý. 

CAN Controller
      |
      +-- RX FIFO / Mailbox
              |
              v
            HRH_0
              |
              v
         CAN Driver
              |
              v
            CanIf

HRH có thể liên quan đến receive filtering và mapping của Hardware Object tùy controller/configuration.

TX thường được tư duy qua HTH, RX thường được tư duy qua HRH. Đây là hai khái niệm cần nhớ khi đọc CAN Driver configuration.

15. Interrupt và Polling

CAN Driver có thể xử lý một số event theo interrupt hoặc polling, tùy configuration và implementation.

Với polling, driver thường cung cấp các Can_MainFunction_* phù hợp. Ví dụ có thể có processing cho Write, Read, Bus-Off hoặc Wakeup.

Điều này cho phép architecture linh hoạt hơn: không phải mọi event đều bắt buộc phải được xử lý trực tiếp bằng ISR.

16. Can_MainFunction_Write

Khi TX processing được cấu hình theo polling, CAN Driver có thể sử dụng main function để xử lý transmission-related events. 

Periodic Task
     |
     +-- Can_MainFunction_Write()
              |
              +-- Check TX resources
              +-- Process TX events
              +-- Handle confirmation
              |
              v
            CanIf

Main function thường được scheduler/OS gọi theo chu kỳ được configuration. Vì vậy timing của main function có thể ảnh hưởng đến thời điểm driver xử lý event.

17. Can_MainFunction_Read

Tương tự TX, RX có thể được xử lý bằng polling. 

Periodic Task
     |
     +-- Can_MainFunction_Read()
              |
              +-- Check RX hardware object
              +-- Read received message
              +-- Process RX data
              |
              v
            CanIf

Khi debug RX delay, cần kiểm tra cả:

  • CAN Controller đã nhận frame chưa.
  • RX resource có chứa message không.
  • Polling function có được gọi không.
  • Polling period là bao nhiêu.
  • Driver có xử lý đúng HRH không.
  • CanIf có nhận được indication không.

18. Bus-Off Handling

Bus-Off là một trạng thái quan trọng trong CAN. CAN Driver phải cung cấp cơ chế để xử lý/report trạng thái theo configuration và controller capability. 

CAN Controller
      |
      | Bus-Off detected
      v
CAN Driver
      |
      +-- Interrupt processing
      |       hoặc
      +-- Can_MainFunction_BusOff()
      |
      v
CanIf
      |
      v
Upper Layer / Recovery Logic

Một điểm quan trọng: CAN Driver không nên bị hiểu là module quyết định toàn bộ chiến lược recovery của ECU. Driver chịu trách nhiệm phần behavior thuộc driver, sau đó thông tin được đưa lên layer phù hợp.

19. Controller Error State

CAN Driver cũng cần cung cấp thông tin về error state của CAN Controller. 

Can_GetControllerErrorState(
    Controller,
    &ErrorState
);

Error state của controller có thể được sử dụng để theo dõi tình trạng communication và hỗ trợ diagnostic/debugging.

Thông tin Ý nghĩa
Error state Trạng thái lỗi hiện tại của CAN Controller.
Bus-Off Controller đã đi vào trạng thái bus-off.
RX/TX event Event liên quan đến reception/transmission.
Controller mode Trạng thái hoạt động của controller.

20. Development Error và Runtime Error

AUTOSAR phân biệt các loại error trong software behavior. Đây là một khái niệm quan trọng khi đọc SWS.

Loại Ý nghĩa
Development Error Lỗi liên quan đến việc sử dụng API/configuration không đúng trong development.
Runtime Error Lỗi có thể xảy ra trong quá trình ECU đang chạy.
Transient / Hardware event Event phát sinh từ controller hoặc communication environment.

Ví dụ, nếu một API được gọi với parameter không hợp lệ, đó có thể là vấn đề khác hoàn toàn so với việc CAN Controller phát hiện một communication error trên bus.

Khi debug AUTOSAR, luôn hỏi: Đây là lỗi do caller sử dụng API sai, lỗi configuration, lỗi software runtime hay hardware/communication error?

Tuy nhiên, cần phân biệt error reporting của software với CAN bus error xảy ra ở communication level.

22. Configuration của CAN Driver

SWS CAN Driver cũng đặc tả các cấu hình cần thiết để module hoạt động.

Configuration Ví dụ
CAN Controller Controller number, hardware channel.
Bit Timing Nominal timing và các thông số liên quan.
Hardware Objects HTH, HRH, mailbox/FIFO mapping.
CAN ID / filtering Receive filtering configuration.
Processing mode Interrupt hoặc polling.
Notification Callbacks/indications cần thiết.
CAN FD Configuration liên quan nếu controller hỗ trợ.

Configuration sau đó thường được xử lý bởi toolchain/generator của AUTOSAR project để tạo ra configuration data phù hợp với implementation của CAN Driver.

23. Pre-Compile, Link-Time và Post-Build Configuration

AUTOSAR CAN Driver hỗ trợ các cơ chế configuration khác nhau tùy requirement và implementation. Đây là một khái niệm quan trọng trong MCAL.

Loại Ý tưởng
Pre-Compile Configuration được xác định trước khi compile.
Link-Time Configuration được xác định ở giai đoạn link.
Post-Build Configuration có thể được lựa chọn/cung cấp sau khi build theo cơ chế được hỗ trợ.

Mục tiêu của các cơ chế này là cho phép ECU software có mức flexibility phù hợp với project.

Đừng nhầm "configuration" với "runtime application logic". Configuration xác định cách CAN Driver được thiết lập; runtime code thực hiện behavior dựa trên configuration đó.

24. CAN Driver và CAN FD

Với controller hỗ trợ CAN FD, CAN Driver cần có configuration và behavior phù hợp với capability của controller.

Classic CAN CAN FD
Payload tối đa 8 bytes Payload có thể lớn hơn 8 bytes
Không có data phase tốc độ cao riêng Có thể sử dụng tốc độ cao hơn trong data phase
Controller capability tương ứng Cần CAN FD-capable controller
Driver xử lý configuration tương ứng Driver cần hỗ trợ configuration/behavior tương ứng

Tuy nhiên, CAN Driver không tự "biến" một Classic CAN Controller thành CAN FD Controller. Hardware capability vẫn là yếu tố quyết định.

Một trong những mục tiêu lớn của AUTOSAR là hardware independence. CAN Driver là một phần quan trọng để đạt được mục tiêu đó.

Ví dụ hai MCU có CAN Controller khác nhau:

Phần hardware-specific bên dưới có thể khác nhau, nhưng interface với layer phía trên được chuẩn hóa theo AUTOSAR architecture.

Vì vậy CAN Driver không có nghĩa là một source code duy nhất chạy trên mọi MCU. Nó có nghĩa là các implementation khác nhau phải tuân theo interface/behavior được AUTOSAR specification quy định.

32. SWS CAN Driver và Unit Test

SWS specification có thể được sử dụng làm cơ sở để xây dựng unit test và integration test.

Ví dụ với Can_SetControllerMode():

Tóm tắt

AUTOSAR_SWS_CANDriver là specification cho CAN Driver trong AUTOSAR Classic Platform. Nếu Bài 11 tập trung vào requirements của CAN, thì Bài 12 tập trung vào cách CAN Driver được đặc tả ở mức module, interface, API, behavior và configuration.

Những API/concept quan trọng cần nhớ gồm: Can_Init, Can_SetControllerMode, Can_GetControllerMode, Can_Write, HTH, HRH, RX/TX processing, Can_MainFunction_*, Bus-Off, Error State .

Có thể nhớ flow chính bằng chuỗi: CanIf → Can_Write → CAN Driver → HTH → CAN Controller → CAN Bus cho TX, và: CAN Bus → CAN Controller → HRH → CAN Driver → CanIf cho RX.

Quan trọng nhất: SWS CAN Driver không phải source code của CAN Driver. Nó là specification để các implementation/vendor khác nhau tuân theo một interface và behavior AUTOSAR thống nhất.
