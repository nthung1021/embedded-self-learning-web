Bài 11: AUTOSAR_SRS_CAN

Ở Bài 10, chúng ta đã xác định scope của CAN Driver: CAN Driver nằm giữa CanIf và CAN Controller, chịu trách nhiệm điều khiển controller, Hardware Object, transmission, reception và các controller status/error event.

Nhưng một câu hỏi quan trọng hơn là: AUTOSAR yêu cầu CAN Driver và các thành phần CAN phải hoạt động như thế nào?

Đây chính là nơi AUTOSAR_SRS_CAN trở nên quan trọng. SRS CAN không phải là một file source code và cũng không phải là implementation của CAN Driver. Nó là tài liệu mô tả các software requirements mà các thành phần CAN trong AUTOSAR cần đáp ứng.

Có thể nhớ ngắn gọn: SRS CAN nói "CAN software phải đáp ứng những yêu cầu gì", còn SWS sẽ đi sâu hơn vào "module thực hiện các yêu cầu đó bằng interface/API như thế nào".

1. AUTOSAR_SRS_CAN là gì?

SRS là viết tắt của Software Requirements Specification. Vì vậy, AUTOSAR_SRS_CAN có thể hiểu là tài liệu tập hợp các requirements liên quan đến CAN trong AUTOSAR.

Mục đích của SRS là xác định rõ hành vi và capability mà phần mềm CAN cần cung cấp, trước khi đi vào thiết kế và implementation cụ thể.

Điều quan trọng là SRS nằm ở mức requirement. Nó không bắt implementation phải sử dụng một loại MCU, compiler hay một cấu trúc source code cụ thể nếu requirement không yêu cầu điều đó.

2. SRS CAN khác SWS CAN như thế nào?

Đây là điểm rất dễ nhầm khi bắt đầu đọc AUTOSAR specification. Hai loại tài liệu có vai trò khác nhau.

SRS SWS
Software Requirements Specification Software Specification
Trả lời: phần mềm cần đáp ứng điều gì? Trả lời: module được đặc tả và cung cấp interface như thế nào?
Tập trung vào requirements Chi tiết hơn về module, API, behavior và interface
Có thể dùng làm cơ sở để xác định requirement cần verify Dùng gần hơn với design và implementation
Không phải source code Cũng không phải source code implementation
Một cách nhớ đơn giản: SRS = What?
SWS = How is the software interface/behavior specified?
Implementation = How is it actually coded for the target?

3. AUTOSAR_SRS_CAN bao phủ những gì?

SRS CAN không chỉ nói về một API của CAN Driver. Phạm vi của tài liệu rộng hơn và liên quan tới nhiều thành phần trong CAN communication architecture.

Nhóm Ví dụ nội dung
CAN Driver Controller, transmission, reception, interrupt, status và error handling.
CAN Interface Abstraction giữa communication stack và CAN Driver.
CAN Transport Layer Các yêu cầu liên quan đến truyền dữ liệu vượt quá một CAN frame.
CAN Transceiver Driver Điều khiển và quản lý CAN transceiver.
Configuration Các yêu cầu về khả năng cấu hình của CAN software.
Non-functional requirements Data consistency, interrupt handling và các yêu cầu chung của BSW.

Vì vậy, khi đọc tài liệu có tên AUTOSAR_SRS_CAN, không nên hiểu nó đơn giản là "requirements cho CanDrv". Nó mô tả requirements cho nhiều thành phần liên quan đến CAN.

4. Requirement ID trong SRS CAN

Một đặc điểm quan trọng của AUTOSAR specification là các requirement thường có một identifier riêng. Trong SRS CAN, các requirement có dạng như: 

SRS_Can_01043
SRS_Can_01045
SRS_Can_01059
...

Identifier này rất hữu ích khi làm việc với requirement engineering, implementation và testing.

Khi đọc requirement, không nên chỉ đọc phần mô tả. Hãy ghi nhớ cả requirement ID, vì ID này có thể được dùng để trace từ requirement sang design, implementation và test.

5. Một requirement AUTOSAR thường được đọc như thế nào?

Requirement trong AUTOSAR thường đi kèm nhiều thông tin, không chỉ một câu mô tả chức năng.

Thông tin Ý nghĩa

Type Loại requirement hoặc trạng thái theo specification.
Description Nội dung yêu cầu phần mềm cần đáp ứng.
Rationale Lý do requirement tồn tại.
Use Case Tình huống sử dụng hoặc ví dụ áp dụng.
Dependencies Requirement hoặc chức năng liên quan.
Supporting Material Tài liệu hoặc requirement khác hỗ trợ cho requirement.
Khi học SRS, đừng chỉ học thuộc câu requirement. Hãy hiểu: requirement yêu cầu gì → tại sao cần → khi nào xảy ra → test như thế nào.

6. CAN Driver Initialization

Một nhóm requirement quan trọng liên quan đến CAN Driver là initialization.

Trước khi CAN Controller có thể thực hiện communication bình thường, driver phải đưa hardware vào trạng thái phù hợp dựa trên configuration. 

CAN Driver Initialization

        Configuration
             |
             v
      Can_Init(...)
             |
             v
    Configure Controller
             |
             v
    Configure HW Objects
             |
             v
      Controller ready
             |
             v
       Runtime operation

Configuration có thể chứa những thông tin như controller, bit timing, hardware objects, filtering và các notification liên quan.

Vì vậy, khi debug một CAN system không hoạt động ngay từ đầu, cần kiểm tra cả configuration + initialization + controller state, chứ không chỉ kiểm tra runtime transmit code.

7. CAN Driver phải quản lý Controller như thế nào?

CAN Driver không chỉ ghi data vào CAN Controller. Nó còn phải cung cấp cơ chế quản lý trạng thái của controller.

Tên state và chi tiết state machine phụ thuộc specification/module version, nhưng về mặt tư duy cần nhớ rằng CAN Driver phải biết controller đang ở trạng thái nào trước khi thực hiện một operation.

Ví dụ: một transmission request hợp lệ về mặt dữ liệu vẫn có thể không thực hiện được nếu CAN Controller đang ở state không cho phép transmission.

8. Transmission requirement

Một phần quan trọng của CAN Driver là hỗ trợ transmission. Khi layer phía trên yêu cầu gửi một PDU, CAN Driver phải chuyển request đó xuống hardware resource phù hợp.

Ở đây requirement không chỉ là "driver gửi message". Cần quan tâm đến các vấn đề như:

  • Request có được tiếp nhận hay không.
  • Hardware Object nào được sử dụng.
  • Controller có đang ở state phù hợp hay không.
  • Transmission resource có sẵn hay không.
  • Notification hoặc status được xử lý như thế nào.
  • Dữ liệu có được truyền nhất quán xuống hardware hay không.

9. Reception và Data Consistency

Reception cũng là một phần quan trọng của CAN Driver. Tuy nhiên, một vấn đề đặc biệt quan trọng trong embedded system là data consistency.

Hãy tưởng tượng CAN Controller đang giữ một received message trong hardware buffer. Trong lúc CPU đang đọc message, một message mới có thể đến và ảnh hưởng tới resource đó. 

CAN Hardware Buffer

        Message A
            |
            | CPU starts copying
            v
      +-------------+
      |   RX Buffer |
      +-------------+
            ^
            |
        Message B arrives
        at an unsafe time

Potential problem:
    Data copied to software
    may become inconsistent.

Vì vậy SRS CAN có requirement liên quan đến việc CAN Driver phải bảo đảm dữ liệu nhận được không bị trở nên inconsistent trong quá trình copy từ Hardware Object.

Đây là một ví dụ rất tốt để hiểu rằng requirement của embedded software không chỉ nói về functionality. Nó còn phải quan tâm đến timing, concurrency và data consistency.

10. Interrupt trong CAN Driver

CAN Controller có thể tạo interrupt khi xảy ra các event như transmission, reception hoặc các trạng thái liên quan.

Vì interrupt là asynchronous event, CAN Driver cần có cơ chế phù hợp để enable hoặc disable các interrupt của controller.

Trong một số implementation, event có thể được xử lý bằng interrupt, polling hoặc kết hợp tùy configuration và architecture.

Khi debug một CAN RX/TX event không xảy ra, cần xác định:

  1. Hardware event có thực sự xảy ra không?
  2. Interrupt có được enable không?
  3. ISR có được gọi không?
  4. Driver có xử lý đúng event không?
  5. Notification có được truyền lên CanIf không?

11. Error và Bus-Off

CAN Controller có thể gặp các trạng thái lỗi liên quan đến CAN communication. Một trong những trạng thái quan trọng nhất là Bus-Off.

CAN Driver cần cung cấp cơ chế để phát hiện và thông báo những trạng thái mà controller/driver được yêu cầu quản lý. 

CAN Controller
      |
      | error event
      v
CAN Driver
      |
      | controller status
      | / error notification
      v
  CanIf / Upper Layer
      |
      v
Communication Management
or Diagnostic / Recovery Logic

Điều quan trọng cần phân biệt: CAN Driver không nhất thiết quyết định toàn bộ system recovery strategy. Driver cung cấp thông tin và thực hiện phần behavior thuộc scope của nó; các layer phía trên có thể sử dụng thông tin đó để thực hiện logic hệ thống.

Khi debug Bus-Off, đừng chỉ hỏi "CAN Driver có lỗi không?". Hãy trace: CAN Controller → Driver → CanIf → Communication Management → Recovery behavior.

12. Configuration là một phần quan trọng của SRS

CAN software trong AUTOSAR có tính configurable. Vì vậy requirements không chỉ mô tả runtime API mà còn liên quan tới khả năng cấu hình của driver.

Configuration Ví dụ
Controller CAN Controller được sử dụng.
Bit Timing Baud rate và các thông số timing.
Hardware Object HTH / HRH và resource mapping.
Receive Filter Message nào được nhận bởi Hardware Object.
Interrupt Interrupt configuration.
Notification Các callback/event notification cần thiết.
CAN FD Khả năng và configuration liên quan nếu controller hỗ trợ.

Đây là lý do trong AUTOSAR project, configuration tool và generated configuration có vai trò rất lớn.

Một requirement có thể hoàn toàn đúng trong source code, nhưng system vẫn không hoạt động nếu configuration được generate sai. Vì vậy debugging AUTOSAR CAN phải xem xét cả source code + generated configuration + hardware configuration.

13. CAN Interface và CAN Driver trong SRS CAN

Một mục tiêu quan trọng của AUTOSAR là tách phần communication logic phía trên khỏi hardware-specific CAN Driver.

CanIf giúp communication stack không cần phụ thuộc trực tiếp vào implementation cụ thể của CAN Controller.

Ví dụ một project có thể thay đổi MCU hoặc CAN peripheral. Phần CAN Driver có thể thay đổi theo hardware, trong khi các layer phía trên vẫn có thể giữ architecture interface tương đối ổn định.

Đây chính là một trong những mục tiêu quan trọng của AUTOSAR: tách software khỏi hardware-specific implementation thông qua abstraction và standardized interfaces.

14. CAN Transport Layer trong SRS CAN

SRS CAN không chỉ tập trung vào CAN Driver. CAN Transport Layer cũng là một phần của CAN requirements.

Một CAN frame có giới hạn kích thước payload. Khi dữ liệu cần truyền lớn hơn khả năng của một frame, cần có transport mechanism để chia dữ liệu thành nhiều frame và ghép chúng lại ở phía nhận.

Đây là một ví dụ quan trọng để phân biệt scope:

Chức năng Layer phù hợp
Điều khiển CAN Controller CAN Driver
CAN hardware TX/RX CAN Driver
Chia dữ liệu lớn thành nhiều CAN frame CanTp
Ghép nhiều frame thành dữ liệu lớn CanTp
Signal packing COM

15. CAN Transceiver Driver

Một phần khác của SRS CAN liên quan đến CAN Bus Transceiver Driver.

Cần phân biệt ba thành phần:

Transceiver driver có những requirements riêng vì transceiver là thiết bị khác với CAN Controller. Ví dụ, configuration có thể liên quan đến loại transceiver, bus wake-up hoặc cách điều khiển transceiver tùy hardware.

Vì vậy: 

CAN Driver
    ↓
CAN Controller
    ↓
CAN Transceiver Driver / Transceiver
    ↓
Physical CAN Bus
Không nên gộp tất cả thành "CAN Driver". Trong AUTOSAR architecture, mỗi abstraction boundary có responsibility riêng.

16. SRS CAN và Data Consistency

Embedded software phải xử lý những vấn đề mà application software thông thường có thể ít gặp hơn, đặc biệt là concurrency giữa CPU và hardware.

Ví dụ một RX Hardware Object đang được driver đọc trong khi hardware tiếp tục nhận message mới.

Nguy cơ Hậu quả Cần quan tâm
Hardware ghi đè buffer trong lúc CPU copy Data inconsistent Data consistency mechanism
Interrupt xảy ra giữa critical operation Race / unexpected state Interrupt handling
TX resource đang được sử dụng Transmission không thực hiện được Resource management
Controller thay đổi state Operation không còn hợp lệ Controller state handling

Đây là lý do khi đọc SRS CAN, bạn sẽ thấy các requirement không chỉ mô tả "CAN phải gửi và nhận được message", mà còn mô tả behavior cần thiết để phần mềm hoạt động an toàn và nhất quán.

17. Từ SRS Requirement đến Test Case

Một kỹ năng rất quan trọng đối với Embedded Software Engineer là chuyển requirement thành test case.

Ví dụ một requirement nói rằng CAN Driver phải cung cấp reception indication.

Không nên chỉ viết test: "Call receive function and check result."

Thay vào đó cần suy nghĩ theo requirement:

Phần Câu hỏi
Precondition Controller và driver đang ở state nào?
Input CAN frame nào được đưa vào hardware?
Trigger Interrupt hay polling?
Expected behavior Driver có nhận biết message không?
Notification CanIf có nhận được indication không?
Data ID, DLC và payload có đúng không?

Tư duy này rất gần với công việc thực tế của embedded engineer: Requirement → Test Condition → Input → Expected Result → Verification.

20. Ví dụ Debug dựa trên SRS CAN

Giả sử requirement của hệ thống yêu cầu một CAN message phải được nhận. Nhưng application không nhận được message.

Không nên ngay lập tức sửa code application. Hãy trace từ dưới lên:

Step Kiểm tra
1 CAN frame có thực sự xuất hiện trên bus không?
2 CAN Controller có nhận frame không?
3 Hardware Object / filter có đúng không?
4 CAN Driver có xử lý RX event không?
5 CanIf có nhận được indication không?
6 PDU có được route đúng không?
7 COM có unpack signal đúng không?
8 Application có nhận được signal không?
Tư duy debug: Bus → Controller → CanDrv → CanIf → PduR/COM → Application. SRS giúp xác định expected behavior ở từng phần thay vì debug dựa trên phỏng đoán.

21. SRS CAN và vai trò của Embedded Engineer

Đối với một fresher hoặc junior embedded engineer, bạn không nhất thiết phải thuộc toàn bộ AUTOSAR_SRS_CAN. Điều quan trọng hơn là biết cách đọc và sử dụng requirement.

Khi nhận một requirement CAN, bạn nên có khả năng:

  1. Xác định requirement ID.
  2. Hiểu chính xác requirement yêu cầu gì.
  3. Xác định module chịu trách nhiệm.
  4. Xác định precondition và trigger.
  5. Xác định expected behavior.
  6. Chuyển requirement thành test condition.
  7. Trace requirement tới implementation.
  8. Trace requirement tới test result.

Đây là kỹ năng có giá trị cao trong automotive software vì công việc không chỉ là viết C/C++, mà còn là làm việc với requirements, specifications, testing và traceability.

26. Requirement → Code → Test Checklist

Khi làm một task CAN trong project, có thể sử dụng checklist sau:

  • Xác định requirement ID.
  • Đọc Description và hiểu expected behavior.
  • Đọc Rationale để hiểu tại sao requirement tồn tại.
  • Xác định module chịu trách nhiệm.
  • Xác định configuration liên quan.
  • Xác định runtime trigger.
  • Xác định input và output.
  • Xác định error condition.
  • Thiết kế implementation phù hợp.
  • Viết unit/integration test.
  • Kiểm tra expected result.
  • Trace test result về requirement ID.

Khái niệm Ý nghĩa
SRS Software Requirements Specification.
SRS CAN Requirements specification liên quan đến CAN trong AUTOSAR.
Requirement ID Identifier để trace một requirement cụ thể.
CAN Driver Software điều khiển CAN Controller và xử lý TX/RX hardware interaction.
CanIf CAN abstraction layer giữa communication stack và CAN Driver.
CanTp Transport layer cho việc truyền dữ liệu vượt giới hạn một CAN frame.
Transceiver Driver Software liên quan đến việc điều khiển CAN transceiver.
Traceability Liên kết requirement với design, code và test.

Tóm tắt

AUTOSAR_SRS_CAN là tài liệu requirements mô tả những gì các CAN-related software components trong AUTOSAR cần đáp ứng. Nó không phải source code và cũng không phải implementation cụ thể của CAN Driver.

Khi học SRS CAN, cần đặc biệt hiểu: requirement ID, CAN Driver requirements, TX/RX behavior, controller state, interrupt handling, data consistency, error handling, configuration và traceability.

Có thể nhớ toàn bộ bài bằng chuỗi: Requirement → Design → Implementation → Test → Verification .

Và đối với CAN architecture: SRS CAN → CanIf / CanDrv / CanTp / Transceiver → CAN Controller → CAN Bus .
