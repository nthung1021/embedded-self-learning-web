Bài 14: CAN - MCU/PORT/INTC Modules

Ở Bài 13, chúng ta đã tìm hiểu các module mà CAN Driver tương tác hoặc có liên quan trong AUTOSAR. Trong bài này, chúng ta đi sâu hơn vào ba thành phần rất quan trọng khi CAN Driver làm việc với hardware: MCU, PORT và INTC.

Đây là ba khái niệm rất quan trọng đối với Embedded Engineer vì CAN Driver không thể hoạt động đúng nếu CAN Controller chưa có clock, chân CAN chưa được multiplex đúng hoặc interrupt của CAN Controller không được xử lý đúng.

Ý tưởng quan trọng: MCU, PORT và INTC không nên được hiểu đơn giản là "ba module mà CanDrv luôn gọi trực tiếp". Chúng chủ yếu nằm trong chuỗi khởi tạo và hardware integration: MCU cung cấp clock/system setup → PORT cấu hình chân → INTC/interrupt infrastructure chuyển interrupt tới ISR → CanDrv xử lý sự kiện CAN.

1. Ba module này giải quyết vấn đề gì?

Module Vấn đề chính Ví dụ với CAN
MCU Clock, reset và một số cấu hình mức microcontroller Cấp clock cho CAN peripheral
PORT Cấu hình các chân vật lý và pin multiplexing CAN_TX / CAN_RX được nối tới đúng peripheral function
INTC Quản lý việc nhận và phân phối interrupt CAN Controller tạo interrupt và CPU nhận được ISR
CanDrv Điều khiển CAN Controller TX, RX, controller mode, bus-off, CAN interrupt handling

Có thể hình dung đơn giản: 

MCU
 │
 ├── Clock / System setup
 │
 └──────────────┐
                │
PORT            │
 │              │
 ├── CAN_TX     │
 └── CAN_RX     │
                │
                ▼
        CAN Controller
                │
                │ Interrupt
                ▼
              INTC
                │
                ▼
              ISR
                │
                ▼
             CanDrv
                │
                ▼
              CanIf

2. Tổng quan vị trí trong AUTOSAR MCAL

CAN Driver thuộc nhóm Communication Drivers trong MCAL, trong khi MCU Driver và Port Driver là những driver gần microcontroller/hardware hơn.

Cần lưu ý rằng sơ đồ trên thể hiện mối quan hệ về hardware/platform, không có nghĩa rằng mọi mũi tên đều tương ứng với một API gọi trực tiếp giữa hai module.

3. MCU Module là gì?

MCU Driver là driver cung cấp các chức năng liên quan tới microcontroller như clock initialization, clock configuration, một số system-level initialization và các chức năng phần cứng liên quan được AUTOSAR specification của MCU định nghĩa.

Trong một ECU có CAN, điều quan trọng nhất đối với CAN là CAN peripheral phải được cấp clock đúng. Nếu clock của CAN Controller không hoạt động hoặc cấu hình sai, CAN Driver có thể đã được initialize nhưng controller vẫn không hoạt động như mong muốn. 

MCU initialization
       │
       ├── Configure system clock
       │
       ├── Configure peripheral clock
       │
       └── CAN peripheral receives clock
                    │
                    ▼
                 CanDrv
                    │
                    ▼
             CAN Controller

4. CAN phụ thuộc MCU như thế nào?

Để CAN Controller hoạt động, nhiều microcontroller yêu cầu một clock source hoặc peripheral clock được cấu hình trước. Vì vậy trong quá trình ECU startup, MCU configuration thường phải được thực hiện trước khi các peripheral driver sử dụng phần cứng đó.

Có thể hình dung một chuỗi khởi tạo đơn giản: 

Power-On / Reset
      │
      ▼
MCU initialization
      │
      ├── System clock
      ├── Peripheral clock
      └── Basic MCU setup
      │
      ▼
PORT initialization
      │
      └── CAN pin multiplexing
      │
      ▼
CAN Driver initialization
      │
      ▼
CAN Controller configuration
      │
      ▼
CAN communication ready
Điểm phỏng vấn: Nếu interviewer hỏi "Tại sao CanDrv Init đúng nhưng CAN vẫn không chạy?", một câu trả lời tốt là: hãy kiểm tra trước clock configuration, pin configuration, controller configuration và interrupt configuration, thay vì chỉ kiểm tra code bên trong CanDrv.

5. MCU Clock ảnh hưởng CAN như thế nào?

CAN communication phụ thuộc vào timing của CAN Controller. CAN Controller cần một clock phù hợp để tạo các timing parameter dùng trong việc phát và nhận bit trên CAN bus.

Ví dụ, nếu project yêu cầu một baudrate cụ thể nhưng clock source của CAN peripheral bị cấu hình khác với giá trị mà CAN configuration dự kiến, CAN Controller có thể tạo timing không đúng.

6. PORT Module là gì?

PORT Driver quản lý việc cấu hình các microcontroller pins. Trong AUTOSAR, Port Driver có trách nhiệm cấu hình những thuộc tính của các pin theo configuration, bao gồm cả chức năng của pin và các thuộc tính điện phù hợp tùy hardware.

Với CAN, hai tín hiệu quan trọng thường là: 

CAN_TX
   │
   └── MCU pin configured as CAN transmit function

CAN_RX
   │
   └── MCU pin configured as CAN receive function

Tuy nhiên, trên một MCU hiện đại, CAN Controller thường có nhiều lựa chọn pin. Vì vậy cần cấu hình đúng pin multiplexing / alternate function.

7. Tại sao PORT quan trọng với CAN?

Giả sử CAN Controller hoạt động hoàn toàn bình thường và CAN Driver không có lỗi. Nhưng CAN_TX vẫn được cấu hình thành GPIO thay vì CAN peripheral function. Khi đó frame có thể được "truyền" ở bên trong controller, nhưng tín hiệu không xuất hiện đúng trên chân vật lý.

Tư duy debug: Nếu CAN Controller báo transmission thành công nhưng oscilloscope/logic analyzer không thấy tín hiệu đúng, hãy kiểm tra pin mux, port configuration, transceiver và physical connection thay vì chỉ debug Can_Write().

8. PORT Configuration cho CAN

Tên configuration cụ thể sẽ phụ thuộc vào MCU và vendor, nhưng về mặt khái niệm CAN pin configuration thường bao gồm:

Configuration Ý nghĩa Ví dụ
Pin Function Chọn peripheral function cho pin CAN_TX / CAN_RX
Direction Xác định hướng hoạt động của pin TX output, RX input
Pull configuration Cấu hình pull-up / pull-down nếu hardware hỗ trợ Phụ thuộc MCU/board design
Pad / electrical configuration Các thuộc tính điện của pin Drive strength, slew rate...
Pin mode Chọn alternate/peripheral mode CAN peripheral mode

Đây là một ví dụ conceptual: 

Port_Init(...);

CAN_TX_PIN
    → Peripheral Mode
    → CAN_TX Function
    → Output

CAN_RX_PIN
    → Peripheral Mode
    → CAN_RX Function
    → Input

Code configuration thực tế sẽ khác nhau giữa các MCU và vendor. Điều quan trọng đối với Embedded Engineer là hiểu tại sao các cấu hình đó cần thiết.

9. INTC là gì?

INTC có thể được hiểu là Interrupt Controller / Interrupt Controller infrastructure. Đây là thành phần xử lý việc nhận, quản lý và phân phối các interrupt từ peripheral tới CPU.

Không nên mặc định rằng mọi AUTOSAR MCU đều có một module chuẩn với tên chính xác là INTC. Tên gọi và kiến trúc interrupt controller phụ thuộc vào MCU, vendor và integration architecture.

Cách hiểu nên dùng: Trong bài học này, "INTC" được dùng như một tên khái niệm cho interrupt-controller layer, không phải khẳng định rằng mọi implementation AUTOSAR đều có một BSW module độc lập tên "INTC".

10. CAN Interrupt hoạt động như thế nào?

CAN Controller có thể tạo interrupt khi xảy ra các sự kiện như transmission completed, receive event, error hoặc các trạng thái CAN khác, tùy hardware và configuration.

Chuỗi xử lý khái niệm: 

CAN Controller
      │
      │ Interrupt request
      ▼
Interrupt Controller / INTC
      │
      │ route interrupt
      ▼
CPU / ISR
      │
      ▼
CanDrv interrupt handler
      │
      ├── Process RX
      ├── Process TX confirmation
      ├── Process error
      └── Process Bus-Off / status
      │
      ▼
CanIf notification

11. Interrupt và CanDrv có quan hệ như thế nào?

AUTOSAR CAN Driver có các API và behavior liên quan đến controller interrupts. Điều đó cho phép driver enable/disable và xử lý interrupt state theo cấu hình và implementation.

Một khái niệm thường gặp là: 

Can_DisableControllerInterrupts(...)
        │
        ▼
CAN Controller interrupts disabled
        │
        │ critical operation
        ▼
Can_EnableControllerInterrupts(...)
        │
        ▼
CAN Controller interrupts restored

Mục đích của cơ chế này là tránh một số trạng thái không nhất quán khi CanDrv đang thực hiện thao tác cần bảo vệ khỏi interrupt.

Lưu ý: Việc enable/disable interrupt ở đây là behavior của CAN Driver đối với CAN Controller; nó không có nghĩa rằng CanDrv tự mình thay thế toàn bộ Interrupt Controller của MCU.

12. Interrupt Context và Main Function

Một CAN implementation có thể sử dụng interrupt processing, polling hoặc kết hợp cả hai tùy configuration và hardware. Do đó cần phân biệt:

Processing Cách hoạt động Ví dụ
Interrupt Hardware event tạo interrupt để driver xử lý RX/TX event
Polling Driver được gọi định kỳ để kiểm tra trạng thái Can_MainFunction_Read()
Hybrid Một số event dùng interrupt, một số event dùng polling Tùy configuration

Với polling, interrupt controller không nhất thiết phải tham gia vào event đó. Với interrupt-driven processing, INTC/ISR path trở thành một phần quan trọng của hệ thống.

13. Startup Sequence: MCU → PORT → CAN

Khi ECU khởi động, thứ tự thực tế phụ thuộc vào integration và configuration, nhưng về mặt tư duy có thể hình dung: 

1. MCU / system initialization
        │
        ├── Clock
        ├── Reset related setup
        └── Peripheral availability
        │
        ▼
2. PORT initialization
        │
        ├── CAN_TX
        └── CAN_RX
        │
        ▼
3. Interrupt infrastructure
        │
        └── CAN interrupt configuration
        │
        ▼
4. CAN Driver initialization
        │
        └── CAN Controller configuration
        │
        ▼
5. Controller START
        │
        ▼
6. CAN communication

Khi debug startup, nếu bỏ qua một bước ở đầu chuỗi, lỗi có thể xuất hiện ở bước cuối và khiến người phát triển tưởng rằng CanDrv là nguyên nhân.

14. Ví dụ: Clock CAN sai

Giả sử project yêu cầu CAN communication với một baudrate cụ thể nhưng peripheral clock của CAN không đúng với giá trị mà configuration dự kiến. 

Expected:
MCU Clock
   ↓
CAN Peripheral Clock
   ↓
CAN Bit Timing
   ↓
Required CAN Baudrate

Actual:
Wrong MCU Clock
   ↓
Wrong CAN Peripheral Clock
   ↓
Wrong CAN Bit Timing
   ↓
CAN communication problem

Khi gặp vấn đề như vậy, việc sửa trực tiếp Can_Write() thường không giải quyết được nguyên nhân gốc.

15. Ví dụ: PORT configuration sai

Giả sử CAN Controller đã START và software báo transmission thành công, nhưng CAN bus không nhận được frame. 

CanDrv
   │
   ▼
CAN Controller
   │
   │ TX complete
   ▼
Software thinks: "Transmission OK"
   │
   ▼
Physical pin
   │
   X
   └── PIN MUX sai / pin function sai

Trong trường hợp này, CAN Controller và CanDrv có thể vẫn hoạt động bình thường. Vấn đề nằm ở hardware configuration của pin.

Debug hint: Khi CAN software cho thấy TX đã hoàn thành nhưng trên bus không có waveform, hãy kiểm tra lần lượt: CAN Controller → PORT/MUX → CAN Transceiver → physical CANH/CANL.

16. Ví dụ: CAN RX Interrupt không hoạt động

Một trường hợp khác là CAN bus có frame đến, nhưng application không nhận được. 

CAN Bus
   │
   ▼
CAN Controller
   │
   │ RX event
   ▼
Interrupt?
   │
   ├── NO → Check interrupt configuration / INTC / ISR
   │
   └── YES
        │
        ▼
      CanDrv
        │
        ▼
      CanIf
        │
        ▼
   Upper layer

Nếu CAN Controller thực sự nhận frame nhưng ISR không chạy, nên kiểm tra interrupt path trước khi sửa Receive logic trong application.

18. MCU, PORT, INTC không phải là trách nhiệm của CanDrv

Đây là phần rất quan trọng để tránh hiểu sai boundary giữa các module.

Chức năng CanDrv chịu trách nhiệm? Thành phần liên quan
CAN Controller configuration Có CanDrv
CAN TX/RX processing Có CanDrv
System/peripheral clock setup Không MCU
CAN pin multiplexing Không PORT
Global interrupt routing Không trực tiếp INTC / MCU / OS integration
CAN interrupt handling Có CanDrv
Application signal processing Không COM / Application

19. Quan hệ giữa MCU, PORT, INTC và CanDrv

Có thể nhớ vai trò của từng thành phần bằng ba câu: 

MCU   → "CAN Controller lấy clock ở đâu?"
PORT  → "CAN signal đi ra/vào chân nào?"
INTC  → "CAN interrupt đi đến CPU/ISR bằng đường nào?"
CanDrv → "CAN Controller phải làm gì?"

20. Ví dụ Debug từ đầu đến cuối

Giả sử một ECU không thể gửi CAN message. Thay vì ngay lập tức mở Can_Write(), hãy debug theo tầng. 

Step 1:
MCU Clock
   │
   └── CAN peripheral clock đúng?

Step 2:
PORT
   │
   ├── CAN_TX function đúng?
   └── CAN_RX function đúng?

Step 3:
CanDrv
   │
   ├── Init thành công?
   ├── Controller START?
   └── Can_Write() trả E_OK?

Step 4:
INTC
   │
   └── Interrupt configuration đúng?

Step 5:
CAN Controller
   │
   └── TX request / status đúng?

Step 6:
CAN Transceiver
   │
   └── Normal mode?

Step 7:
Physical bus
   │

Step 8:
Other ECU
   │
   └── ACK / bus participation?
Điểm quan trọng: Embedded debugging hiệu quả thường bắt đầu từ hardware assumptions → low-level driver → communication stack → application. Không nên mặc định rằng mọi lỗi CAN đều là lỗi của CanDrv.

21. MCU / PORT / INTC trong một CAN Interview

Nếu interviewer hỏi: "What can cause a CAN driver to initialize successfully but CAN communication still does not work?"

Một câu trả lời tốt có thể bao gồm: 

"I would not check only the CAN driver.
I would also check the MCU clock configuration,
the CAN peripheral clock, the CAN pin multiplexing,
the interrupt configuration, the CAN controller state,
the transceiver mode, and finally the physical CAN bus."

Đây là cách trả lời cho thấy bạn hiểu rằng CAN Driver nằm trong một hệ thống embedded hoàn chỉnh chứ không hoạt động độc lập.

22. Tóm tắt



MCU Driver chịu trách nhiệm cho các chức năng ở mức microcontroller, trong đó clock của CAN peripheral là một yếu tố quan trọng đối với CAN communication.

PORT Driver cấu hình các chân vật lý của MCU. Với CAN, cần đảm bảo CAN_TX và CAN_RX được multiplex đúng sang CAN peripheral.

INTC / interrupt infrastructure xử lý đường đi của interrupt từ CAN Controller tới CPU/ISR. CAN Driver sau đó xử lý sự kiện CAN trong driver.

Một cách ghi nhớ rất đơn giản:

MCU → Clock
PORT → Pin
INTC → Interrupt
CanDrv → CAN Controller

Khi debug CAN, hãy kiểm tra theo chuỗi: Clock → Pin → Controller → Interrupt → CanDrv → CanIf → Upper Layer → Physical Bus.

Đặc biệt, không nên mặc định rằng MCU, PORT và INTC đều là các API dependency trực tiếp của CanDrv. Chúng có thể là những thành phần platform/hardware mà CanDrv phụ thuộc về mặt tích hợp và cấu hình.
