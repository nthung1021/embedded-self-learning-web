Bài 13: CAN Interact/Depend Modules

Trong các bài trước, chúng ta đã tìm hiểu CAN Driver, CAN-COM Stack, phạm vi của CAN Driver và hai tài liệu quan trọng trong AUTOSAR là AUTOSAR_SRS_CAN và AUTOSAR_SWS_CANDriver.

Tuy nhiên, CAN Driver không hoạt động độc lập. Trong một ECU thực tế, CanDrv nằm giữa nhiều module AUTOSAR và phải phối hợp với chúng để thực hiện việc truyền, nhận frame, thay đổi trạng thái controller, xử lý lỗi và hỗ trợ wake-up.

Ý tưởng quan trọng: Không phải mọi module liên quan đến CAN đều gọi trực tiếp vào CAN Driver. CanIf là lớp giao tiếp trung gian quan trọng nhất: CanDrv chủ yếu nhìn thấy CanIf ở phía trên, còn nhiều module cấp cao như PduR, COM, CanSM hoặc ComM được tách khỏi phần cứng CAN nhờ lớp CanIf.

1. CAN Driver nằm ở đâu trong kiến trúc AUTOSAR?

Trong AUTOSAR Classic Platform, CAN Driver thuộc nhóm MCAL (Microcontroller Abstraction Layer). Nó giao tiếp gần với phần cứng CAN Controller và cung cấp interface chuẩn cho lớp phía trên.

Có thể hiểu đơn giản: 

Application
     ↓
COM / PduR / CanTp / CanNm
     ↓
   CanIf
     ↓
   CanDrv
     ↓
CAN Controller
     ↓
CAN Transceiver
     ↓
CAN Bus

Trong đó, CanIf giúp tách phần giao tiếp CAN khỏi sự khác biệt giữa các CAN Controller và các CAN Driver của từng nhà cung cấp.

2. "Interact" và "Depend" có nghĩa là gì?

Hai khái niệm này khá gần nhau nhưng không hoàn toàn giống nhau.

Khái niệm Ý nghĩa Ví dụ
Interact Hai module trao đổi thông tin hoặc gọi interface của nhau trong một luồng xử lý. CanDrv gọi notification của CanIf.
Depend Một module cần service, API, configuration hoặc infrastructure của module khác để hoạt động đúng. CanDrv cần DET để report development error.
Indirect relation Hai module có liên quan trong kiến trúc nhưng không trực tiếp gọi nhau. CanSM điều khiển CAN communication thông qua CanIf thay vì trực tiếp điều khiển CanDrv.
Điểm cần nhớ: Khi đọc tài liệu AUTOSAR, không nên hiểu từ "dependency" theo nghĩa module A luôn gọi trực tiếp API của module B. Một dependency có thể là dependency về interface, configuration, callback hoặc service của hệ thống.

3. Module quan trọng nhất: CanIf

Nếu phải chọn một module quan trọng nhất khi học mối quan hệ của CAN Driver với các module khác, đó là CanIf (CAN Interface).

CanIf nằm ở phía trên CanDrv và cung cấp một interface chuẩn hóa giữa các module CAN cấp cao và CAN Driver.

Ví dụ, khi CAN Driver nhận được một frame từ hardware, CanDrv không gửi trực tiếp frame đó tới COM. Nó thông báo cho CanIf, sau đó CanIf mới quyết định frame sẽ được chuyển tiếp tới module phía trên nào.

4. CanDrv và CanIf tương tác như thế nào?

Có hai luồng cơ bản cần nhớ: Transmit và Receive.

4.1. Luồng truyền dữ liệu

Khi một PDU cần được truyền ra CAN bus, dữ liệu đi từ các module cấp cao xuống CanIf, sau đó CanIf yêu cầu CanDrv truyền frame. 

COM / PduR
     │
     ▼
   CanIf
     │
     │ Can_Write(...)
     ▼
   CanDrv
     │
     ▼
CAN Controller
     │
     ▼
 CAN Bus
     │
     ▼
Transmission finished
     │
     ▼
   CanDrv
     │
     │ Tx Confirmation
     ▼
   CanIf
     │
     ▼
PduR / Upper layer

API tiêu biểu ở phía CanDrv là: 

Can_Write(
    Hth,
    &PduInfo
);

Sau khi hardware hoàn thành việc truyền, CAN Driver có thể thông báo kết quả truyền tới CanIf thông qua cơ chế notification được cấu hình.

4.2. Luồng nhận dữ liệu

Ở chiều ngược lại, frame xuất hiện trên CAN bus, CAN Controller nhận frame và báo sự kiện tới CanDrv. 

CAN Bus
   │
   ▼
CAN Controller
   │
   ▼
 CanDrv
   │
   │ Rx Indication
   ▼
 CanIf
   │
   ▼
PduR / CanTp / Upper CAN layer
   │
   ▼
 COM / Application

CanDrv xử lý phần hardware-level như nhận frame, kiểm tra Hardware Object và chuyển thông tin cần thiết cho CanIf.

Không nên nhầm: CanDrv không phải là nơi quyết định business meaning của CAN message. Ví dụ CAN ID này là "Vehicle Speed" hay "Engine RPM" thuộc phạm vi của các lớp giao tiếp/cấu hình cao hơn.

5. CanTrcv - CAN Transceiver Driver

CanTrcv là driver dành cho CAN Transceiver, tức phần cứng nằm giữa CAN Controller và physical CAN bus.

Điều này dẫn tới một điểm dễ nhầm: 

CanIf
 ├── CanDrv   → CAN Controller
 │
 └── CanTrcv  → CAN Transceiver

CanDrv và CanTrcv không phải là cùng một module. CanDrv xử lý CAN Controller, còn CanTrcv quản lý trạng thái hoạt động của transceiver.

Module Quản lý Ví dụ
CanDrv CAN Controller Controller mode, transmit, receive, error state, bus-off
CanTrcv CAN Transceiver Transceiver operating mode, wake/sleep behavior
CanIf Abstraction / mapping Chuẩn hóa interface cho các driver phía dưới

Vì vậy, khi cần thay đổi mode của CAN communication, CanIf có thể làm việc với cả CanDrv và CanTrcv, trong khi CanSM ở tầng phía trên có thể điều phối communication state.

6. EcuM - ECU State Manager

EcuM quản lý các trạng thái hoạt động của ECU và có liên quan đến các cơ chế như startup, shutdown và wake-up.

Trong CAN communication, wake-up là một trường hợp đặc biệt. ECU có thể đang ở trạng thái sleep và một sự kiện CAN có thể trở thành nguyên nhân khiến ECU cần thức dậy.

Điều quan trọng ở đây là không nên kết luận rằng EcuM trực tiếp điều khiển mọi hành vi của CanDrv. Trong kiến trúc AUTOSAR, nhiều luồng wake-up được thực hiện qua các interface của CAN communication stack.

7. DET - Default Error Tracer

Trong quá trình development, CAN Driver có thể phát hiện các lỗi liên quan tới việc gọi API sai hoặc cấu hình không hợp lệ. Khi đó, cơ chế DET (Default Error Tracer) có thể được sử dụng để report development error. 

Application / CanIf
        │
        │ gọi API CanDrv không hợp lệ
        ▼
     CanDrv
        │
        │ Detect Development Error
        ▼
      DET
        │
        ▼
 Development Log / Debug Information

Ví dụ về mặt khái niệm: 

Can_Write(...)
        │
        ├── Parameter hợp lệ
        │       └── tiếp tục xử lý
        │
        └── Parameter/configuration không hợp lệ
                └── Report Development Error → DET
Lưu ý: DET chủ yếu phục vụ quá trình development và debugging. Không nên đồng nhất development error với lỗi runtime của hệ thống hoặc lỗi vật lý trên CAN bus.

8. SchM - BSW Scheduler

SchM (BSW Scheduler) là một phần của cơ chế quản lý việc gọi các main functions của BSW.

Với CAN Driver, một số processing có thể được thực hiện theo cơ chế polling thông qua các main functions, tùy cấu hình và AUTOSAR release. 

BSW Scheduler / OS scheduling
             │
             ├── Can_MainFunction_Read()
             │
             ├── Can_MainFunction_Write()
             │
             ├── Can_MainFunction_BusOff()
             │
             └── Can_MainFunction_Wakeup()
                        │
                        ▼
                     CanDrv

Vì vậy cần phân biệt hai cơ chế:

Cơ chế Mô tả Đặc điểm
Interrupt Hardware tạo interrupt khi có sự kiện. Phản ứng nhanh, thường được sử dụng cho các sự kiện cần xử lý tức thời.
Polling Main function được gọi định kỳ để kiểm tra trạng thái hoặc xử lý sự kiện. Timing phụ thuộc vào chu kỳ scheduler/main function.
Quan trọng: Không phải mọi ECU đều sử dụng cùng một cách xử lý. AUTOSAR cho phép behavior phụ thuộc vào configuration và khả năng của CAN hardware/driver.

9. CanSM và ComM có trực tiếp gọi CanDrv không?

Đây là một câu hỏi rất hay trong phỏng vấn Embedded AUTOSAR.

Câu trả lời quan trọng là: không nên xem CanSM hoặc ComM là các client trực tiếp của CanDrv cho việc truyền/nhận CAN frame.

Kiến trúc điển hình được hiểu như sau: 

ComM
  │
  ▼
CanSM
  │
  ▼
CanIf
  │
  ├──► CanDrv
  │
  └──► CanTrcv

ComM chịu trách nhiệm quản lý communication request ở mức communication management. CanSM quản lý CAN network state, sau đó các request phù hợp được đưa xuống CanIf.

CanIf mới thực hiện việc mapping các yêu cầu đó tới CAN Driver và CAN Transceiver Driver phù hợp.

10. Tổng hợp các module liên quan

Module Quan hệ với CanDrv Vai trò chính
CanIf Trực tiếp / interface chính Abstraction giữa upper communication layers và CAN Driver
CanTrcv Liên quan qua CanIf Điều khiển CAN Transceiver
EcuM Liên quan tới wakeup/ECU state Startup, shutdown, sleep và wakeup
DET Service hỗ trợ Development error reporting
SchM Service/scheduling support Main-function scheduling và BSW synchronization support
CanSM Indirect CAN network state management
ComM Indirect Communication mode/request management
PduR Indirect / upper layer Routing PDU giữa các communication modules
COM Indirect / upper layer Signal-oriented communication

11. Direct Dependency và Indirect Dependency

Một cách rất hữu ích để ghi nhớ kiến trúc là chia các module thành hai nhóm.

Tuy nhiên, sơ đồ trên chỉ mang tính khái niệm. Mức độ "direct" hoặc "indirect" cụ thể phải được xác định theo interface và AUTOSAR release/configuration đang sử dụng.

12. Một ví dụ hoàn chỉnh: gửi một CAN message

Giả sử Application muốn gửi một giá trị tốc độ xe. Ta có thể hình dung toàn bộ chuỗi như sau: 

1. Application tạo / cập nhật signal
                │
                ▼
2. COM đóng gói signal thành I-PDU
                │
                ▼
3. PduR route PDU
                │
                ▼
4. CanIf xác định CAN PDU / HTH
                │
                ▼
5. CanIf gọi Can_Write(...)
                │
                ▼
6. CanDrv ghi dữ liệu vào CAN Controller
                │
                ▼
7. CAN Controller thực hiện transmission
                │
                ▼
8. CAN message xuất hiện trên bus
                │
                ▼
9. CanDrv nhận sự kiện transmission complete
                │
                ▼
10. CanIf nhận Tx Confirmation
                │
                ▼
11. Upper layer tiếp tục xử lý

Qua ví dụ này có thể thấy tại sao mỗi module phải có một responsibility riêng. Application không cần biết thanh ghi CAN nằm ở đâu, còn CanDrv cũng không cần biết message đó biểu diễn "Vehicle Speed" hay "Engine RPM".

                │

Tư duy debug: Khi message không đến Application, không nên chỉ kiểm tra Application. Hãy đi ngược từ CAN Bus → CAN Controller → CanDrv → CanIf → PduR/COM → Application để xác định message bị mất ở tầng nào.

14. CAN Driver không phụ trách những gì?

Hiểu dependency cũng phải đi kèm với hiểu boundary. Một số nhiệm vụ thường không thuộc trách nhiệm trực tiếp của CanDrv.

Nhiệm vụ CanDrv? Module liên quan
Điều khiển CAN Controller Có CanDrv
Đóng gói Signal thành PDU Không COM
Routing PDU Không PduR
Quản lý CAN network state Không trực tiếp CanSM
Quản lý communication mode Không trực tiếp ComM / CanSM
Điều khiển CAN Transceiver Không trực tiếp CanTrcv
Development error tracing Không phải nơi lưu trữ DET
ECU startup / shutdown Không EcuM

15. Dependency Map cần nhớ khi đi phỏng vấn

Một cách đơn giản để nhớ là sử dụng sơ đồ sau: 

                 ComM
                   │
                   ▼
                 CanSM
                   │
                   ▼
COM ──► PduR ──► CanIf ◄──────── EcuM
                   │
            ┌──────┴──────┐
            │             │
            ▼             ▼
         CanDrv        CanTrcv
            │             │
            ▼             ▼
     CAN Controller   CAN Transceiver
            │             │
            └──────┬──────┘
                   ▼
                 CAN Bus

CanDrv ─────► DET
CanDrv ◄──── Scheduler / SchM
Memory trick:
CanIf = Interface
CanDrv = Controller
CanTrcv = Transceiver
CanSM = CAN State
ComM = Communication Mode
EcuM = ECU State / Wakeup
DET = Development Error
SchM = Scheduling / BSW support

16. Góc nhìn Debug thực tế

Khi gặp lỗi CAN trong một project AUTOSAR, việc biết module nào chịu trách nhiệm sẽ giúp thu hẹp phạm vi debug rất nhanh.

Hiện tượng Những nơi nên kiểm tra
Không gửi được CAN frame COM → PduR → CanIf → Can_Write → CanDrv → CAN Controller
CAN controller không START CanIf → CanDrv → Controller mode / configuration
Hardware nhận frame nhưng Application không thấy CanDrv → CanIf → PduR/COM
Bus-off không được xử lý CanDrv → CanIf → CanSM
CAN wakeup không hoạt động CAN hardware → CanDrv / CanTrcv → CanIf → EcuM / wakeup handling
API bị gọi sai trong development CanDrv → DET
Polling xử lý quá chậm Main Function → Scheduler / SchM → CAN timing/configuration

19. Tóm tắt



CAN Driver không hoạt động độc lập mà nằm trong một hệ thống nhiều module AUTOSAR.

CanIf là module giao tiếp quan trọng nhất giữa CanDrv và các upper-layer communication modules.

CanDrv chịu trách nhiệm chính với CAN Controller, trong khi CanTrcv chịu trách nhiệm với CAN Transceiver.

CanSM và ComM quản lý communication/network state ở các tầng cao hơn, không phải nơi trực tiếp xử lý CAN frame trong CanDrv.

EcuM liên quan tới ECU state và wake-up, còn DET hỗ trợ development error reporting.

Khi debug, hãy đi theo chain: CAN Bus → Controller → CanDrv → CanIf → PduR/COM → Application. Đây là cách rất hiệu quả để xác định lỗi nằm ở tầng nào.
