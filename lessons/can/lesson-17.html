Bài 17: Init và DeInit

Trong các bài trước, chúng ta đã tìm hiểu kiến trúc CAN Driver, các module liên quan như CanIf, EcuM, OS, SchM, DET và DEM. Một trong những vấn đề quan trọng tiếp theo khi làm việc với CAN Driver là hiểu rõ Initialization (Init) và Deinitialization (DeInit).

Init và DeInit quyết định thời điểm CAN Driver được đưa vào trạng thái có thể hoạt động và thời điểm driver được đưa trở về trạng thái không hoạt động. Đây cũng là một trong những khái niệm rất quan trọng khi debug lỗi CAN communication.

Ý tưởng chính:

Init = chuẩn bị CAN Driver và các thành phần liên quan để có thể hoạt động.
DeInit = đưa CAN Driver trở về trạng thái không hoạt động và giải phóng/reset những state cần thiết theo configuration.

Có thể nhớ đơn giản:
Init → Ready to use
DeInit → No longer initialized

1. Init và DeInit là gì?

Khái niệm Ý nghĩa
Init Khởi tạo module và chuẩn bị state/configuration để module có thể hoạt động.
DeInit Đưa module về trạng thái không initialized và ngừng hoạt động theo thiết kế.

Trong AUTOSAR, initialization không đơn giản chỉ là "set một biến thành TRUE". CAN Driver cần được chuẩn bị cả software state, hardware configuration và các thành phần liên quan tới CAN Controller. 

ECU Startup
    │
    ▼
CAN Driver Init
    │
    ├── Software state
    ├── Configuration
    ├── CAN Controller
    ├── Interrupt / polling
    └── Hardware-related setup
    │
    ▼
CAN Driver Ready

2. Tại sao Init quan trọng?

Một CAN Driver chưa được initialized không thể được coi là sẵn sàng để xử lý CAN communication.

Nếu application hoặc upper-layer module gọi API của CAN Driver trước khi initialization hoàn tất, có thể xảy ra development error hoặc hành vi không hợp lệ. 

ECU Startup
    │
    ▼
Can_Init()
    │
    ▼
Driver Initialized
    │
    ├── Can_SetControllerMode()
    ├── Can_Write()
    └── CAN processing
            │
            ▼
       CAN Communication
Điểm cần nhớ: Init phải hoàn thành trước khi các operation yêu cầu CAN Driver ở trạng thái initialized được thực hiện.

3. Can_Init()

Trong AUTOSAR CAN Driver, API quan trọng nhất cho initialization là Can_Init(). 

Can_Init(&CanConfig)
       │
       ▼
    CanDrv
       │
       ├── Initialize driver state
       ├── Load / apply configuration
       ├── Configure CAN controllers
       └── Prepare CAN hardware
       │
       ▼
CAN Driver initialized

Prototype cụ thể có thể phụ thuộc AUTOSAR release và implementation, nhưng về mặt khái niệm Can_Init() nhận configuration và sử dụng configuration đó để đưa driver vào trạng thái hoạt động.

4. Configuration trong Can_Init()

CAN Driver không tự biết mọi thông tin về ECU. Các thông tin cần thiết thường được tạo ra từ configuration của project.

Ví dụ configuration có thể liên quan tới:

  • CAN Controller.
  • Hardware Object.
  • Baudrate / timing configuration.
  • Tx / Rx configuration.
  • Interrupt configuration.
  • CAN controller options.
CAN Configuration
       │
       ├── Controller configuration
       ├── Hardware Objects
       ├── Tx configuration
       ├── Rx configuration
       ├── Timing
       └── Interrupt / Polling settings
       │
       ▼
     Can_Init()
       │
       ▼
   CAN Driver state

Configuration thực tế phụ thuộc vào ECU, MCU, CAN peripheral và vendor implementation.

Một phần quan trọng của initialization là thiết lập internal software state của CAN Driver.

Các state cụ thể và cách biểu diễn nội bộ phụ thuộc implementation. Sơ đồ trên chỉ nhằm mô tả concept: trước Init driver chưa sẵn sàng, sau Init driver đã có configuration và state cần thiết.

6. Init CAN Controller

Initialization của CAN Driver có liên quan chặt chẽ tới CAN Controller. 

Can_Init()
    │
    ▼
CAN Driver
    │
    ▼
CAN Controller Configuration
    │
    ├── Timing
    ├── Mode
    ├── Tx configuration
    ├── Rx configuration
    └── Hardware Objects
    │

Tuy nhiên cần phân biệt giữa việc initialize driver và việc đưa controller vào trạng thái STARTED. Hai khái niệm này không nhất thiết là cùng một operation.

Quan trọng: Can_Init() không nên được hiểu đơn giản là "CAN bắt đầu truyền frame ngay lập tức". Sau initialization còn có thể cần các bước controller mode / communication state phù hợp.

7. Init không đồng nghĩa với START

Đây là một trong những điểm rất dễ nhầm khi học CAN Driver. 

Can_Init()

Khái niệm Ý nghĩa

Controller Mode Điều khiển trạng thái hoạt động của CAN Controller.
STARTED Controller được đưa vào trạng thái cho phép CAN communication theo configuration.

8. CAN Initialization Flow

Flow thực tế có thể có thêm MCU, PORT, INTC, CanTrcv, CanIf, CanSM và các module khác. Thứ tự chính xác phụ thuộc ECU integration và configuration.

9. Init và CanIf

CAN Driver không hoạt động độc lập với CanIf. Trong CAN communication stack, CanIf cũng cần được initialized trước khi communication flow đầy đủ có thể hoạt động. 

ECU Startup
    │
    ├── CanDrv Init
    │
    ├── CanIf Init
    │
    ├── CAN communication stack Init
    │
    ▼
Communication Stack Ready

Không nên coi sơ đồ trên là một thứ tự API cố định cho mọi project. Nó chỉ mô tả rằng các module phải được initialize phù hợp với dependency của hệ thống.

10. Init và OS / SchM

OS và SchM cũng có thể liên quan tới lifecycle của CAN Driver. Ví dụ, nếu CAN Driver sử dụng polling-based MainFunction, execution environment phải sẵn sàng để MainFunction được gọi đúng cách. 

ECU Startup
    │
    ▼
OS Ready
    │
    ▼
BSW / CAN Initialization
    │
    ▼
MainFunction configuration
    │
    ▼
CAN Runtime Processing

Nếu CAN Driver đã initialized nhưng MainFunction không được schedule trong polling configuration, CAN communication vẫn có thể không hoạt động đúng.

11. Init và Interrupt

Với interrupt-driven CAN configuration, interrupt infrastructure cũng phải được cấu hình phù hợp. 

Can_Init()

    │
    ▼
CAN Controller Event
    │
    ▼
INTC
    │

Vì vậy khi debug CAN RX/TX trong interrupt mode, không nên chỉ kiểm tra Can_Init(). Cần kiểm tra cả interrupt configuration, ISR mapping và execution path.

12. Can_Init và DET

Init cũng liên quan tới DET. Nếu API được gọi với trạng thái hoặc tham số không hợp lệ, development error có thể được report.

Điều này giúp developer phát hiện configuration hoặc integration issue sớm trong quá trình phát triển.

13. Can_Init và DEM

Cần phân biệt DET và DEM ngay trong initialization context.

Tình huống Thành phần liên quan
Can_Init() được gọi sai DET
Invalid initialization parameter DET
CAN communication timeout sau khi ECU chạy DEM có thể liên quan
Diagnostic event trong runtime DEM

Nói cách khác, lỗi trong quá trình sử dụng API Init và diagnostic fault trong runtime là hai vấn đề khác nhau.

14. Khi nào cần DeInit?

DeInit được sử dụng khi CAN Driver cần được đưa ra khỏi trạng thái initialized.

Tùy architecture, DeInit có thể liên quan tới:

  • ECU shutdown.
  • Reconfiguration.
  • Special lifecycle transition.
  • Testing hoặc controlled restart.
  • Vendor-specific integration scenarios.
CAN Communication
       │
       ▼
Stop Communication
       │
       ▼
Controller stopped
       │
       ▼
CAN Driver DeInit
       │
       ▼
Driver not initialized
Lưu ý: DeInit không có nghĩa là ECU luôn luôn phải shutdown. Việc module có hỗ trợ DeInit, khi nào được gọi và mức độ cleanup như thế nào phụ thuộc specification, configuration và integration.

15. Can_DeInit()

Một CAN Driver implementation có thể cung cấp API deinitialization theo AUTOSAR specification/configuration. Conceptually, operation này đưa driver ra khỏi trạng thái initialized. 

Can_DeInit()
      │
      ▼
   CanDrv
      │
      ├── Stop / disable processing
      ├── Reset internal state
      ├── Disable relevant functionality
      └── Return to uninitialized state
      │
      ▼
    UNINIT

Tên API và availability cần được kiểm tra theo đúng AUTOSAR CAN Driver release và implementation đang sử dụng. Không nên giả định mọi project đều expose chính xác cùng một API DeInit.

16. DeInit không phải Controller STOP đơn giản

Một điểm dễ nhầm khác là: Controller STOP và Driver DeInit không phải cùng một khái niệm.

Operation Ý nghĩa
Controller STOP Đưa CAN Controller ra khỏi trạng thái communication đang hoạt động.
Driver DeInit Đưa CAN Driver về trạng thái không initialized theo lifecycle của module. 
Driver Initialized
       │
       ▼
Controller STARTED
       │
       ▼
CAN Communication
       │
       ▼
Controller STOPPED
       │
       ▼
Driver DeInit
       │
       ▼
Driver UNINIT

17. Init → Runtime → DeInit

Sơ đồ trên mô tả lifecycle ở mức khái niệm: driver bắt đầu ở trạng thái chưa initialized, sau Init mới bước vào runtime operation, và có thể trở về trạng thái chưa initialized khi DeInit được thực hiện.

18. Init lại sau DeInit

Một câu hỏi thường gặp là: "Sau khi DeInit, có thể Init lại không?"

Về mặt concept, lifecycle có thể có dạng: 

UNINIT
  │
  │ Init
  ▼
INITIALIZED
  │
  │ Runtime
  ▼
ACTIVE
  │
  │ DeInit
  ▼

  │
  │ Init again
  ▼
INITIALIZED

Tuy nhiên việc hỗ trợ và điều kiện để thực hiện Init lại phụ thuộc specification, configuration và integration của module.

19. Init và DeInit trong ECU Shutdown

Khi ECU shutdown, communication thường cần được đưa về trạng thái phù hợp trước khi các module được shutdown. 

ECU RUNNING
    │
    ▼

    │
    ├── Stop CAN communication
    ├── Stop controller
    └── Stop related processing
    │
    ▼

    │
    ▼

Thứ tự chính xác phụ thuộc ECU lifecycle và AUTOSAR integration. Vì vậy không nên coi đây là một shutdown sequence cố định cho mọi ECU.

21. Init và CanIf trong startup

26. Những lỗi Init thường gặp

Lỗi Nguyên nhân có thể Hướng kiểm tra
Driver vẫn UNINIT Can_Init chưa được gọi Kiểm tra startup sequence
Init error Configuration / parameter không hợp lệ Kiểm tra DET và configuration
Controller không hoạt động Controller chưa được start Kiểm tra controller mode
RX không hoạt động Interrupt / polling chưa được cấu hình Kiểm tra INTC / MainFunction
TX không hoạt động Controller chưa ready Kiểm tra Init → Start → Can_Write
MainFunction không chạy OS scheduling chưa đúng Kiểm tra Task / period

27. Những lỗi DeInit thường gặp

Lỗi Nguyên nhân có thể
DeInit khi module vẫn đang được sử dụng Lifecycle sequence không đúng
Communication vẫn được gọi sau DeInit Upper layer chưa shutdown đúng
Interrupt vẫn hoạt động Shutdown / interrupt disable sequence chưa đúng
MainFunction vẫn chạy OS scheduling chưa được stop/adjust
Init lại không hoạt động Driver state hoặc configuration chưa được reset đúng

29. Interview Perspective

Nếu interviewer hỏi: "What is the purpose of Can_Init()?" 

Can_Init() initializes the CAN Driver
and prepares its configuration and internal
state so that the driver can operate.

It may also configure the CAN controller
according to the generated configuration,
but initialization should not be confused
with putting the controller into the STARTED state.

Nếu interviewer hỏi: "What is the difference between Init and Start?" 

Initialization prepares the driver
and its configuration for operation.

Starting the controller changes the
controller state so that CAN communication
can be performed.

Therefore, Init and Start are related
but they are not the same operation.

Nếu interviewer hỏi: "What should you check if CAN communication does not work after initialization?" 

I would first verify that the CAN Driver
was initialized successfully.

Then I would check the controller state,
CAN configuration, interrupt or polling path,
OS scheduling if required, and finally
the CanIf and upper communication layers.

30. Memory Map

Memory trick:

Init → Configure / Prepare
Start → Controller can communicate
Runtime → TX / RX / Processing
Stop → Controller stops communication
DeInit → Driver no longer initialized

31. Tóm tắt



Init là quá trình chuẩn bị CAN Driver để có thể hoạt động. Nó bao gồm việc thiết lập software state, configuration và các thành phần liên quan tới CAN Controller theo configuration.

API quan trọng là Can_Init(), nhưng cần nhớ rằng Init không đồng nghĩa với Controller START. Driver có thể đã initialized nhưng controller vẫn chưa được đưa vào trạng thái communication phù hợp.

Một flow conceptual có thể nhớ là:

Can_Init()
↓
Controller Configuration
↓
Controller Start
↓
CAN Communication

DeInit đưa CAN Driver trở về trạng thái không initialized theo lifecycle của module. DeInit cũng không giống hoàn toàn với Controller STOP.

Khi debug CAN không hoạt động, hãy kiểm tra theo thứ tự:

1. Driver đã Init chưa?
2. Controller đã ở state phù hợp chưa?
3. Configuration có đúng không?
4. Interrupt hoặc Polling path có hoạt động không?
5. OS / MainFunction có được execute không?
6. CanIf và upper communication layers có hoạt động không?

Có thể ghi nhớ toàn bộ bài bằng:

Init → Prepare
Start → Communicate
Runtime → Process
Stop → Stop Controller
DeInit → Uninitialize
