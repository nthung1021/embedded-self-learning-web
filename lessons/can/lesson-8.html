Bài 8: AUTOSAR CAN-Driver

Ở các bài trước, chúng ta đã tìm hiểu CAN ở mức protocol: frame, Identifier, arbitration, bit stuffing và CAN FD. Khi làm việc với một ECU sử dụng AUTOSAR Classic Platform, ứng dụng không truy cập trực tiếp thanh ghi của CAN Controller. Thay vào đó, AUTOSAR chia phần mềm thành nhiều lớp và đặt CAN Driver (CanDrv) ở tầng Microcontroller Abstraction Layer (MCAL).

Mục tiêu của bài này là hiểu CAN Driver nằm ở đâu, giao tiếp với lớp nào, các API quan trọng, Hardware Object hoạt động ra sao và một message đi qua AUTOSAR CAN stack như thế nào.

1. CAN Driver nằm ở đâu trong AUTOSAR?

AUTOSAR Classic Platform tổ chức phần mềm ECU thành các lớp có mức độ trừu tượng khác nhau. Trong Basic Software (BSW), Microcontroller Abstraction Layer (MCAL) chứa các driver giao tiếp gần với phần cứng microcontroller.

Điểm quan trọng là CanDrv không phải là toàn bộ CAN communication stack. CanDrv chịu trách nhiệm giao tiếp với CAN Controller ở mức thấp. Các lớp phía trên đảm nhiệm những chức năng trừu tượng hơn như routing PDU, mapping cấu hình và communication services.

2. CAN Driver làm nhiệm vụ gì?

Có thể xem CAN Driver như lớp trung gian giữa phần mềm AUTOSAR và phần cứng CAN Controller. Một số nhiệm vụ chính gồm:

  • Khởi tạo CAN Controller theo cấu hình.
  • Chuyển CAN Controller giữa các operation mode.
  • Nhận yêu cầu truyền CAN message từ CanIf.
  • Đọc CAN message nhận được từ hardware.
  • Thông báo sự kiện truyền và nhận lên CanIf.
  • Xử lý hoặc thông báo các trạng thái đặc biệt như bus-off.
  • Cung cấp interface chuẩn hóa để CanIf không phụ thuộc trực tiếp vào loại CAN Controller cụ thể.
Nói đơn giản: CanIf nói "hãy gửi message này", CanDrv chuyển yêu cầu đó thành thao tác với CAN Controller; khi hardware nhận hoặc truyền xong, CanDrv thông báo kết quả ngược lên CanIf.

3. Luồng truyền CAN message

Hãy xét một message có Identifier 0x123 và 8 byte dữ liệu. Ở mức AUTOSAR, message không được gửi trực tiếp từ application xuống thanh ghi CAN Controller.

Ở phía CAN Driver, API quan trọng cho truyền message là Can_Write(). AUTOSAR định nghĩa API này để CanIf truyền một CAN PDU xuống CanDrv. 

Std_ReturnType Can_Write(
    Can_HwHandleType Hth,
    const Can_PduType* PduInfo
);

Trong đó:

  • Hth: Hardware Transmit Handle, xác định Hardware Transmit Object được sử dụng.
  • PduInfo: chứa thông tin PDU như Identifier, độ dài dữ liệu và con trỏ tới dữ liệu.
Can_Write() không có nghĩa là "đã truyền thành công lên bus". Nó cho biết yêu cầu truyền đã được driver chấp nhận hay chưa. Việc truyền hoàn tất được thông báo bằng cơ chế transmit confirmation.

4. Hardware Object: HTH và HRH

Một khái niệm rất quan trọng khi học AUTOSAR CAN Driver là CAN Hardware Object (HOH). Hardware Object đại diện cho cách CAN Driver sử dụng các vùng tài nguyên hoặc buffer của CAN Controller để truyền và nhận message.

Loại Tên Mục đích
Transmit HTH - Hardware Transmit Handle Xác định Hardware Transmit Object dùng để gửi message.
Receive HRH - Hardware Receive Handle Xác định Hardware Receive Object dùng để nhận message.

Ví dụ một ECU có hai nhóm message:

  • HTH_0: dùng cho các message điều khiển có priority cao.
  • HTH_1: dùng cho các message thông thường.
  • HRH_0: nhận một nhóm Identifier thông qua hardware filter.
  • HRH_1: nhận một nhóm Identifier khác.
HTH và HRH là khái niệm ở lớp CAN Driver. Không nên nhầm chúng với CAN Identifier. Identifier là một phần của CAN message và được dùng trong arbitration/filtering; HTH/HRH là handle của Hardware Object trong cấu hình driver.

5. Cấu hình CAN Controller

Trước khi CAN Driver có thể sử dụng controller, driver phải được khởi tạo bằng cấu hình AUTOSAR. Các thông số cụ thể phụ thuộc vào MCU, CAN controller và configuration tool của dự án.

Một cấu hình CAN thường liên quan đến các thành phần như:

  • CAN Controller.
  • Controller baud rate và bit timing.
  • CAN Hardware Objects.
  • Transmit Hardware Objects (HTH).
  • Receive Hardware Objects (HRH).
  • Hardware filtering.
  • Interrupt hoặc polling configuration.
  • CAN FD configuration nếu controller hỗ trợ CAN FD.

Sau khi configuration tool sinh ra configuration data, CAN Driver sử dụng dữ liệu này trong quá trình initialization. 

void Can_Init(const Can_ConfigType* Config);

/* Ví dụ minh họa */
Can_Init(&Can_Config);
Đoạn code trên chỉ mang tính minh họa. Trong một project AUTOSAR thực tế, tên configuration object và cách startup được sinh bởi toolchain/configuration của vendor và project.

6. Controller Mode

CAN Controller không phải lúc nào cũng được phép truyền message. AUTOSAR CAN Driver cung cấp API để điều khiển operation mode của từng CAN Controller. 

Can_ReturnType Can_SetControllerMode(
    uint8 Controller,
    Can_StateTransitionType Transition
);

Về mặt khái niệm, controller có thể được chuyển giữa các trạng thái như:

Trạng thái Ý nghĩa
STOPPED Controller chưa tham gia truyền thông bình thường trên bus.
STARTED Controller có thể tham gia hoạt động CAN bình thường.
SLEEP Controller ở trạng thái tiết kiệm năng lượng theo khả năng và cấu hình của hệ thống.

Việc chuyển mode không chỉ là một thao tác nội bộ của CanDrv. Các lớp phía trên, đặc biệt là CanIf và CanSM, có thể tham gia quản lý trạng thái của communication stack.

7. Luồng nhận CAN message

Khi một CAN frame xuất hiện trên bus và phù hợp với cấu hình receive hardware object, CAN Controller lưu message vào vùng nhận tương ứng. CAN Driver sau đó lấy message từ hardware và thông báo lên CanIf.

Với cơ chế interrupt, CAN Controller có thể tạo interrupt khi có message hoặc sự kiện phù hợp. Với polling, CAN Driver định kỳ kiểm tra hardware. AUTOSAR cũng hỗ trợ cấu hình kết hợp hai cơ chế này tùy Hardware Object.

Một API scheduled function quan trọng là: 

void Can_MainFunction_Read(void);

Khi receive processing được cấu hình sử dụng polling, hàm này thực hiện việc polling các receive indications theo cấu hình của driver.

8. Các API quan trọng cần nhớ

API Vai trò
Can_Init() Khởi tạo CAN Driver với configuration.
Can_SetControllerMode() Yêu cầu thay đổi operation mode của CAN Controller.
Can_Write() Nhận yêu cầu truyền CAN PDU từ CanIf.
Can_MainFunction_Read() Polling receive indications khi cấu hình sử dụng polling.
Can_MainFunction_BusOff() Polling bus-off events khi bus-off được cấu hình xử lý bằng polling.
Can_MainFunction_Write() Polling transmit events khi transmission processing được cấu hình bằng polling.
Không phải project nào cũng sử dụng tất cả API theo cùng một cách. Việc sử dụng interrupt hay polling, số lượng controller, Hardware Object và các tính năng CAN FD phụ thuộc vào cấu hình ECU và khả năng của CAN Controller.

9. Transmit Confirmation và Receive Indication

Một điểm rất quan trọng khi đọc code AUTOSAR là phân biệt request với notification.

Luồng Ý nghĩa
CanIf → CanDrv: Can_Write() CanIf yêu cầu driver truyền một PDU.
CanDrv → CanIf: Tx Confirmation Driver thông báo transmission event đã xảy ra.
CAN Controller → CanDrv Hardware phát hiện receive event và driver lấy message.
CanDrv → CanIf: Rx Indication Driver thông báo một CAN PDU đã được nhận.

Vì vậy, khi debug một message không xuất hiện trên CAN bus, không nên chỉ kiểm tra Can_Write(). Cần xác định message đã đi qua những bước nào:

  1. CanIf có gọi Can_Write() không?
  2. HTH được sử dụng có đúng configuration không?
  3. Can_Write() trả về kết quả gì?
  4. CAN Controller có ở trạng thái STARTED không?
  5. CAN Controller có thực sự phát frame không?
  6. Có nhận được transmit confirmation không?
  7. CAN bus có lỗi về bit timing, transceiver hoặc physical connection không?

10. Bus-Off và Error Handling

CAN Controller có cơ chế phát hiện lỗi và có thể chuyển sang trạng thái bus-off khi error counter đạt điều kiện tương ứng của CAN. CAN Driver phải phát hiện trạng thái này và thông báo lên các lớp phía trên.

Trong AUTOSAR, bus-off có thể được xử lý bằng interrupt hoặc polling tùy configuration. Khi dùng polling, Can_MainFunction_BusOff() được sử dụng để kiểm tra bus-off events đã được cấu hình theo cơ chế polling.

Bus-off không đơn giản là "CAN Driver bị crash". Đây là một trạng thái lỗi của CAN Controller liên quan đến việc controller phát hiện quá nhiều lỗi trên bus. Phần mềm phía trên cần nhận notification và thực hiện chiến lược quản lý communication phù hợp.

11. CAN FD trong CAN Driver

CAN Driver hiện đại có thể hỗ trợ cả Classic CAN và CAN FD nếu CAN Controller và configuration của ECU hỗ trợ. Khi đó, driver phải biết controller đang được cấu hình với CAN FD capability và xử lý các thông tin liên quan đến CAN FD frame.

Một điểm cần nhớ là CAN FD không làm thay đổi kiến trúc AUTOSAR. Vẫn có thể hình dung luồng cơ bản: 

Application
    ↓
RTE / Communication Stack
    ↓
CanIf
    ↓
CanDrv
    ↓
CAN Controller
    ↓
CAN Bus

Sự khác biệt chủ yếu nằm ở khả năng và configuration của CAN Controller cũng như dữ liệu frame được truyền. Vì vậy khi debug CAN FD, ngoài Identifier và DLC, cần quan tâm thêm đến các tham số như nominal bitrate, data bitrate và BRS.

12. Ví dụ cấu hình và truyền message

Ví dụ dưới đây chỉ minh họa tư duy sử dụng API. Tên type, configuration object và cách khởi tạo thực tế có thể khác giữa các AUTOSAR implementation và vendor. 

void CanApp_Init(void)
{
    /* Generated configuration */
    Can_Init(&Can_Config);

    /* Start CAN controller */
    Can_SetControllerMode(
        0,
        CAN_T_START
    );
}

void CanApp_Send(void)
{
    uint8 data[8] = {
        0x10, 0x20, 0x30, 0x40,
        0x50, 0x60, 0x70, 0x80
    };

    Can_PduType pdu = {
        .swPduHandle = 0,
        .length      = 8,
        .id          = 0x123,
        .sdu         = data
    };

    Can_Write(HTH_0, &pdu);
}
Trong một project AUTOSAR đầy đủ, application thường không gọi trực tiếp Can_Write(). API này thuộc interface của CanDrv và được gọi từ CanIf. Ví dụ trên nhằm giúp hình dung interface của CAN Driver, không phải mô hình application trực tiếp bypass toàn bộ communication stack.

13. Những khái niệm dễ nhầm

Khái niệm Không nên nhầm với Ý nghĩa
CAN Identifier HTH / HRH Identifier thuộc CAN frame; HTH/HRH là Hardware Object handle.
CanIf CanDrv CanIf cung cấp abstraction interface; CanDrv giao tiếp trực tiếp với CAN Controller.
Can_Write() Transmit confirmation Can_Write là yêu cầu truyền; confirmation là notification về transmission event.
HRH CAN RX FIFO HRH là AUTOSAR Hardware Object handle; FIFO là cơ chế lưu message của hardware.
CAN Controller CAN Transceiver Controller xử lý protocol; transceiver kết nối logic CAN với physical bus.

14. Khi debug CAN Driver nên kiểm tra gì?

Với một Junior Embedded Engineer, một checklist đơn giản sẽ rất hữu ích khi message không được truyền hoặc nhận.

  • Configuration: Controller, baud rate, HTH/HRH và filter có đúng không?
  • Controller mode: Controller đã được chuyển sang STARTED chưa?
  • Transmission: CanIf có gọi Can_Write không?
  • Return value: Can_Write có trả về lỗi hoặc trạng thái busy không?
  • Hardware: CAN Controller có ghi nhận transmit/receive event không?
  • Interrupt/Polling: Event đang được xử lý bằng interrupt hay polling?
  • CAN bus: Bit timing, transceiver, termination và physical connection có đúng không?
  • Error: Controller có đang ở error passive hoặc bus-off không?
  • Callback: CanIf có nhận được Tx Confirmation hoặc Rx Indication không?
Khi debug nên đi theo data flow thay vì chỉ nhìn một function. Ví dụ: Application → communication stack → CanIf → CanDrv → CAN Controller → CAN Bus. Sau đó kiểm tra chiều ngược lại đối với receive path.

15. CAN Driver và mục tiêu của AUTOSAR

Một trong những ý tưởng quan trọng của AUTOSAR là tách phần mềm ứng dụng khỏi sự phụ thuộc trực tiếp vào hardware cụ thể. AUTOSAR Classic sử dụng kiến trúc phân lớp để tạo abstraction giữa application và microcontroller hardware.

Vì vậy, khi thay đổi một CAN Controller hoặc MCU khác, phần application phía trên không nên phải biết chi tiết về các register của CAN peripheral. Phần CAN Driver và configuration đảm nhiệm phần lớn sự khác biệt ở tầng hardware.

Đây là lý do kiến thức CAN protocol và kiến thức AUTOSAR CAN Driver cần đi cùng nhau: CAN protocol giúp hiểu frame và bus hoạt động thế nào, còn CAN Driver giúp hiểu software trên ECU điều khiển hardware CAN như thế nào.

Tóm tắt

CAN Driver (CanDrv) là driver thuộc MCAL của AUTOSAR Classic Platform, nằm giữa CanIf và CAN Controller. Nó cung cấp các API chuẩn hóa để khởi tạo controller, thay đổi controller mode, truyền message bằng Can_Write() và xử lý receive theo interrupt hoặc polling. HTH và HRH đại diện cho Hardware Transmit/Receive Object, trong khi CAN Identifier vẫn là thông tin thuộc CAN frame. Khi debug, cần theo dõi toàn bộ data flow từ CanIf → CanDrv → CAN Controller → CAN Bus và chiều ngược lại thay vì chỉ kiểm tra một API riêng lẻ.
