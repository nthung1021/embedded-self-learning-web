Bài 15: CAN-IF, EcuM, OS, SchM

Ở các bài trước, chúng ta đã tìm hiểu CAN Driver và các module liên quan như MCU, PORT, INTC, CanTrcv, DET và CanSM. Trong bài này, chúng ta tập trung vào bốn thành phần rất quan trọng trong quá trình tích hợp CAN Driver vào một ECU AUTOSAR: CanIf, EcuM, OS và SchM.

Bốn thành phần này nằm ở những tầng khác nhau và có responsibility khác nhau. Việc hiểu đúng ranh giới giữa chúng rất quan trọng, đặc biệt khi đọc AUTOSAR architecture hoặc debug một CAN stack.

Ý tưởng chính:

CanIf là abstraction/interface giữa CAN Driver và các module communication phía trên.
EcuM quản lý trạng thái tổng thể của ECU, đặc biệt startup, shutdown, sleep và wakeup.
OS cung cấp execution environment như Task, ISR và scheduling.
SchM hỗ trợ việc điều phối các MainFunction và các cơ chế bảo vệ/synchronization của BSW.

1. Nhìn tổng thể bốn thành phần

Thành phần Vai trò chính Liên quan tới CAN như thế nào?
CanIf CAN Interface Giao tiếp giữa upper CAN modules và CanDrv
EcuM ECU State Manager Startup, shutdown, sleep, wakeup
OS Operating System Task, ISR, scheduling và execution context
SchM BSW Scheduler / synchronization support Hỗ trợ scheduling MainFunction và critical-section/synchronization mechanisms

2. Vị trí của các thành phần trong ECU

Lưu ý rằng OS và SchM không phải là các tầng xử lý CAN message. Chúng cung cấp môi trường để các BSW module như CanDrv thực thi công việc của mình.

3. CanIf là gì?

CanIf (CAN Interface) là module nằm giữa các upper-layer communication modules và CAN Driver. Nó cung cấp một abstraction layer để upper layers không phải phụ thuộc trực tiếp vào CAN Controller hoặc implementation cụ thể của CAN Driver. 

Upper CAN Modules
        │
        ▼
      CanIf
        │
        ▼
      CanDrv
        │
        ▼
CAN Controller

Ví dụ, upper layer có thể yêu cầu truyền một CAN PDU. CanIf chịu trách nhiệm mapping thông tin PDU đó tới các thông tin mà CanDrv cần để thực hiện transmission.

4. CanIf và CanDrv: Transmission

Một luồng truyền CAN message có thể được hình dung như sau: 

Application
    │
    ▼
   COM
    │
    ▼
   PduR
    │
    ▼
  CanIf
    │
    │ Can_Write(...)
    ▼
  CanDrv
    │
    ▼
CAN Controller
    │
    ▼
 CAN Bus

CanIf giúp upper layer không cần biết trực tiếp:

  • CAN Controller register nằm ở đâu.
  • Hardware Object cụ thể được map như thế nào.
  • CAN Driver của vendor được implement ra sao.
  • Cách CAN Controller thực hiện transmission ở mức hardware.
Boundary cần nhớ: CanIf xử lý abstraction và mapping ở communication interface; CanDrv xử lý CAN Controller ở mức driver.

5. CanIf và CanDrv: Reception

Ở chiều nhận, flow được đảo ngược: 

CAN Bus
    │
    ▼
CAN Controller
    │
    ▼
  CanDrv
    │
    │ Rx Indication
    ▼
  CanIf
    │
    ▼
 PduR / CanTp / COM
    │
    ▼
Application

CanDrv xử lý event từ CAN Controller rồi thông báo lên CanIf. CanIf tiếp tục xác định PDU cần được chuyển tới module nào.

6. EcuM là gì?

EcuM (ECU State Manager) chịu trách nhiệm quản lý các trạng thái lớn của ECU trong vòng đời hoạt động, bao gồm các quá trình như startup, shutdown, sleep và wakeup.

Vì CAN Driver là một BSW module trong ECU, nó phải được initialize ở thời điểm phù hợp trong quá trình ECU startup. 

ECU Reset
   │
   ▼
EcuM Startup
   │
   ├── Initialize system
   ├── Initialize BSW modules
   ├── Initialize communication stack
   │
   ▼
CanIf / CanDrv ready
   │
   ▼
CAN communication available

EcuM không phải là module xử lý CAN frame. Nó quản lý trạng thái của ECU và điều phối quá trình startup/shutdown để các BSW module có thể hoạt động trong đúng lifecycle.

7. EcuM và CAN Startup

Có thể hình dung một ECU startup đơn giản như sau: 

Power On
   │
   ▼
Reset
   │
   ▼
EcuM / Startup
   │
   ├── MCU initialization
   ├── PORT initialization
   ├── OS initialization
   ├── BSW initialization
   │
   ▼
CanDrv initialization
   │
   ▼
CanIf initialization
   │
   ▼
Communication stack ready
   │
   ▼
ECU RUNNING

Thứ tự chi tiết và cách gọi từng module phụ thuộc vào ECU integration và AUTOSAR configuration. Vì vậy không nên coi sơ đồ trên là một danh sách API cố định cho mọi project.

Điểm quan trọng: EcuM quản lý lifecycle của ECU; nó không thay thế CanIf hoặc CanDrv và cũng không trực tiếp xử lý CAN transmit/receive.

8. EcuM và CAN Wakeup

Một trong những điểm CAN liên quan rõ nhất tới EcuM là wakeup.

Khi ECU đang ở một trạng thái low-power hoặc sleep, một sự kiện CAN có thể là nguồn wakeup tùy thiết kế hệ thống. Khi đó CAN hardware, transceiver và wakeup infrastructure phải phối hợp để ECU quay trở lại trạng thái hoạt động.

9. OS là gì?

OS (Operating System) trong AUTOSAR Classic cung cấp cơ chế thực thi cho application và BSW. Một số khái niệm quan trọng gồm:

  • Task
  • ISR (Interrupt Service Routine)
  • Scheduling
  • Event
  • Counter / Alarm
  • Resource và synchronization

Đối với CAN, OS đặc biệt quan trọng vì CAN Driver có thể được thực thi trong nhiều execution context khác nhau, chẳng hạn ISR hoặc task/main function.

10. CAN Driver và ISR

Nếu CAN Controller sử dụng interrupt-driven processing, một sự kiện từ CAN Controller có thể kích hoạt ISR. 

CAN Controller
       │
       │ Interrupt
       ▼
      INTC
       │
       ▼
      ISR
       │
       ▼
    CanDrv
       │
       ▼
    CanIf
       │
       ▼
 Upper modules

ISR phải được cấu hình và tích hợp đúng với OS/MCU. CanDrv chịu trách nhiệm xử lý phần CAN event của mình, nhưng không có nghĩa rằng CanDrv tự quản lý toàn bộ interrupt infrastructure của ECU.

11. CAN Driver và Task

Không phải tất cả CAN processing đều nhất thiết xảy ra trong ISR. Với polling configuration, một MainFunction của CAN Driver có thể được gọi định kỳ từ một task hoặc scheduling mechanism. 

OS Task
   │
   │ periodic execution
   ▼
Can_MainFunction_Read()
   │
   ▼
CanDrv
   │
   ▼
Check CAN Controller
   │
   ├── RX event
   ├── TX event
   └── Error / status
   │
   ▼
CanIf

Vì vậy, khi debug một CAN reception problem, cần biết project đang sử dụng interrupt processing hay polling processing.

12. OS Scheduling ảnh hưởng CAN như thế nào?

Với polling-based processing, thời gian mà CAN MainFunction được gọi sẽ ảnh hưởng tới thời điểm driver phát hiện và xử lý event.

Ví dụ, nếu CAN frame đến ngay sau khi Can_MainFunction_Read() vừa chạy, driver có thể phải chờ tới lần polling tiếp theo mới xử lý event.

Debug hint: Nếu reception có độ trễ bất thường trong polling mode, hãy kiểm tra period của MainFunction và scheduling của OS.

13. SchM là gì?

SchM (BSW Scheduler) là một phần của AUTOSAR BSW infrastructure, cung cấp các cơ chế hỗ trợ scheduling và synchronization cho BSW modules.

SchM không phải là một CAN-specific scheduler. Nó được sử dụng bởi nhiều BSW modules và giúp module thực hiện các thao tác cần được bảo vệ hoặc được điều phối trong execution environment phù hợp. 

BSW Module
    │
    ├── MainFunction
    │
    ├── Critical Section
    │
    └── Synchronization
             │
             ▼
            SchM
             │
             ▼
        OS / Scheduler

14. SchM và CAN MainFunction

Trong CAN Driver, các MainFunction có thể được cấu hình để thực hiện các processing định kỳ. 

OS / Scheduling
       │
       ▼
      SchM
       │
       ▼
Can_MainFunction_Read()
Can_MainFunction_Write()
Can_MainFunction_BusOff()
Can_MainFunction_Wakeup()
       │
       ▼
     CanDrv

Tên và việc sử dụng từng MainFunction phụ thuộc vào CAN Driver specification và configuration của project. Không phải tất cả MainFunction đều luôn được sử dụng.

15. SchM và Critical Section

Một driver có thể cần bảo vệ một đoạn code khi dữ liệu hoặc trạng thái nội bộ không được phép bị thay đổi đồng thời bởi một execution context khác.

Có thể hình dung: 

Normal execution
       │
       ▼
SchM_Enter_...
       │
       ▼
Critical Section
       │
       ├── Access shared driver data
       ├── Update driver state
       └── Hardware-related operation
       │
       ▼
SchM_Exit_...
       │
       ▼
Normal execution
Không nên hiểu SchM là "nơi chứa toàn bộ CAN scheduling". SchM cung cấp các service/infrastructure để BSW module sử dụng; OS vẫn là thành phần chịu trách nhiệm về execution scheduling ở cấp hệ thống.

16. OS và SchM khác nhau như thế nào?

21. EcuM, OS và SchM có cùng responsibility không?

Không. Đây là một trong những phần dễ nhầm nhất.

Thành phần Câu hỏi mà nó giải quyết
EcuM ECU đang ở lifecycle/state nào?
OS Code nào được thực thi, khi nào và trong context nào?
SchM BSW module sử dụng scheduling/synchronization abstraction như thế nào?
CanIf CAN communication interface giữa upper layer và CanDrv là gì?

22. CAN Initialization nhìn từ bốn module

Sơ đồ trên chỉ mô tả relationship ở mức conceptual. Startup sequence thực tế của một ECU sẽ phụ thuộc vào ECU configuration, OS configuration và vendor integration.

23. Debug CAN theo CanIf → EcuM → OS → SchM

Khi CAN communication không hoạt động, có thể chia việc debug thành bốn nhóm:

Nhóm Câu hỏi debug
CanIf PDU có được mapping đúng? Tx/Rx notification có được gọi?
EcuM ECU đã ở trạng thái cho phép communication chưa? Startup/wakeup có hoàn tất không?
OS Task/ISR có được execute không? Priority và scheduling có đúng không?
SchM MainFunction có được schedule? Critical section/synchronization có vấn đề không?

Giả sử bạn dùng CAN analyzer và thấy ECU thực sự nhận được CAN frame nhưng Application không nhận được signal.

26. Những điều không nên nhầm lẫn

Dễ nhầm Cách hiểu đúng
CanIf = CanDrv Không. CanIf là interface/abstraction, CanDrv điều khiển CAN Controller.
EcuM = CAN Manager Không. EcuM quản lý ECU lifecycle.
OS = SchM Không. OS quản lý execution environment; SchM hỗ trợ BSW scheduling/synchronization.
SchM trực tiếp schedule CPU Không nên hiểu như vậy. System scheduling thuộc OS; SchM cung cấp abstraction cho BSW.
EcuM xử lý CAN frame Không. CAN frame processing thuộc CAN stack.
CanIf là OS task Không. CanIf là BSW communication module.

27. Interview Perspective

Nếu interviewer hỏi: "What is the relationship between CanIf, CanDrv, OS and SchM?"

Có thể trả lời theo logic: 

CanIf:
Provides the CAN abstraction/interface
between upper communication layers and CanDrv.

CanDrv:
Controls the CAN controller and handles
CAN-specific hardware events.

OS:
Provides the execution context such as
tasks, ISRs and scheduling.

SchM:
Provides BSW scheduling/synchronization
support used by BSW modules.

Nếu interviewer hỏi thêm về EcuM: 

EcuM:
Manages the ECU lifecycle, including
startup, shutdown, sleep and wakeup.
It does not process CAN frames directly.

28. Memory Map

Memory trick:

CanIf → Interface
EcuM → ECU State
OS → Execution
SchM → BSW Scheduling / Synchronization
CanDrv → CAN Controller

29. Tóm tắt



CanIf là abstraction layer giữa upper communication modules và CAN Driver. Nó giúp upper layers không cần biết implementation cụ thể của CAN Controller/CanDrv.

EcuM quản lý lifecycle của ECU, bao gồm startup, shutdown, sleep và wakeup. Nó không trực tiếp xử lý CAN frame.

OS cung cấp execution environment: Task, ISR, scheduling và synchronization mechanisms. CAN Driver có thể được thực thi trong ISR hoặc task/main-function context tùy configuration.

SchM cung cấp BSW scheduling và synchronization abstraction. Nó không thay thế OS.

Có thể ghi nhớ toàn bộ bài bằng:

CanIf → Interface
EcuM → ECU Lifecycle
OS → Execution
SchM → BSW Scheduling / Synchronization
CanDrv → CAN Controller

Khi debug CAN, hãy xác định trước ECU đang sử dụng interrupt hay polling, sau đó kiểm tra execution path tương ứng: ISR → CanDrv → CanIf hoặc OS scheduling → MainFunction → CanDrv → CanIf.
