Bài 22: Theo dõi Bus-Error

CAN được thiết kế với cơ chế phát hiện và xử lý lỗi rất mạnh. Khi một node phát hiện lỗi trong quá trình truyền hoặc nhận frame, CAN Controller có thể tạo Error Frame, cập nhật các bộ đếm lỗi và thay đổi trạng thái Error State của controller.

Ý chính: Theo dõi Bus-Error không chỉ là kiểm tra xem có lỗi hay không. Kỹ sư cần biết loại lỗi, lỗi xảy ra ở đâu, error counter đang thay đổi thế nào và CAN Controller đang ở trạng thái nào.

1. Bus-Error là gì?

Bus-Error là lỗi xảy ra trong quá trình CAN Controller giao tiếp trên CAN bus. Lỗi có thể xuất phát từ:

  • Bit timing không phù hợp.
  • Baud-rate không tương thích.
  • Physical layer có vấn đề.
  • CAN Transceiver lỗi.
  • Wiring hoặc termination không đúng.
  • Frame bị vi phạm quy tắc CAN.
  • CAN Controller phát hiện trạng thái bus không như mong đợi.

CAN Controller có cơ chế tự phát hiện nhiều loại lỗi ngay trong quá trình truyền và nhận frame.

2. Tại sao cần theo dõi Bus-Error?

Nếu chỉ quan sát việc "có nhận được message hay không", kỹ sư có thể bỏ sót nguyên nhân thực sự của communication failure.

Theo dõi Bus-Error đặc biệt quan trọng trong giai đoạn integration test, system test và debugging trên ECU thực tế.

3. Các loại CAN Error chính

CAN định nghĩa các nhóm lỗi chính:

Loại lỗi Ý nghĩa
Bit Error Giá trị bit được quan sát trên bus không phù hợp với bit mà node đang truyền, trong trường hợp áp dụng.
Stuff Error Vi phạm quy tắc bit stuffing.
CRC Error CRC kiểm tra frame không phù hợp.
Form Error Một field cố định của frame có giá trị không đúng quy định.
ACK Error Node truyền không nhận được dominant ACK như mong đợi.

4. Bit Error

Bit Error xảy ra khi node đang truyền một giá trị bit nhưng phát hiện trạng thái trên bus không phù hợp với giá trị mà nó đang truyền, trong các phần của frame mà cơ chế bit monitoring được áp dụng. 

Node đang truyền:

TX Bit
  │
  ▼
  1
  │
  │ Bit Monitoring
  ▼
CAN Bus
  │
  ▼
  0

Expected ≠ Observed
        ↓
    Bit Error
Có các trường hợp đặc biệt trong CAN, chẳng hạn quá trình arbitration, khiến việc quan sát dominant/recessive không được xử lý giống một Bit Error thông thường. Không nên hiểu đơn giản rằng mọi trường hợp TX khác RX đều là lỗi.

5. Stuff Error

CAN sử dụng bit stuffing để hỗ trợ synchronization. Sau một số lượng bit liên tiếp cùng giá trị theo quy tắc CAN, transmitter chèn một bit ngược lại. 

Data sequence:

11111
     ↓
Bit stuffing
     ↓
111110

Nếu receiver phát hiện quy tắc stuffing bị vi phạm, controller có thể xác định đây là Stuff Error.

6. CRC Error

CAN frame có trường CRC để giúp receiver kiểm tra tính toàn vẹn của dữ liệu frame. 

Transmitter
    │
    │ Calculate CRC
    ▼
┌───────────────────────┐
│ CAN Frame + CRC       │
└───────────────────────┘
    │
    ▼
   Bus
    │
    ▼
Receiver
    │
    │ Calculate / Check CRC
    ▼
CRC Match?
   │
 ┌─┴─┐
Yes  No
 │    │
 ▼    ▼
 OK  CRC Error

7. Form Error

Một số field trong CAN frame phải có giá trị cố định theo format của frame. Nếu receiver phát hiện một field như vậy có trạng thái không hợp lệ, có thể xảy ra Form Error.

Ví dụ, các delimiter và một số trường điều khiển frame có quy tắc cố định. Nếu quy tắc đó bị vi phạm, CAN Controller có thể phát hiện lỗi.

8. ACK Error

Trong quá trình truyền frame, transmitter mong đợi ít nhất một receiver hợp lệ xác nhận bằng ACK. 

Transmitter
     │
     │ Send Frame
     ▼
════════════════ CAN BUS ════════════════
     │
     │            ACK
     ▼             ▼
 Receiver A    Receiver B
     │
     └──────── ACK = Dominant

Nếu không có ACK phù hợp
            ↓
        ACK Error

ACK Error không nhất thiết có nghĩa là "receiver bị hỏng". Nó có thể xảy ra khi không có node nào nhận frame hợp lệ, ví dụ do cấu hình baud-rate hoặc network không phù hợp.

9. Error Frame

Khi một node phát hiện lỗi, CAN có cơ chế thông báo lỗi trên bus bằng Error Frame. 

Normal Frame
───────────────────────────────────►

             Node phát hiện lỗi
                     │
                     ▼
               Error Frame
                     │
                     ▼
════════════════ CAN BUS ════════════════
                     │
                     ▼
          Các node nhận biết lỗi

Error Frame giúp các node khác biết rằng frame hiện tại đã không được truyền hoặc nhận đúng theo quy tắc CAN.

10. Error Active và Error Passive

CAN Controller theo dõi mức độ lỗi thông qua các error counter. Từ đó controller có thể ở các trạng thái error khác nhau. 

        Error Active
             │
             │ Error tăng
             ▼
       Error Passive
             │
             │ Error tiếp tục nghiêm trọng
             ▼
        Bus-Off

Đây là mô hình khái niệm. Chuyển trạng thái thực tế được quyết định bởi các quy tắc của CAN và giá trị của các error counters.

11. Error Counter

CAN Controller thường có hai bộ đếm quan trọng:

  • TEC — Transmit Error Counter.
  • REC — Receive Error Counter.
CAN Controller
      │
      ├───────────────┐
      │               │
      ▼               ▼
    TEC             REC
Transmit Error   Receive Error
   Counter          Counter

Hai counter này giúp controller đánh giá mức độ lỗi liên quan đến transmission và reception.

12. TEC - Transmit Error Counter

TEC liên quan đến các lỗi mà CAN Controller gặp trong quá trình truyền.

Ví dụ: 

Transmission
     │
     ▼
Error detected
     │
     ▼
Transmit Error Counter
     │
     ▼
Controller evaluates
Error State

TEC không đơn giản chỉ tăng một đơn vị cho mọi loại lỗi. Quy tắc cập nhật counter phụ thuộc vào loại lỗi và hoàn cảnh xảy ra lỗi theo CAN specification.

13. REC - Receive Error Counter

REC liên quan đến các lỗi được phát hiện trong quá trình nhận. 

CAN Bus
   │
   ▼
Receive Frame
   │
   ▼
Error detected
   │
   ▼
Receive Error Counter
   │
   ▼
Error State evaluation
Khi debug thực tế, không nên chỉ nhìn một counter riêng lẻ. Hãy xem cả TEC, REC, loại error và controller state.

14. Error State

Ba trạng thái quan trọng cần nhớ là:

State Ý nghĩa khái quát
Error Active Controller đang hoạt động trong trạng thái lỗi bình thường.
Error Passive Error counter đã đạt mức khiến controller bị hạn chế hơn trong việc báo lỗi.
Bus-Off Controller bị tách khỏi CAN bus để ngăn một node lỗi tiếp tục ảnh hưởng bus.

15. Error Active

Khi controller ở Error Active, nó vẫn có thể giao tiếp bình thường và có thể sử dụng Active Error Flag khi cần báo lỗi. 

CAN Controller
      │
      ▼
 Error Active
      │
      ├── Transmit
      ├── Receive
      └── Active Error Flag

16. Error Passive

Khi mức độ lỗi tăng cao, controller có thể chuyển sang Error Passive. Khi đó hành vi báo lỗi của node bị hạn chế so với Error Active. 

Error Active
     │
     │ Error counters increase
     ▼
Error Passive
     │
     │ Continue severe errors
     ▼
  Bus-Off

17. Bus-Off

Bus-Off là trạng thái quan trọng trong CAN error handling. Khi controller chuyển sang Bus-Off, nó ngừng tham gia truyền thông trên bus theo cơ chế của CAN để tránh một node liên tục gây lỗi ảnh hưởng toàn mạng. 

          CAN Bus
             │
             ▼
       CAN Controller
             │
        Too many TX errors
             │
             ▼
          BUS-OFF
             │
             X
       Không tiếp tục
       giao tiếp bình thường
Bus-Off không nên được hiểu đơn giản là "CAN Driver bị crash". Đây là một trạng thái error handling được định nghĩa trong CAN protocol.

18. Vì sao Bus-Off quan trọng?

CAN là một mạng multi-node. Nếu một node bị lỗi nghiêm trọng và liên tục tạo error, node đó có thể gây ảnh hưởng tới các node khác. 

             CAN BUS
─────────────────────────────────────
       │          │           │
       ▼          ▼           ▼
     ECU A      ECU B       ECU C
                  │
                  │ repeated errors
                  ▼
               BUS-OFF

ECU B được tách khỏi communication
để hạn chế ảnh hưởng tới network.

19. Bus-Off Recovery

Sau khi Bus-Off, controller không đơn giản tự động quay lại giao tiếp trong mọi implementation/configuration.

Hệ thống cần có cơ chế recovery phù hợp. Recovery có thể liên quan đến:

  • CAN Controller.
  • CAN Driver.
  • CanIf.
  • CanSM.
  • EcuM hoặc các module quản lý ECU.
  • Cấu hình recovery của project.

22. DET và Bus-Error

Cần phân biệt Bus-Error với Development Error.

Bus-Error DET Error
Lỗi xảy ra trong CAN communication. Lỗi do software gọi API/configuration không hợp lệ theo development checks.
Ví dụ: CRC Error, ACK Error, Bit Error. Ví dụ: API được gọi với parameter không hợp lệ.
Được phát hiện bởi CAN protocol/controller. Được phát hiện bởi software development error checks.

27. Debug khi REC tăng

Nếu REC tăng, cần tập trung vào các vấn đề liên quan đến reception.

  • Kiểm tra baud-rate.
  • Kiểm tra bit timing.
  • Kiểm tra physical bus.
  • Kiểm tra CAN transceiver.
  • Kiểm tra chất lượng tín hiệu.
  • Kiểm tra các node khác trên bus.
  • Kiểm tra CAN controller configuration.

30. Ví dụ: Termination có vấn đề

Một CAN bus thông thường cần termination phù hợp ở hai đầu bus. Nếu termination không đúng, signal integrity có thể bị ảnh hưởng. 

120Ω                           120Ω
  │                               │
  ▼                               ▼
┌─────┐=========================┌─────┐
│ ECU │        CAN BUS           │ ECU │
└─────┘=========================└─────┘
   ▲                               ▲
Termination                    Termination

Nếu termination, wiring hoặc topology không đúng, CAN communication có thể xuất hiện error dù software configuration nhìn có vẻ chính xác.

32. Góc nhìn phỏng vấn

Với vị trí Junior Automotive Embedded Software Engineer, một số câu hỏi có thể được sử dụng để kiểm tra khả năng debug CAN:

  • What are the main CAN error types?
  • What is an Error Frame?
  • What are TEC and REC?
  • What is Error Active?
  • What is Error Passive?
  • What is Bus-Off?
  • Why does a CAN node enter Bus-Off?
  • How would you debug a CAN Bus-Off issue?
  • What can cause ACK Error?
  • What is the difference between a CAN Bus-Error and a DET error?
Câu trả lời ngắn nên nhớ: CAN monitors communication errors using mechanisms such as error detection, error counters and controller error states. When debugging a Bus-Error, I would first identify the error type and controller state, then check baud-rate, bit timing, CAN clock, transceiver, wiring, termination and software configuration.

34. Tóm tắt

Theo dõi Bus-Error là một phần quan trọng trong CAN communication và automotive embedded debugging. CAN Controller có khả năng phát hiện nhiều loại lỗi và sử dụng error counters để theo dõi mức độ lỗi.

Điểm quan trọng nhất: Khi gặp CAN Bus-Error, đừng chỉ nhìn vào một error code. Hãy xác định error type → TEC/REC → controller state → timing → physical layer → CAN Driver/stack. Đây là cách tiếp cận có hệ thống để tìm root cause thay vì chỉ reset ECU và thử lại.
