Bài 16: DET và DEM

Trong các bài trước, chúng ta đã tìm hiểu CAN Driver, CanIf, EcuM, OS, SchM và các module liên quan đến CAN communication trong AUTOSAR. Tuy nhiên, khi một BSW module gặp lỗi thì hệ thống cần một cơ chế để phát hiện, báo cáo và quản lý những lỗi đó.

Hai module thường được nhắc tới trong context này là DET (Default Error Tracer) và DEM (Diagnostic Event Manager). Mặc dù cả hai đều liên quan tới error handling, chúng có mục đích và phạm vi hoàn toàn khác nhau.

Ý tưởng chính:

DET dùng để báo cáo các development error trong quá trình phát triển và tích hợp BSW.
DEM quản lý diagnostic events và diagnostic trouble information ở runtime.

Có thể nhớ đơn giản:
DET → Developer / Development Error
DEM → Diagnostic Event / Vehicle Diagnosis

1. DET và DEM là gì?

Điểm quan trọng nhất là không nên coi DET và DEM là hai module thực hiện cùng một công việc.

2. DET nằm ở đâu trong AUTOSAR?

DET là một phần của BSW infrastructure. Các BSW modules có thể gọi DET để báo cáo những lỗi xảy ra do cách sử dụng module không hợp lệ hoặc vi phạm các điều kiện được định nghĩa trong specification.

DET thường được sử dụng để hỗ trợ developer trong quá trình development và integration. Nó đặc biệt hữu ích khi cần phát hiện một BSW API được gọi sai hoặc module đang ở trạng thái không hợp lệ.

3. Development Error là gì?

Development error là lỗi liên quan tới việc sử dụng một BSW module không đúng theo điều kiện mà module đó yêu cầu.

Ví dụ, một API yêu cầu module phải được initialize trước khi được gọi. Nếu code gọi API khi module vẫn ở trạng thái chưa initialize, module có thể phát hiện development error. 

Application / BSW code
        │
        │ Call API
        ▼
   BSW Module
        │
        ├── Is API usage valid?
        │
        ├── Is module initialized?
        │
        └── Are parameters valid?
        │
        ▼
   Development Error
        │
        ▼
       DET
Điểm cần nhớ: DET chủ yếu giúp phát hiện vấn đề trong cách sử dụng hoặc tích hợp BSW module. Nó không phải là cơ chế quản lý DTC cho chẩn đoán vehicle.

4. DET Error Report

Khi một BSW module phát hiện development error, module có thể report lỗi tới DET.

Một error report thường gắn với các thông tin như:

  • Module ID.
  • Instance ID.
  • API / Service ID.
  • Error ID.

Những thông tin này giúp developer xác định: module nào phát hiện lỗi, instance nào, API nào và loại lỗi gì. 

DET Error Report

Module ID
    │
    ├── Which BSW module?
    │
Instance ID
    │
    ├── Which instance?
    │
API / Service ID
    │
    ├── Which API?
    │
Error ID
    │
    └── What development error?

5. Ví dụ DET trong CAN Driver

Hãy xét một ví dụ đơn giản với CAN Driver. Giả sử một API của CAN Driver yêu cầu Can_Init() phải được gọi trước. 

Application
     │
     ▼
Can_Write(...)
     │
     ▼
CanDrv
     │
     ├── Driver initialized?
     │
     ├── YES → Continue
     │
     └── NO
          │
          ▼
         DET
          │
          ▼
   Development Error

Trong trường hợp này, DET giúp developer phát hiện rằng CAN Driver đang được sử dụng không đúng lifecycle.

Điều này rất hữu ích trong integration testing vì lỗi có thể được phát hiện ngay tại nơi API được gọi thay vì chỉ quan sát một triệu chứng CAN communication không hoạt động.

6. DET không phải là CAN Error Handler

Một điểm rất dễ nhầm là nghĩ rằng DET sẽ xử lý tất cả các lỗi của CAN bus.

Điều đó không đúng. DET không phải là module chịu trách nhiệm xử lý CAN protocol error, Bus-Off hoặc các vấn đề vật lý của CAN bus.

Vấn đề DET có xử lý trực tiếp không?
API được gọi trước initialization Có thể report qua DET
Invalid parameter Có thể report qua DET
CAN Bus-Off Không phải responsibility chính
CAN physical wiring problem Không
CAN protocol error Không

7. DEM là gì?

DEM (Diagnostic Event Manager) là module chịu trách nhiệm quản lý các diagnostic event trong ECU.

Trong quá trình ECU hoạt động, một module có thể phát hiện một điều kiện bất thường. Điều kiện này có thể được report tới DEM dưới dạng một diagnostic event. 

Runtime
   │
   ▼
Monitor / BSW / SWC
   │
   │ Event detected
   ▼
  DEM
   │
   ├── Event status
   ├── Debouncing
   ├── Fault memory
   └── Diagnostic information

DEM vì vậy có vai trò khác DET: DEM phục vụ diagnostic management trong quá trình ECU vận hành và chẩn đoán.

8. Diagnostic Event là gì?

Một Diagnostic Event đại diện cho một điều kiện lỗi hoặc bất thường mà hệ thống muốn theo dõi cho mục đích diagnostics.

Ví dụ, một ECU có thể giám sát:

  • CAN communication timeout.
  • Sensor signal không hợp lệ.
  • Communication error.
  • ECU internal fault.
  • Giá trị signal nằm ngoài phạm vi cho phép.

Những điều kiện này có thể được monitor và report tới DEM tùy theo thiết kế hệ thống. 

Monitor
   │
   ├── Condition OK
   │       │
   │       ▼
   │   Event Passed
   │
   └── Condition Failed
           │
           ▼
          DEM
           │
           ▼
   Diagnostic Event Status

DET DEM

Memory trick:

DET = "Developer made an integration/API usage mistake"
DEM = "ECU detected a diagnostic fault during operation"

10. DEM và Diagnostic Trouble Code

Một khái niệm quan trọng khi học DEM là DTC (Diagnostic Trouble Code).

DEM quản lý diagnostic events và thông tin liên quan tới fault. Trong hệ thống diagnostics, event có thể được liên kết với một DTC theo configuration. 

Fault Condition
      │
      ▼
Diagnostic Event
      │
      ▼
     DEM
      │
      ├── Event status
      ├── Debouncing
      ├── Fault information
      │
      ▼
     DTC
      │
      ▼
Diagnostic Services / Tester

Vì vậy, không nên hiểu rằng mọi lỗi runtime đều tự động trở thành một DTC. Việc mapping event, status và DTC phụ thuộc vào diagnostic configuration của ECU.

11. DEM Event Status

DEM không chỉ lưu một giá trị "error / no error". Diagnostic event có thể có nhiều trạng thái khác nhau trong quá trình monitor.

Ví dụ về logic khái niệm: 

Monitor
   │
   ├── Test passed
   │       │
   │       ▼
   │   Event Passed
   │
   └── Test failed
           │
           ▼
       Event Failed
           │
           ▼
      DEM processing
           │
           ├── Update status
           ├── Debounce
           └── Store information

Trong AUTOSAR DEM có nhiều status và cơ chế xử lý chi tiết hơn. Khi học ở mức CAN Driver integration, điều quan trọng trước tiên là hiểu rằng DEM theo dõi trạng thái của diagnostic event thay vì chỉ nhận một thông báo lỗi đơn giản.

12. Debouncing là gì?

Trong thực tế, một điều kiện lỗi có thể xuất hiện trong thời gian rất ngắn và sau đó biến mất. Nếu hệ thống coi ngay lần xuất hiện đầu tiên là một fault thực sự, có thể xảy ra false detection.

Vì vậy diagnostic event có thể sử dụng cơ chế debouncing để xác định khi nào một lỗi đủ điều kiện được coi là confirmed fault.

Debouncing có thể dựa trên số lần test, thời gian, counter hoặc cơ chế khác tùy configuration.

13. DEM và Fault Memory

Một chức năng quan trọng của DEM là quản lý thông tin liên quan tới diagnostic event trong fault memory. 

Diagnostic Event
       │
       ▼
      DEM
       │
       ├── Event detected
       ├── Debounce
       ├── Confirmed fault
       │
       ▼
Fault Memory
       │
       ├── Event status
       ├── Diagnostic information
       └── Related data

Việc lưu trữ chính xác dữ liệu nào, khi nào lưu, khi nào clear và cách persistent storage được thực hiện phụ thuộc vào configuration và các module liên quan.

14. DEM và CAN Communication Error

DEM có thể liên quan tới CAN communication diagnostics, nhưng cần phân biệt rõ: 

CAN Controller
      │
      │ Hardware / protocol status
      ▼
   CanDrv
      │
      ▼
   CanIf / CanSM
      │
      │ Communication state / event
      ▼
    DEM
      │
      ▼
Diagnostic information

Ví dụ, một hệ thống có thể monitor việc mất communication với một ECU khác. Nếu message không xuất hiện trong khoảng thời gian yêu cầu, communication monitor có thể report một diagnostic event tới DEM.

Quan trọng: CAN Driver không phải lúc nào cũng trực tiếp gọi DEM cho mọi CAN error. Diagnostic event có thể được phát hiện và report bởi module phù hợp với diagnostic architecture của ECU.

15. Ví dụ: CAN Message Timeout

Giả sử ECU yêu cầu một CAN message phải được nhận ít nhất một lần trong mỗi 100 ms. 

Expected CAN Message
        │
        ▼
Wait 100 ms
        │
        ├── Message received
        │       │
        │       ▼
        │   Test Passed
        │
        └── Message missing
                │
                ▼
          Communication Monitor
                │
                ▼
               DEM
                │
                ▼

Nếu message bị mất chỉ một lần thì hệ thống chưa nhất thiết phải xác nhận ngay một fault. Diagnostic configuration có thể yêu cầu một số điều kiện hoặc số lần failure trước khi event được confirmed.

16. DET và DEM trong CAN Stack

Sơ đồ trên giúp phân biệt hai đường xử lý: DET phục vụ development error reporting, trong khi DEM phục vụ diagnostic event management.

17. Khi nào sử dụng DET?

DET thường hữu ích khi developer muốn phát hiện lỗi trong quá trình phát triển hoặc integration.

Tình huống DET
API được gọi sai thứ tự Có thể report
Module chưa initialized Có thể report
Parameter không hợp lệ Có thể report
Configuration không hợp lệ khi development Có thể liên quan
Vehicle communication timeout Không phải mục tiêu chính

18. Khi nào sử dụng DEM?

DEM phù hợp khi hệ thống cần quản lý một diagnostic event trong quá trình ECU hoạt động.

Tình huống DEM
CAN message timeout Có thể sử dụng
Sensor signal failure Có thể sử dụng
Communication monitoring fault Có thể sử dụng
Runtime diagnostic event Có
Invalid API parameter trong development Không phải mục tiêu chính

19. DET và DEM trong Development vs Runtime

20. DET có chạy trong Production ECU không?

Trong một hệ thống AUTOSAR thực tế, việc DET có được enable và hoạt động như thế nào phụ thuộc vào build, configuration và mục đích của ECU.

Trong development build, DET thường rất hữu ích để phát hiện integration errors. Trong production build, cơ chế development error reporting có thể được giới hạn hoặc disable tùy theo project.

Không nên kết luận: "DET luôn luôn chạy trong production" hoặc "DET luôn luôn bị loại bỏ trong production". Cách cấu hình thực tế phụ thuộc project và implementation.

21. DEM có thay thế DET không?

Không.

DET và DEM giải quyết hai loại vấn đề khác nhau. DEM không phải phiên bản runtime của DET và cũng không phải DET nâng cấp. 

Invalid API usage
       │
       ▼
      DET
       │
       ▼
Development debugging


Runtime diagnostic fault
       │
       ▼
      DEM
       │
       ▼
Diagnostic management

Hãy xét một ECU có CAN communication. Trong quá trình development, developer có thể mắc một lỗi integration; trong runtime, ECU lại có thể phát hiện một communication fault. 

CASE 1: Development Error

Hai trường hợp đều là "error", nhưng bản chất khác nhau: một lỗi là development/integration error, lỗi còn lại là runtime diagnostic event.

26. DET, DEM và CanSM

Một điểm quan trọng khi học CAN stack là phân biệt CanSM với DEM.

Module Responsibility
CanDrv CAN Controller / hardware-level processing
CanIf CAN interface / abstraction
CanSM CAN network state management
DET Development error reporting
DEM Diagnostic event management

Ví dụ khi CAN Controller xảy ra Bus-Off, CanDrv xử lý controller-level event và thông báo lên tầng CAN stack. CanSM có thể quản lý communication state/recovery behavior. Nếu hệ thống cần theo dõi một điều kiện lỗi cho diagnostic purpose, diagnostic event có thể được report tới DEM theo architecture của ECU.

28. Những điều không nên nhầm lẫn

Dễ nhầm Cách hiểu đúng
DET = Diagnostic Error Manager Không. DET là Default Error Tracer.
DEM = Development Error Manager Không. DEM là Diagnostic Event Manager.
DET quản lý DTC Không. DEM mới liên quan tới diagnostic event và DTC management.

29. Interview Perspective

Nếu interviewer hỏi: "What is the difference between DET and DEM?"

Có thể trả lời: 

DET stands for Default Error Tracer.
It is mainly used to report development errors,
such as invalid API usage, invalid parameters,
or calling a BSW module in an invalid state.

DEM stands for Diagnostic Event Manager.
It manages diagnostic events during runtime,
including event status, fault handling and
diagnostic information such as DTC-related data.

Nếu interviewer hỏi: "Is DET used for CAN Bus-Off?" 

DET is not the module responsible for
handling CAN Bus-Off.

Bus-Off is handled by the CAN communication
stack and CAN state management.
If the condition needs to be monitored as
a diagnostic event, it may be reported to DEM
according to the ECU diagnostic architecture.

32. Tóm tắt



DET (Default Error Tracer) dùng để report development errors từ các BSW modules. Những lỗi này thường liên quan tới invalid API usage, invalid parameters hoặc module state không hợp lệ.

DET chủ yếu hỗ trợ development và integration. Nó giúp developer tìm ra lỗi trong cách sử dụng hoặc tích hợp BSW module.

DEM (Diagnostic Event Manager) quản lý các diagnostic events trong quá trình ECU hoạt động. Nó có thể quản lý event status, debouncing, fault information và các thông tin liên quan tới DTC theo diagnostic configuration.

DET và DEM không thay thế cho nhau:

DET → Development Error
DEM → Diagnostic Event

Với CAN:

Invalid CanDrv API usage → DET
CAN communication diagnostic event → DEM

Cần nhớ rằng DET không phải CAN error handler, còn DEM không trực tiếp điều khiển CAN Controller. CAN communication errors vẫn phải được xử lý bởi các module phù hợp như CanDrv, CanIf và CanSM; chỉ khi có diagnostic event phù hợp thì event đó mới đi vào diagnostic path của DEM.
