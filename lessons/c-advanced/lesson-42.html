Bài 42: Error Handling Strategy in C

1. Introduction

Trong quá trình thực thi chương trình C, một Function có thể gặp nhiều tình huống khiến nó không thể hoàn thành công việc như mong đợi. Ví dụ: tham số đầu vào không hợp lệ, dữ liệu nhận được sai định dạng, phần cứng không phản hồi, Buffer không đủ dung lượng hoặc một thao tác ngoại vi thất bại.

Nếu chương trình không có cơ chế phát hiện và xử lý những tình huống này, lỗi có thể lan truyền sang các Module khác, làm sai lệch dữ liệu hoặc khiến toàn bộ hệ thống hoạt động không ổn định.

Trong C, ngôn ngữ không cung cấp cơ chế Exception Handling như C++. Vì vậy, lập trình viên thường phải thiết kế Error Handling thông qua Return Value, Error Code, Status Enumeration, Error Flag hoặc các cơ chế quản lý lỗi riêng.

Đối với Embedded Systems, Error Handling không chỉ là việc thông báo một Function thất bại. Chương trình còn cần xác định mức độ nghiêm trọng, trạng thái hệ thống sau lỗi và cách đưa thiết bị về trạng thái an toàn khi cần thiết.

Mục tiêu bài học:
  • Hiểu vai trò của Error Handling trong C.
  • Phân biệt Return Value, Error Code và Status Enumeration.
  • Biết cách thiết kế Error Handling cho Function và Module.
  • Hiểu Error Propagation và Error Recovery.
  • Phân biệt Error, Fault và Failure ở mức khái niệm.
  • Áp dụng chiến lược xử lý lỗi trong Embedded Software.

2. Core Concepts

2.1. Error Handling là gì?

Error Handling là quá trình phát hiện, thông báo, ghi nhận và xử lý các tình huống bất thường xảy ra trong quá trình thực thi chương trình.

Một quy trình xử lý lỗi cơ bản có thể bao gồm:

  1. Error Detection: phát hiện điều kiện lỗi.
  2. Error Reporting: thông báo lỗi cho thành phần gọi.
  3. Error Handling: lựa chọn hành động phù hợp.
  4. Error Recovery: khôi phục hoạt động nếu có thể.
  5. Error Logging: ghi nhận thông tin phục vụ Debug.

Không phải mọi lỗi đều cần được xử lý giống nhau. Một lỗi do tham số đầu vào không hợp lệ có thể chỉ cần trả về Error Code. Trong khi đó, lỗi nghiêm trọng liên quan đến Hardware hoặc trạng thái an toàn của hệ thống có thể cần kích hoạt cơ chế Fault Handling riêng.

2.2. Return Value

Return Value là cách đơn giản nhất để một Function thông báo kết quả thực thi cho Function gọi nó.

Ví dụ, Function trả về true nếu thao tác thành công và false nếu thao tác thất bại: 

#include <stdbool.h>

bool Sensor_Init(void)
{
    /* Perform initialization */

    return true;
}

int main(void)
{
    if (Sensor_Init() == false)
    {
        /* Handle initialization error */
        return -1;
    }

    return 0;
}

Cách tiếp cận này dễ hiểu và phù hợp với Function chỉ cần thông báo hai trạng thái: Success hoặc Failure.

Tuy nhiên, nếu có nhiều nguyên nhân lỗi khác nhau, kiểu bool không cung cấp đủ thông tin để Function gọi xác định chính xác vấn đề.

2.3. Error Code

Error Code là một giá trị được sử dụng để biểu diễn trạng thái hoặc nguyên nhân khiến một thao tác thất bại.

Ví dụ:

#include <stdint.h>

#define ERROR_NONE             0U
#define ERROR_INVALID_PARAM    1U
#define ERROR_TIMEOUT          2U
#define ERROR_HARDWARE         3U
#define ERROR_BUFFER_FULL      4U

uint8_t Sensor_Read(void)
{
    /* Example error condition */

    return ERROR_TIMEOUT;
}

Function có thể trả về một Error Code để Function gọi biết được nguyên nhân thất bại.

Ưu điểm của phương pháp này là đơn giản, dễ triển khai và có thể sử dụng trong các API có nhiều trạng thái kết quả.

2.4. Status Enumeration

Thay vì sử dụng các con số hoặc Macro rời rạc, có thể định nghĩa một Enumeration để biểu diễn trạng thái của Function. 

typedef enum
{
    STATUS_OK = 0,
    STATUS_ERROR_INVALID_PARAM,
    STATUS_ERROR_TIMEOUT,
    STATUS_ERROR_HARDWARE,
    STATUS_ERROR_BUFFER_FULL
} Status_t;

Khi sử dụng Enumeration, tên trạng thái có ý nghĩa rõ ràng hơn so với các giá trị số nguyên.

Ví dụ:

Status_t Sensor_Init(void)
{
    /* Initialization logic */

    return STATUS_OK;
}

int main(void)
{
    Status_t status;

    status = Sensor_Init();

    if (status != STATUS_OK)
    {
        /* Handle error */
    }

    return 0;
}

Đây là một cách tổ chức Error Handling phổ biến trong Embedded C vì có thể mở rộng nhiều trạng thái mà vẫn giữ được tính dễ đọc của chương trình.

2.5. Error Flag

Error Flag là một biến được sử dụng để ghi nhận trạng thái lỗi của một Module hoặc một thành phần trong hệ thống. 

#include <stdbool.h>

static bool sensorErrorFlag = false;

void Sensor_SetError(void)
{
    sensorErrorFlag = true;
}

bool Sensor_HasError(void)
{
    return sensorErrorFlag;
}

Error Flag có thể hữu ích khi một Module cần ghi nhận trạng thái lỗi để thành phần khác kiểm tra sau đó.

Tuy nhiên, nếu sử dụng Global Error Flag không có quy tắc quản lý, chương trình có thể gặp khó khăn trong việc xác định lỗi xuất phát từ đâu và khi nào trạng thái lỗi được xóa.

2.6. Phân biệt Error, Fault và Failure

Trong lĩnh vực Software và Embedded Systems, các thuật ngữ Error, Fault và Failure có thể được sử dụng trong những ngữ cảnh khác nhau.

Thuật ngữ Ý nghĩa khái quát Ví dụ
Error Trạng thái hoặc kết quả xử lý không đúng mong đợi. Giá trị Sensor được tính toán sai.
Fault Nguyên nhân hoặc điều kiện bất thường có thể dẫn đến lỗi hệ thống. Sensor mất kết nối.
Failure Hệ thống hoặc chức năng không thực hiện được yêu cầu. ECU không thể cung cấp chức năng mong muốn.

Trong thực tế, cách sử dụng các thuật ngữ này có thể khác nhau tùy theo tiêu chuẩn và quy trình của từng dự án. Điều quan trọng là cần thống nhất định nghĩa trong tài liệu kỹ thuật của hệ thống.

3. Detailed Explanation

3.1. Thiết kế Error Handling cho Function

Một Function được thiết kế tốt cần xác định rõ những điều kiện khiến nó thất bại và cách thông báo trạng thái đó cho Function gọi.

Ví dụ, một Function đọc dữ liệu Sensor có thể gặp các trường hợp:

  • Con trỏ đầu ra không hợp lệ.
  • Sensor chưa được khởi tạo.
  • Hardware không phản hồi.
  • Dữ liệu nhận được không hợp lệ.
  • Thao tác đọc thành công.

Có thể biểu diễn những trạng thái này bằng Enumeration: 

typedef enum
{
    SENSOR_OK = 0,
    SENSOR_ERROR_INVALID_PARAM,
    SENSOR_ERROR_NOT_INITIALIZED,
    SENSOR_ERROR_TIMEOUT,
    SENSOR_ERROR_INVALID_DATA
} SensorStatus_t;

Sau đó, Function sử dụng kiểu trả về này để thông báo kết quả: 

#include <stdint.h>
#include <stdbool.h>

typedef enum
{
    SENSOR_OK = 0,
    SENSOR_ERROR_INVALID_PARAM,
    SENSOR_ERROR_NOT_INITIALIZED,
    SENSOR_ERROR_TIMEOUT,
    SENSOR_ERROR_INVALID_DATA
} SensorStatus_t;

static bool sensorInitialized = false;

SensorStatus_t Sensor_Read(uint16_t *value)
{
    if (value == NULL)
    {
        return SENSOR_ERROR_INVALID_PARAM;
    }

    if (sensorInitialized == false)
    {
        return SENSOR_ERROR_NOT_INITIALIZED;
    }

    /*
     * Hardware reading would be performed here.
     */

    *value = 250U;

    return SENSOR_OK;
}

Function kiểm tra các điều kiện cần thiết trước khi thực hiện thao tác. Nếu có lỗi, Function trả về trạng thái tương ứng thay vì tiếp tục xử lý với dữ liệu không hợp lệ.

3.2. Error Propagation

Error Propagation là quá trình truyền thông tin lỗi từ Function cấp thấp lên các Function hoặc Module cấp cao hơn.

Ví dụ, một ứng dụng có thể gọi nhiều tầng Function: 

Application
     |
     v
Sensor_Service
     |
     v
Sensor_Driver
     |
     v
Hardware Interface

Nếu Hardware Interface gặp lỗi, Sensor Driver cần thông báo trạng thái đó cho Sensor Service. Sau đó, Sensor Service tiếp tục truyền trạng thái lên Application.

Ví dụ:

typedef enum
{
    STATUS_OK = 0,
    STATUS_ERROR_TIMEOUT,
    STATUS_ERROR_HARDWARE
} Status_t;

Status_t Hardware_Read(uint16_t *value)
{
    if (value == NULL)
    {
        return STATUS_ERROR_HARDWARE;
    }

    /*
     * Simulate hardware timeout.
     */

    return STATUS_ERROR_TIMEOUT;
}

Status_t Sensor_Read(uint16_t *value)
{
    Status_t status;

    status = Hardware_Read(value);

    if (status != STATUS_OK)
    {
        return status;
    }

    return STATUS_OK;
}

Status_t Application_ReadSensor(void)
{
    uint16_t sensorValue;
    Status_t status;

    status = Sensor_Read(&sensorValue);

    if (status != STATUS_OK)
    {
        return status;
    }

    /* Process sensorValue */

    return STATUS_OK;
}

Trong ví dụ trên, mỗi tầng chịu trách nhiệm truyền trạng thái lỗi lên tầng gọi nó. Nhờ đó, Application có thể biết thao tác đọc Sensor đã thất bại mà không cần truy cập trực tiếp vào chi tiết triển khai của Hardware Interface.

3.3. Không bỏ qua Return Value

Một lỗi phổ biến là gọi Function có thể thất bại nhưng không kiểm tra giá trị trả về.

Ví dụ không nên sử dụng:

void Application_Task(void)
{
    Sensor_Init();

    Sensor_ReadData();
}

Nếu Sensor_Init() thất bại, chương trình vẫn tiếp tục gọi Sensor_ReadData(). Điều này có thể khiến Module hoạt động trong trạng thái chưa được khởi tạo.

Cách xử lý tốt hơn:

void Application_Task(void)
{
    Status_t status;

    status = Sensor_Init();

    if (status != STATUS_OK)
    {
        /* Handle initialization failure */
        return;
    }

    status = Sensor_ReadData();

    if (status != STATUS_OK)
    {
        /* Handle read failure */
        return;
    }
}

Mỗi Function quan trọng cần có quy tắc kiểm tra kết quả trả về. Không nên mặc định rằng mọi thao tác đều thành công.

3.4. Error Recovery

Error Recovery là quá trình đưa chương trình hoặc Module trở lại trạng thái có thể hoạt động sau khi xảy ra lỗi.

Một số chiến lược thường gặp:

  • Retry: thử thực hiện lại thao tác nếu lỗi có khả năng chỉ xảy ra tạm thời.
  • Re-initialization: khởi tạo lại Module nếu trạng thái hiện tại không còn hợp lệ.
  • Fallback: sử dụng một giá trị hoặc chế độ hoạt động dự phòng đã được thiết kế.
  • Safe State: chuyển hệ thống về trạng thái an toàn được xác định trước.
  • Shutdown: dừng chức năng khi không thể tiếp tục hoạt động an toàn.

Không phải lỗi nào cũng nên được Retry. Nếu nguyên nhân lỗi là dữ liệu đầu vào không hợp lệ hoặc cấu hình sai, việc thử lại cùng một thao tác thường không giải quyết được vấn đề.

3.5. Retry Strategy

Retry có thể được sử dụng khi thao tác thất bại do những nguyên nhân tạm thời, chẳng hạn thiết bị chưa phản hồi trong khoảng thời gian mong đợi.

Ví dụ:

#include <stdint.h>
#include <stdbool.h>

#define MAX_RETRY_COUNT 3U

typedef enum
{
    STATUS_OK = 0,
    STATUS_ERROR_TIMEOUT
} Status_t;

Status_t Sensor_ReadWithRetry(uint16_t *value)
{
    Status_t status = STATUS_ERROR_TIMEOUT;

    if (value == NULL)
    {
        return STATUS_ERROR_TIMEOUT;
    }

    for (uint32_t retry = 0U;
         retry < MAX_RETRY_COUNT;
         retry++)
    {
        status = Sensor_Read(value);

        if (status == STATUS_OK)
        {
            return STATUS_OK;
        }
    }

    return status;
}

Ví dụ trên minh họa giới hạn số lần thử lại. Trong ứng dụng thực tế, cần xác định rõ loại lỗi nào được phép Retry, thời gian chờ giữa các lần thử và tổng thời gian tối đa dành cho thao tác.

Lưu ý: Retry không phù hợp với mọi Function. Nếu Function thực hiện một thao tác không thể lặp lại an toàn, chẳng hạn gửi một lệnh làm thay đổi trạng thái thiết bị, việc Retry có thể tạo ra tác động ngoài dự kiến.

3.6. Safe State và Fail-safe Behavior

Trong Embedded Systems, một số lỗi có thể ảnh hưởng đến trạng thái hoạt động của thiết bị. Khi đó, hệ thống cần có một hành vi được xác định trước để giảm thiểu rủi ro.

Ví dụ, nếu một chức năng điều khiển không nhận được dữ liệu Sensor hợp lệ, hệ thống có thể:

  • Đánh dấu dữ liệu Sensor là không hợp lệ.
  • Không sử dụng giá trị mới để cập nhật trạng thái điều khiển.
  • Chuyển sang chế độ hoạt động dự phòng đã được thiết kế.
  • Thông báo lỗi cho thành phần quản lý hệ thống.

Safe State cần được xác định dựa trên yêu cầu của từng hệ thống. Không có một giá trị mặc định chung phù hợp cho mọi thiết bị.

3.7. Error Logging

Error Logging là quá trình lưu lại thông tin về những lỗi xảy ra trong quá trình vận hành.

Một bản ghi lỗi có thể bao gồm:

  • Error Code.
  • Module phát sinh lỗi.
  • Thời điểm xảy ra lỗi.
  • Trạng thái hệ thống tại thời điểm lỗi.
  • Số lần lỗi xuất hiện.

Ví dụ về một cấu trúc lưu thông tin lỗi: 

#include <stdint.h>

typedef struct
{
    uint32_t errorCode;
    uint32_t timestamp;
    uint16_t moduleId;
    uint16_t occurrenceCount;
} ErrorLog_t;

Trong Embedded Systems, Error Log có thể được lưu trong RAM, Flash hoặc một vùng nhớ được thiết kế riêng. Việc lựa chọn vị trí lưu cần xem xét dung lượng bộ nhớ, tuổi thọ Flash và yêu cầu lưu trữ sau khi mất nguồn.

3.8. Error Handling trong Interrupt Service Routine

Khi lỗi xảy ra trong ISR, việc xử lý cần được thiết kế cẩn thận vì ISR thường có yêu cầu về thời gian thực thi và tính xác định.

Thay vì thực hiện những thao tác phức tạp trong ISR, có thể ghi nhận trạng thái lỗi hoặc thiết lập Event Flag để Main Loop hoặc Task xử lý sau. 

#include <stdint.h>
#include <stdbool.h>

static volatile bool uartErrorPending = false;

void UART_Error_IRQHandler(void)
{
    /*
     * Clear or acknowledge the hardware interrupt
     * according to the MCU specification.
     */

    uartErrorPending = true;
}

void Application_Task(void)
{
    if (uartErrorPending == true)
    {
        uartErrorPending = false;

        /* Handle UART error outside ISR */
    }
}

Ví dụ này chỉ minh họa việc chuyển thông tin lỗi từ ISR sang Main Loop. Trong hệ thống thực tế, cần sử dụng cơ chế đồng bộ phù hợp với MCU, Compiler và RTOS nếu có.

4. C Code Examples

4.1. Xây dựng Error Code cho một Module

Một Module có thể định nghĩa các trạng thái riêng để biểu diễn những lỗi liên quan đến chức năng của nó. 

#include <stdint.h>
#include <stdbool.h>

typedef enum
{
    MOTOR_STATUS_OK = 0,
    MOTOR_ERROR_INVALID_PARAM,
    MOTOR_ERROR_NOT_INITIALIZED,
    MOTOR_ERROR_OVERCURRENT,
    MOTOR_ERROR_TIMEOUT
} MotorStatus_t;

static bool motorInitialized = false;

MotorStatus_t Motor_Init(void)
{
    motorInitialized = true;

    return MOTOR_STATUS_OK;
}

MotorStatus_t Motor_SetSpeed(uint16_t speed)
{
    if (motorInitialized == false)
    {
        return MOTOR_ERROR_NOT_INITIALIZED;
    }

    if (speed > 1000U)
    {
        return MOTOR_ERROR_INVALID_PARAM;
    }

    /*
     * Apply speed configuration.
     */

    return MOTOR_STATUS_OK;
}

int main(void)
{
    MotorStatus_t status;

    status = Motor_Init();

    if (status != MOTOR_STATUS_OK)
    {
        return -1;
    }

    status = Motor_SetSpeed(500U);

    if (status != MOTOR_STATUS_OK)
    {
        /* Handle motor configuration error */
        return -1;
    }

    return 0;
}

Ví dụ này cho thấy cách một Module quản lý trạng thái khởi tạo và trả về Error Code khi một thao tác không đáp ứng điều kiện cần thiết.

4.2. Xây dựng Error Handler tập trung

Trong một ứng dụng có nhiều Module, có thể xây dựng một thành phần Error Handler để tiếp nhận và quản lý các thông tin lỗi. 

#include <stdint.h>

typedef enum
{
    ERROR_MODULE_SENSOR = 1,
    ERROR_MODULE_UART,
    ERROR_MODULE_CAN,
    ERROR_MODULE_MOTOR
} ErrorModule_t;

typedef enum
{
    ERROR_LEVEL_INFO = 0,
    ERROR_LEVEL_WARNING,
    ERROR_LEVEL_CRITICAL
} ErrorLevel_t;

typedef struct
{
    ErrorModule_t module;
    ErrorLevel_t level;
    uint32_t errorCode;
} SystemError_t;

static SystemError_t lastError;

void ErrorHandler_Report(ErrorModule_t module,
                         ErrorLevel_t level,
                         uint32_t errorCode)
{
    lastError.module = module;
    lastError.level = level;
    lastError.errorCode = errorCode;
}

SystemError_t ErrorHandler_GetLastError(void)
{
    return lastError;
}

Error Handler tập trung giúp chương trình có một nơi thống nhất để tiếp nhận và truy xuất thông tin lỗi.

Tuy nhiên, ví dụ trên chỉ lưu lỗi gần nhất. Nếu nhiều Task hoặc ISR cùng gọi Error Handler, cần bổ sung cơ chế đồng bộ và quản lý nhiều bản ghi phù hợp.

4.3. Phân biệt lỗi có thể khôi phục và lỗi nghiêm trọng

Không phải mọi lỗi đều cần dẫn đến việc dừng toàn bộ hệ thống. Có thể phân loại lỗi theo mức độ ảnh hưởng để lựa chọn hành động phù hợp. 

typedef enum
{
    ERROR_SEVERITY_INFO = 0,
    ERROR_SEVERITY_WARNING,
    ERROR_SEVERITY_CRITICAL
} ErrorSeverity_t;

void System_HandleError(ErrorSeverity_t severity)
{
    switch (severity)
    {
        case ERROR_SEVERITY_INFO:
            /* Record information */
            break;

        case ERROR_SEVERITY_WARNING:
            /* Notify and continue if safe */
            break;

        case ERROR_SEVERITY_CRITICAL:
            /* Execute defined safe-state strategy */
            break;

        default:
            /* Handle invalid severity */
            break;
    }
}

Cách phân loại này giúp tách biệt những lỗi chỉ cần ghi nhận với những lỗi cần hành động ngay. Việc lựa chọn hành động cụ thể phải dựa trên yêu cầu và phân tích an toàn của hệ thống.

5. Embedded Applications

5.1. Error Handling trong Sensor Driver

Sensor Driver có thể gặp lỗi khi khởi tạo, đọc dữ liệu hoặc giao tiếp với Sensor.

Một số lỗi thường gặp:

  • Sensor không phản hồi.
  • Giao tiếp I2C hoặc SPI thất bại.
  • Timeout khi chờ dữ liệu.
  • Dữ liệu nhận được không đúng định dạng.
  • Giá trị Sensor nằm ngoài phạm vi được hỗ trợ.

Driver cần trả về trạng thái rõ ràng để Application quyết định tiếp tục xử lý, thử lại hoặc chuyển sang chế độ dự phòng.

5.2. Error Handling trong UART Driver

UART Driver có thể gặp các lỗi như:

  • Receive Buffer đầy.
  • UART Overrun.
  • Framing Error.
  • Parity Error.
  • Timeout khi nhận dữ liệu.

Khi phát hiện lỗi, Driver cần ghi nhận trạng thái và cung cấp thông tin cho thành phần quản lý phía trên. Một số lỗi có thể được xử lý bằng cách xóa trạng thái Hardware Error và tiếp tục nhận dữ liệu theo quy trình của MCU.

5.3. Error Handling trong CAN Communication

Trong CAN Communication, lỗi có thể xuất hiện ở nhiều tầng khác nhau, từ Controller đến Communication Stack.

Ví dụ:

  • CAN Controller báo lỗi truyền hoặc nhận.
  • Message không được nhận đúng thời gian.
  • Communication Timeout.
  • Message có định dạng hoặc nội dung không hợp lệ.
  • Communication Module chưa được khởi tạo.

CAN Driver có thể thông báo trạng thái cho CAN Interface, trong khi Application hoặc Diagnostic Module thực hiện xử lý ở mức cao hơn.

5.4. Error Handling trong AUTOSAR

Trong AUTOSAR Classic Platform, việc xử lý lỗi có thể được phân chia giữa nhiều thành phần tùy theo loại lỗi và yêu cầu của hệ thống.

  • DET (Default Error Tracer): hỗ trợ ghi nhận các lỗi phát triển và lỗi sử dụng API của BSW Module.
  • DEM (Diagnostic Event Manager): quản lý Diagnostic Event và trạng thái lỗi liên quan đến chẩn đoán.
  • Application Software: xử lý trạng thái trả về từ các Service hoặc SWC theo yêu cầu chức năng.
  • ECU State Management: tham gia quản lý trạng thái hoạt động của ECU và các yêu cầu chuyển trạng thái.

DET và DEM có mục đích khác nhau. Không nên xem mọi lỗi trong chương trình đều cần được chuyển trực tiếp thành Diagnostic Event.

5.5. Error Handling trong Automotive Embedded Software

Trong Automotive Embedded Software, Error Handling cần được thiết kế dựa trên yêu cầu chức năng và mức độ ảnh hưởng của lỗi.

Ví dụ, nếu một ECU không nhận được tín hiệu cần thiết từ một ECU khác trong khoảng thời gian quy định, hệ thống có thể:

  • Đánh dấu tín hiệu là Timeout hoặc Invalid.
  • Không tiếp tục sử dụng dữ liệu cũ như dữ liệu mới hợp lệ.
  • Thông báo trạng thái lỗi cho thành phần liên quan.
  • Thực hiện hành vi dự phòng theo System Requirement.
  • Ghi nhận Diagnostic Event nếu đáp ứng điều kiện chẩn đoán.

Hành vi cụ thể cần được định nghĩa trong yêu cầu hệ thống, không nên tự ý lựa chọn một giá trị thay thế mà chưa có cơ sở thiết kế.

6. Common Mistakes

6.1. Không kiểm tra giá trị trả về

Gọi Function có thể thất bại nhưng bỏ qua Return Value sẽ khiến chương trình không phát hiện được lỗi.

6.2. Sử dụng một Error Code cho mọi loại lỗi

Nếu tất cả lỗi đều trả về cùng một giá trị, Function gọi sẽ khó xác định nguyên nhân và lựa chọn cách xử lý phù hợp.

6.3. Tiếp tục sử dụng dữ liệu không hợp lệ

Sau khi một thao tác đọc dữ liệu thất bại, chương trình không nên mặc định rằng biến đầu ra đã chứa dữ liệu hợp lệ.

Cần xác định rõ Function có thay đổi Output Parameter khi thất bại hay không và thông báo trạng thái tương ứng.

6.4. Sử dụng Global Error Flag không có quy tắc

Một Global Error Flag có thể bị nhiều Module thay đổi, khiến việc xác định nguồn gốc lỗi và trạng thái hiện tại trở nên khó khăn.

6.5. Retry vô hạn

Nếu một thao tác luôn thất bại nhưng chương trình liên tục Retry mà không có giới hạn, hệ thống có thể bị mắc kẹt và không thực hiện được những công việc khác.

6.6. Xử lý quá nhiều công việc trong ISR

Thực hiện Logging phức tạp, chờ đợi lâu hoặc khởi tạo lại nhiều Module ngay trong ISR có thể làm tăng thời gian Interrupt Latency và ảnh hưởng đến các hoạt động thời gian thực.

6.7. Không phân biệt Error Reporting và Error Recovery

Ghi nhận lỗi không đồng nghĩa với việc hệ thống đã khôi phục. Chương trình cần xác định riêng cách thông báo lỗi và cách đưa Module về trạng thái hoạt động phù hợp.

6.8. Không xác định trạng thái hệ thống sau khi lỗi

Sau khi Function thất bại, cần xác định dữ liệu đầu ra, trạng thái Module và các tài nguyên đang sử dụng có còn hợp lệ hay không.

7. Best Practices

7.1. Thiết kế Error Code thống nhất

Mỗi Module nên có quy ước trạng thái rõ ràng, bao gồm Success và các loại lỗi có thể xảy ra.

7.2. Quy định rõ Function Contract

Tài liệu của Function nên mô tả:

  • Điều kiện đầu vào hợp lệ.
  • Giá trị trả về khi thành công.
  • Các Error Code có thể xuất hiện.
  • Output Parameter có thay đổi khi thất bại hay không.
  • Trạng thái của Module sau khi Function thất bại.

7.3. Không bỏ qua lỗi từ Function cấp thấp

Khi một Function gọi Function khác, cần kiểm tra trạng thái trả về và quyết định tiếp tục, truyền lỗi lên trên hoặc thực hiện Recovery.

7.4. Giới hạn số lần Retry

Retry cần có giới hạn về số lần thử, thời gian chờ và tổng thời gian thực hiện để tránh làm ảnh hưởng đến các hoạt động khác của hệ thống.

7.5. Xác định Safe State theo yêu cầu

Đối với các chức năng quan trọng, cần xác định trước hành vi của hệ thống khi xảy ra lỗi. Không nên tự ý sử dụng một giá trị mặc định nếu chưa được quy định trong thiết kế.

7.6. Tách biệt Error Logging và Error Handling

Error Logging phục vụ ghi nhận và phân tích lỗi, trong khi Error Handling quyết định chương trình cần thực hiện hành động gì. Hai thành phần này có thể phối hợp nhưng không nên phụ thuộc hoàn toàn vào nhau.

7.7. Tránh sử dụng Dynamic Memory trong Error Path nếu không cần thiết

Trong Embedded Systems, Error Handling nên có hành vi dễ dự đoán. Việc cấp phát bộ nhớ động khi đang xử lý lỗi có thể tạo thêm rủi ro nếu Heap đã cạn hoặc bị phân mảnh.

Có thể ưu tiên sử dụng Error Buffer có kích thước cố định hoặc cơ chế Logging được thiết kế trước.

7.8. Kiểm thử các tình huống lỗi

Không chỉ kiểm thử trường hợp Function hoạt động thành công. Cần kiểm thử cả những tình huống như:

  • Tham số đầu vào không hợp lệ.
  • Hardware không phản hồi.
  • Communication Timeout.
  • Buffer đầy.
  • Module chưa được khởi tạo.
  • Function cấp thấp trả về Error Code.
  • Retry vượt quá giới hạn.
  • Recovery không thành công.

7.9. Sử dụng Static Analysis và Code Review

Static Analysis và Code Review có thể giúp phát hiện:

  • Function trả về lỗi nhưng kết quả không được kiểm tra.
  • Nhánh Error Handling bị thiếu.
  • Output Parameter được sử dụng sau khi thao tác thất bại.
  • Retry không có giới hạn.
  • Global Error State không được quản lý rõ ràng.

8. Summary

Error Handling là một phần quan trọng trong việc xây dựng phần mềm C đáng tin cậy. Một chương trình không chỉ cần xử lý trường hợp thành công mà còn phải có khả năng phát hiện, thông báo và xử lý các tình huống bất thường.

Những kiến thức trọng tâm cần ghi nhớ:

  • Error Handling bao gồm phát hiện, thông báo, xử lý, khôi phục và ghi nhận lỗi.
  • Return Value phù hợp với những Function có ít trạng thái kết quả.
  • Error Code và Status Enumeration giúp biểu diễn nhiều nguyên nhân lỗi khác nhau.
  • Error Propagation cho phép truyền thông tin lỗi giữa các tầng Function và Module.
  • Error Recovery có thể sử dụng Retry, Re-initialization, Fallback hoặc Safe State tùy theo yêu cầu.
  • Error Logging giúp lưu lại thông tin phục vụ Debug và Fault Diagnosis.
  • ISR cần xử lý lỗi theo cách phù hợp với yêu cầu thời gian thực.
  • Trong AUTOSAR, DET và DEM có vai trò khác nhau trong việc ghi nhận lỗi phát triển và quản lý Diagnostic Event.
Key Takeaway: Một Function đáng tin cậy không chỉ thực hiện đúng công việc khi mọi thứ thuận lợi mà còn phải thông báo rõ ràng khi không thể hoàn thành công việc. Hãy thiết kế Error Handling ngay từ đầu, kiểm tra Return Value, truyền lỗi đúng cách và xác định hành vi của hệ thống khi xảy ra lỗi.
