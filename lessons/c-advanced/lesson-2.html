Bài 2: C Compilation Process & Embedded Toolchain

Trước khi một chương trình C có thể được thực thi trên máy tính hoặc vi điều khiển, mã nguồn cần trải qua một quy trình xử lý để chuyển đổi từ các câu lệnh mà lập trình viên viết thành mã máy mà CPU có thể thực thi. Quy trình này được gọi là C Compilation Process.

Trong quá trình phát triển Embedded Software, việc biên dịch không chỉ đơn giản là chuyển đổi một file .c thành một chương trình thực thi. Hệ thống thường cần nhiều công cụ phối hợp với nhau như Preprocessor, Compiler, Assembler, Linker và các công cụ hỗ trợ tạo, kiểm tra và nạp Firmware.

Tập hợp các công cụ này được gọi là Embedded Toolchain. Đây là một thành phần quan trọng trong môi trường phát triển Firmware, giúp lập trình viên xây dựng chương trình phù hợp với kiến trúc của vi điều khiển mục tiêu.

1. C Compilation Process là gì?

C Compilation Process là quy trình chuyển đổi mã nguồn C thành các dạng mã trung gian và cuối cùng là chương trình có thể thực thi. Quy trình này thường được chia thành bốn giai đoạn chính:

  1. Preprocessing: xử lý các chỉ thị tiền xử lý như #include và #define.
  2. Compilation: phân tích và chuyển đổi mã nguồn C thành mã Assembly.
  3. Assembly: chuyển mã Assembly thành mã máy trong Object File.
  4. Linking: kết hợp các Object File và thư viện để tạo chương trình hoàn chỉnh.

Mỗi giai đoạn có một nhiệm vụ riêng và tạo ra một loại dữ liệu đầu ra khác nhau. Các giai đoạn này phối hợp với nhau để tạo nên một chương trình hoàn chỉnh.

Sơ đồ trên mô tả luồng xử lý phổ biến của một chương trình C. Trong thực tế, các công cụ như GCC thường tự động thực hiện và kết hợp các giai đoạn này khi lập trình viên chạy một lệnh biên dịch duy nhất.

Lưu ý: Preprocessor, Compiler, Assembler và Linker là các thành phần xử lý khác nhau. Tuy nhiên, khi sử dụng một Compiler Driver như GCC, lập trình viên thường không cần gọi riêng từng công cụ. GCC sẽ điều phối các thành phần phù hợp dựa trên tham số được truyền vào.

2. Host Compiler và Cross Compiler

Trước khi tìm hiểu chi tiết từng giai đoạn biên dịch, cần phân biệt hai khái niệm quan trọng trong môi trường phát triển phần mềm: Native Compiler và Cross Compiler.

2.1. Native Compiler

Native Compiler là Compiler chạy trên một hệ thống và tạo ra chương trình dành cho cùng kiến trúc hoặc môi trường thực thi của hệ thống đó.

Ví dụ, khi lập trình C trên một máy tính Windows hoặc Linux sử dụng GCC, Compiler có thể tạo ra chương trình thực thi cho chính hệ điều hành và kiến trúc máy tính đang sử dụng. 

gcc main.c -o application

Trong ví dụ trên, GCC sẽ biên dịch file main.c và tạo chương trình application dành cho môi trường máy tính hiện tại.

2.2. Cross Compiler

Cross Compiler là Compiler chạy trên một hệ thống nhưng tạo ra chương trình dành cho một hệ thống mục tiêu khác.

Trong Embedded Development, lập trình viên thường viết code trên máy tính cá nhân nhưng chương trình cần được thực thi trên một vi điều khiển có kiến trúc CPU khác. Vì vậy, cần sử dụng Cross Compiler để tạo mã máy phù hợp với vi điều khiển đó.

Tiêu chí Native Compiler Cross Compiler
Compiler chạy trên Host Machine Host Machine
Kiến trúc đích Thường cùng kiến trúc với Host Kiến trúc khác với Host hoặc môi trường thực thi khác
Mục đích Tạo ứng dụng chạy trên máy tính hiện tại. Tạo chương trình cho MCU hoặc Target Platform.
Ví dụ GCC trên Linux tạo chương trình Linux x86-64. ARM GCC tạo Firmware cho vi điều khiển ARM.

2.3. Host Machine và Target Machine

Trong quá trình Cross Compilation, có hai hệ thống cần phân biệt:

  • Host Machine: máy tính được sử dụng để viết mã nguồn, chạy Compiler và thực hiện các công việc build chương trình.
  • Target Machine: hệ thống mà chương trình sau khi biên dịch sẽ được thực thi, chẳng hạn như một vi điều khiển STM32.

Ví dụ, một lập trình viên sử dụng máy tính Windows chạy bộ công cụ ARM GCC để biên dịch chương trình C thành mã máy dành cho vi điều khiển ARM Cortex-M. Trong trường hợp này, máy tính là Host Machine và vi điều khiển là Target Machine.

Cross Compiler không có nghĩa là Compiler được chạy trên vi điều khiển. Compiler thường chạy trên máy tính phát triển và tạo ra chương trình dành cho kiến trúc phần cứng mục tiêu.

3. Giai đoạn 1: Preprocessing

Preprocessing là giai đoạn đầu tiên của quá trình biên dịch C. Nhiệm vụ của Preprocessor là xử lý các chỉ thị tiền xử lý (Preprocessor Directives) trước khi mã nguồn được đưa vào Compiler.

Những chỉ thị thường gặp bao gồm:

Directive Chức năng
#include Đưa nội dung của Header File vào vị trí chỉ thị.
#define Định nghĩa Macro hoặc Symbol.
#undef Hủy định nghĩa một Macro.
#ifdef Kiểm tra một Macro đã được định nghĩa hay chưa.
#ifndef Kiểm tra một Macro chưa được định nghĩa.
#if / #else / #elif Xử lý biên dịch có điều kiện.

3.1. Xử lý Header File

Khi sử dụng chỉ thị #include, Preprocessor sẽ tìm và đưa nội dung của Header File vào chương trình tại vị trí tương ứng.

Ví dụ, chương trình ban đầu có nội dung:

#include <stdio.h>

#define DEVICE_NAME "Embedded Device"

int main(void)
{
    printf("Hello %s\n", DEVICE_NAME);

    return 0;
}

Trong quá trình Preprocessing, nội dung Header File stdio.h được đưa vào mã nguồn sau khi Preprocessor tìm thấy file phù hợp. Macro DEVICE_NAME cũng được thay thế bằng giá trị đã định nghĩa.

Vì vậy, mã nguồn sau Preprocessing không còn giữ nguyên toàn bộ các chỉ thị như #include và định nghĩa Macro ban đầu.

3.2. Output của Preprocessing

Kết quả của giai đoạn này thường được lưu dưới dạng file có phần mở rộng .i, chứa mã nguồn C sau khi đã xử lý các chỉ thị tiền xử lý.

Sử dụng GCC để thực hiện riêng bước Preprocessing:

gcc -E main.c -o main.i

Trong đó:

  • gcc: gọi GNU Compiler Collection.
  • -E: chỉ thực hiện Preprocessing.
  • main.c: file mã nguồn ban đầu.
  • -o main.i: chỉ định tên file đầu ra.

File main.i có thể được mở để kiểm tra kết quả sau khi xử lý #include, Macro và Conditional Compilation.

Khi chương trình có nhiều Header File và Macro, file sau Preprocessing có thể chứa lượng mã nguồn lớn hơn rất nhiều so với file C ban đầu. Đây là điều bình thường vì nội dung các Header File đã được đưa vào quá trình xử lý.

4. Giai đoạn 2: Compilation

Sau khi Preprocessing hoàn tất, mã nguồn được chuyển đến Compiler để thực hiện quá trình phân tích và chuyển đổi.

Compilation là giai đoạn Compiler phân tích mã nguồn C, kiểm tra các quy tắc của ngôn ngữ và chuyển chương trình thành biểu diễn trung gian, sau đó tạo mã Assembly phù hợp với kiến trúc CPU mục tiêu.

4.1. Các công việc chính của Compiler

Trong quá trình Compilation, Compiler thực hiện nhiều công việc khác nhau:

  • Lexical Analysis: phân tích mã nguồn thành các Token như Keyword, Identifier, Operator và Literal.
  • Syntax Analysis: kiểm tra cú pháp và cấu trúc của chương trình theo quy tắc ngôn ngữ C.
  • Semantic Analysis: kiểm tra ý nghĩa của các câu lệnh, kiểu dữ liệu và cách sử dụng các Identifier.
  • Intermediate Representation: chuyển chương trình thành dạng biểu diễn trung gian để Compiler xử lý.
  • Code Generation: tạo mã Assembly tương ứng với kiến trúc CPU mục tiêu.

Ngoài ra, Compiler có thể thực hiện những kỹ thuật tối ưu mã nguồn tùy thuộc vào các tùy chọn biên dịch được thiết lập.

4.2. Ví dụ chuyển đổi C sang Assembly

Xét chương trình C đơn giản sau: 

int add_numbers(int a, int b)
{
    return a + b;
}

Compiler sẽ phân tích hàm trên và tạo ra các lệnh Assembly tương ứng với kiến trúc CPU mục tiêu.

Ví dụ minh họa dưới đây sử dụng cú pháp Assembly theo kiến trúc ARM. Mã thực tế có thể khác nhau tùy theo kiến trúc ARM cụ thể, Compiler, ABI và các tùy chọn Optimization. 

add_numbers:
    ADD  r0, r0, r1
    BX   lr

Trong ví dụ minh họa này:

  • ADD: thực hiện phép cộng hai giá trị.
  • r0, r1: các thanh ghi CPU dùng để chứa dữ liệu và tham số theo quy ước gọi hàm.
  • BX lr: quay trở về vị trí gọi hàm thông qua địa chỉ lưu trong Link Register.
Assembly ở trên chỉ mang tính minh họa cho một trường hợp đơn giản. Không nên giả định rằng mọi Compiler hoặc mọi kiến trúc ARM đều sinh ra chính xác những lệnh này. Mục đích của ví dụ là cho thấy mã C được chuyển thành các lệnh mà CPU mục tiêu có thể hiểu và thực thi.

4.3. Output của Compilation

Một trong những kết quả thường gặp của giai đoạn Compilation là file Assembly có phần mở rộng .s.

Sử dụng GCC:

gcc -S main.c -o main.s

Trong đó:

  • -S: thực hiện Preprocessing và Compilation, sau đó dừng ở mã Assembly.
  • main.s: file chứa Assembly Code.

File Assembly có thể được mở để quan sát các lệnh CPU do Compiler tạo ra, từ đó giúp lập trình viên hiểu rõ hơn cách chương trình C được chuyển đổi thành những thao tác ở mức thấp.

5. Giai đoạn 3: Assembly

Sau khi Compiler tạo ra mã Assembly, chương trình tiếp tục được chuyển đến Assembler.

Assembler là công cụ chuyển đổi Assembly Code thành mã máy. Kết quả thường được lưu trong một file có định dạng Object File, phổ biến là file .o trên các hệ thống sử dụng GCC.

5.1. Assembly Code và Machine Code

Assembly sử dụng các ký hiệu và câu lệnh dễ đọc hơn so với mã máy. Trong khi đó, Machine Code là biểu diễn nhị phân của các lệnh mà CPU có thể thực thi.

Tiêu chí Assembly Code Machine Code
Cách biểu diễn Các Mnemonic và Operand. Các bit nhị phân hoặc biểu diễn Hexadecimal.
Khả năng đọc Tương đối dễ đọc đối với lập trình viên. Khó đọc trực tiếp.
Thực thi trực tiếp CPU không thực thi trực tiếp mã Assembly dạng văn bản. CPU thực thi các lệnh máy phù hợp với kiến trúc của nó.
Công cụ xử lý Assembler chuyển đổi sang mã máy. Được lưu trong Object File hoặc chương trình thực thi.

5.2. Object File là gì?

Object File là file chứa mã máy đã được Assembler tạo ra từ một đơn vị mã nguồn sau khi biên dịch.

Một Object File có thể chứa:

  • Machine Code của các Function.
  • Các vùng dữ liệu được tạo từ mã nguồn.
  • Symbol Table chứa thông tin về các Symbol.
  • Relocation Information phục vụ quá trình Linking.
  • Thông tin Debug nếu được tạo trong quá trình biên dịch.

Tuy nhiên, Object File chưa nhất thiết là một chương trình hoàn chỉnh có thể thực thi. Những tham chiếu đến Function hoặc Symbol nằm trong các Object File khác thường cần được giải quyết trong giai đoạn Linking.

5.3. Thực hiện Assembly bằng GCC

gcc -c main.s -o main.o

Trong đó:

  • -c: biên dịch đến Object File và không thực hiện Linking.
  • main.s: file Assembly đầu vào.
  • main.o: Object File đầu ra.

Ngoài ra, có thể sử dụng GCC để thực hiện nhiều giai đoạn liên tiếp mà không cần tạo thủ công file Assembly: 

gcc -c main.c -o main.o

Lệnh trên tự động thực hiện Preprocessing, Compilation và Assembly, sau đó tạo ra main.o.

6. Giai đoạn 4: Linking

Sau khi các file nguồn được biên dịch thành những Object File, chúng cần được kết hợp lại thành một chương trình hoàn chỉnh. Quá trình này được gọi là Linking.

Linker là công cụ chịu trách nhiệm kết hợp Object File, thư viện và các thành phần cần thiết để tạo ra chương trình đầu ra. Trong Embedded Systems, đây là một giai đoạn rất quan trọng vì chương trình phải được tổ chức phù hợp với bộ nhớ và kiến trúc của vi điều khiển mục tiêu.

6.1. Vì sao cần Linking?

Trong các dự án C, chương trình thường được chia thành nhiều Source File để tổ chức chức năng thành từng Module riêng biệt. Mỗi Source File có thể được biên dịch độc lập thành một Object File.

Ví dụ, một chương trình có cấu trúc như sau: 

project/
|
|-- main.c
|-- math_utils.c
|-- math_utils.h
|
|-- main.o
|-- math_utils.o

File main.c có thể gọi một Function được định nghĩa trong math_utils.c. Sau khi biên dịch riêng từng file, chương trình cần được Linking để kết hợp các thành phần này.

6.2. Symbol Resolution

Một nhiệm vụ quan trọng của Linker là tìm và liên kết các Symbol được tham chiếu giữa các Object File.

Ví dụ, trong main.c, lập trình viên gọi Function add_numbers(), nhưng phần triển khai Function lại nằm trong math_utils.c.

File math_utils.h:

#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int add_numbers(int a, int b);

#endif

File math_utils.c:

#include "math_utils.h"

int add_numbers(int a, int b)
{
    return a + b;
}

File main.c:

#include "math_utils.h"

int main(void)
{
    int result = add_numbers(10, 20);

    return 0;
}

Khi biên dịch riêng từng file, main.o sẽ có thông tin tham chiếu đến Symbol add_numbers. Trong khi đó, math_utils.o chứa phần triển khai thực tế của Function này.

Linker sẽ tìm và liên kết các Symbol tương ứng để tạo thành chương trình hoàn chỉnh.

6.3. Address Resolution và Relocation

Bên cạnh việc tìm Symbol, Linker còn phải xử lý địa chỉ của các thành phần trong chương trình.

Một Object File có thể chưa biết chính xác vị trí cuối cùng của Function hoặc biến trong chương trình hoàn chỉnh. Linker sử dụng các thông tin Relocation để điều chỉnh những tham chiếu địa chỉ sau khi xác định vị trí của các thành phần.

Trong Embedded Systems, việc bố trí các vùng nhớ còn phụ thuộc vào cấu hình bộ nhớ của vi điều khiển và các thông tin được cung cấp cho Linker. Nội dung về Linker Script, Memory Map và cách phân bố các Section sẽ được trình bày chi tiết tại Bài 9.

6.4. Thực hiện Linking bằng GCC

Sau khi có hai Object File, có thể sử dụng GCC để kết hợp chúng: 

gcc main.o math_utils.o -o application

Trong đó:

  • main.o: Object File chứa chương trình chính.
  • math_utils.o: Object File chứa Function hỗ trợ.
  • -o application: chỉ định tên chương trình đầu ra.

Với chương trình chạy trên máy tính, kết quả thường là một Executable File. Với chương trình Embedded, Linker sẽ tạo một file phù hợp với kiến trúc và môi trường thực thi của Target MCU.

Trong các dự án Embedded thực tế, quá trình Linking thường còn sử dụng Startup Code, System Initialization, Library và Linker Script. Lệnh Linking sẽ phụ thuộc vào MCU và bộ công cụ được sử dụng.

7. Các loại file được tạo ra trong quá trình biên dịch

Trong quá trình phát triển chương trình C, lập trình viên sẽ thường xuyên làm việc với nhiều loại file khác nhau. Mỗi loại file có mục đích và vai trò riêng.

File Mô tả
.c Source File chứa mã nguồn C.
.h Header File chứa khai báo Function, Macro, kiểu dữ liệu và các khai báo dùng chung.
.i Preprocessed File, chứa mã nguồn sau khi xử lý Preprocessor.
.s Assembly File chứa mã Assembly do Compiler tạo ra.
.o / .obj Object File chứa mã máy và thông tin phục vụ Linking.
.a / .lib Static Library, chứa các Object File được đóng gói để tái sử dụng.
.elf Executable and Linkable Format, thường chứa chương trình đã liên kết cùng các thông tin Symbol và Debug tùy cấu hình.
.hex Intel HEX File, biểu diễn dữ liệu dưới dạng bản ghi văn bản Hexadecimal kèm thông tin địa chỉ.
.bin Binary File, chứa dữ liệu nhị phân thô của Image được tạo ra.
.map Map File, cung cấp thông tin về vị trí các Section, Symbol và mức sử dụng bộ nhớ sau Linking.

7.1. Phân biệt ELF, HEX và BIN

Trong Embedded Development, ba định dạng file thường gặp là ELF, HEX và BIN. Mặc dù chúng có thể chứa dữ liệu liên quan đến cùng một chương trình Firmware, nhưng mục đích sử dụng không hoàn toàn giống nhau.

ELF File

ELF (Executable and Linkable Format) là định dạng file được sử dụng rộng rãi trong các hệ thống Linux và Embedded.

Một file ELF sau khi Linking có thể chứa:

  • Machine Code và các vùng dữ liệu của chương trình.
  • Thông tin về các Section.
  • Symbol Table nếu được giữ lại.
  • Thông tin Debug nếu được tạo trong quá trình Build.
  • Thông tin cần thiết cho Loader hoặc Debugger.

ELF thường được sử dụng để Debug, phân tích chương trình và làm đầu vào cho các công cụ chuyển đổi Firmware.

HEX File

Intel HEX là định dạng file biểu diễn dữ liệu nhị phân dưới dạng các dòng ký tự Hexadecimal. Các bản ghi thường chứa thông tin về địa chỉ, dữ liệu và Checksum.

Định dạng này thường được sử dụng trong quá trình nạp Firmware vào bộ nhớ của vi điều khiển.

BIN File

Binary File chứa dữ liệu nhị phân thô, không có cấu trúc bản ghi địa chỉ và Checksum như Intel HEX.

Vì vậy, khi sử dụng BIN File, công cụ nạp thường cần biết địa chỉ bộ nhớ đích để ghi dữ liệu vào đúng vị trí.

Tiêu chí ELF HEX BIN
Định dạng Executable / Linkable Format Văn bản Hexadecimal Dữ liệu nhị phân thô
Thông tin địa chỉ Có thông tin địa chỉ và các Section. Có thông tin địa chỉ trong các bản ghi. Không chứa thông tin địa chỉ tải độc lập.
Symbol / Debug Có thể chứa. Không chứa Symbol / Debug theo cấu trúc thông thường. Không chứa Symbol / Debug.
Mục đích phổ biến Debug và phân tích chương trình. Nạp Firmware. Nạp Firmware.
Không nên xem ELF, HEX và BIN là ba file hoàn toàn giống nhau chỉ khác phần mở rộng. Chúng có cấu trúc và mục đích sử dụng khác nhau. Công cụ nạp Firmware sẽ lựa chọn định dạng phù hợp với quy trình và yêu cầu của Target Hardware.

8. Embedded Toolchain là gì?

Sau khi hiểu quá trình biên dịch, chúng ta có thể tìm hiểu Embedded Toolchain.

Embedded Toolchain là tập hợp các công cụ được sử dụng để phát triển, biên dịch, liên kết, kiểm tra và hỗ trợ nạp chương trình vào hệ thống nhúng. Những công cụ này phối hợp với nhau để chuyển mã nguồn C thành Firmware có thể chạy trên vi điều khiển mục tiêu.

Một Embedded Toolchain thường bao gồm các thành phần sau:

8.1. Compiler

Compiler chịu trách nhiệm chuyển đổi mã nguồn C thành mã Assembly hoặc các dạng biểu diễn trung gian phù hợp với kiến trúc mục tiêu.

Trong Embedded Development, Compiler phải hỗ trợ kiến trúc CPU của vi điều khiển, chẳng hạn ARM Cortex-M, AVR hoặc các kiến trúc khác.

8.2. Assembler

Assembler chuyển mã Assembly thành mã máy và tạo ra Object File. Đây là thành phần tiếp nối giai đoạn Compilation.

8.3. Linker

Linker kết hợp các Object File và Library, xử lý các Symbol và tham chiếu địa chỉ, sau đó tạo chương trình đầu ra phù hợp với Target Platform.

8.4. Library

Library chứa các thành phần mã nguồn đã được biên dịch và đóng gói để chương trình có thể tái sử dụng.

Trong dự án Embedded, có thể sử dụng các Library cung cấp chức năng toán học, xử lý tín hiệu, giao tiếp hoặc các dịch vụ hỗ trợ khác.

8.5. Build System

Build System giúp quản lý quá trình biên dịch và liên kết nhiều file trong cùng một dự án.

Thay vì phải chạy thủ công từng lệnh Compiler cho tất cả Source File, Build System sẽ xác định những file cần biên dịch và tự động thực hiện các bước cần thiết.

Một số công cụ phổ biến:

  • Make: tự động hóa quá trình Build dựa trên các quy tắc trong Makefile.
  • CMake: công cụ quản lý và tạo cấu hình Build cho nhiều nền tảng khác nhau.
  • Ninja: Build System tập trung vào việc thực thi các tác vụ Build nhanh.

8.6. Debugger

Debugger hỗ trợ lập trình viên kiểm tra hoạt động của chương trình trong quá trình thực thi.

Những chức năng thường gặp gồm đặt Breakpoint, theo dõi giá trị biến, kiểm tra thanh ghi CPU và thực hiện từng bước lệnh.

Đối với Embedded Systems, Debugger có thể kết hợp với các thiết bị Debug Probe để giao tiếp với vi điều khiển thông qua các giao diện như JTAG hoặc SWD.

8.7. Programmer / Flash Tool

Sau khi Firmware được tạo ra, cần có công cụ để ghi chương trình vào bộ nhớ của vi điều khiển.

Programmer hoặc Flash Tool hỗ trợ quá trình này bằng cách giao tiếp với Target MCU thông qua những giao diện phần cứng phù hợp.

Một số công cụ có thể kết hợp cả chức năng Debugging và Flash Programming, giúp lập trình viên không cần sử dụng nhiều thiết bị riêng biệt.

9. Một số Embedded Toolchain phổ biến

Tùy vào kiến trúc vi điều khiển và môi trường phát triển, lập trình viên có thể lựa chọn các bộ công cụ khác nhau.

Toolchain / IDE Mục đích sử dụng
GNU Arm Embedded Toolchain Biên dịch và liên kết chương trình C/C++ cho các hệ thống sử dụng kiến trúc Arm.
Keil MDK Môi trường phát triển và công cụ hỗ trợ cho nhiều dòng vi điều khiển Arm.
STM32CubeIDE IDE hỗ trợ phát triển, cấu hình, Build và Debug các dự án STM32.
AVR-GCC Toolchain sử dụng GCC để phát triển phần mềm cho các vi điều khiển AVR.
IAR Embedded Workbench Môi trường phát triển thương mại với Compiler và Debugger cho nhiều kiến trúc nhúng.

Cần lưu ý rằng IDE và Toolchain không hoàn toàn là một khái niệm. IDE là môi trường tích hợp hỗ trợ lập trình viên quản lý dự án, chỉnh sửa mã nguồn, Build và Debug. Toolchain là tập hợp các công cụ thực hiện những công việc kỹ thuật bên trong quá trình phát triển.

10. Cross Compilation trong Embedded Development

Để hiểu rõ cách Embedded Toolchain được sử dụng trong thực tế, hãy xét trường hợp phát triển phần mềm cho một vi điều khiển ARM Cortex-M.

Lập trình viên viết chương trình trên máy tính cá nhân, sử dụng ARM GCC để tạo mã máy dành cho vi điều khiển. Chương trình sau đó được liên kết thành Firmware và nạp vào bộ nhớ Flash của MCU.

10.1. Ví dụ về ARM GCC

Một bộ công cụ GNU Arm thường cung cấp những chương trình như:

Tool Chức năng
arm-none-eabi-gcc Compiler Driver dùng để biên dịch và liên kết chương trình cho môi trường Arm bare-metal.
arm-none-eabi-as Assembler.
arm-none-eabi-ld Linker.
arm-none-eabi-objcopy Chuyển đổi định dạng file đối tượng hoặc Firmware.
arm-none-eabi-objdump Phân tích và hiển thị nội dung Object File hoặc ELF.
arm-none-eabi-size Hiển thị kích thước các Section của chương trình.
arm-none-eabi-gdb Debugger dành cho các chương trình mục tiêu Arm.

10.2. Một số tùy chọn Compiler thường gặp

Khi biên dịch cho MCU, lập trình viên thường phải chỉ định kiến trúc CPU và một số tùy chọn phù hợp với Target Platform. 

arm-none-eabi-gcc \
    -mcpu=cortex-m4 \
    -mthumb \
    -O0 \
    -g \
    -c main.c \
    -o main.o

Ý nghĩa các tùy chọn:

Option Chức năng
-mcpu=cortex-m4 Chỉ định CPU mục tiêu là ARM Cortex-M4.
-mthumb Yêu cầu tạo mã theo tập lệnh Thumb phù hợp với kiến trúc mục tiêu.
-O0 Không thực hiện hoặc hạn chế tối đa các tối ưu hóa Compiler.
-g Tạo thông tin Debug.
-c Biên dịch thành Object File, không thực hiện Linking.
-o main.o Đặt tên file đầu ra là main.o.
Các tùy chọn trên là ví dụ cho một mục tiêu Cortex-M4. Khi làm việc với MCU thực tế, cần lựa chọn chính xác CPU, kiến trúc FPU, ABI và các tham số liên quan theo tài liệu của thiết bị và Compiler.

11. Quy trình Build Firmware hoàn chỉnh

Bây giờ chúng ta có thể kết hợp những kiến thức đã tìm hiểu để hình dung một quy trình Build Firmware cơ bản.

Giả sử dự án có nhiều Source File và được xây dựng cho một vi điều khiển ARM. Quy trình tổng quan có thể được mô tả như sau:

  1. Source Code: lập trình viên viết mã nguồn C, Header File và các file Assembly cần thiết.
  2. Preprocessing: xử lý Header File, Macro và những chỉ thị tiền xử lý.
  3. Compilation: kiểm tra và chuyển đổi mã nguồn C thành Assembly.
  4. Assembly: chuyển Assembly thành các Object File.
  5. Linking: kết hợp các Object File, Library và những thành phần cần thiết.
  6. ELF Generation: tạo chương trình đầu ra dưới dạng ELF.
  7. File Conversion: chuyển ELF thành HEX hoặc BIN nếu quy trình nạp Firmware yêu cầu.
  8. Programming: sử dụng Flash Tool để ghi Firmware vào bộ nhớ của Target MCU.
  9. Debugging: kiểm tra chương trình sau khi nạp và xác định các vấn đề nếu có.

Sau khi nạp Firmware thành công, chương trình có thể bắt đầu thực thi trên vi điều khiển theo cơ chế khởi động của hệ thống. Quá trình khởi tạo phần cứng và thiết lập môi trường chạy chương trình sẽ được tìm hiểu sâu hơn ở Bài 9 về Linker Script, Memory Map và Startup Code.

12. Các lỗi thường gặp trong quá trình Build

Trong quá trình biên dịch và phát triển Embedded Software, lập trình viên có thể gặp nhiều loại lỗi khác nhau. Việc xác định lỗi thuộc giai đoạn nào sẽ giúp quá trình Debug hiệu quả hơn.

Loại lỗi Giai đoạn Ví dụ
Preprocessor Error Preprocessing Không tìm thấy Header File được khai báo bằng #include.
Syntax Error Compilation Thiếu dấu chấm phẩy, sai cú pháp hoặc khai báo không hợp lệ.
Type Error Compilation Sử dụng kiểu dữ liệu hoặc Function không phù hợp.
Assembler Error Assembly Mã Assembly có lệnh không hợp lệ với kiến trúc mục tiêu.
Undefined Reference Linking Gọi Function nhưng Linker không tìm thấy phần triển khai cần thiết.
Multiple Definition Linking Một Symbol bị định nghĩa trùng lặp trong nhiều Object File.
Memory Overflow Linking / Configuration Các Section được ánh xạ vượt quá vùng nhớ đã cấu hình.
Runtime Error Runtime Chương trình hoạt động sai sau khi nạp Firmware.

12.1. Preprocessor và Compilation Error

Đây là những lỗi thường được phát hiện trước khi chương trình được tạo thành Object File. Nguyên nhân có thể đến từ việc không tìm thấy Header File, sai cú pháp, thiếu khai báo hoặc sử dụng kiểu dữ liệu không phù hợp.

12.2. Linking Error

Linking Error thường xuất hiện khi Linker không thể hoàn thành việc kết hợp các Object File.

Ví dụ, một Function đã được khai báo trong Header File và được gọi từ main.c, nhưng file chứa phần triển khai chưa được đưa vào quá trình Build. 

undefined reference to `add_numbers'

Để xử lý, cần kiểm tra xem file chứa Function có được biên dịch thành Object File và được đưa vào lệnh Linking hay chưa.

12.3. Runtime Error

Không phải tất cả lỗi đều được phát hiện trong quá trình Build. Một chương trình có thể biên dịch và Linking thành công nhưng vẫn hoạt động sai khi chạy trên vi điều khiển.

Ví dụ, chương trình có thể cấu hình ngoại vi không đúng, xử lý dữ liệu sai hoặc gặp vấn đề khi truy cập bộ nhớ. Những trường hợp này cần được kiểm tra bằng Debugger, kiểm thử trên Target Hardware và các công cụ phù hợp.

Build thành công không đồng nghĩa với chương trình hoạt động đúng. Compilation và Linking chỉ xác nhận rằng chương trình vượt qua những bước xử lý tương ứng. Chất lượng và hành vi thực tế của Firmware vẫn cần được kiểm thử và xác minh.

13. Debug và kiểm tra các file sau khi Build

Bên cạnh việc tạo ra Firmware, Embedded Toolchain còn cung cấp các công cụ giúp lập trình viên phân tích kết quả Build. Một số công cụ hữu ích trong GNU Toolchain bao gồm:

13.1. Kiểm tra kích thước chương trình

Có thể sử dụng lệnh size để xem kích thước các Section chính trong ELF File: 

arm-none-eabi-size firmware.elf

Kết quả thường hiển thị kích thước các Section như:

  • text: tổng kích thước các Section Code và những Section được tính vào nhóm Text theo công cụ.
  • data: dữ liệu đã khởi tạo.
  • bss: dữ liệu được khởi tạo bằng 0 hoặc chưa có giá trị khởi tạo tường minh.

Kết quả cụ thể phụ thuộc vào cấu trúc ELF và cách Toolchain phân loại Section. Những thông tin này giúp lập trình viên có cái nhìn tổng quan về mức sử dụng bộ nhớ.

13.2. Phân tích nội dung Object File

Có thể sử dụng objdump để xem thông tin về Section, Symbol hoặc Assembly tương ứng với chương trình. 

arm-none-eabi-objdump -h firmware.elf

arm-none-eabi-objdump -d firmware.elf
  • -h: hiển thị thông tin các Section.
  • -d: Disassemble các Section chứa mã có thể được giải mã thành lệnh.

13.3. Tạo HEX và BIN từ ELF

Khi cần tạo file để nạp Firmware, có thể sử dụng objcopy: 

arm-none-eabi-objcopy -O ihex firmware.elf firmware.hex

arm-none-eabi-objcopy -O binary firmware.elf firmware.bin

Trong đó:

  • -O ihex: tạo file theo định dạng Intel HEX.
  • -O binary: tạo file nhị phân thô.

Những lệnh trên chỉ minh họa các thao tác cơ bản với ELF. Trong một dự án thực tế, cần kiểm tra cấu hình Linker, vùng nhớ và quy định của công cụ Flash trước khi sử dụng file đầu ra.

Tóm tắt

C Compilation Process là quy trình chuyển đổi mã nguồn C thành chương trình có thể thực thi. Quy trình này thường bao gồm bốn giai đoạn chính: Preprocessing, Compilation, Assembly và Linking.

Trong Embedded Development, lập trình viên thường sử dụng Cross Compiler để tạo chương trình cho vi điều khiển có kiến trúc khác với máy tính phát triển. Tập hợp các công cụ như Compiler, Assembler, Linker, Library, Build System và Debugger được gọi là Embedded Toolchain.

Các loại file quan trọng trong quá trình Build bao gồm Source File (.c), Header File (.h), Preprocessed File (.i), Assembly File (.s), Object File (.o), ELF (.elf), HEX (.hex), BIN (.bin) và Map File (.map).

Hiểu rõ quá trình Compilation và Embedded Toolchain giúp lập trình viên xác định nguyên nhân các lỗi Build, phân tích kết quả biên dịch và quản lý quá trình tạo Firmware cho Target Microcontroller.
