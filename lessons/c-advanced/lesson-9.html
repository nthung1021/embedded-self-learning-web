Bài 9: Linker Script, Memory Map & Startup Code

Trong các bài học trước, chúng ta đã tìm hiểu cách chương trình C sử dụng bộ nhớ, bao gồm Stack, Heap, Data Segment, BSS Segment, Memory Alignment và Padding. Tuy nhiên, trong một hệ thống Embedded, vẫn còn một câu hỏi quan trọng: những vùng dữ liệu và mã lệnh đó thực sự được đặt ở đâu trong bộ nhớ vật lý của MCU?

Một chương trình Embedded thường chạy trực tiếp trên vi điều khiển, nơi dung lượng Flash và RAM có giới hạn, đồng thời mỗi vùng nhớ có địa chỉ và mục đích sử dụng riêng. Compiler không tự quyết định toàn bộ cách chương trình được phân bố vào các vùng nhớ này.

Đây là nhiệm vụ của Linker và Linker Script. Bên cạnh đó, trước khi chương trình có thể thực thi hàm main(), hệ thống còn cần thực hiện một số bước khởi tạo ban đầu. Những công việc này thuộc Startup Code.

1. Tổng quan về Linker trong Embedded C

1.1. Linker là gì?

Linker là công cụ kết hợp các Object File và thư viện cần thiết thành một chương trình hoàn chỉnh. Trong quá trình này, Linker thực hiện việc liên kết các symbol, giải quyết những tham chiếu giữa các module và bố trí các section vào những địa chỉ bộ nhớ cụ thể.

Khi một project C có nhiều file source, mỗi file thường được biên dịch thành một Object File riêng. Các Object File này có thể chứa:

  • Mã máy của các function.
  • Dữ liệu toàn cục và dữ liệu static.
  • Thông tin về các symbol được định nghĩa hoặc được tham chiếu.
  • Các section chứa code và data.
  • Thông tin relocation để Linker điều chỉnh địa chỉ tham chiếu.

Linker sẽ kết hợp những thành phần này và tạo ra file chương trình có thể được sử dụng bởi debugger, programmer hoặc các công cụ tạo firmware image.

1.2. Compiler và Linker khác nhau như thế nào?

Compiler và Linker là hai thành phần khác nhau trong quá trình xây dựng chương trình.

Tiêu chí Compiler Linker
Đầu vào Source Code như file .c và header liên quan. Object File và Library.
Nhiệm vụ Phân tích, kiểm tra và chuyển đổi source code thành mã máy hoặc Assembly. Kết hợp các Object File, giải quyết symbol và bố trí section.
Đầu ra Object File hoặc Assembly tùy cấu hình. Executable, ELF hoặc định dạng đầu ra khác tùy toolchain.
Lỗi thường gặp Syntax Error, Type Error, Compilation Error. Undefined Reference, Multiple Definition, Memory Region Overflow.

1.3. Vai trò của Linker trong Embedded Systems

Trong ứng dụng chạy trên máy tính thông thường, hệ điều hành thường chịu trách nhiệm nạp chương trình và cấp phát một không gian địa chỉ cho process.

Trong nhiều hệ thống Embedded Bare-metal, chương trình được nạp trực tiếp vào Flash hoặc một vùng nhớ xác định của MCU. Do đó, Linker cần biết chính xác:

  • Flash bắt đầu tại địa chỉ nào và có dung lượng bao nhiêu.
  • RAM bắt đầu tại địa chỉ nào và có dung lượng bao nhiêu.
  • Code và constant data sẽ được lưu ở đâu.
  • Biến global và static sẽ được bố trí ở vùng RAM nào.
  • Vùng Stack và Heap được sử dụng như thế nào.
  • Vector Table cần nằm tại vị trí nào theo yêu cầu của MCU.

Linker Script cung cấp thông tin và quy tắc để Linker thực hiện việc bố trí đó.

2. Object File và các Section

2.1. Object File là gì?

Sau khi một source file được biên dịch, compiler thường tạo ra Object File, chẳng hạn file có phần mở rộng .o hoặc .obj.

Object File chưa nhất thiết là chương trình hoàn chỉnh. Nó có thể chứa các tham chiếu đến function hoặc variable được định nghĩa trong những module khác.

Ví dụ project có cấu trúc: 

project/
|
|-- main.c
|-- sensor.c
|-- uart.c
|
|-- main.o
|-- sensor.o
|-- uart.o

Sau quá trình compile, mỗi file source có thể tạo ra một Object File tương ứng. Linker sau đó kết hợp các Object File cần thiết thành chương trình cuối cùng.

2.2. Section là gì?

Section là một vùng trong Object File dùng để chứa một nhóm nội dung có đặc điểm hoặc mục đích tương tự nhau.

Ví dụ, code của function thường được đưa vào section .text, trong khi dữ liệu global đã khởi tạo có thể được đưa vào .data.

Một số section phổ biến trong Embedded C:

Section Nội dung Vị trí thường gặp
.text Mã lệnh của các function. Flash / Code Memory
.rodata Read-only data như string literal và một số constant. Flash / Read-only Memory
.data Biến global hoặc static đã khởi tạo. RAM khi chạy; giá trị khởi tạo được lưu trong Flash.
.bss Biến global hoặc static chưa khởi tạo rõ ràng hoặc được khởi tạo bằng zero theo quy tắc C. RAM
.noinit Vùng dữ liệu tùy chỉnh không được Startup Code khởi tạo lại theo cách thông thường. RAM
.isr_vector Vector Table của interrupt và exception. Flash hoặc vùng nhớ được MCU yêu cầu.
.init_array Danh sách function khởi tạo được runtime gọi trước main trong những toolchain hỗ trợ. Thường nằm trong Flash
Lưu ý: Tên section và cách compiler tạo ra chúng phụ thuộc vào toolchain. Các tên như .text, .data và .bss rất phổ biến trong hệ sinh thái GNU, nhưng không nên xem đây là tên bắt buộc của mọi compiler.

2.3. Ví dụ về các biến thuộc những section khác nhau

#include <stdint.h>

uint32_t global_init = 100U;

uint32_t global_zero = 0U;

uint32_t global_uninit;

static uint16_t sensor_value = 50U;

const uint32_t MAX_SENSOR_VALUE = 1000U;

void read_sensor(void)
{
    static uint32_t read_count = 0U;

    read_count++;

    /* Sensor reading logic */
}

int main(void)
{
    read_sensor();

    return 0;
}

Trên một toolchain Embedded phổ biến, có thể hình dung cách phân loại như sau:

Biến / Thành phần Section có thể sử dụng Lý do
global_init .data Global variable có giá trị khởi tạo khác zero.
global_zero .bss Global variable được khởi tạo bằng zero.
global_uninit .bss Global variable không có initializer.
sensor_value .data Static variable đã khởi tạo.
MAX_SENSOR_VALUE .rodata Constant object có thể được đặt trong read-only section.
read_sensor() .text Function code.
read_count .data Static local variable có thời gian tồn tại static.

Việc một biến được đưa vào section nào còn phụ thuộc vào compiler, optimization và các tùy chọn biên dịch. Bảng trên mô tả cách phân loại phổ biến để chúng ta hiểu nguyên lý.

3. Memory Map trong Embedded Systems

3.1. Memory Map là gì?

Memory Map mô tả cách các vùng nhớ được bố trí trong không gian địa chỉ của một hệ thống.

Đối với một MCU, Memory Map thường thể hiện các vùng như:

  • Flash Memory: lưu firmware và dữ liệu không mất khi mất nguồn.
  • SRAM: lưu dữ liệu chương trình trong quá trình chạy.
  • Peripheral Memory: vùng địa chỉ dùng để truy cập các peripheral register.
  • System Memory: một số vùng nhớ hệ thống đặc biệt theo thiết kế MCU.
  • External Memory: bộ nhớ ngoài nếu hệ thống có hỗ trợ.

3.2. Ví dụ Memory Map đơn giản

Giả sử một MCU có:

  • Flash Memory: 512 KB, bắt đầu tại địa chỉ 0x08000000.
  • SRAM: 128 KB, bắt đầu tại địa chỉ 0x20000000.

Memory Map minh họa có thể được biểu diễn như sau:

Hình trên mô tả một cách tổ chức bộ nhớ thường gặp, nhưng cần lưu ý rằng vị trí Stack, Heap và các section trong RAM có thể khác nhau tùy Linker Script và thiết kế hệ thống.

3.3. Địa chỉ bắt đầu và dung lượng vùng nhớ

Khi làm việc với Memory Map, hai thông tin rất quan trọng là:

  • ORIGIN: địa chỉ bắt đầu của vùng nhớ.
  • LENGTH: dung lượng của vùng nhớ.

Ví dụ, nếu Flash bắt đầu tại 0x08000000 và có dung lượng 512 KB: 

Flash Start = 0x08000000
Flash Size  = 512 KB
Flash End   = 0x0807FFFF

Nếu SRAM bắt đầu tại 0x20000000 và có dung lượng 128 KB: 

RAM Start = 0x20000000
RAM Size  = 128 KB
RAM End   = 0x2001FFFF

Các địa chỉ trên chỉ là ví dụ. Khi phát triển firmware, phải lấy thông tin chính xác từ datasheet, reference manual và tài liệu memory map của MCU đang sử dụng.

4. Linker Script là gì?

4.1. Khái niệm Linker Script

Linker Script là file cấu hình mô tả cách Linker bố trí các section của chương trình vào không gian địa chỉ.

Với GNU Linker (GNU ld), Linker Script thường sử dụng phần mở rộng .ld. Nó giúp xác định:

  • Các vùng nhớ mà chương trình được phép sử dụng.
  • Địa chỉ bắt đầu và dung lượng của từng vùng.
  • Section nào được đặt trong Flash hoặc RAM.
  • Địa chỉ nạp dữ liệu và địa chỉ sử dụng dữ liệu khi chạy.
  • Các symbol phục vụ quá trình Startup.
  • Những section cần được giữ lại hoặc xử lý đặc biệt.

4.2. Cấu trúc cơ bản của Linker Script

Một GNU Linker Script thường có hai phần quan trọng:

Phần Vai trò
MEMORY Khai báo các vùng nhớ có thể sử dụng, địa chỉ bắt đầu và dung lượng.
SECTIONS Quy định cách các input section được gom và đặt vào output section.

4.3. Ví dụ khai báo MEMORY

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

Giải thích:

  • FLASH là tên vùng nhớ Flash.
  • RAM là tên vùng nhớ RAM.
  • ORIGIN xác định địa chỉ bắt đầu.
  • LENGTH xác định dung lượng của vùng nhớ.
  • Các ký hiệu r, w, x mô tả thuộc tính vùng nhớ theo cú pháp của GNU ld: đọc, ghi và thực thi.

Đây là cách khai báo phổ biến trong GNU Linker Script. Các toolchain khác có thể sử dụng định dạng file và cú pháp khác.

4.4. Ví dụ khai báo SECTIONS

Sau khi khai báo vùng nhớ, chúng ta sử dụng SECTIONS để chỉ định vị trí của các section. 

SECTIONS
{
    .text :
    {
        *(.text)
        *(.text*)
    } > FLASH

    .rodata :
    {
        *(.rodata)
        *(.rodata*)
    } > FLASH

    .data :
    {
        *(.data)
        *(.data*)
    } > RAM

    .bss :
    {
        *(.bss)
        *(.bss*)
        *(COMMON)
    } > RAM
}

Trong ví dụ trên:

  • .text được đặt vào vùng FLASH.
  • .rodata được đặt vào vùng FLASH.
  • .data được đặt vào vùng RAM.
  • .bss được đặt vào vùng RAM.

Cú pháp *(<section-name>) dùng để chọn những input section tương ứng từ các Object File đầu vào. Ví dụ *(.text*) có thể chọn cả những section bắt đầu bằng .text.

Ví dụ trên chỉ thể hiện ý tưởng cơ bản. Trong Embedded thực tế, section .data cần có cả vùng lưu bản khởi tạo trong Flash và vùng sử dụng khi chạy trong RAM. Phần này sẽ được trình bày cụ thể ở mục tiếp theo.

5. Load Address và Run Address

5.1. Sự khác nhau giữa LMA và VMA

Một khái niệm rất quan trọng khi đọc Linker Script là sự khác nhau giữa địa chỉ lưu dữ liệu trong file chương trình và địa chỉ mà dữ liệu được sử dụng khi chạy.

Hai khái niệm thường gặp là:

Khái niệm Ý nghĩa
Load Memory Address (LMA) Địa chỉ nạp hoặc lưu nội dung ban đầu của section trong image.
Virtual Memory Address (VMA) Địa chỉ mà section được sử dụng khi chương trình chạy.

Trong nhiều hệ thống MCU, một biến global có giá trị khởi tạo được lưu bản khởi tạo trong Flash, nhưng lại cần nằm trong RAM khi chương trình chạy.

Khi đó:

  • LMA của section .data nằm trong Flash.
  • VMA của section .data nằm trong RAM.

5.2. Ví dụ với biến global đã khởi tạo

uint32_t sensor_timeout = 5000U;

int main(void)
{
    sensor_timeout++;

    return 0;
}

Biến sensor_timeout cần có giá trị ban đầu là 5000. Vì biến có thể thay đổi trong quá trình chương trình chạy, nó thường được đặt trong RAM.

Tuy nhiên, ngay sau khi MCU reset, RAM không tự động chứa giá trị khởi tạo 5000 theo cách mà chương trình C yêu cầu. Do đó, giá trị ban đầu cần được lưu trong Flash và được Startup Code sao chép sang RAM.

Quá trình này thường được thực hiện trước khi gọi main(), thông qua các địa chỉ được định nghĩa bởi Linker Script.

5.3. Cách biểu diễn trong GNU Linker Script

Với GNU ld, có thể sử dụng AT> để chỉ định vùng nhớ nạp dữ liệu khác với vùng nhớ chạy. 

.data :
{
    . = ALIGN(4);

    _sdata = .;

    *(.data)
    *(.data*)

    . = ALIGN(4);

    _edata = .;
} > RAM AT> FLASH

_sidata = LOADADDR(.data);

Giải thích:

  • > RAM: VMA của section .data nằm trong RAM.
  • AT> FLASH: LMA của section .data nằm trong Flash.
  • _sdata: symbol đánh dấu địa chỉ bắt đầu của vùng .data trong RAM.
  • _edata: symbol đánh dấu địa chỉ kết thúc của vùng .data trong RAM.
  • LOADADDR(.data): lấy địa chỉ nạp của section .data.
  • _sidata: symbol lưu địa chỉ nguồn để Startup Code sao chép dữ liệu.
Các tên như _sdata, _edata và _sidata là symbol do người thiết kế Linker Script đặt tên. Startup Code phải sử dụng đúng những tên mà Linker Script thực sự cung cấp.

6. BSS Section và quá trình Zero Initialization

6.1. Tại sao cần khởi tạo BSS?

Trong C, các biến có static storage duration không được khởi tạo tường minh sẽ được khởi tạo bằng giá trị zero theo quy tắc của ngôn ngữ.

Ví dụ:

#include <stdint.h>

uint32_t system_status;
static uint8_t sensor_ready;

int main(void)
{
    /* Both variables should begin with zero values */

    return 0;
}

Những biến này thường được đưa vào section .bss. Khi khởi động, Startup Code cần đảm bảo vùng BSS được đưa về zero trước khi chương trình sử dụng các biến đó.

6.2. Cách khai báo BSS trong Linker Script

.bss (NOLOAD) :
{
    . = ALIGN(4);

    _sbss = .;

    *(.bss)
    *(.bss*)
    *(COMMON)

    . = ALIGN(4);

    _ebss = .;
} > RAM

Giải thích:

  • .bss là output section dành cho dữ liệu BSS.
  • NOLOAD trong GNU ld chỉ định section không cần được tải như một vùng dữ liệu khởi tạo thông thường.
  • _sbss đánh dấu địa chỉ bắt đầu của BSS.
  • _ebss đánh dấu địa chỉ kết thúc của BSS.
  • > RAM đặt section vào vùng RAM.

6.3. Zero Initialization

Startup Code có thể sử dụng hai symbol _sbss và _ebss để xác định phạm vi cần xóa dữ liệu. 

extern uint32_t _sbss;
extern uint32_t _ebss;

static void zero_bss(void)
{
    uint32_t *dst = &_sbss;

    while (dst < &_ebss) {
        *dst = 0U;
        dst++;
    }
}

Hàm trên minh họa việc ghi zero vào vùng BSS theo từng đơn vị uint32_t. Cách triển khai thực tế cần đảm bảo Alignment, kích thước section và ABI phù hợp với nền tảng.

7. Linker Script hoàn chỉnh ở mức cơ bản

7.1. Ví dụ Linker Script sử dụng GNU ld

Dưới đây là một ví dụ tổng hợp để minh họa cách khai báo Flash, RAM và một số section thường gặp trong firmware.

Giả định:

  • Flash có dung lượng 512 KB.
  • RAM có dung lượng 128 KB.
  • Vector Table được đặt đầu vùng Flash.
  • Code và read-only data được đặt trong Flash.
  • Dữ liệu khởi tạo được lưu trong Flash và chạy trong RAM.
  • BSS và vùng noinit nằm trong RAM.
/* Example linker script for GNU ld */

ENTRY(Reset_Handler)

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

__StackTop = ORIGIN(RAM) + LENGTH(RAM);

SECTIONS
{
    /* Interrupt Vector Table */
    .isr_vector :
    {
        . = ALIGN(4);

        KEEP(*(.isr_vector))

        . = ALIGN(4);
    } > FLASH

    /* Program Code */
    .text :
    {
        . = ALIGN(4);

        *(.text)
        *(.text*)

        . = ALIGN(4);
    } > FLASH

    /* Read-only Data */
    .rodata :
    {
        . = ALIGN(4);

        *(.rodata)
        *(.rodata*)

        . = ALIGN(4);
    } > FLASH

    /* Initialization Function Pointers */
    .init_array :
    {
        . = ALIGN(4);

        PROVIDE_HIDDEN(__init_array_start = .);

        KEEP(*(.init_array*))

        PROVIDE_HIDDEN(__init_array_end = .);

        . = ALIGN(4);
    } > FLASH

    /* Initialized Data:
       Load Address: FLASH
       Run Address : RAM */
    .data :
    {
        . = ALIGN(4);

        _sdata = .;

        *(.data)
        *(.data*)

        . = ALIGN(4);

        _edata = .;
    } > RAM AT> FLASH

    _sidata = LOADADDR(.data);

    /* Zero-initialized Data */
    .bss (NOLOAD) :
    {
        . = ALIGN(4);

        _sbss = .;

        *(.bss)
        *(.bss*)
        *(COMMON)

        . = ALIGN(4);

        _ebss = .;
    } > RAM

    /* Data that should not be cleared by normal startup */
    .noinit (NOLOAD) :
    {
        . = ALIGN(4);

        *(.noinit)
        *(.noinit*)

        . = ALIGN(4);
    } > RAM

    /* End of statically allocated RAM data */
    _end = .;

    /* Check that static RAM sections do not overlap the stack reserve */
    ASSERT(_end <= (__StackTop - 0x400),
           "RAM overflow: static data overlaps stack reserve")
}

Đây là Linker Script minh họa cho một môi trường sử dụng GNU ld. Nó chưa phải cấu hình hoàn chỉnh cho một MCU cụ thể vì mỗi architecture và startup environment có thể yêu cầu thêm section, symbol hoặc cách bố trí riêng.

7.2. Giải thích các thành phần quan trọng

Thành phần Ý nghĩa
ENTRY(Reset_Handler) Khai báo entry point của chương trình cho Linker. Trên MCU, quá trình reset thực tế thường đi qua cơ chế Reset Vector của kiến trúc.
MEMORY Khai báo vùng nhớ Flash và RAM.
SECTIONS Định nghĩa cách bố trí output section.
KEEP() Yêu cầu Linker giữ lại input section được chỉ định ngay cả khi sử dụng một số cơ chế loại bỏ section không được tham chiếu.
ALIGN(4) Điều chỉnh vị trí hiện tại theo Alignment 4 byte trong ví dụ.
AT> FLASH Đặt vùng load của section vào Flash.
LOADADDR() Lấy Load Memory Address của một section.
ASSERT() Kiểm tra một điều kiện trong quá trình Link.

7.3. Tại sao cần KEEP()?

Một số toolchain hỗ trợ loại bỏ những section không được tham chiếu khi bật các tùy chọn như --gc-sections.

Tuy nhiên, Vector Table có thể không được chương trình C tham chiếu trực tiếp bằng một symbol thông thường. Nếu bị loại bỏ, firmware sẽ không có Vector Table như mong đợi.

Vì vậy, GNU Linker cung cấp KEEP() để yêu cầu giữ lại section quan trọng. 

.isr_vector :
{
    KEEP(*(.isr_vector))
} > FLASH
Không phải mọi section đều cần KEEP(). Chỉ nên sử dụng cho các section cần tồn tại theo yêu cầu của hệ thống, chẳng hạn Vector Table hoặc một số vùng metadata đặc biệt.

8. Startup Code là gì?

8.1. Khái niệm Startup Code

Startup Code là phần code thực hiện các bước khởi tạo ban đầu sau khi MCU reset và trước khi chương trình bắt đầu thực thi logic chính trong main().

Startup Code thường được cung cấp bởi:

  • Nhà sản xuất MCU.
  • CMSIS hoặc framework hỗ trợ kiến trúc.
  • Embedded SDK hoặc Hardware Abstraction Package.
  • Toolchain hoặc runtime library.
  • Project tự xây dựng nếu có yêu cầu đặc biệt.

Startup Code thường được viết bằng Assembly, C hoặc kết hợp cả hai, tùy architecture và toolchain.

8.2. Tại sao không thể gọi main() ngay sau khi reset?

Khi MCU vừa reset, môi trường thực thi C chưa chắc đã được chuẩn bị đầy đủ. Các biến global và static cần có giá trị đúng, Stack Pointer phải được thiết lập và một số cấu hình hệ thống có thể cần được khởi tạo.

Ví dụ, xét chương trình: 

#include <stdint.h>

uint32_t system_counter = 100U;
uint32_t error_count;

int main(void)
{
    system_counter++;

    if (error_count == 0U) {
        /* Normal startup behavior */
    }

    return 0;
}

Trước khi thực thi logic trong main():

  • system_counter cần nhận giá trị khởi tạo 100.
  • error_count cần được khởi tạo bằng zero.
  • Stack cần sẵn sàng để sử dụng cho function call và local variable.

Startup Code và C runtime thực hiện những bước cần thiết để tạo môi trường chạy phù hợp.

9. Trình tự khởi động của một MCU

9.1. Reset Sequence tổng quát

Khi MCU nhận một sự kiện reset, CPU sẽ bắt đầu quá trình khởi động theo quy tắc của kiến trúc phần cứng.

Với một MCU sử dụng cơ chế Vector Table, quá trình tổng quát có thể được hình dung như sau:

Đây là luồng minh họa tổng quát. Thứ tự chính xác của các bước như System Initialization, FPU initialization, runtime initialization và C library initialization có thể khác nhau giữa các MCU và toolchain.

9.2. Vector Table

Vector Table là bảng chứa các thông tin liên quan đến điểm bắt đầu và địa chỉ các exception hoặc interrupt handler theo quy tắc của kiến trúc MCU.

Với một số kiến trúc, entry đầu tiên của Vector Table chứa giá trị Stack Pointer ban đầu. Entry tiếp theo chứa địa chỉ của Reset Handler. Các entry sau đó tương ứng với những exception hoặc interrupt khác.

Có thể hình dung một bảng đơn giản như sau:

Entry Nội dung minh họa
Entry 0 Initial Stack Pointer
Entry 1 Reset Handler
Entry 2 NMI Handler
Entry 3 Hard Fault Handler
Entry tiếp theo Các exception và interrupt handler khác

Cấu trúc cụ thể của Vector Table phụ thuộc vào kiến trúc MCU. Không phải mọi vi điều khiển đều sử dụng cùng một định dạng.

9.3. Reset Handler

Reset Handler là function hoặc routine được gọi đầu tiên sau khi cơ chế reset của CPU chuyển quyền thực thi cho chương trình.

Reset Handler thường chịu trách nhiệm:

  • Thực hiện những bước thiết lập môi trường ban đầu.
  • Sao chép dữ liệu khởi tạo từ Flash sang RAM.
  • Đưa vùng BSS về zero.
  • Gọi các bước khởi tạo hệ thống cần thiết.
  • Khởi tạo C runtime nếu được yêu cầu.
  • Chuyển quyền điều khiển đến main().

10. Data Initialization và BSS Initialization trong Startup Code

10.1. Sao chép .data từ Flash sang RAM

Như đã trình bày ở phần LMA và VMA, dữ liệu khởi tạo của section .data thường có bản lưu trong Flash, trong khi địa chỉ sử dụng khi chạy nằm trong RAM.

Startup Code cần sao chép nội dung từ địa chỉ nguồn _sidata sang vùng đích bắt đầu tại _sdata và kết thúc tại _edata. 

#include <stdint.h>

extern uint32_t _sidata;
extern uint32_t _sdata;
extern uint32_t _edata;

static void initialize_data(void)
{
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;

    while (dst < &_edata) {
        *dst = *src;

        dst++;
        src++;
    }
}

Hàm trên minh họa cách sao chép dữ liệu theo từng word 32 bit. Việc này giả định các symbol và vùng dữ liệu đã được căn chỉnh phù hợp. Startup Code thực tế có thể dùng Assembly hoặc cách sao chép khác tùy toolchain.

10.2. Khởi tạo .bss về zero

Tiếp theo, vùng .bss được đưa về zero: 

#include <stdint.h>

extern uint32_t _sbss;
extern uint32_t _ebss;

static void initialize_bss(void)
{
    uint32_t *dst = &_sbss;

    while (dst < &_ebss) {
        *dst = 0U;
        dst++;
    }
}

Việc khởi tạo này giúp các biến global và static trong BSS có giá trị ban đầu phù hợp với yêu cầu của ngôn ngữ C.

10.3. Startup Code minh họa

Có thể kết hợp hai hàm trên thành một Reset Handler đơn giản: 

#include <stdint.h>

extern uint32_t _sidata;
extern uint32_t _sdata;
extern uint32_t _edata;

extern uint32_t _sbss;
extern uint32_t _ebss;

extern void SystemInit(void);
extern void __libc_init_array(void);
extern int main(void);

void Reset_Handler(void)
{
    uint32_t *src;
    uint32_t *dst;

    /* Copy initialized data from Flash to RAM */
    src = &_sidata;
    dst = &_sdata;

    while (dst < &_edata) {
        *dst++ = *src++;
    }

    /* Clear BSS section */
    dst = &_sbss;

    while (dst < &_ebss) {
        *dst++ = 0U;
    }

    /* Initialize MCU-specific system configuration */
    SystemInit();

    /* Initialize C runtime functions, if required */
    __libc_init_array();

    /* Start the application */
    (void)main();

    /* main() should not normally return in a bare-metal application */
    for (;;) {
    }
}

Đoạn code trên giúp minh họa trách nhiệm của Reset Handler, không phải Startup Code hoàn chỉnh cho mọi MCU.

Quan trọng: Reset Handler thực tế thường cần được viết hoặc gọi theo đúng quy ước của CPU. Trên một số kiến trúc, việc thiết lập Stack Pointer được thực hiện bởi phần cứng từ Vector Table trước khi Reset Handler chạy. Ngoài ra, việc khởi tạo clock, FPU, C runtime và các vùng nhớ đặc biệt phải tuân theo startup implementation của toolchain và MCU.

11. Stack và Heap trong Linker Script

11.1. Vì sao Stack cần được xem xét?

Stack được sử dụng trong quá trình thực thi function, lưu trữ local variable, return address và một số thông tin phục vụ hoạt động của CPU theo calling convention.

Trong Embedded Systems, dung lượng Stack thường bị giới hạn bởi tổng dung lượng RAM. Nếu Stack sử dụng vượt quá vùng được cấp phát, chương trình có thể gây Stack Overflow và làm hỏng dữ liệu ở những vùng nhớ khác.

11.2. Stack Pointer ban đầu

Nhiều kiến trúc MCU sử dụng Stack Pointer để xác định vị trí hiện tại của Stack. Giá trị ban đầu thường được thiết lập theo quy tắc của kiến trúc hoặc Startup Code.

Ví dụ trong GNU Linker Script: 

__StackTop = ORIGIN(RAM) + LENGTH(RAM);

Symbol __StackTop biểu diễn địa chỉ ở cuối vùng RAM trong ví dụ. Trên các hệ thống mà Stack phát triển theo hướng địa chỉ giảm, đây thường là vị trí khởi tạo Stack Pointer.

11.3. Heap và vùng RAM còn lại

Heap được sử dụng khi chương trình cần cấp phát bộ nhớ động, chẳng hạn thông qua malloc(), calloc() hoặc realloc().

Trong một số bare-metal toolchain, Heap có thể được quản lý thông qua runtime library và các symbol do Linker Script cung cấp. Tuy nhiên, không phải mọi Embedded project đều sử dụng Heap.

Ví dụ, một firmware có thể lựa chọn:

  • Sử dụng Stack cho biến cục bộ và function call.
  • Sử dụng Static Allocation cho các buffer có kích thước cố định.
  • Hạn chế hoặc không sử dụng Dynamic Allocation.

Cách tổ chức này giúp kiểm soát dung lượng RAM và thời gian thực thi tốt hơn trong nhiều ứng dụng có yêu cầu ổn định cao.

11.4. Kiểm tra vùng nhớ dành cho Stack

Một Linker Script có thể sử dụng ASSERT để kiểm tra một vùng RAM dự phòng cho Stack. 

__StackTop = ORIGIN(RAM) + LENGTH(RAM);

_Min_Stack_Size = 0x400;

ASSERT(_end <= (__StackTop - _Min_Stack_Size),
       "Not enough RAM for stack")

Trong ví dụ này, Linker kiểm tra xem vùng dữ liệu tĩnh đã sử dụng có vượt quá giới hạn dành cho Stack hay không.

Đây chỉ là kiểm tra mức bố trí ban đầu. Nó không đảm bảo Stack sẽ không bị tràn trong lúc chương trình chạy. Việc xác định Stack Size vẫn cần dựa trên phân tích call depth, local variable, interrupt nesting và cách RTOS quản lý task stack nếu có.

12. Memory Map File và cách đọc kết quả Linker

12.1. Memory Map File là gì?

Map File là file báo cáo do Linker tạo ra, mô tả cách các section, symbol và vùng nhớ được bố trí trong chương trình sau khi Link.

Trong GNU toolchain, Map File thường được tạo bằng tùy chọn -Map. 

arm-none-eabi-gcc \
    main.o sensor.o uart.o \
    -T linker_script.ld \
    -Wl,-Map=firmware.map \
    -o firmware.elf

File firmware.map giúp developer kiểm tra:

  • Section được đặt tại địa chỉ nào.
  • Code và data chiếm bao nhiêu bộ nhớ.
  • Symbol nào nằm ở địa chỉ cụ thể.
  • Object File hoặc Library nào đóng góp vào section.
  • Có vùng nhớ nào vượt quá giới hạn được khai báo hay không.

12.2. Ví dụ nội dung Map File đơn giản

Một phần Map File có thể chứa thông tin minh họa như sau: 

Memory Configuration

Name        Origin          Length
FLASH       0x08000000      0x00080000
RAM         0x20000000      0x00020000


Linker script and memory map

.isr_vector  0x08000000   0x00000100
.text        0x08000100   0x00012000
.rodata      0x08012100   0x00002000

.data        0x20000000   0x00001000
.bss         0x20001000   0x00000800
.noinit      0x20001800   0x00000100

Các địa chỉ và kích thước ở trên chỉ là ví dụ để minh họa cách đọc báo cáo.

12.3. Ý nghĩa của thông tin trong Map File

Thông tin Cách hiểu
Memory Configuration Các vùng nhớ được khai báo trong Linker Script.
Origin Địa chỉ bắt đầu của một vùng nhớ.
Length Dung lượng của vùng nhớ.
Section Address Địa chỉ bố trí của section.
Section Size Kích thước section.
Symbol Tên và địa chỉ của function, variable hoặc symbol do Linker tạo ra.

12.4. Tính dung lượng bộ nhớ được sử dụng

Giả sử Map File cho thấy: 

.text   = 72 KB
.rodata = 12 KB
.data   = 4 KB
.bss    = 16 KB

Có thể ước lượng:

  • Flash cần chứa code và read-only data, cùng dữ liệu khởi tạo của .data.
  • RAM cần chứa .data, .bss và các vùng dữ liệu runtime khác.

Theo ví dụ trên, phần dữ liệu tĩnh trong RAM là khoảng: 

RAM static usage = .data + .bss
                 = 4 KB + 16 KB
                 = 20 KB

Phần Flash sử dụng cho các section đang xét có thể ước lượng: 

Flash usage = .text + .rodata + .data load image
            = 72 KB + 12 KB + 4 KB
            = 88 KB

Khi phân tích Map File thực tế, cần kiểm tra cả các section khác như Vector Table, initialization data, metadata, boot information và các vùng dành riêng.

13. Các công cụ hỗ trợ kiểm tra Memory Layout

13.1. readelf

readelf là công cụ có thể sử dụng để kiểm tra thông tin trong file ELF. 

arm-none-eabi-readelf -S firmware.elf

Tùy chọn -S hiển thị thông tin các section, bao gồm tên, kích thước và thuộc tính.

13.2. objdump

objdump hỗ trợ phân tích cấu trúc file object hoặc executable. 

arm-none-eabi-objdump -h firmware.elf

Tùy chọn -h hiển thị thông tin các section. Có thể sử dụng thêm tùy chọn disassembly khi cần kiểm tra mã máy của chương trình.

13.3. nm

nm được dùng để liệt kê symbol trong Object File hoặc file ELF. 

arm-none-eabi-nm -n firmware.elf

Lệnh trên giúp hiển thị symbol theo thứ tự địa chỉ tăng dần, hữu ích khi kiểm tra các symbol như:

  • Reset_Handler
  • _sdata
  • _edata
  • _sidata
  • _sbss
  • _ebss
  • __StackTop

13.4. So sánh các công cụ

Công cụ Mục đích sử dụng
Map File Xem tổng quan bố trí section và symbol sau khi Link.
readelf Phân tích section, segment và thông tin ELF.
objdump Kiểm tra section, disassembly và thông tin Object File.
nm Liệt kê và kiểm tra symbol.

14. Các lỗi thường gặp liên quan đến Linker và Startup

14.1. Undefined Reference

Lỗi Undefined Reference xảy ra khi Linker không tìm thấy định nghĩa của một symbol đang được tham chiếu. 

/* main.c */

extern void sensor_init(void);

int main(void)
{
    sensor_init();

    return 0;
}

Nếu project không cung cấp implementation của sensor_init() hoặc file chứa implementation không được đưa vào quá trình Link, Linker có thể báo lỗi Undefined Reference.

14.2. Multiple Definition

Lỗi Multiple Definition xảy ra khi nhiều Object File cùng định nghĩa một symbol không được phép có nhiều định nghĩa theo cách sử dụng đó.

Ví dụ, khai báo một biến global trong header mà không sử dụng extern có thể dẫn đến nhiều định nghĩa khi header được include ở nhiều source file.

14.3. Region RAM Overflowed

Lỗi này xảy ra khi tổng lượng dữ liệu mà Linker bố trí vượt quá dung lượng vùng RAM được khai báo.

Một số nguyên nhân thường gặp:

  • Có quá nhiều biến global hoặc static.
  • Khai báo buffer kích thước lớn.
  • Stack hoặc Heap được dành dung lượng quá lớn.
  • Vùng RAM bị giới hạn nhưng project sử dụng nhiều dữ liệu hơn dự kiến.

14.4. Region FLASH Overflowed

Lỗi này xuất hiện khi chương trình hoặc dữ liệu cần lưu trong Flash vượt quá dung lượng được khai báo.

Nguyên nhân có thể là:

  • Code size quá lớn.
  • Có nhiều constant data hoặc lookup table.
  • Link thêm Library không cần thiết.
  • Các section đặc biệt chiếm nhiều dung lượng.
  • Vùng Flash bị chia sẻ với Bootloader hoặc khu vực dữ liệu riêng.

14.5. Startup không khởi tạo đúng .data hoặc .bss

Nếu các symbol trong Linker Script không trùng với những symbol được Startup Code sử dụng, quá trình copy hoặc zero initialization có thể không hoạt động đúng.

Một số biểu hiện có thể gặp:

  • Biến global có giá trị khác với giá trị khởi tạo mong muốn.
  • Biến global chưa khởi tạo không nhận được giá trị zero.
  • Chương trình gặp lỗi ngay sau reset.
  • Dữ liệu RAM bị ghi sai vùng nhớ.

14.6. Vector Table đặt sai vị trí

Nếu Vector Table không nằm ở địa chỉ mà MCU mong đợi hoặc không được cấu hình đúng theo cơ chế của kiến trúc, CPU có thể không thực thi đúng Reset Handler hoặc không xử lý interrupt như mong muốn.

Khi gặp lỗi khởi động, không nên chỉ kiểm tra source code. Cần kiểm tra đồng thời Linker Script, Vector Table, Startup Code, Memory Map và cấu hình nạp firmware.

15. Linker Script và Startup Code trong thực tế Embedded Project

15.1. Khi sử dụng MCU SDK hoặc Vendor IDE

Trong một project sử dụng SDK hoặc IDE của nhà sản xuất MCU, developer thường không cần tự viết toàn bộ Linker Script hoặc Startup Code từ đầu.

Những thành phần này thường được cung cấp sẵn trong:

  • MCU Startup Package.
  • CMSIS Device Package.
  • Vendor SDK hoặc Hardware Abstraction Library.
  • Project Template do IDE tạo ra.
  • Toolchain support package.

Tuy nhiên, developer vẫn cần hiểu cách chúng hoạt động để có thể đọc cấu hình, kiểm tra lỗi và điều chỉnh khi project có yêu cầu đặc biệt.

15.2. Khi sử dụng Bootloader

Một số hệ thống Embedded có Bootloader nằm ở một vùng Flash riêng. Application Firmware sẽ được đặt tại một địa chỉ khác thay vì địa chỉ bắt đầu mặc định của Flash.

Ví dụ minh họa: 

Flash Start       : 0x08000000
Bootloader Region : 0x08000000 - 0x08007FFF
Application Start : 0x08008000

Khi đó, Linker Script của Application phải được cấu hình để bố trí Vector Table và các section theo vùng nhớ dành cho Application.

Ngoài ra, Bootloader và Application cần tuân thủ cùng một quy ước về cách chuyển quyền điều khiển, Stack Pointer và vị trí Vector Table.

Các địa chỉ trong ví dụ chỉ mang tính minh họa. Cấu hình thực tế phải tuân theo memory layout, boot configuration và yêu cầu bảo vệ bộ nhớ của MCU.

15.3. Khi sử dụng RTOS

Trong hệ thống sử dụng RTOS, ngoài Main Stack hoặc Stack ban đầu của hệ thống, mỗi Task thường có Stack riêng.

Do đó, việc tính toán bộ nhớ cần xem xét:

  • System hoặc Main Stack.
  • Stack của từng Task.
  • RTOS object và control block.
  • Heap hoặc Memory Pool theo cấu hình RTOS.
  • Global và static data của các module.
  • Buffer phục vụ communication và peripheral.

Linker Script quản lý cách bố trí các section tĩnh, trong khi RTOS có thể quản lý một phần bộ nhớ runtime thông qua cơ chế cấp phát riêng.

16. Best Practices khi làm việc với Linker Script và Startup Code

Một số nguyên tắc hữu ích khi phát triển và bảo trì firmware:

  1. Luôn kiểm tra Memory Map của MCU: Không sử dụng địa chỉ Flash hoặc RAM theo phỏng đoán. Cần đối chiếu với datasheet và reference manual.
  2. Hiểu Linker Script đang sử dụng: Nắm được các vùng nhớ, section và symbol chính.
  3. Kiểm tra LMA và VMA: Đặc biệt quan trọng với section .data và các vùng cần sao chép khi khởi động.
  4. Không tùy tiện thay đổi Startup Code: Những thay đổi không đúng có thể ảnh hưởng đến quá trình khởi tạo bộ nhớ và runtime.
  5. Kiểm tra Vector Table: Đảm bảo vị trí và cách bố trí đúng với architecture.
  6. Sử dụng Map File: Theo dõi mức sử dụng Flash và RAM sau mỗi lần build quan trọng.
  7. Kiểm tra Stack và Heap: Đánh giá dung lượng cần thiết theo workload thực tế.
  8. Sử dụng ASSERT khi phù hợp: Phát hiện sớm tình trạng vượt giới hạn vùng nhớ trong quá trình Link.
  9. Chú ý Bootloader: Đảm bảo Application được Link vào đúng vùng nhớ mà hệ thống quy định.
  10. Ưu tiên cấu hình đã được nhà sản xuất kiểm chứng: Khi sử dụng Vendor SDK, nên hiểu và điều chỉnh trên cơ sở cấu hình chính thức thay vì tự thay thế toàn bộ startup environment.

17. Tổng kết

Trong bài học này, chúng ta đã tìm hiểu quá trình Link và cách firmware được bố trí vào Flash và RAM trước khi chương trình bắt đầu chạy.

Khái niệm Ý nghĩa
Linker Kết hợp Object File, giải quyết symbol và bố trí các section của chương trình.
Object File File trung gian chứa code, data, symbol và thông tin cần thiết cho quá trình Link.
Section Vùng nội dung trong Object File hoặc Executable, chẳng hạn .text, .data và .bss.
Memory Map Mô tả không gian địa chỉ và các vùng nhớ của hệ thống.
Linker Script Quy định cách Linker đặt các section vào những vùng nhớ cụ thể.
LMA Địa chỉ nạp hoặc lưu nội dung ban đầu của section.
VMA Địa chỉ sử dụng của section khi chương trình chạy.
Startup Code Chuẩn bị môi trường thực thi trước khi gọi main().
Vector Table Chứa thông tin địa chỉ phục vụ reset, exception và interrupt theo kiến trúc MCU.
Reset Handler Routine khởi động ban đầu của firmware.
Memory Initialization Sao chép .data và đưa .bss về zero trước khi chương trình sử dụng các biến tương ứng.
Map File Báo cáo cách Linker bố trí section và symbol sau quá trình Link.

Có thể tóm tắt mối liên hệ giữa các thành phần như sau:

  • Compiler: chuyển Source Code thành Object File.
  • Linker: kết hợp Object File và bố trí các Section.
  • Linker Script: quy định cách bố trí chương trình vào Memory Map.
  • Startup Code: chuẩn bị bộ nhớ và runtime environment khi MCU khởi động.
  • main(): điểm bắt đầu của logic ứng dụng C sau các bước khởi tạo cần thiết.
Ghi nhớ: Trong Embedded Systems, việc chương trình biên dịch thành công chưa có nghĩa là firmware đã được bố trí bộ nhớ đúng cách hoặc có thể khởi động chính xác. Cần kiểm tra đồng thời Linker Script, Memory Map, Startup Code và kết quả Link.
