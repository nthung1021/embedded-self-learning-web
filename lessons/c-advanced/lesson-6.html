Bài 6: Dynamic Memory Allocation

Trong ngôn ngữ C, bộ nhớ không nhất thiết phải được xác định hoàn toàn tại thời điểm biên dịch. Chương trình có thể yêu cầu thêm bộ nhớ trong quá trình thực thi để lưu trữ dữ liệu có kích thước thay đổi hoặc tạo các đối tượng chỉ cần tồn tại trong một khoảng thời gian nhất định.

Cơ chế này được gọi là Dynamic Memory Allocation. Đây là kỹ thuật cho phép chương trình chủ động yêu cầu và giải phóng bộ nhớ trong Runtime, thông thường thông qua các hàm thư viện như malloc(), calloc(), realloc() và free().

Đối với Embedded Systems, Dynamic Memory Allocation mang lại khả năng quản lý dữ liệu linh hoạt hơn. Tuy nhiên, việc sử dụng bộ nhớ động cần được kiểm soát cẩn thận vì các vi điều khiển thường có RAM giới hạn, đồng thời các yêu cầu về tính ổn định và thời gian thực thi có thể rất chặt chẽ.

Bài học này tập trung vào cách sử dụng các hàm Dynamic Memory Allocation trong C, cách quản lý vùng nhớ được cấp phát và những nguyên tắc cần lưu ý. Các vấn đề Memory Leak, Dangling Pointer, Double Free và Memory Safety sẽ được phân tích riêng ở Bài 7.

1. Dynamic Memory Allocation là gì?

Dynamic Memory Allocation là cơ chế cho phép chương trình yêu cầu một vùng nhớ có kích thước xác định trong quá trình thực thi, thay vì phải xác định toàn bộ vùng nhớ ngay từ thời điểm khai báo biến.

Trong C, các hàm cấp phát bộ nhớ động được cung cấp thông qua Header File <stdlib.h>. Bốn hàm quan trọng nhất bao gồm:

  • malloc(): cấp phát một vùng nhớ với kích thước được yêu cầu.
  • calloc(): cấp phát vùng nhớ cho nhiều phần tử và thiết lập tất cả bit của vùng nhớ bằng 0.
  • realloc(): thay đổi kích thước vùng nhớ đã được cấp phát trước đó.
  • free(): giải phóng vùng nhớ được cấp phát động.

Những vùng nhớ này thường được quản lý bởi một thành phần gọi là Memory Allocator. Trong cách triển khai phổ biến, Memory Allocator quản lý một vùng Heap và cung cấp bộ nhớ theo yêu cầu của chương trình.

Khi chương trình gọi một hàm cấp phát bộ nhớ, Memory Allocator sẽ xử lý yêu cầu và trả về địa chỉ của vùng nhớ nếu cấp phát thành công. Nếu không thể đáp ứng yêu cầu, hàm cấp phát thường trả về Null Pointer.

Trong ngôn ngữ C, các hàm cấp phát động thuộc thư viện chuẩn. Vùng nhớ được quản lý bởi những hàm này được gọi là Allocated Storage. Heap là cách triển khai phổ biến trong nhiều hệ thống, nhưng cách tổ chức thực tế của Memory Allocator phụ thuộc vào nền tảng.

2. Static Allocation vs Dynamic Allocation

Trước khi đi vào các hàm cụ thể, cần phân biệt hai phương pháp quản lý bộ nhớ phổ biến: Static Allocation và Dynamic Allocation.

2.1. Static Memory Allocation

Static Allocation là cách tổ chức bộ nhớ mà kích thước và vị trí lưu trữ của các đối tượng được xác định trước khi chương trình thực thi hoặc theo cơ chế tự động của Function.

Ví dụ: 

#include <stdint.h>

#define BUFFER_SIZE 100U

int main(void)
{
    uint8_t buffer[BUFFER_SIZE];

    /* Sử dụng Buffer */

    return 0;
}

Trong ví dụ trên, kích thước mảng buffer được xác định bằng một hằng số tại thời điểm biên dịch. Bộ nhớ cần thiết không phải được yêu cầu thông qua malloc() trong quá trình chạy.

2.2. Dynamic Memory Allocation

Ngược lại, Dynamic Allocation cho phép xác định kích thước vùng nhớ dựa trên dữ liệu có được trong Runtime. 

#include <stdint.h>
#include <stdlib.h>

int main(void)
{
    uint32_t buffer_size = 100U;

    uint8_t *buffer = malloc(buffer_size * sizeof(uint8_t));

    if (buffer == NULL)
    {
        return 1;
    }

    /* Sử dụng Buffer */

    free(buffer);

    return 0;
}

Trong trường hợp này, kích thước cấp phát được xác định thông qua biến buffer_size khi chương trình đang chạy.

3. malloc() – Memory Allocation

malloc() (Memory Allocation) là hàm được sử dụng để cấp phát một vùng nhớ có kích thước xác định trong Runtime.

Hàm được khai báo trong thư viện <stdlib.h> với Prototype: 

void *malloc(size_t size);

Trong đó:

  • size: số lượng Byte cần cấp phát.
  • Giá trị trả về: Pointer đến vùng nhớ được cấp phát nếu thành công.
  • Nếu không thể cấp phát, hàm trả về NULL.
  • Nội dung của vùng nhớ mới cấp phát không được khởi tạo.

3.1. Cách sử dụng malloc()

Ví dụ cấp phát bộ nhớ để lưu một biến kiểu int: 

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *data = malloc(sizeof(int));

    if (data == NULL)
    {
        printf("Memory allocation failed!\n");
        return 1;
    }

    *data = 100;

    printf("Value: %d\n", *data);

    free(data);

    return 0;
}

Giải thích:

  1. sizeof(int) xác định số Byte cần thiết để lưu một biến kiểu int.
  2. malloc() yêu cầu cấp phát vùng nhớ có kích thước tương ứng.
  3. Địa chỉ trả về được lưu trong Pointer data.
  4. Kiểm tra data == NULL để xác nhận cấp phát thành công.
  5. *data = 100 ghi giá trị vào vùng nhớ được cấp phát.
  6. free(data) giải phóng vùng nhớ khi không còn cần sử dụng.

3.2. Cấp phát Array bằng malloc()

Một ứng dụng phổ biến của malloc() là cấp phát bộ nhớ để lưu một mảng có kích thước được xác định trong Runtime. 

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    size_t count = 5U;

    int *numbers = malloc(count * sizeof(int));

    if (numbers == NULL)
    {
        return 1;
    }

    /* Khởi tạo các phần tử */
    for (size_t i = 0U; i < count; i++)
    {
        numbers[i] = (int)(i * 10U);
    }

    /* Hiển thị dữ liệu */
    for (size_t i = 0U; i < count; i++)
    {
        printf("%d\n", numbers[i]);
    }

    free(numbers);

    return 0;
}

Trong ví dụ trên, chương trình yêu cầu một vùng nhớ đủ để lưu năm phần tử kiểu int.

Biểu thức: 

count * sizeof(int)

được sử dụng để tính tổng số Byte cần thiết. Khi cấp phát thành công, vùng nhớ có thể được truy cập thông qua Pointer numbers như một mảng thông thường.

3.3. Vì sao nên sử dụng sizeof(*pointer)?

Ngoài cách sử dụng sizeof(int), lập trình viên thường sử dụng sizeof(*pointer) để xác định kích thước của kiểu dữ liệu mà Pointer đang trỏ đến. 

int *numbers = malloc(count * sizeof(*numbers));

Ưu điểm của cách viết này là khi kiểu dữ liệu của Pointer thay đổi, biểu thức sizeof(*numbers) vẫn tự động phản ánh đúng kích thước kiểu dữ liệu mới.

Ví dụ: 

uint32_t *sensor_values;

sensor_values = malloc(10U * sizeof(*sensor_values));

Trong trường hợp này, chương trình tự xác định kích thước mỗi phần tử theo kiểu uint32_t.

3.4. malloc() không tự khởi tạo dữ liệu

Một điểm quan trọng cần ghi nhớ là malloc() chỉ yêu cầu cấp phát bộ nhớ, không thiết lập giá trị ban đầu cho các phần tử của vùng nhớ đó. 

int *data = malloc(5U * sizeof(*data));

if (data != NULL)
{
    /*
     * Không được giả định các phần tử
     * đã có giá trị bằng 0.
     */

    data[0] = 10;
    data[1] = 20;

    free(data);
}

Trước khi đọc giá trị của những phần tử được cấp phát, chương trình cần ghi các giá trị hợp lệ vào chúng. Việc đọc một giá trị chưa được khởi tạo có thể dẫn đến hành vi không xác định hoặc kết quả không mong muốn tùy trường hợp.

Ghi nhớ: malloc() cấp phát bộ nhớ nhưng không khởi tạo nội dung của vùng nhớ. Vì vậy, lập trình viên phải chủ động khởi tạo dữ liệu trước khi sử dụng.

4. calloc() – Contiguous Allocation

calloc() là một hàm cấp phát bộ nhớ động khác trong thư viện chuẩn C. Điểm khác biệt quan trọng của calloc() so với malloc() là nó cấp phát bộ nhớ cho một số lượng phần tử và thiết lập toàn bộ các bit của vùng nhớ được cấp phát bằng 0.

Prototype: 

void *calloc(size_t num, size_t size);

Trong đó:

  • num: số lượng phần tử cần cấp phát.
  • size: kích thước của mỗi phần tử tính bằng Byte.
  • Tổng dung lượng bộ nhớ được yêu cầu tương ứng với num * size.
  • Nếu cấp phát thất bại, hàm trả về NULL.
  • Toàn bộ vùng nhớ được cấp phát có giá trị tất cả bit bằng 0.

4.1. Cách sử dụng calloc()

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    size_t count = 5U;

    int *numbers = calloc(count, sizeof(*numbers));

    if (numbers == NULL)
    {
        printf("Memory allocation failed!\n");
        return 1;
    }

    /* Các phần tử đã được zero-initialized
       theo biểu diễn all-bits-zero của calloc. */

    for (size_t i = 0U; i < count; i++)
    {
        printf("%d\n", numbers[i]);
    }

    free(numbers);

    return 0;
}

Trong ví dụ trên, chương trình cấp phát bộ nhớ cho năm phần tử kiểu int. Các Byte trong vùng nhớ được thiết lập về 0 trước khi chương trình sử dụng.

Ứng dụng Cấp phát bộ nhớ khi chương trình tự khởi tạo dữ liệu. Cấp phát bộ nhớ khi cần vùng nhớ có nội dung ban đầu bằng 0 theo biểu diễn bit.

4.3. Khi nào nên sử dụng calloc()?

calloc() có thể hữu ích khi cần cấp phát một vùng nhớ cho nhiều phần tử và muốn thiết lập ban đầu tất cả các Byte bằng 0.

Ví dụ, một chương trình cần tạo mảng lưu số lần xuất hiện của các sự kiện: 

#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>

int main(void)
{
    size_t event_count = 8U;

    uint32_t *event_counters =
        calloc(event_count, sizeof(*event_counters));

    if (event_counters == NULL)
    {
        return 1;
    }

    /* Ghi nhận một số sự kiện */
    event_counters[0]++;
    event_counters[2]++;
    event_counters[2]++;

    for (size_t i = 0U; i < event_count; i++)
    {
        printf("Event %zu: %u\n",
               i, event_counters[i]);
    }

    free(event_counters);

    return 0;
}

Trong ví dụ này, các phần tử ban đầu có biểu diễn all-bits-zero, phù hợp với biểu diễn số nguyên không dấu có giá trị 0 trên các nền tảng thông dụng. Sau đó, chương trình có thể tăng bộ đếm cho từng loại sự kiện.

Về mặt chuẩn C, calloc() thiết lập toàn bộ bit của vùng nhớ bằng 0. Điều này không đồng nghĩa với việc mọi kiểu dữ liệu trong C đều được bảo đảm có giá trị ngữ nghĩa bằng 0 khi biểu diễn bằng all-bits-zero. Với các kiểu số nguyên thông dụng trên MCU, biểu diễn này tương ứng với 0; nhưng cần thận trọng khi làm việc với Pointer và các kiểu dữ liệu đặc biệt.

5. realloc() – Reallocation Memory

Trong một số trường hợp, chương trình cần thay đổi kích thước vùng nhớ đã cấp phát trước đó. Ví dụ, một Buffer ban đầu được cấp phát với kích thước nhỏ, nhưng sau đó cần mở rộng để chứa thêm dữ liệu.

Hàm realloc() được sử dụng để thay đổi kích thước của một vùng nhớ đã được cấp phát động.

Prototype:

void *realloc(void *ptr, size_t new_size);

Trong đó:

  • ptr: Pointer đến vùng nhớ đã được cấp phát trước đó hoặc NULL.
  • new_size: kích thước mới cần yêu cầu.
  • Hàm trả về Pointer đến vùng nhớ sau khi thay đổi kích thước thành công.
  • Nếu yêu cầu thất bại với kích thước khác 0, hàm trả về NULL và vùng nhớ ban đầu vẫn còn hiệu lực.

5.1. Cách sử dụng realloc()

Ví dụ, chương trình ban đầu cấp phát một Array gồm năm phần tử, sau đó thay đổi kích thước để lưu mười phần tử. 

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    size_t old_count = 5U;
    size_t new_count = 10U;

    int *numbers = malloc(old_count * sizeof(*numbers));

    if (numbers == NULL)
    {
        return 1;
    }

    /* Khởi tạo dữ liệu ban đầu */
    for (size_t i = 0U; i < old_count; i++)
    {
        numbers[i] = (int)i;
    }

    /* Thay đổi kích thước vùng nhớ */
    int *temp = realloc(
        numbers,
        new_count * sizeof(*numbers)
    );

    if (temp == NULL)
    {
        /*
         * Cấp phát thất bại.
         * numbers vẫn còn hợp lệ.
         */
        free(numbers);
        return 1;
    }

    numbers = temp;

    /* Khởi tạo những phần tử mới */
    for (size_t i = old_count; i < new_count; i++)
    {
        numbers[i] = (int)i;
    }

    /* Hiển thị toàn bộ dữ liệu */
    for (size_t i = 0U; i < new_count; i++)
    {
        printf("%d\n", numbers[i]);
    }

    free(numbers);

    return 0;
}

Trong ví dụ trên, vùng nhớ ban đầu có thể được mở rộng ngay tại vị trí cũ hoặc được chuyển sang một vùng nhớ mới, tùy thuộc vào Memory Allocator.

5.2. Khi tăng kích thước bộ nhớ

Khi yêu cầu kích thước mới lớn hơn kích thước cũ, realloc() cố gắng cung cấp một vùng nhớ đủ lớn để chứa dữ liệu mới.

Nếu cấp phát thành công:

  • Nội dung cũ được bảo toàn trong phạm vi kích thước nhỏ hơn giữa vùng cũ và vùng mới.
  • Vùng nhớ có thể được mở rộng tại địa chỉ cũ hoặc chuyển sang địa chỉ mới.
  • Phần dung lượng tăng thêm không được khởi tạo.
  • Pointer trả về cần được sử dụng để tham chiếu đến vùng nhớ sau khi cấp phát lại.

5.3. Khi giảm kích thước bộ nhớ

Nếu kích thước mới nhỏ hơn kích thước cũ, realloc() có thể thu nhỏ vùng nhớ. 

size_t old_count = 10U;
size_t new_count = 5U;

int *numbers = malloc(old_count * sizeof(*numbers));

if (numbers != NULL)
{
    /* Sử dụng 10 phần tử */

    int *temp = realloc(
        numbers,
        new_count * sizeof(*numbers)
    );

    if (temp != NULL)
    {
        numbers = temp;

        /* Tiếp tục sử dụng 5 phần tử */
    }

    free(numbers);
}

Khi thu nhỏ bộ nhớ, chỉ phần dữ liệu nằm trong phạm vi kích thước mới được bảo toàn. Những phần dữ liệu nằm ngoài phạm vi này không còn thuộc vùng nhớ được cấp phát sau khi thao tác thành công.

5.4. realloc() có thể di chuyển vùng nhớ

Một đặc điểm rất quan trọng của realloc() là địa chỉ vùng nhớ sau khi cấp phát lại có thể khác địa chỉ ban đầu.

Nếu Memory Allocator không thể mở rộng Block tại vị trí cũ, nó có thể cấp phát một vùng mới, sao chép dữ liệu cũ sang vùng mới, sau đó giải phóng vùng nhớ cũ.

Vì vậy, khi sử dụng realloc(), không nên giả định Pointer cũ vẫn luôn tham chiếu đến vị trí hợp lệ. Sau khi cấp phát lại thành công, cần sử dụng Pointer mới trả về.

Sau khi realloc() thành công, cần xem vùng nhớ cũ đã được thay thế. Những Pointer hoặc địa chỉ phụ từng trỏ vào vùng nhớ cũ không nên tiếp tục được sử dụng. Hãy cập nhật tất cả các tham chiếu liên quan theo thiết kế của chương trình.

6. free() – Releasing Allocated Memory

free() là hàm được sử dụng để giải phóng vùng nhớ đã được cấp phát động trước đó.

Prototype: 

void free(void *ptr);

Khi vùng nhớ không còn cần thiết, chương trình nên gọi free() để thông báo cho Memory Allocator rằng vùng nhớ đó có thể được sử dụng lại.

6.1. Cách sử dụng free()

#include <stdlib.h>

int main(void)
{
    int *data = malloc(10U * sizeof(*data));

    if (data == NULL)
    {
        return 1;
    }

    /* Sử dụng vùng nhớ */

    data[0] = 100;

    /* Giải phóng vùng nhớ */
    free(data);

    return 0;
}

Sau khi gọi free(data), vùng nhớ được cấp phát trước đó đã được trả lại cho Memory Allocator để có thể phục vụ những yêu cầu cấp phát khác.

Tuy nhiên, việc gọi free() không nhất thiết có nghĩa hệ thống sẽ lập tức trả vùng nhớ vật lý đó về cho hệ điều hành hoặc hệ thống phần cứng. Điều này phụ thuộc vào cách Memory Allocator quản lý vùng nhớ.

6.2. free(NULL)

Một đặc điểm hữu ích của hàm free() là có thể truyền Null Pointer vào hàm mà không gây ra lỗi. 

int *data = NULL;

free(data);

/*
 * free(NULL) không thực hiện thao tác giải phóng.
 * Có thể sử dụng an toàn.
 */

Điều này giúp đơn giản hóa một số đoạn mã quản lý bộ nhớ, đặc biệt khi Pointer được khởi tạo bằng NULL trước khi cấp phát.

6.3. Vì sao cần giải phóng bộ nhớ?

Nếu chương trình liên tục cấp phát bộ nhớ mà không giải phóng những vùng nhớ không còn sử dụng, lượng bộ nhớ khả dụng có thể giảm dần.

Điều này đặc biệt nguy hiểm đối với các hệ thống Embedded cần hoạt động trong thời gian dài.

Ví dụ: 

void process_data(void)
{
    int *buffer = malloc(100U * sizeof(*buffer));

    if (buffer == NULL)
    {
        return;
    }

    /* Xử lý dữ liệu */

    free(buffer);
}

Trong ví dụ trên, vùng nhớ được giải phóng khi Function hoàn thành công việc xử lý.

Việc gọi free() chỉ giải phóng vùng nhớ đã cấp phát động. Nó không tự động kết thúc Storage Duration của các biến Pointer hoặc những đối tượng khác đang tham chiếu đến vùng nhớ đó.

7. Quy trình sử dụng Dynamic Memory Allocation

Trong một chương trình C, việc cấp phát và giải phóng bộ nhớ động thường được thực hiện theo một quy trình có thứ tự.

Quy trình sử dụng cơ bản:

  1. Request Memory: yêu cầu cấp phát một vùng nhớ với kích thước phù hợp.
  2. Check Allocation Result: kiểm tra Pointer trả về để xác định cấp phát thành công hay thất bại.
  3. Initialize and Use: khởi tạo các phần tử cần thiết và sử dụng vùng nhớ.
  4. Finish Using Memory: xác định thời điểm chương trình không còn cần vùng nhớ.
  5. Release Memory: gọi free() để giải phóng vùng nhớ.

8. Kiểm tra lỗi khi cấp phát bộ nhớ

Một trong những nguyên tắc quan trọng khi sử dụng Dynamic Memory Allocation là luôn kiểm tra kết quả trả về của các hàm cấp phát.

Khi không đủ bộ nhớ hoặc không đáp ứng được yêu cầu, các hàm như malloc(), calloc() và realloc() có thể trả về NULL.

8.1. Không sử dụng Pointer trước khi kiểm tra NULL

Ví dụ không nên sử dụng: 

int *data = malloc(100U * sizeof(*data));

/* Không kiểm tra kết quả cấp phát */
data[0] = 100;

Nếu cấp phát thất bại, data sẽ là NULL. Việc truy cập data[0] trong trường hợp này sẽ dẫn đến hành vi không xác định.

8.2. Cách kiểm tra đúng

int *data = malloc(100U * sizeof(*data));

if (data == NULL)
{
    /* Xử lý lỗi cấp phát */

    return 1;
}

/* Chỉ sử dụng sau khi xác nhận thành công */
data[0] = 100;

free(data);

Với các hệ thống Embedded, lỗi cấp phát cần được xử lý theo chiến lược phù hợp với chức năng của hệ thống. Không nên mặc định rằng việc cấp phát bộ nhớ luôn thành công.

8.3. Xử lý lỗi khi sử dụng realloc()

Khi làm việc với realloc(), cần đặc biệt chú ý đến cách quản lý Pointer.

Một lỗi phổ biến là ghi đè trực tiếp Pointer ban đầu bằng kết quả trả về của realloc(). 

int *data = malloc(5U * sizeof(*data));

if (data != NULL)
{
    /* Cách viết không an toàn khi realloc thất bại */
    data = realloc(data, 10U * sizeof(*data));
}

Nếu realloc() thất bại với kích thước khác 0, hàm trả về NULL nhưng vùng nhớ ban đầu vẫn còn được cấp phát. Khi ghi đè Pointer ban đầu, chương trình sẽ mất địa chỉ của vùng nhớ đó và không thể giải phóng thông qua Pointer đã bị ghi đè.

Cách viết an toàn hơn là sử dụng một Temporary Pointer: 

int *data = malloc(5U * sizeof(*data));

if (data == NULL)
{
    return 1;
}

int *temp = realloc(data, 10U * sizeof(*data));

if (temp == NULL)
{
    /*
     * data vẫn còn hợp lệ.
     * Có thể tiếp tục sử dụng hoặc giải phóng.
     */

    free(data);

    return 1;
}

/* Cập nhật Pointer sau khi thành công */
data = temp;

free(data);
Nguyên tắc quan trọng: Khi sử dụng realloc(), hãy lưu kết quả vào một Temporary Pointer. Chỉ cập nhật Pointer ban đầu sau khi xác nhận cấp phát lại thành công.

9. Safe Memory Allocation Techniques

Ngoài việc kiểm tra NULL, lập trình viên cần chú ý đến kích thước bộ nhớ được yêu cầu cấp phát. Một phép tính kích thước không hợp lệ có thể khiến chương trình cấp phát ít bộ nhớ hơn nhu cầu thực tế.

9.1. Kiểm tra phép tính kích thước

Khi cấp phát Array, kích thước thường được tính bằng: 

number_of_elements * sizeof(element_type)

Tuy nhiên, nếu số lượng phần tử quá lớn, phép nhân có thể vượt quá phạm vi biểu diễn của kiểu size_t. Điều này được gọi là Integer Overflow trong phép tính kích thước.

Để hạn chế vấn đề này, có thể kiểm tra trước khi nhân: 

#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdint.h>

int main(void)
{
    size_t count = 100U;

    int *data = NULL;

    /* Kiểm tra phép nhân có thể vượt SIZE_MAX */
    if (count > SIZE_MAX / sizeof(*data))
    {
        printf("Requested size is too large!\n");
        return 1;
    }

    data = malloc(count * sizeof(*data));

    if (data == NULL)
    {
        printf("Allocation failed!\n");
        return 1;
    }

    /* Sử dụng bộ nhớ */

    free(data);

    return 0;
}

Trong ví dụ trên:

  • SIZE_MAX là giá trị lớn nhất mà kiểu size_t có thể biểu diễn.
  • sizeof(*data) xác định kích thước của một phần tử.
  • Phép chia giúp kiểm tra trước khi thực hiện phép nhân.
  • Nếu kích thước yêu cầu không hợp lệ, chương trình từ chối cấp phát.

9.2. Không cấp phát kích thước bằng 0 nếu không cần thiết

Khi sử dụng các hàm cấp phát động, nên xác định rõ cách xử lý khi số lượng phần tử bằng 0. 

size_t count = 0U;

if (count == 0U)
{
    /* Không cần cấp phát */
    return 0;
}

Điều này giúp tránh các trường hợp khó kiểm soát khi sử dụng malloc(0), calloc() với kích thước bằng 0 hoặc realloc() với kích thước mới bằng 0.

Hành vi của một số trường hợp cấp phát kích thước 0 phụ thuộc vào quy định của phiên bản C và cách triển khai thư viện. Vì vậy, thiết kế chương trình nên xử lý riêng trường hợp không cần bộ nhớ.

9.3. Khởi tạo dữ liệu sau khi malloc()

Nếu chương trình sử dụng malloc(), cần bảo đảm các phần tử được khởi tạo trước khi đọc. 

int *numbers = malloc(5U * sizeof(*numbers));

if (numbers == NULL)
{
    return 1;
}

/* Initialize values */
for (size_t i = 0U; i < 5U; i++)
{
    numbers[i] = 0;
}

/* Có thể đọc và sử dụng sau khi khởi tạo */
printf("%d\n", numbers[0]);

free(numbers);

9.4. Sử dụng kiểu dữ liệu phù hợp

Khi xử lý kích thước bộ nhớ, nên sử dụng kiểu size_t thay vì những kiểu số nguyên có kích thước cố định như int để biểu diễn số Byte hoặc số lượng phần tử. 

#include <stddef.h>
#include <stdint.h>

size_t buffer_size = 256U;

uint8_t *buffer = malloc(buffer_size * sizeof(*buffer));

size_t là kiểu dữ liệu không dấu được sử dụng để biểu diễn kích thước đối tượng và các giá trị liên quan đến kích thước bộ nhớ.

10. Tổng hợp bốn hàm Dynamic Memory Allocation

Sau khi tìm hiểu từng hàm, chúng ta có thể tổng hợp chức năng và đặc điểm của chúng trong bảng sau:

Function Chức năng Khởi tạo dữ liệu Trường hợp sử dụng
malloc() Cấp phát một vùng nhớ theo số Byte. Không khởi tạo. Khi cần bộ nhớ và chương trình tự ghi dữ liệu ban đầu.
calloc() Cấp phát bộ nhớ cho nhiều phần tử. Thiết lập tất cả bit bằng 0. Khi cần cấp phát mảng và yêu cầu nội dung ban đầu all-bits-zero.
realloc() Thay đổi kích thước vùng nhớ đã cấp phát. Giữ lại phần dữ liệu cũ phù hợp; vùng mở rộng không được khởi tạo. Khi cần tăng hoặc giảm kích thước vùng nhớ.
free() Giải phóng vùng nhớ được cấp phát. Không áp dụng. Khi chương trình không còn cần sử dụng vùng nhớ.

11. Dynamic Memory Allocation trong Embedded Systems

Trong các ứng dụng Embedded, việc sử dụng Dynamic Memory Allocation cần được đánh giá dựa trên yêu cầu phần cứng và đặc điểm của hệ thống.

Khác với máy tính thông thường, nhiều vi điều khiển có dung lượng RAM nhỏ, không có hệ điều hành quản lý bộ nhớ đầy đủ và cần đáp ứng những yêu cầu thời gian thực nhất định.

11.1. Những trường hợp có thể sử dụng Dynamic Allocation

Một số ứng dụng Embedded vẫn có thể sử dụng bộ nhớ động khi cần khả năng quản lý dữ liệu linh hoạt.

  • Variable-size Buffer: tạo Buffer có kích thước phụ thuộc vào dữ liệu nhận được.
  • Communication Data: lưu trữ những dữ liệu giao tiếp có kích thước thay đổi.
  • Complex Data Structure: xây dựng các cấu trúc dữ liệu động khi số lượng phần tử không cố định.
  • RTOS Application: một số RTOS hoặc thư viện hỗ trợ cấp phát bộ nhớ trong Runtime theo những chính sách riêng.
  • High-level Embedded Software: những ứng dụng nhúng có bộ nhớ tương đối lớn và cơ chế quản lý tài nguyên phù hợp.

11.2. Những hạn chế khi sử dụng Heap trong MCU

Hạn chế Ảnh hưởng
Limited RAM Không gian bộ nhớ dành cho cấp phát động có thể rất nhỏ.
Memory Fragmentation Các Block trống bị chia nhỏ sau nhiều lần cấp phát và giải phóng.
Non-deterministic Allocation Time Thời gian cấp phát có thể thay đổi theo trạng thái của Allocator.
Allocation Failure Hệ thống có thể không cấp phát được khi thiếu bộ nhớ.
Memory Management Complexity Cần theo dõi vòng đời của các đối tượng và những Pointer liên quan.
Long-running Operation Những lỗi quản lý bộ nhớ có thể tích lũy và ảnh hưởng đến hoạt động lâu dài.

11.3. Không phải mọi Embedded Compiler đều cung cấp Heap giống nhau

Trong một dự án Embedded, khả năng sử dụng malloc() và các hàm liên quan còn phụ thuộc vào thư viện C được cung cấp bởi Toolchain.

Một số bộ công cụ sử dụng các thư viện C đầy đủ, trong khi một số môi trường Embedded sử dụng phiên bản thư viện rút gọn hoặc cấu hình bộ nhớ riêng.

Đối với một số hệ thống Bare-metal, lập trình viên có thể cần cấu hình vùng Heap hoặc cơ chế cung cấp bộ nhớ cho Allocator. Nếu vùng nhớ không được cấu hình phù hợp, các yêu cầu cấp phát có thể thất bại dù chương trình đã biên dịch thành công.

Khi làm việc với một Target MCU cụ thể, cần kiểm tra tài liệu của Compiler, C Library và cấu hình Linker để xác định cơ chế cấp phát được hỗ trợ.

Việc thư viện chuẩn C có khai báo malloc() không đồng nghĩa với việc mọi dự án Embedded đều có vùng Heap đủ lớn để sử dụng. Khả năng cấp phát thực tế còn phụ thuộc cấu hình Runtime và bộ nhớ của hệ thống.

12. Static Allocation vs Dynamic Allocation trong thực tế Embedded

Trong nhiều dự án Embedded, lập trình viên thường cân nhắc sử dụng Static Allocation thay cho việc cấp phát động liên tục trong Runtime.

Lý do không phải vì Dynamic Allocation luôn không phù hợp, mà vì Static Allocation thường giúp kiểm soát tài nguyên và xác định mức sử dụng bộ nhớ dễ dàng hơn.

12.1. Ví dụ sử dụng Static Buffer

#include <stdint.h>

#define BUFFER_SIZE 256U

static uint8_t receive_buffer[BUFFER_SIZE];

int main(void)
{
    /* Sử dụng receive_buffer */

    return 0;
}

Trong trường hợp này, Buffer được khai báo với kích thước cố định. Không cần thực hiện yêu cầu cấp phát bộ nhớ động trong Runtime.

12.2. Ví dụ sử dụng Dynamic Buffer

#include <stdint.h>
#include <stdlib.h>

int main(void)
{
    size_t buffer_size = 256U;

    uint8_t *receive_buffer =
        malloc(buffer_size * sizeof(*receive_buffer));

    if (receive_buffer == NULL)
    {
        return 1;
    }

    /* Sử dụng receive_buffer */

    free(receive_buffer);

    return 0;
}

Dynamic Buffer cho phép thay đổi kích thước theo yêu cầu. Tuy nhiên, chương trình cần quản lý thời điểm cấp phát, kiểm tra lỗi và giải phóng bộ nhớ.

12.3. Khi nào nên chọn phương pháp nào?

Yêu cầu Phương pháp phù hợp
Kích thước dữ liệu được xác định trước và không thay đổi. Static Allocation.
Cần thời gian xử lý dễ dự đoán. Ưu tiên Static Allocation hoặc Memory Pool có giới hạn rõ ràng.
Kích thước dữ liệu thay đổi trong Runtime. Có thể cân nhắc Dynamic Allocation.
Đối tượng cần tồn tại độc lập với Function tạo ra nó. Dynamic Allocation hoặc một cơ chế lưu trữ có Lifetime phù hợp.
RAM rất hạn chế. Ưu tiên quản lý bộ nhớ cố định và kiểm soát ngân sách RAM.
Hệ thống có Memory Allocator được kiểm thử và quản lý phù hợp. Có thể sử dụng Dynamic Allocation theo chính sách của dự án.

13. Memory Pool – Một giải pháp quản lý bộ nhớ trong Embedded

Khi không muốn sử dụng cấp phát động tổng quát nhưng vẫn cần khả năng lấy và trả bộ nhớ trong Runtime, một giải pháp có thể được cân nhắc là Memory Pool.

Memory Pool là phương pháp quản lý một vùng nhớ đã được chuẩn bị trước, sau đó chia thành các Block có kích thước xác định. Khi chương trình cần bộ nhớ, nó lấy một Block còn trống từ Pool. Khi không còn cần sử dụng, Block được trả lại để có thể tái sử dụng.

13.1. Đặc điểm của Memory Pool

  • Vùng nhớ được chuẩn bị trước.
  • Các Block thường có kích thước cố định.
  • Việc lấy và trả Block có thể được thiết kế với thời gian thực thi dễ dự đoán.
  • Hạn chế nhu cầu cấp phát các vùng nhớ có kích thước tùy ý.
  • Phù hợp với các ứng dụng cần kiểm soát tài nguyên chặt chẽ.

13.2. Ví dụ Memory Pool đơn giản

Ví dụ dưới đây minh họa một Pool gồm bốn Block, mỗi Block có khả năng lưu một phần dữ liệu kiểu uint32_t. 

#include <stdint.h>
#include <stdbool.h>

#define POOL_SIZE 4U

static uint32_t memory_pool[POOL_SIZE];

static bool block_used[POOL_SIZE] = { false };

/* Lấy một Block trống */
int Pool_Allocate(void)
{
    for (uint32_t i = 0U; i < POOL_SIZE; i++)
    {
        if (block_used[i] == false)
        {
            block_used[i] = true;

            return (int)i;
        }
    }

    /* Không còn Block trống */
    return -1;
}

/* Trả Block về Pool */
void Pool_Free(uint32_t index)
{
    if (index < POOL_SIZE)
    {
        block_used[index] = false;
    }
}

int main(void)
{
    int block = Pool_Allocate();

    if (block >= 0)
    {
        memory_pool[(uint32_t)block] = 100U;

        Pool_Free((uint32_t)block);
    }

    return 0;
}

Đây là ví dụ đơn giản để minh họa nguyên lý của Memory Pool. Trong dự án thực tế, cần bổ sung các cơ chế kiểm tra quyền sở hữu, trạng thái Block và đồng bộ hóa nếu Pool được sử dụng từ nhiều Task hoặc nhiều ngữ cảnh thực thi.

Memory Pool không phải là một trong bốn hàm cấp phát động chuẩn của C. Đây là một phương pháp thiết kế bộ quản lý bộ nhớ riêng, có thể được triển khai dựa trên Static Allocation.

14. Những lỗi thường gặp khi sử dụng Dynamic Memory Allocation

Mặc dù các hàm cấp phát bộ nhớ động tương đối đơn giản, việc sử dụng sai có thể gây ra nhiều vấn đề nghiêm trọng trong chương trình C.

Lỗi Nguyên nhân Hướng xử lý
Allocation Failure Không đủ bộ nhớ để cấp phát. Kiểm tra NULL và xử lý lỗi phù hợp.
Incorrect Allocation Size Tính toán sai số lượng Byte cần cấp phát. Sử dụng sizeof và kiểm tra phép tính kích thước.
Uninitialized Memory Đọc dữ liệu sau malloc() khi chưa khởi tạo. Khởi tạo các phần tử trước khi sử dụng.
Lost Pointer after realloc() Ghi đè Pointer gốc khi realloc thất bại. Sử dụng Temporary Pointer.
Memory Fragmentation Cấp phát và giải phóng các Block với kích thước không phù hợp. Kiểm soát Heap hoặc sử dụng Memory Pool.
Unnecessary Allocation Cấp phát nhiều vùng nhớ không thực sự cần thiết. Đánh giá lại thiết kế và tái sử dụng Buffer.

14.1. Không kiểm tra NULL

int *data = malloc(100U * sizeof(*data));

/* Sai: sử dụng khi chưa kiểm tra cấp phát */
data[0] = 10;

Cần kiểm tra Pointer trước khi sử dụng vùng nhớ. Nếu cấp phát thất bại, chương trình phải xử lý lỗi thay vì tiếp tục thao tác với Pointer không hợp lệ.

14.2. Không giải phóng bộ nhớ sau khi sử dụng

void process_data(void)
{
    int *data = malloc(100U * sizeof(*data));

    if (data == NULL)
    {
        return;
    }

    /* Xử lý dữ liệu */

    /* Cần có free(data) khi không còn sử dụng */
}

Việc không giải phóng vùng nhớ có thể làm lượng Heap khả dụng giảm dần theo thời gian. Vấn đề này sẽ được phân tích chi tiết ở Bài 7: Memory Leakage, Dangling Pointer & Memory Safety.

14.3. Ghi đè Pointer khi realloc thất bại

data = realloc(data, new_size);

Nếu yêu cầu cấp phát lại thất bại, chương trình có thể mất địa chỉ vùng nhớ ban đầu do đã ghi đè Pointer.

Nên sử dụng Temporary Pointer và chỉ cập nhật biến ban đầu sau khi xác nhận thành công.

14.4. Sử dụng Heap không phù hợp với yêu cầu hệ thống

Việc cấp phát và giải phóng bộ nhớ liên tục trong một hệ thống thời gian thực có thể làm thay đổi thời gian xử lý và mức sử dụng RAM.

Trước khi sử dụng Dynamic Allocation, cần đánh giá khả năng đáp ứng của Memory Allocator và yêu cầu của dự án.

15. Best Practices khi sử dụng Dynamic Memory Allocation

Để sử dụng bộ nhớ động an toàn và hiệu quả hơn, lập trình viên nên áp dụng các nguyên tắc sau:

  • Check Allocation Result: luôn kiểm tra Pointer trả về từ malloc(), calloc() và realloc().
  • Calculate Size Carefully: sử dụng sizeof và kiểm tra nguy cơ tràn số khi tính kích thước vùng nhớ.
  • Initialize Before Use: khởi tạo dữ liệu trước khi đọc vùng nhớ được cấp phát bằng malloc().
  • Use Temporary Pointer: không ghi đè Pointer gốc trực tiếp bằng kết quả realloc() khi chưa kiểm tra thành công.
  • Release Unused Memory: giải phóng vùng nhớ khi không còn cần sử dụng.
  • Minimize Allocation Frequency: hạn chế cấp phát và giải phóng lặp lại không cần thiết trong những đoạn xử lý quan trọng.
  • Prefer Fixed-size Buffer: cân nhắc sử dụng Buffer cố định khi kích thước dữ liệu có thể xác định trước.
  • Monitor Memory Usage: kiểm tra mức sử dụng Heap và khả năng cấp phát của hệ thống.
  • Follow Project Requirements: tuân thủ quy định về Dynamic Allocation của dự án Embedded hoặc Automotive.

Tóm tắt

Dynamic Memory Allocation là cơ chế cho phép chương trình C yêu cầu và quản lý bộ nhớ trong Runtime thay vì phải xác định toàn bộ kích thước dữ liệu từ trước.

Bốn hàm quan trọng nhất trong thư viện chuẩn C là malloc(), calloc(), realloc() và free(). malloc() cấp phát bộ nhớ nhưng không khởi tạo dữ liệu; calloc() cấp phát bộ nhớ cho nhiều phần tử và thiết lập tất cả bit bằng 0; realloc() thay đổi kích thước vùng nhớ đã cấp phát; free() giải phóng vùng nhớ khi chương trình không còn cần sử dụng.

Khi sử dụng các hàm này, lập trình viên cần kiểm tra NULL, tính toán kích thước bộ nhớ chính xác, khởi tạo dữ liệu trước khi đọc và quản lý Pointer phù hợp. Đặc biệt, khi sử dụng realloc(), cần dùng Temporary Pointer để tránh mất địa chỉ vùng nhớ ban đầu nếu cấp phát lại thất bại.

Trong Embedded Systems, Dynamic Memory Allocation mang lại sự linh hoạt nhưng cũng có thể gây ra những vấn đề về RAM Usage, Fragmentation, thời gian cấp phát và độ ổn định của hệ thống. Vì vậy, cần đánh giá cẩn thận trước khi lựa chọn sử dụng Heap.

Đối với những hệ thống cần khả năng kiểm soát tài nguyên tốt, Static Allocation, Fixed-size Buffer và Memory Pool có thể là những giải pháp phù hợp hơn tùy thuộc yêu cầu dự án.
