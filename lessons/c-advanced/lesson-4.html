Bài 4: Stack vs Heap vs Data vs BSS Segments

Ở bài trước, chúng ta đã tìm hiểu tổng quan về Memory Layout của một chương trình C, bao gồm Text Segment, Read-only Data, Initialized Data, BSS, Heap và Stack. Trong đó, mỗi vùng nhớ có nhiệm vụ riêng và được sử dụng cho những mục đích khác nhau.

Trong bài học này, chúng ta sẽ tập trung phân tích sâu hơn bốn vùng nhớ quan trọng: Stack, Heap, Data và BSS. Đây là những vùng nhớ có ảnh hưởng trực tiếp đến cách chương trình lưu trữ biến, quản lý dữ liệu và sử dụng tài nguyên RAM.

Đối với Embedded Systems, việc hiểu rõ cách hoạt động của các vùng nhớ này đặc biệt quan trọng vì các vi điều khiển thường có dung lượng RAM giới hạn. Một chương trình sử dụng Stack quá nhiều, cấp phát Heap không hợp lý hoặc tổ chức dữ liệu Global không hiệu quả đều có thể gây ra những vấn đề về bộ nhớ và ảnh hưởng đến độ ổn định của hệ thống.

Bài học này tập trung vào cơ chế hoạt động, đặc điểm và cách sử dụng Stack, Heap, Data và BSS. Các kỹ thuật cấp phát động chuyên sâu sẽ được trình bày ở Bài 6, trong khi Memory Leakage, Dangling Pointer và Memory Safety sẽ được phân tích ở Bài 7.

1. Tổng quan về Stack, Heap, Data và BSS

Trong một chương trình C, các biến và dữ liệu không được lưu trữ trong cùng một vùng nhớ. Vị trí lưu trữ thường phụ thuộc vào Storage Duration, cách khai báo biến, mục đích sử dụng và cách Compiler triển khai chương trình.

Bốn vùng nhớ được tìm hiểu trong bài này có những chức năng chính như sau:

Vùng nhớ Chức năng Dữ liệu thường gặp
Stack Quản lý dữ liệu liên quan đến quá trình thực thi các Function. Local Variable, Function Call Data và một số tham số hàm.
Heap Cung cấp bộ nhớ được cấp phát trong thời gian chương trình chạy. Dynamic Memory được yêu cầu thông qua malloc và các hàm liên quan.
Data Lưu các biến có Static Storage Duration với giá trị khởi tạo cần được duy trì. Global Variable và Static Variable đã khởi tạo.
BSS Lưu các dữ liệu có Static Storage Duration được khởi tạo mặc định bằng 0 hoặc khởi tạo bằng 0. Global Variable và Static Variable chưa khởi tạo hoặc khởi tạo bằng 0.

Sơ đồ sau minh họa mối quan hệ giữa các vùng nhớ này trong một mô hình chương trình C phổ biến:

Sơ đồ trên chỉ mang tính khái niệm, không thể hiện địa chỉ thật hoặc thứ tự bắt buộc trên mọi nền tảng. Hướng phát triển của Stack và Heap phụ thuộc vào kiến trúc, Runtime, Compiler và cấu hình bộ nhớ.

2. Stack Memory

Stack Memory là vùng nhớ được sử dụng để quản lý dữ liệu liên quan đến quá trình thực thi các Function. Trong những hệ thống phổ biến, Stack hoạt động theo nguyên tắc LIFO (Last In, First Out), nghĩa là phần tử được đưa vào sau cùng sẽ được lấy ra trước.

Khi một Function được gọi, hệ thống có thể tạo một vùng dữ liệu gọi là Stack Frame để quản lý các thông tin cần thiết cho lần gọi hàm đó. Khi Function hoàn thành, vùng dữ liệu liên quan sẽ được thu hồi hoặc tái sử dụng.

2.1. Nguyên lý hoạt động của Stack

Để hiểu cách Stack hoạt động, hãy xem xét một chương trình có Function gọi Function khác: 

#include <stdio.h>

void function_c(void)
{
    int value_c = 30;
    printf("C: %d\n", value_c);
}

void function_b(void)
{
    int value_b = 20;

    function_c();

    printf("B: %d\n", value_b);
}

void function_a(void)
{
    int value_a = 10;

    function_b();

    printf("A: %d\n", value_a);
}

int main(void)
{
    function_a();

    return 0;
}

Trình tự gọi Function trong chương trình là: 

main()
   |
   +-- function_a()
          |
          +-- function_b()
                 |
                 +-- function_c()

Khi chương trình thực thi, mỗi lần gọi Function sẽ tạo ra một ngữ cảnh thực thi riêng. Trong cách triển khai sử dụng Stack, các Stack Frame được tổ chức theo thứ tự gọi hàm.

Khi function_c() hoàn thành, chương trình quay về function_b(). Sau đó function_b() hoàn thành và chương trình tiếp tục quay về function_a(). Cuối cùng, chương trình trở lại main().

Sơ đồ trên minh họa bốn Stack Frame tương ứng với bốn Function đang hoạt động. Khi Function cuối cùng kết thúc, Stack Frame của nó được giải phóng trước.

2.2. Stack Frame gồm những gì?

Một Stack Frame có thể chứa nhiều loại thông tin phục vụ quá trình thực thi Function. Thành phần cụ thể phụ thuộc vào kiến trúc CPU, Calling Convention, Compiler và cách tối ưu mã nguồn.

Thành phần Vai trò
Local Variables Lưu các biến Local cần không gian lưu trữ trong Stack Frame.
Function Parameters Lưu các tham số hàm nếu chúng được truyền hoặc lưu trên Stack.
Return Address Thông tin phục vụ việc quay lại vị trí gọi Function.
Saved Registers Lưu các CPU Register cần bảo toàn khi gọi Function theo Calling Convention.
Temporary Data Lưu dữ liệu tạm thời cần thiết cho quá trình xử lý.

Không phải tất cả các thành phần trên đều luôn nằm trong Stack. Ví dụ, tham số Function có thể được truyền thông qua CPU Register theo quy ước gọi hàm. Compiler cũng có thể tối ưu và không tạo một Stack Frame riêng cho một số Function đơn giản.

2.3. Stack Pointer (SP)

Stack Pointer (SP) là một thanh ghi CPU được sử dụng để theo dõi vị trí hiện tại của Stack.

Khi chương trình thực hiện các thao tác liên quan đến Stack, giá trị của Stack Pointer có thể được thay đổi để quản lý vùng nhớ dành cho các Stack Frame.

Trên nhiều kiến trúc vi xử lý, Stack có thể phát triển theo hướng địa chỉ thấp hơn (Descending Stack). Tuy nhiên, đây không phải quy tắc bắt buộc đối với mọi CPU.

Ví dụ khái niệm: 

/* Pseudocode minh họa */

push(value);

/*
 * Stack Pointer thay đổi
 * để phản ánh dữ liệu vừa được đưa vào Stack.
 */

pop();

/*
 * Stack Pointer thay đổi trở lại
 * khi dữ liệu được lấy khỏi Stack.
 */
Stack Pointer là một thành phần ở mức kiến trúc CPU. Khi làm việc với một MCU cụ thể, cần tham khảo Architecture Reference Manual để biết cách tổ chức Stack, quy ước gọi hàm và các thanh ghi liên quan.

2.4. Stack Allocation

Một đặc điểm quan trọng của Stack là việc quản lý bộ nhớ thường được thực hiện theo vòng đời của Function. Khi Function bắt đầu hoạt động, không gian cần thiết cho các dữ liệu tương ứng được thiết lập. Khi Function kết thúc, không gian này có thể được thu hồi để sử dụng cho các lần gọi hàm tiếp theo.

Ví dụ: 

void process_sensor(void)
{
    int sensor_value = 100;

    int converted_value = sensor_value * 2;

    /* Xử lý dữ liệu */

} /* Dữ liệu có automatic storage duration hết lifetime */

Hai biến sensor_value và converted_value có Automatic Storage Duration. Khi Function kết thúc, lifetime của hai biến này kết thúc.

Đây là lý do Stack thường được xem là một vùng nhớ có cơ chế quản lý tương đối đơn giản và nhanh trong các chương trình C.

2.5. Recursion và ảnh hưởng đến Stack

Recursion là kỹ thuật một Function gọi lại chính nó. Mỗi lần gọi đệ quy thường tạo thêm một ngữ cảnh thực thi mới và có thể cần thêm Stack Frame.

Ví dụ: 

int factorial(int n)
{
    if (n <= 1)
    {
        return 1;
    }

    return n * factorial(n - 1);
}

int main(void)
{
    int result = factorial(5);

    return 0;
}

Khi factorial(5) được thực thi, các lần gọi Function tiếp theo được tạo ra cho đến khi đạt điều kiện dừng. Sau đó các Function lần lượt trả kết quả về cho lần gọi trước đó.

Trong trường hợp số lần gọi đệ quy quá lớn, Stack có thể sử dụng hết dung lượng được cấp phát và gây ra Stack Overflow.

Trong Embedded Systems, nên cân nhắc cẩn thận khi sử dụng Recursion, đặc biệt trong những Function có thể được gọi với độ sâu không giới hạn. Các giải pháp lặp (Iteration) có thể giúp kiểm soát việc sử dụng Stack dễ dàng hơn.

2.6. Stack trong Embedded Systems và RTOS

Trong hệ thống Embedded Bare-metal, chương trình thường sử dụng một hoặc một số vùng Stack được cấu hình dành cho quá trình thực thi. Kích thước Stack cần phù hợp với mức sử dụng dữ liệu của chương trình.

Khi sử dụng RTOS, mỗi Task thường được cấp một vùng Stack riêng để quản lý các Function Call và dữ liệu Local trong quá trình Task đó chạy.

Kích thước Stack của từng Task là một phần quan trọng trong cấu hình RTOS. Nếu Stack của Task không đủ lớn, chương trình có thể gặp lỗi khi Task thực hiện Function Call lồng nhau hoặc xử lý những dữ liệu Local có kích thước lớn.

Ngoài ra, Interrupt có thể sử dụng Stack theo quy định của kiến trúc CPU và cấu hình hệ thống. Với một số RTOS, Interrupt Handler có thể sử dụng System Stack riêng hoặc Stack đang hoạt động tùy thiết kế nền tảng.

3. Stack Overflow và Stack Management

Stack Overflow xảy ra khi chương trình sử dụng Stack vượt quá vùng nhớ được cấp phát hoặc cấu hình cho Stack. Đây là một vấn đề nghiêm trọng trong Embedded Systems vì có thể làm ghi đè lên vùng nhớ lân cận và gây ra hành vi không mong muốn.

3.1. Nguyên nhân gây Stack Overflow

Một số nguyên nhân phổ biến bao gồm:

  • Function gọi lồng nhau quá nhiều cấp.
  • Recursion có độ sâu lớn hoặc không có điều kiện dừng phù hợp.
  • Khai báo Array hoặc Structure có kích thước lớn dưới dạng biến Local.
  • Interrupt lồng nhau làm tăng mức sử dụng Stack.
  • Stack của RTOS Task được cấu hình quá nhỏ.
  • Compiler hoặc ABI yêu cầu thêm Stack cho dữ liệu tạm thời và các Function Call.

3.2. Ví dụ về sử dụng Stack quá nhiều

#include <stdint.h>

void process_data(void)
{
    /* Local Array có kích thước lớn */
    uint8_t buffer[4096];

    /* Xử lý dữ liệu */

    buffer[0] = 0;
}

int main(void)
{
    process_data();

    return 0;
}

Trong ví dụ trên, Function process_data() khai báo một Array có kích thước 4096 byte. Nếu Compiler đặt Array này trên Stack, lượng Stack cần thiết sẽ tăng đáng kể.

Đối với một vi điều khiển chỉ có vài chục KB RAM, việc khai báo nhiều Buffer Local có kích thước lớn có thể khiến Stack không còn đủ không gian cho các hoạt động khác.

3.3. Biện pháp hạn chế Stack Overflow

Biện pháp Ý nghĩa
Kiểm soát Local Variable Hạn chế khai báo những biến hoặc Array quá lớn trong Function.
Kiểm soát Function Call Tránh các chuỗi gọi hàm quá sâu và không cần thiết.
Hạn chế Recursion Sử dụng Iteration nếu cần kiểm soát chặt chẽ mức sử dụng Stack.
Stack Sizing Cấu hình kích thước Stack dựa trên việc phân tích và kiểm thử.
Stack Monitoring Kiểm tra mức sử dụng Stack trong quá trình phát triển.
Stack Protection Sử dụng Stack Guard hoặc cơ chế kiểm tra Overflow nếu nền tảng hỗ trợ.

3.4. Stack Monitoring trong Embedded

Trong quá trình phát triển Firmware, lập trình viên cần xác định chương trình đã sử dụng bao nhiêu Stack và còn lại bao nhiêu dung lượng.

Một số phương pháp thường được sử dụng:

  • Stack Watermarking: điền một mẫu dữ liệu cố định vào Stack khi khởi tạo, sau đó kiểm tra phần dữ liệu đã bị ghi đè để ước lượng mức sử dụng cao nhất.
  • Stack Canary: đặt một giá trị kiểm tra tại vùng được giám sát để phát hiện một số trường hợp ghi đè Stack.
  • Debugger Inspection: quan sát Stack Pointer và vùng Stack trong quá trình Debug.
  • RTOS Stack Monitoring: sử dụng các API hoặc chức năng hỗ trợ kiểm tra mức sử dụng Stack của Task.
Stack Watermarking và Stack Canary có thể giúp phát hiện hoặc đánh giá một số vấn đề về Stack, nhưng không bảo đảm phát hiện mọi trường hợp Overflow. Cần kết hợp phân tích tĩnh, kiểm thử và kiểm tra trên Target Hardware.

4. Heap Memory

Heap Memory là vùng nhớ được sử dụng để cấp phát bộ nhớ động trong quá trình chương trình đang chạy. Khác với Stack, việc tạo và giải phóng các vùng nhớ Heap không nhất thiết gắn với thời điểm bắt đầu và kết thúc của một Function.

Trong C, chương trình thường sử dụng các Function như malloc(), calloc(), realloc() và free() để quản lý bộ nhớ động.

4.1. Nguyên lý hoạt động của Heap

Khi chương trình yêu cầu cấp phát bộ nhớ động, Memory Allocator sẽ tìm một vùng nhớ phù hợp trong khu vực Heap mà nó quản lý và trả về địa chỉ của vùng nhớ đó.

Vùng nhớ được cấp phát sẽ tiếp tục tồn tại cho đến khi được giải phóng theo cơ chế quản lý tương ứng. Lifetime của vùng nhớ này không tự động kết thúc chỉ vì Function đã thực hiện yêu cầu cấp phát kết thúc.

Ví dụ: 

#include <stdlib.h>
#include <stdint.h>

int main(void)
{
    uint32_t *data = malloc(10 * sizeof(uint32_t));

    if (data == NULL)
    {
        return 1;
    }

    data[0] = 100;

    /* Sử dụng vùng nhớ được cấp phát */

    free(data);

    return 0;
}

Trong ví dụ trên, cần phân biệt hai đối tượng:

  • data là biến Pointer Local, có automatic storage duration.
  • Vùng nhớ được cấp phát thông qua malloc() là đối tượng được quản lý bằng Dynamic Memory Allocation.

Hai đối tượng này không nhất thiết nằm trong cùng một vùng nhớ. Biến Pointer có thể được lưu trên Stack hoặc Register, trong khi vùng nhớ được cấp phát được lấy từ Heap của Memory Allocator.

4.2. Memory Allocator

Memory Allocator là thành phần quản lý việc cấp phát và giải phóng bộ nhớ động.

Khi sử dụng malloc(), chương trình không cần tự xác định chính xác địa chỉ của vùng nhớ có thể sử dụng. Memory Allocator sẽ quản lý các vùng nhớ và tìm một khu vực phù hợp với yêu cầu cấp phát.

Tùy theo thuật toán được sử dụng, Memory Allocator có thể duy trì thông tin về các Block đã cấp phát, các Block còn trống và kích thước của từng vùng nhớ.

Trong sơ đồ trên, Heap được minh họa thành các Block có trạng thái khác nhau. Memory Allocator có thể tìm Block còn trống phù hợp để phục vụ yêu cầu mới.

4.3. Đặc điểm của Heap

  • Cho phép cấp phát bộ nhớ trong Runtime.
  • Kích thước vùng nhớ có thể thay đổi theo yêu cầu chương trình.
  • Đối tượng được cấp phát có thể tồn tại sau khi Function yêu cầu cấp phát kết thúc.
  • Việc giải phóng bộ nhớ thường cần được quản lý rõ ràng.
  • Có thể phát sinh Memory Fragmentation.
  • Thời gian cấp phát và giải phóng có thể phụ thuộc vào thuật toán Memory Allocator.

4.4. Heap trong Embedded Systems

Trong các ứng dụng Embedded, Heap có thể hữu ích khi dữ liệu có kích thước không xác định trước hoặc cần thay đổi trong quá trình chương trình hoạt động.

Ví dụ:

  • Các Buffer được tạo theo kích thước dữ liệu nhận được.
  • Các cấu trúc dữ liệu có kích thước linh hoạt.
  • Các đối tượng được tạo và giải phóng theo yêu cầu ứng dụng.
  • Các Module cần quản lý vùng nhớ có vòng đời độc lập với Function hiện tại.

Tuy nhiên, Heap cần được sử dụng thận trọng trên MCU có RAM nhỏ. Nếu Memory Allocator hoạt động không phù hợp, chương trình có thể gặp tình trạng thiếu bộ nhớ hoặc không đáp ứng được yêu cầu thời gian thực.

5. Heap Fragmentation

Một trong những vấn đề quan trọng khi sử dụng Heap là Memory Fragmentation. Đây là hiện tượng bộ nhớ bị chia thành nhiều vùng nhỏ sau quá trình cấp phát và giải phóng các Block có kích thước khác nhau.

5.1. External Fragmentation

External Fragmentation xảy ra khi tổng dung lượng bộ nhớ còn trống vẫn đủ lớn, nhưng các vùng nhớ trống lại bị chia nhỏ và không có vùng liên tục nào đáp ứng được yêu cầu cấp phát.

Ví dụ, một Heap có các Block như sau:

Trong sơ đồ minh họa, tổng dung lượng Free Memory là 160 units. Tuy nhiên, hai Block trống chỉ có kích thước 70 và 90 units. Nếu Memory Allocator cần một vùng liên tục có kích thước 150 units, yêu cầu cấp phát có thể thất bại.

5.2. Internal Fragmentation

Internal Fragmentation xảy ra khi một Block được cấp phát có kích thước lớn hơn lượng bộ nhớ thực tế mà chương trình cần sử dụng. Phần bộ nhớ dư bên trong Block đã cấp phát không thể được sử dụng cho những yêu cầu khác trong thời gian đó.

Ví dụ, Memory Allocator cấp phát một Block 64 bytes trong khi chương trình chỉ cần sử dụng 40 bytes. Khi đó, 24 bytes còn lại nằm trong vùng đã cấp phát nhưng không được sử dụng.

5.3. So sánh External và Internal Fragmentation

Tiêu chí External Fragmentation Internal Fragmentation
Đặc điểm Bộ nhớ trống bị chia thành nhiều Block nhỏ. Bộ nhớ dư bên trong Block đã cấp phát.
Vị trí bộ nhớ lãng phí Nằm giữa các Block đã cấp phát. Nằm bên trong Block đã cấp phát.
Ảnh hưởng Có thể không cấp phát được một vùng liên tục đủ lớn. Làm giảm lượng bộ nhớ thực tế có thể sử dụng.
Giải pháp thường gặp Memory Pool, thuật toán Allocator phù hợp và kiểm soát vòng đời cấp phát. Thiết kế kích thước Block và cơ chế cấp phát phù hợp.
Trong các ứng dụng Embedded yêu cầu hoạt động ổn định lâu dài, cần đặc biệt chú ý đến Fragmentation khi sử dụng Dynamic Memory Allocation. Đây là một trong những lý do nhiều dự án lựa chọn Static Allocation hoặc Memory Pool thay cho việc cấp phát và giải phóng tùy ý.

6. Initialized Data Segment (.data)

Data Segment là vùng nhớ chứa các biến có Static Storage Duration đã được khởi tạo và cần có giá trị ban đầu. Trong những Toolchain phổ biến, vùng này thường được biểu diễn bằng Section .data.

Những biến thuộc nhóm này thường là Global Variable hoặc Static Variable. Khác với biến Local thông thường, các biến này tồn tại trong suốt thời gian thực thi của chương trình.

6.1. Biến Global đã khởi tạo

Ví dụ:

#include <stdint.h>

/* Global variable */
int system_status = 1;

uint32_t device_counter = 100;

int main(void)
{
    system_status = 2;

    device_counter++;

    return 0;
}

Hai biến system_status và device_counter được khai báo bên ngoài tất cả Function. Chúng có Static Storage Duration và có giá trị khởi tạo tường minh.

Trong một cách triển khai phổ biến, các biến này được bố trí trong Initialized Data Segment. Giá trị ban đầu của chúng được lưu trong Load Image và được thiết lập vào RAM khi chương trình khởi động.

6.2. Biến Static đã khởi tạo

Từ khóa static có thể được sử dụng để khai báo các biến có Static Storage Duration, kể cả khi biến được khai báo bên trong Function. 

void update_counter(void)
{
    static int call_count = 1;

    call_count++;

    /* Xử lý khác */
}

int main(void)
{
    update_counter();
    update_counter();
    update_counter();

    return 0;
}

Biến call_count là biến Static Local. Mặc dù được khai báo bên trong Function, nó không được tạo mới và khởi tạo lại mỗi lần Function được gọi.

Giá trị của biến được giữ lại giữa các lần gọi Function. Do được khởi tạo bằng 1, biến này thường được đưa vào Initialized Data Segment trong cách triển khai phổ biến.

6.3. Đặc điểm của Data Segment

  • Thường chứa biến Global và Static đã khởi tạo.
  • Các biến có thể được đọc và thay đổi nếu không được khai báo chỉ đọc.
  • Các đối tượng có Static Storage Duration tồn tại trong toàn bộ quá trình thực thi chương trình.
  • Vùng dữ liệu Runtime thường nằm trong RAM.
  • Giá trị khởi tạo ban đầu thường được lưu trong Load Image.

6.4. Quá trình khởi tạo Data Segment

Trong Embedded Systems, giá trị khởi tạo của các biến Data thường được đặt trong bộ nhớ không mất dữ liệu như Flash. Khi MCU khởi động, Startup Code sẽ sao chép dữ liệu này vào vùng RAM tương ứng.

Sau khi sao chép, các biến có thể được sử dụng trong chương trình với giá trị khởi tạo ban đầu như đã khai báo trong mã nguồn.

Ví dụ: 

int system_status = 1;

/*
 * Sau khi Startup Code hoàn thành:
 *
 * system_status = 1
 *
 * Chương trình có thể thay đổi giá trị này
 * trong quá trình hoạt động.
 */
Cần phân biệt vị trí lưu trữ ban đầu của dữ liệu và vị trí sử dụng khi chương trình chạy. Một biến thuộc .data thường có Run Address trong RAM, trong khi giá trị khởi tạo của nó được lưu tại Load Address trong Flash.

7. BSS Segment (.bss)

BSS Segment là vùng nhớ được sử dụng cho những biến có Static Storage Duration chưa được khởi tạo tường minh hoặc được khởi tạo bằng giá trị 0.

Trong nhiều Toolchain, vùng này được biểu diễn bằng Section có tên .bss. Các biến thuộc vùng này thường được dành riêng không gian trong RAM và được Startup Code khởi tạo về 0 trước khi chương trình chính chạy.

7.1. Biến Global chưa khởi tạo

#include <stdint.h>

/* Global variables */
int system_state;

uint32_t sensor_value;

int main(void)
{
    /* Các biến trên có giá trị ban đầu bằng 0 */

    return 0;
}

Trong ví dụ trên, các biến Global được khai báo nhưng không có giá trị khởi tạo tường minh. Theo quy tắc của C, chúng được khởi tạo mặc định bằng 0.

Trong cách triển khai phổ biến, các biến này được đưa vào BSS Segment.

7.2. Biến Static chưa khởi tạo

Các biến được khai báo bằng từ khóa static cũng có Static Storage Duration. Nếu không có giá trị khởi tạo tường minh, chúng được khởi tạo mặc định bằng 0. 

void update_sensor(void)
{
    static int sample_count;

    sample_count++;

    /* Sample Count được giữ lại qua các lần gọi */
}

int main(void)
{
    update_sensor();
    update_sensor();

    return 0;
}

Trong ví dụ này, sample_count là biến Static Local. Biến có lifetime kéo dài trong toàn bộ quá trình thực thi chương trình và giá trị ban đầu bằng 0.

7.3. Biến khởi tạo tường minh bằng 0

Không chỉ biến chưa được khởi tạo tường minh mới có thể nằm trong BSS. Một số Compiler và Linker cũng đưa các biến được khởi tạo bằng 0 vào vùng này. 

int error_code = 0;

static int retry_count = 0;

int main(void)
{
    return 0;
}

Mặc dù hai biến đã được khai báo với giá trị ban đầu, giá trị của chúng bằng 0 nên Toolchain có thể bố trí chúng trong BSS để giảm lượng dữ liệu khởi tạo cần lưu trong Image.

7.4. Đặc điểm của BSS

  • Chứa các biến có Static Storage Duration được khởi tạo mặc định bằng 0 hoặc khởi tạo tường minh bằng 0 trong cách triển khai phổ biến.
  • Các biến được dành riêng không gian trong RAM.
  • Startup Code thường thực hiện việc khởi tạo vùng nhớ về 0.
  • Trong ELF, BSS thường được biểu diễn bằng một loại Section không cần lưu toàn bộ byte 0 trong file Image.
  • Giúp giảm kích thước dữ liệu khởi tạo phải lưu trong chương trình.

7.5. Vì sao BSS không cần lưu toàn bộ giá trị 0 trong Flash?

Giả sử chương trình có một Buffer Global với kích thước 4096 bytes và cần được khởi tạo ban đầu bằng 0. 

uint8_t receive_buffer[4096];

Nếu toàn bộ 4096 bytes đều phải được ghi rõ trong file Image, kích thước dữ liệu khởi tạo sẽ tăng lên đáng kể.

Thay vào đó, Toolchain có thể chỉ lưu thông tin về vị trí và kích thước của vùng BSS. Khi hệ thống khởi động, Startup Code thực hiện việc ghi 0 vào toàn bộ vùng này.

BSS giúp tiết kiệm không gian lưu trữ của Load Image. Tuy nhiên, các biến thuộc BSS vẫn chiếm RAM khi chương trình chạy. Vì vậy, khai báo Buffer Global có kích thước lớn vẫn làm tăng mức sử dụng RAM của Firmware.

8. So sánh Stack, Heap, Data và BSS

Bốn vùng nhớ này có cách quản lý và vòng đời dữ liệu khác nhau. Bảng sau tổng hợp những đặc điểm quan trọng:

8.1. Điểm khác biệt quan trọng nhất

Có thể phân biệt bốn vùng nhớ dựa trên cách chương trình quản lý dữ liệu:

  • Stack: thường gắn với quá trình gọi và kết thúc Function.
  • Heap: được quản lý thông qua các yêu cầu cấp phát và giải phóng bộ nhớ động.
  • Data: chứa các biến có Static Storage Duration với giá trị khởi tạo cần được lưu.
  • BSS: chứa các biến có Static Storage Duration được khởi tạo về 0.

Một điểm rất quan trọng là Data và BSS không được phân biệt dựa trên việc biến có được truy cập nhiều lần hay không, mà dựa trên đặc điểm khởi tạo và cách Compiler/Linker bố trí dữ liệu.

9. Ví dụ tổng hợp: Phân loại biến theo từng vùng nhớ

Xét chương trình C sau: 

#include <stdint.h>
#include <stdlib.h>

/* Initialized Data */
int system_status = 1;

static int error_count = 5;

/* BSS */
int global_counter;

static uint32_t sensor_value;

/* Read-only Data - typical implementation */
const char device_name[] = "Embedded ECU";

/* Function */
void process_sensor(void)
{
    int local_value = 100;

    static int call_count;

    call_count++;

    local_value++;
}

int main(void)
{
    int main_counter = 0;

    /* Pointer local */
    int *buffer = malloc(10 * sizeof(int));

    if (buffer == NULL)
    {
        return 1;
    }

    buffer[0] = 100;

    process_sensor();

    free(buffer);

    return 0;
}

Dựa trên cách khai báo các biến, chúng ta có thể phân loại như sau:

Đối tượng Đặc điểm Vùng nhớ thường gặp
system_status Global, khởi tạo bằng 1. .data
error_count Static Global, khởi tạo bằng 5. .data
global_counter Global, chưa khởi tạo. .bss
sensor_value Static Global, chưa khởi tạo. .bss
device_name Const Array có Static Storage Duration. .rodata (thường gặp)
local_value Automatic Local Variable. Stack hoặc Register tùy Compiler
call_count Static Local Variable, chưa khởi tạo. .bss (thường gặp)
main_counter Automatic Local Variable. Stack hoặc Register tùy Compiler
buffer Local Pointer Variable. Stack hoặc Register tùy Compiler
Vùng nhớ malloc Đối tượng được cấp phát động. Heap
Điểm cần ghi nhớ: Vùng nhớ chứa Pointer không nhất thiết là vùng nhớ chứa dữ liệu mà Pointer trỏ đến. Trong ví dụ này, buffer là một biến Pointer Local, còn vùng nhớ được cấp phát bằng malloc() được quản lý trong Heap.

10. Stack vs Heap trong Embedded Systems

Trong các ứng dụng Embedded, việc lựa chọn giữa Stack và Heap không chỉ phụ thuộc vào cách khai báo biến mà còn liên quan đến tài nguyên phần cứng, yêu cầu thời gian thực và tính ổn định của Firmware.

10.1. Stack phù hợp với những trường hợp nào?

Stack thường phù hợp với những dữ liệu:

  • Có kích thước tương đối nhỏ và xác định được trước.
  • Chỉ cần tồn tại trong thời gian Function đang thực thi.
  • Không cần chia sẻ vòng đời với các Function khác.
  • Có thể quản lý theo cấu trúc gọi hàm thông thường.

Ví dụ: 

void calculate_average(void)
{
    uint16_t sum = 0;
    uint8_t count = 10;
    uint16_t average;

    sum = 500;

    average = sum / count;

    /* Sử dụng average */
}

Trong trường hợp này, các biến Local có kích thước nhỏ và chỉ cần phục vụ việc tính toán bên trong Function. Do đó, việc sử dụng Automatic Storage Duration là lựa chọn hợp lý.

10.2. Heap phù hợp với những trường hợp nào?

Heap có thể phù hợp khi:

  • Kích thước dữ liệu chưa xác định trước thời điểm Build.
  • Đối tượng cần tồn tại sau khi Function tạo ra nó kết thúc.
  • Ứng dụng cần tạo cấu trúc dữ liệu có kích thước thay đổi.
  • Hệ thống có cơ chế quản lý bộ nhớ động phù hợp.

Ví dụ, một ứng dụng cần tạo Buffer dựa trên kích thước dữ liệu nhận được từ một thiết bị ngoại vi. Trong một số thiết kế, bộ nhớ động có thể giúp ứng dụng linh hoạt hơn.

10.3. So sánh Stack và Heap trong Embedded

Tiêu chí Stack Heap
Cấp phát Thường được quản lý tự động khi thực thi Function. Được yêu cầu thông qua Memory Allocator.
Giải phóng Thường tự động theo vòng đời của Function. Cần thực hiện quản lý giải phóng phù hợp.
Tốc độ Thường nhanh và có chi phí quản lý tương đối thấp. Phụ thuộc thuật toán Allocator và trạng thái Heap.
Fragmentation Ít gặp vấn đề Fragmentation theo cách quản lý Stack thông thường. Có thể gặp External và Internal Fragmentation.
Kiểm soát kích thước Cần phân tích độ sâu Function Call và dung lượng Stack. Cần quản lý tổng dung lượng, kích thước Block và vòng đời cấp phát.
Real-time Thường có thời gian quản lý dễ dự đoán hơn. Có thể có thời gian cấp phát thay đổi tùy Allocator.
Ứng dụng Local Variable, dữ liệu tạm thời và Function Call. Buffer và đối tượng có kích thước hoặc vòng đời linh hoạt.

10.4. Vì sao nhiều dự án Embedded hạn chế sử dụng Heap?

Không phải tất cả dự án Embedded đều cấm sử dụng Heap. Tuy nhiên, một số dự án lựa chọn hạn chế Dynamic Memory Allocation vì những lý do sau:

  • Predictability: cấp phát động có thể khiến thời gian xử lý thay đổi tùy trạng thái Memory Allocator.
  • Fragmentation: việc cấp phát và giải phóng liên tục có thể làm Heap bị phân mảnh.
  • Resource Limitation: các MCU có RAM nhỏ cần kiểm soát chặt chẽ dung lượng bộ nhớ.
  • Reliability: lỗi liên quan đến vòng đời và quản lý bộ nhớ có thể gây ra sự cố khó phát hiện.
  • Verification: việc xác định chính xác mức sử dụng bộ nhớ có thể phức tạp hơn khi bộ nhớ được cấp phát linh hoạt trong Runtime.

10.5. Các giải pháp thay thế Heap

Trong những ứng dụng cần kiểm soát bộ nhớ chặt chẽ, lập trình viên có thể sử dụng các phương pháp thay thế:

Phương pháp Mô tả
Static Allocation Khai báo các vùng dữ liệu có kích thước cố định trước khi chương trình chạy.
Fixed-size Buffer Sử dụng các Buffer có kích thước xác định và tái sử dụng chúng.
Memory Pool Chia một vùng nhớ thành những Block có kích thước xác định để quản lý.
Object Pool Quản lý tập hợp các đối tượng có cùng cấu trúc và tái sử dụng khi cần.

Những phương pháp này có thể giúp việc sử dụng bộ nhớ trở nên dễ dự đoán hơn, đặc biệt đối với hệ thống có yêu cầu thời gian thực.

11. Data và BSS trong Embedded Systems

Đối với các hệ thống Embedded, Data và BSS có liên hệ trực tiếp đến dung lượng RAM mà Firmware sử dụng. Hai vùng nhớ này thường được xác định trong quá trình Build và được Startup Code khởi tạo trước khi ứng dụng bắt đầu chạy.

11.1. Ảnh hưởng của biến Global đến RAM Usage

Giả sử một chương trình khai báo: 

#include <stdint.h>

uint8_t receive_buffer[1024];

uint8_t transmit_buffer[1024];

int system_status = 1;

int error_count = 0;

int main(void)
{
    return 0;
}

Trong một cách triển khai phổ biến:

  • receive_buffer và transmit_buffer thường thuộc BSS.
  • system_status thường thuộc Data.
  • error_count có thể được đưa vào BSS vì giá trị khởi tạo bằng 0.

Mặc dù các Buffer chưa được sử dụng ngay lập tức, chúng vẫn cần không gian trong RAM vì có Static Storage Duration.

11.2. Ví dụ phân bổ RAM

Giả sử một vi điều khiển có RAM tổng cộng 64 KB. Sau khi phân tích Build và cấu hình bộ nhớ, một dự án có thể có mức phân bổ giả định như sau:

Thành phần Dung lượng Ghi chú
.data 4 KB Biến Global và Static đã khởi tạo.
.bss 12 KB Biến Global và Static khởi tạo bằng 0.
Heap 8 KB Vùng bộ nhớ dành cho cấp phát động.
Stack 8 KB Vùng Stack được dành riêng theo cấu hình.
Other / Reserved 8 KB Các vùng RAM chuyên dụng hoặc dự trữ.
Tổng đã phân bổ 40 KB Minh họa giả định.
Remaining RAM 24 KB Phụ thuộc Memory Map và cách hệ thống phân bổ thực tế.

Ví dụ này cho thấy RAM không chỉ được sử dụng bởi các biến trong chương trình. Stack, Heap và các vùng dữ liệu dành riêng cho hệ thống cũng cần được tính đến.

Đây là ví dụ phân bổ RAM giả định, không phải quy tắc cố định cho mọi MCU. Khi phát triển Firmware thực tế, cần sử dụng Linker Map File, tài liệu phần cứng và cấu hình Build để xác định dung lượng thực sự của từng vùng.

11.3. Tác động của BSS đến dung lượng RAM

Một sai lầm thường gặp là cho rằng các biến thuộc BSS không tiêu tốn bộ nhớ vì chúng không cần lưu các byte 0 trong Flash.

Trên thực tế, BSS vẫn chiếm dung lượng RAM tương ứng với kích thước các đối tượng được đặt trong vùng này.

Ví dụ: 

uint8_t large_buffer[8192];

Biến trên có thể được bố trí trong BSS và chiếm khoảng 8 KB RAM. Mặc dù không cần lưu toàn bộ 8192 byte giá trị 0 trong Load Image, vùng RAM tương ứng vẫn phải được dành riêng khi chương trình hoạt động.

12. Những lỗi thường gặp khi sử dụng các vùng nhớ

Khi làm việc với chương trình C, lập trình viên cần hiểu rõ cách mỗi vùng nhớ được quản lý. Một số lỗi thường xuất hiện khi sử dụng Stack, Heap, Data và BSS không hợp lý.

Lỗi Nguyên nhân Hướng xử lý
Stack Overflow Sử dụng Stack vượt giới hạn cấu hình. Phân tích Stack Usage, giới hạn Function Call và kiểm soát Local Data.
Heap Fragmentation Cấp phát và giải phóng các Block có kích thước không đồng đều. Kiểm soát vòng đời bộ nhớ và cân nhắc Memory Pool.
RAM Exhaustion Tổng Data, BSS, Stack và Heap vượt quá khả năng RAM. Phân tích Memory Map và tối ưu RAM Usage.
Incorrect Initialization Startup Code không thiết lập Data hoặc BSS đúng cách. Kiểm tra Startup Code và cấu hình Linker.
Large Local Array Khai báo Buffer lớn trong Function. Cân nhắc Static Buffer hoặc giải pháp quản lý bộ nhớ khác.
Lifetime Misunderstanding Nhầm lẫn giữa vòng đời của Pointer và vùng nhớ được Pointer trỏ đến. Phân biệt Storage Duration và Lifetime của từng đối tượng.

12.1. Sử dụng Buffer lớn trên Stack

void receive_data(void)
{
    uint8_t data[8192];

    /* Xử lý dữ liệu */
}

Nếu Buffer được đặt trên Stack, Function có thể yêu cầu một lượng Stack rất lớn mỗi khi được gọi. Điều này cần được xem xét kỹ trên các MCU có RAM hạn chế.

12.2. Khai báo quá nhiều biến Global

uint8_t buffer_a[4096];

uint8_t buffer_b[4096];

uint8_t buffer_c[4096];

int main(void)
{
    return 0;
}

Các Buffer trên có Static Storage Duration nên sẽ chiếm không gian RAM trong toàn bộ thời gian chương trình chạy, dù tại một thời điểm chỉ có một Buffer được sử dụng.

Trong trường hợp các Buffer không cần sử dụng đồng thời, lập trình viên có thể xem xét thiết kế một cơ chế quản lý và tái sử dụng vùng nhớ phù hợp với yêu cầu hệ thống.

12.3. Nhầm lẫn giữa Pointer và vùng nhớ được cấp phát

void example(void)
{
    int *data;

    data = malloc(100 * sizeof(int));

    if (data == NULL)
    {
        return;
    }

    /*
     * data là Pointer Local.
     * Vùng nhớ được cấp phát là Dynamic Memory.
     */

    free(data);
}

Trong trường hợp này, cần phân biệt vòng đời của biến Pointer với vòng đời của vùng nhớ được cấp phát. Đây là một trong những kiến thức cơ bản để quản lý bộ nhớ an toàn trong C.

13. Công cụ kiểm tra Memory Usage

Trong các dự án Embedded thực tế, lập trình viên không nên chỉ dựa vào việc đọc mã nguồn để ước lượng bộ nhớ chương trình. Các công cụ Build và Debug có thể cung cấp thông tin hữu ích để phân tích mức sử dụng RAM và Flash.

13.1. Kiểm tra Section bằng size

Có thể sử dụng GNU Toolchain để kiểm tra kích thước các Section trong ELF File: 

arm-none-eabi-size firmware.elf

Kết quả thường bao gồm những thông tin:

  • text: nhóm Section chứa mã và một số dữ liệu chỉ đọc theo cách phân loại của công cụ.
  • data: kích thước nhóm dữ liệu đã khởi tạo.
  • bss: kích thước nhóm dữ liệu chưa khởi tạo hoặc khởi tạo bằng 0.

Những thông tin này giúp lập trình viên đánh giá kích thước chương trình và mức sử dụng dữ liệu tĩnh.

13.2. Kiểm tra Memory Map File

Map File cung cấp thông tin về vị trí các Section, kích thước dữ liệu và địa chỉ các Symbol sau khi Linking.

Ví dụ, một số thông tin có thể tìm thấy trong Map File:

  • Địa chỉ bắt đầu và kết thúc của .text.
  • Kích thước của .data và .bss.
  • Vị trí của các biến Global.
  • Phân vùng bộ nhớ và mức sử dụng RAM, Flash.
  • Các Symbol liên quan đến Stack và Heap nếu được cấu hình.

13.3. Theo dõi Stack trong Debugger

Debugger có thể hỗ trợ theo dõi Stack Pointer, kiểm tra vùng Stack và quan sát các Function Call trong Call Stack.

Trong quá trình Debug, lập trình viên có thể đặt Breakpoint, quan sát Call Stack và kiểm tra các biến Local để hiểu cách chương trình đang sử dụng dữ liệu.

Stack, Heap, Data và BSS cần được đánh giá cùng nhau khi phân tích RAM Usage. Chỉ kiểm tra kích thước .data và .bss là chưa đủ để xác định tổng lượng RAM mà Firmware thực sự cần trong Runtime.

14. Best Practices khi quản lý bộ nhớ trong C Embedded

Để xây dựng một chương trình Embedded ổn định, lập trình viên cần lựa chọn vùng nhớ phù hợp cho từng loại dữ liệu và kiểm soát cách chương trình sử dụng tài nguyên.

  • Đối với Stack: ưu tiên sử dụng cho các biến Local có kích thước phù hợp; tránh khai báo Buffer quá lớn hoặc sử dụng Recursion không kiểm soát.
  • Đối với Heap: cân nhắc nhu cầu thực tế trước khi cấp phát động; kiểm soát kích thước, vòng đời và khả năng cấp phát thất bại.
  • Đối với Data: chỉ sử dụng các biến Global và Static khi cần duy trì dữ liệu trong suốt thời gian hoạt động của chương trình.
  • Đối với BSS: lưu ý rằng Buffer lớn vẫn tiêu tốn RAM dù các giá trị ban đầu đều bằng 0.
  • Memory Monitoring: sử dụng Map File, Size Tool và Debugger để theo dõi mức sử dụng bộ nhớ.
  • Memory Planning: xác định ngân sách RAM và Flash phù hợp với tài nguyên của Target MCU.
  • Code Optimization: tổ chức dữ liệu và các Buffer hợp lý, tránh duy trì những vùng nhớ không cần thiết.

15. Tóm tắt các khái niệm quan trọng

Thuật ngữ Ý nghĩa
Stack Memory Vùng nhớ phục vụ Function Call và dữ liệu có Automatic Storage Duration theo cách triển khai phổ biến.
Stack Frame Vùng dữ liệu phục vụ một lần gọi Function.
Stack Pointer Thanh ghi theo dõi vị trí Stack.
Stack Overflow Tình trạng sử dụng Stack vượt quá vùng nhớ được cấp phát.
Heap Memory Vùng nhớ được sử dụng cho Dynamic Memory Allocation.
Memory Allocator Thành phần quản lý cấp phát và giải phóng bộ nhớ động.
External Fragmentation Bộ nhớ trống bị chia thành nhiều vùng nhỏ không liên tục.
Internal Fragmentation Bộ nhớ dư bên trong Block đã cấp phát.
Data Segment Vùng chứa dữ liệu đã khởi tạo có Static Storage Duration.
BSS Segment Vùng chứa dữ liệu có Static Storage Duration được khởi tạo về 0.
Static Storage Duration Thời gian tồn tại của đối tượng trong toàn bộ quá trình thực thi chương trình.
Automatic Storage Duration Thời gian tồn tại của đối tượng gắn với phạm vi thực thi tự động tương ứng.

Tóm tắt

Stack, Heap, Data và BSS là bốn vùng nhớ quan trọng trong quá trình tổ chức và quản lý bộ nhớ của chương trình C.

Stack thường được sử dụng để quản lý dữ liệu liên quan đến Function Call, bao gồm các biến Local và những thông tin cần thiết cho quá trình thực thi. Stack có cơ chế quản lý nhanh nhưng cần được kiểm soát để tránh Stack Overflow.

Heap cung cấp khả năng cấp phát bộ nhớ động trong Runtime. Mặc dù linh hoạt, Heap có thể gặp các vấn đề như Fragmentation, thiếu bộ nhớ và thời gian cấp phát khó dự đoán. Đây là lý do nhiều ứng dụng Embedded hạn chế sử dụng Dynamic Memory Allocation.

Data chứa các biến có Static Storage Duration với giá trị khởi tạo, trong khi BSS chứa các biến có Static Storage Duration được khởi tạo mặc định bằng 0 hoặc khởi tạo tường minh bằng 0. Trong nhiều hệ thống Embedded, Startup Code sẽ sao chép Data từ Flash sang RAM và khởi tạo BSS trước khi gọi main().

Hiểu rõ đặc điểm của từng vùng nhớ giúp lập trình viên lựa chọn cách lưu trữ dữ liệu phù hợp, kiểm soát RAM Usage và xây dựng Firmware ổn định hơn, đặc biệt trên những vi điều khiển có tài nguyên hạn chế.
