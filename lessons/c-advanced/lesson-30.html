Bài 30: Encapsulation, Static Function & Global Variable Management

Trong bài trước, chúng ta đã tìm hiểu cách chia chương trình C thành các module riêng biệt, phân chia Interface và Implementation, đồng thời giảm sự phụ thuộc giữa các module.

Tuy nhiên, việc chia chương trình thành nhiều module chưa đảm bảo rằng các thành phần bên trong module được bảo vệ tốt. Nếu mọi function và variable đều có thể được truy cập từ bên ngoài, các module vẫn có thể phụ thuộc quá nhiều vào dữ liệu nội bộ của nhau.

Để giải quyết vấn đề này, chúng ta cần áp dụng một số kỹ thuật nhằm kiểm soát phạm vi truy cập và quyền sử dụng các thành phần trong chương trình.

Trong C, các kỹ thuật quan trọng bao gồm:

  • Encapsulation: Tổ chức dữ liệu và function liên quan thành một module, đồng thời giới hạn việc truy cập vào chi tiết nội bộ.
  • Static Function: Sử dụng từ khóa static để giới hạn function trong phạm vi một source file.
  • Static Variable: Kiểm soát phạm vi và thời gian tồn tại của variable tùy theo vị trí khai báo.
  • Global Variable Management: Quản lý biến toàn cục để tránh xung đột, truy cập không kiểm soát và dependency không cần thiết.
Mục tiêu bài học:
  • Hiểu khái niệm Encapsulation trong lập trình C.
  • Phân biệt public function và private function trong một module.
  • Hiểu cách sử dụng static với function.
  • Phân biệt file-scope static variable và block-scope static variable.
  • Hiểu sự khác nhau giữa scope, lifetime và linkage.
  • Biết những vấn đề thường gặp khi sử dụng global variable.
  • Biết cách quản lý dữ liệu dùng chung giữa các module.
  • Áp dụng các kỹ thuật này trong Embedded C.

1. Tổng quan về Encapsulation

Encapsulation là nguyên tắc tổ chức dữ liệu và các function liên quan thành một đơn vị, đồng thời kiểm soát cách những thành phần khác truy cập và sử dụng chúng.

Mục đích của Encapsulation là hạn chế việc các thành phần bên ngoài phụ thuộc trực tiếp vào dữ liệu hoặc logic nội bộ của module.

Trong các ngôn ngữ hướng đối tượng như C++, Encapsulation thường được hỗ trợ bằng các access modifier như private, protected và public.

C không có những access modifier này. Tuy nhiên, chúng ta vẫn có thể áp dụng Encapsulation bằng cách kết hợp header file, source file, phạm vi của identifier và từ khóa static.

1.1. Ví dụ về module không có Encapsulation

Giả sử chúng ta có một module quản lý LED. Trạng thái LED được khai báo trong header file: 

/* led.h */

#ifndef LED_H
#define LED_H

extern unsigned char led_state;

void LED_Init(void);
void LED_On(void);
void LED_Off(void);

#endif

Vì led_state được khai báo là một external variable, các source file khác có thể truy cập trực tiếp vào biến này. 

/* main.c */

#include "led.h"

int main(void)
{
    LED_Init();

    led_state = 1U;

    return 0;
}

Application không cần gọi LED_On() mà vẫn có thể thay đổi trực tiếp trạng thái nội bộ của LED Module.

Điều này có thể tạo ra một số vấn đề:

  • Module bên ngoài có thể thay đổi dữ liệu mà không thông qua API chính thức.
  • Logic cập nhật trạng thái bị phân tán ở nhiều source file.
  • Khó xác định thành phần nào chịu trách nhiệm quản lý dữ liệu.
  • Việc thay đổi cách lưu trữ trạng thái có thể ảnh hưởng đến nhiều module.

1.2. Ví dụ có Encapsulation

Thay vì công bố biến trạng thái, chúng ta chỉ công bố những function cần thiết để điều khiển LED. 

/* led.h */

#ifndef LED_H
#define LED_H

void LED_Init(void);
void LED_On(void);
void LED_Off(void);
void LED_Toggle(void);

#endif

Biến trạng thái được giữ trong source file: 

/* led.c */

#include "led.h"

static unsigned char led_state = 0U;

void LED_Init(void)
{
    led_state = 0U;
}

void LED_On(void)
{
    led_state = 1U;
}

void LED_Off(void)
{
    led_state = 0U;
}

void LED_Toggle(void)
{
    led_state = (unsigned char)(!led_state);
}

Lúc này, Application chỉ có thể thay đổi trạng thái LED thông qua những function được module cung cấp. 

/* main.c */

#include "led.h"

int main(void)
{
    LED_Init();

    LED_On();

    LED_Toggle();

    return 0;
}

Application không thể truy cập trực tiếp vào led_state vì biến này không được công bố trong header file và có internal linkage.

1.3. Lợi ích của Encapsulation

Lợi ích Ý nghĩa
Kiểm soát truy cập Hạn chế việc module khác thay đổi dữ liệu nội bộ.
Giảm coupling Module khác chỉ cần phụ thuộc vào public interface.
Dễ bảo trì Có thể thay đổi implementation mà ít ảnh hưởng đến bên ngoài.
Dễ kiểm thử Có thể kiểm tra hành vi thông qua các function được công bố.
Kiểm soát dữ liệu Quá trình đọc và cập nhật dữ liệu được thực hiện thông qua các function xác định.
Điểm cần nhớ: C không có cơ chế private như C++. Tuy nhiên, chúng ta có thể tạo ra sự phân chia public và private ở mức module bằng cách chỉ khai báo những thành phần cần thiết trong header file và giữ các thành phần nội bộ trong source file.

2. Static Function trong C

Trong C, từ khóa static có thể được sử dụng với function ở file scope để giới hạn linkage của function.

Một function được khai báo với static ở file scope có internal linkage, nghĩa là tên function chỉ có thể được sử dụng trong cùng translation unit.

Trong cách tổ chức thông thường, mỗi source file sau khi preprocessing sẽ tạo thành một translation unit. Vì vậy, một static function trong led.c chỉ có thể được sử dụng trong translation unit tương ứng.

2.1. Function thông thường

Nếu không sử dụng static, function ở file scope thường có external linkage. Điều này cho phép source file khác tham chiếu đến function thông qua khai báo phù hợp. 

/* led.c */

void LED_ResetHardware(void)
{
    /* Reset LED hardware */
}

Function trên có thể được khai báo trong header file: 

/* led.h */

#ifndef LED_H
#define LED_H

void LED_ResetHardware(void);

#endif

Khi đó, source file khác có thể include led.h và gọi function LED_ResetHardware().

2.2. Static Function

Nếu function chỉ phục vụ hoạt động bên trong module, chúng ta có thể khai báo function với static. 

/* led.c */

static void LED_ResetHardware(void)
{
    /* Reset LED hardware */
}

void LED_Init(void)
{
    LED_ResetHardware();
}

Trong ví dụ này:

  • LED_ResetHardware() là function nội bộ của source file.
  • LED_Init() có thể gọi function nội bộ này.
  • Source file khác không thể gọi trực tiếp LED_ResetHardware() thông qua external linkage.

2.3. So sánh Function có và không có static

Tiêu chí Function thông thường Static Function
Linkage External linkage theo mặc định ở file scope. Internal linkage.
Phạm vi liên kết Có thể được tham chiếu từ translation unit khác. Chỉ được tham chiếu trong translation unit hiện tại.
Khai báo trong header Có thể công bố nếu cần thiết. Thông thường không công bố cho module khác.
Mục đích Cung cấp chức năng cho thành phần khác. Triển khai chức năng nội bộ.

2.4. Ví dụ thực tế trong một module

Giả sử chúng ta xây dựng một Sensor Module. Module cung cấp function đọc nhiệt độ, nhưng bên trong cần thực hiện nhiều bước xử lý khác nhau. 

/* sensor.c */

#include "sensor.h"

static void Sensor_StartConversion(void)
{
    /* Start ADC conversion */
}

static unsigned int Sensor_ReadRawValue(void)
{
    /* Read ADC result */
    return 250U;
}

static unsigned int Sensor_ConvertToTemperature(
    unsigned int raw_value
)
{
    /* Convert raw value to temperature */
    return raw_value / 10U;
}

unsigned int Sensor_ReadTemperature(void)
{
    unsigned int raw_value;
    unsigned int temperature;

    Sensor_StartConversion();

    raw_value = Sensor_ReadRawValue();

    temperature = Sensor_ConvertToTemperature(raw_value);

    return temperature;
}

Trong ví dụ này:

  • Sensor_StartConversion() chỉ phục vụ quá trình đọc sensor.
  • Sensor_ReadRawValue() thực hiện lấy dữ liệu thô.
  • Sensor_ConvertToTemperature() chuyển đổi dữ liệu.
  • Sensor_ReadTemperature() là function chính được cung cấp cho bên ngoài.

Ba function đầu tiên được khai báo static vì chúng chỉ phục vụ implementation của Sensor Module.

Quy tắc thực tế: Nếu một function chỉ được sử dụng trong một source file, hãy cân nhắc khai báo static để thể hiện rõ phạm vi sử dụng và tránh vô tình công bố function đó ra bên ngoài module.

3. Static Variable trong C

Từ khóa static không chỉ được sử dụng với function. Nó còn có thể được sử dụng với variable.

Khi khai báo variable, ý nghĩa của static phụ thuộc vào vị trí khai báo:

  • File scope: Variable có internal linkage và static storage duration.
  • Block scope: Variable có no linkage và static storage duration.

Một điểm quan trọng là static không có nghĩa là variable không thể thay đổi giá trị. Nó chủ yếu ảnh hưởng đến storage duration và linkage tùy theo vị trí khai báo.

3.1. Static Variable ở file scope

Khi khai báo variable với static bên ngoài function, variable đó có internal linkage. 

/* counter.c */

static unsigned int counter = 0U;

void Counter_Increment(void)
{
    counter++;
}

unsigned int Counter_GetValue(void)
{
    return counter;
}

Trong ví dụ trên:

  • counter được khai báo ở file scope.
  • Variable có static storage duration.
  • Variable có internal linkage.
  • Source file khác không thể tham chiếu trực tiếp đến counter bằng external linkage.
  • Các function trong cùng source file có thể sử dụng variable này.

Đây là một kỹ thuật phổ biến để giữ dữ liệu nội bộ của module.

3.2. Static Variable ở block scope

Khi khai báo static bên trong function hoặc một block, variable có static storage duration. Tuy nhiên, scope của variable vẫn chỉ nằm trong block chứa khai báo. 

#include <stdio.h>

void Counter_Increment(void)
{
    static unsigned int counter = 0U;

    counter++;

    printf("Counter = %u\n", counter);
}

int main(void)
{
    Counter_Increment();
    Counter_Increment();
    Counter_Increment();

    return 0;
}

Kết quả: 

Counter = 1
Counter = 2
Counter = 3

Khác với local variable thông thường, counter không được khởi tạo lại mỗi lần function được gọi. Nó giữ lại giá trị giữa các lần gọi function.

3.3. So sánh Local Variable và Static Local Variable

#include <stdio.h>

void NormalCounter(void)
{
    unsigned int count = 0U;

    count++;

    printf("Normal: %u\n", count);
}

void StaticCounter(void)
{
    static unsigned int count = 0U;

    count++;

    printf("Static: %u\n", count);
}

int main(void)
{
    NormalCounter();
    NormalCounter();

    StaticCounter();
    StaticCounter();

    return 0;
}

Kết quả: 

Normal: 1
Normal: 1
Static: 1
Static: 2

Giải thích:

  • NormalCounter() tạo local variable mới khi function được gọi.
  • count thông thường được khởi tạo lại bằng 0 mỗi lần gọi.
  • StaticCounter() sử dụng variable có static storage duration.
  • Giá trị của static local variable được duy trì giữa các lần gọi function.

3.4. Static Variable không đồng nghĩa với Constant

Một nhầm lẫn thường gặp là cho rằng variable khai báo với static sẽ không thể thay đổi giá trị. Điều này không đúng. 

static unsigned int system_state = 0U;

void System_Update(void)
{
    system_state = 1U;
}

Variable system_state vẫn có thể được cập nhật. Từ khóa static ở đây kiểm soát linkage và storage duration, không biến variable thành read-only.

Nếu muốn biểu diễn dữ liệu không được phép thay đổi thông qua identifier, chúng ta cần tìm hiểu thêm về từ khóa const.

4. Scope, Lifetime và Linkage

Để sử dụng static chính xác, chúng ta cần phân biệt ba khái niệm quan trọng trong C:

  • Scope: Phạm vi mà một identifier có thể được sử dụng trong source code.
  • Lifetime / Storage Duration: Khoảng thời gian object tồn tại trong quá trình thực thi.
  • Linkage: Quy định liệu các khai báo của cùng một identifier ở những phạm vi hoặc translation unit khác nhau có thể tham chiếu đến cùng một entity hay không.

4.1. Scope – Phạm vi sử dụng

Scope quyết định vị trí trong source code mà một identifier có thể được sử dụng.

Ví dụ: 

void Function(void)
{
    int local_value = 10;

    {
        int block_value = 20;

        local_value = block_value;
    }

    /* block_value không còn nằm trong scope tại đây */
}

Trong ví dụ trên:

  • local_value có block scope của function body.
  • block_value có block scope của block bên trong.
  • block_value không thể được sử dụng sau khi ra khỏi block khai báo.

4.2. Lifetime / Storage Duration

Storage duration quyết định thời gian tồn tại của object. Trong C, các nhóm thường gặp gồm:

Storage Duration Đặc điểm
Automatic Object thường tồn tại trong thời gian thực thi block chứa khai báo.
Static Object tồn tại trong toàn bộ thời gian thực thi chương trình.
Allocated Object tồn tại từ khi được cấp phát đến khi được giải phóng.
Thread Object tồn tại trong thời gian thực thi của thread tương ứng, khi chương trình sử dụng hỗ trợ thread storage duration.

4.3. Linkage

Linkage quyết định mối liên hệ giữa các khai báo identifier. C có ba loại linkage chính:

Loại Linkage Ý nghĩa
External Linkage Các khai báo phù hợp ở những translation unit khác nhau có thể tham chiếu đến cùng một entity.
Internal Linkage Identifier chỉ được liên kết trong cùng một translation unit.
No Linkage Identifier không có liên kết với các khai báo tương ứng khác.

4.4. Bảng tổng hợp một số trường hợp thường gặp

Khai báo Scope Storage Duration Linkage
Local variable thông thường Block Automatic No linkage
Static local variable Block Static No linkage
Global variable thông thường File Static External
Static global variable File Static Internal
Function thông thường File Không áp dụng như object variable External
Static function File Không áp dụng như object variable Internal

Bảng trên mô tả các trường hợp thông dụng trong C. Cần phân biệt rằng function không phải object variable, vì vậy không sử dụng khái niệm storage duration cho function theo cách áp dụng với variable.

Điểm cần ghi nhớ: Scope, Storage Duration và Linkage là ba khái niệm khác nhau. Một static local variable có block scope nhưng static storage duration và no linkage.

5. Global Variable trong C

Global Variable thường được hiểu là variable được khai báo bên ngoài các function, tại file scope. Những variable này có thể được sử dụng bởi nhiều function và trong một số trường hợp có thể được chia sẻ giữa nhiều module.

Global variable có thể hữu ích khi nhiều thành phần cần truy cập cùng một dữ liệu. Tuy nhiên, nếu sử dụng không kiểm soát, chúng có thể khiến kiến trúc chương trình trở nên khó bảo trì.

5.1. Khai báo Global Variable

Một global variable có thể được định nghĩa như sau: 

/* system.c */

unsigned int system_status = 0U;

void System_SetStatus(unsigned int status)
{
    system_status = status;
}

Variable system_status được khai báo ở file scope và có external linkage.

Một source file khác có thể tham chiếu đến variable này thông qua khai báo extern: 

/* main.c */

extern unsigned int system_status;

int main(void)
{
    system_status = 1U;

    return 0;
}

Từ khóa extern trong ví dụ trên khai báo rằng variable được định nghĩa ở một nơi khác. Nó không tạo thêm một definition mới cho variable.

5.2. Phân biệt Definition và Declaration

Khi làm việc với global variable, cần phân biệt:

  • Declaration: Giới thiệu identifier và kiểu dữ liệu của nó.
  • Definition: Tạo ra entity tương ứng; với object, definition thường dành chỗ lưu trữ cho object.

Ví dụ:

/* system.c */

/* Definition */
unsigned int system_status = 0U;
/* system.h */

/* Declaration */
extern unsigned int system_status;

Source file khác có thể include system.h để sử dụng variable đã được định nghĩa trong system.c.

5.3. Không định nghĩa cùng một Global Variable ở nhiều source file

Một lỗi thường gặp là vô tình định nghĩa cùng một global variable trong nhiều source file.

Ví dụ không nên làm:

/* module_a.c */

unsigned int system_status = 0U;
/* module_b.c */

unsigned int system_status = 0U;

Khi hai source file cùng được liên kết, linker có thể báo lỗi multiple definition vì tồn tại nhiều definition cho cùng một external symbol.

Cách tổ chức phù hợp hơn là chỉ định nghĩa variable tại một source file: 

/* system.c */

unsigned int system_status = 0U;

Sau đó khai báo extern trong header file: 

/* system.h */

#ifndef SYSTEM_H
#define SYSTEM_H

extern unsigned int system_status;

#endif

Các source file khác chỉ cần include system.h.

6. Những vấn đề khi sử dụng Global Variable

Global variable giúp chia sẻ dữ liệu giữa các function hoặc module. Tuy nhiên, việc sử dụng quá nhiều global variable có thể tạo ra những vấn đề đáng kể trong quá trình phát triển phần mềm.

6.1. Uncontrolled Access – Truy cập không kiểm soát

Nếu một global variable được công bố trong header file, nhiều module có thể đọc và thay đổi giá trị của nó. 

/* system.h */

extern unsigned int system_state;

Các source file khác có thể thay đổi trực tiếp: 

/* application.c */

#include "system.h"

void Application_Task(void)
{
    system_state = 1U;
}
/* communication.c */

#include "system.h"

void Communication_Task(void)
{
    system_state = 2U;
}

Lúc này, nhiều module cùng có quyền thay đổi system_state. Nếu chương trình hoạt động không đúng, việc xác định module nào đã thay đổi giá trị có thể trở nên khó khăn.

6.2. Hidden Dependency – Phụ thuộc ngầm

Khi nhiều module cùng sử dụng một global variable, dependency giữa chúng có thể không được thể hiện rõ qua function call.

Ví dụ: 

/* application.c */

extern unsigned int system_mode;

void Application_Task(void)
{
    if (system_mode == 1U)
    {
        /* Execute mode 1 */
    }
}
/* communication.c */

extern unsigned int system_mode;

void Communication_ProcessCommand(void)
{
    system_mode = 1U;
}

Application phụ thuộc vào giá trị do Communication thay đổi, nhưng mối quan hệ này không được thể hiện trực tiếp thông qua interface của hai module.

6.3. Difficult Debugging – Khó debug

Khi một global variable được sử dụng ở nhiều nơi, việc tìm nguyên nhân khiến giá trị thay đổi có thể mất nhiều thời gian.

Người phát triển cần kiểm tra:

  • Function nào đã cập nhật variable?
  • Module nào có quyền thay đổi variable?
  • Giá trị được thay đổi trong thời điểm nào?
  • Có function nào ghi đè giá trị trước đó không?
  • Có nhiều execution context cùng truy cập variable không?

6.4. Concurrency và Race Condition

Trong hệ thống Embedded có interrupt, RTOS task hoặc nhiều execution context, một global variable có thể được truy cập đồng thời từ nhiều nơi.

Nếu việc đọc và ghi dữ liệu không được tổ chức phù hợp, chương trình có thể gặp race condition hoặc nhận được trạng thái không nhất quán. 

/* Shared global variable */

unsigned int shared_counter = 0U;

void Task_A(void)
{
    shared_counter++;
}

void Task_B(void)
{
    shared_counter++;
}

Nếu hai task có thể thực hiện thao tác cập nhật đồng thời, việc tăng biến có thể không được thực hiện như mong đợi.

Lý do là phép tăng: 

shared_counter++;

thường bao gồm nhiều thao tác đọc, tính toán và ghi. Nếu các thao tác này bị xen kẽ giữa những execution context, kết quả có thể không chính xác.

Việc sử dụng volatile không tự động giải quyết race condition hoặc đảm bảo thao tác tăng biến là atomic. Những vấn đề về concurrency, synchronization và critical section sẽ được tìm hiểu sâu hơn ở Bài 43.

6.5. Khó thay đổi cấu trúc dữ liệu

Khi nhiều module truy cập trực tiếp vào một global variable, các module đó có thể phụ thuộc vào kiểu dữ liệu hoặc cách tổ chức dữ liệu cụ thể.

Nếu thay đổi cấu trúc dữ liệu, nhiều source file có thể phải sửa đổi theo. Điều này làm giảm khả năng thay đổi implementation độc lập.

Lưu ý: Global variable không phải lúc nào cũng sai. Vấn đề nằm ở việc sử dụng global variable không có quy tắc, không kiểm soát quyền cập nhật và khiến nhiều module phụ thuộc trực tiếp vào dữ liệu nội bộ của nhau.

7. Các kỹ thuật quản lý Global Variable

Trong nhiều trường hợp, chương trình vẫn cần chia sẻ dữ liệu giữa các function hoặc module. Thay vì loại bỏ hoàn toàn global variable, chúng ta có thể sử dụng những kỹ thuật phù hợp để quản lý quyền truy cập.

7.1. Giữ Global Variable ở phạm vi nội bộ bằng static

Nếu một variable chỉ phục vụ một module, chúng ta nên cân nhắc khai báo nó với static tại file scope. 

/* system.c */

#include "system.h"

static unsigned int system_state = 0U;

void System_SetState(unsigned int state)
{
    system_state = state;
}

unsigned int System_GetState(void)
{
    return system_state;
}

Trong ví dụ này:

  • system_state không được công bố trực tiếp cho module khác.
  • System_SetState() cho phép cập nhật trạng thái.
  • System_GetState() cho phép đọc trạng thái.
  • Module khác chỉ có thể truy cập dữ liệu thông qua các function được cung cấp.

7.2. Sử dụng Getter và Setter Function

Getter và Setter là những function được sử dụng để đọc và cập nhật dữ liệu thông qua một interface xác định.

Ví dụ:

/* system.h */

#ifndef SYSTEM_H
#define SYSTEM_H

void System_SetMode(unsigned int mode);
unsigned int System_GetMode(void);

#endif
/* system.c */

#include "system.h"

static unsigned int system_mode = 0U;

void System_SetMode(unsigned int mode)
{
    if (mode <= 2U)
    {
        system_mode = mode;
    }
}

unsigned int System_GetMode(void)
{
    return system_mode;
}

Application sử dụng: 

/* main.c */

#include "system.h"

int main(void)
{
    System_SetMode(1U);

    if (System_GetMode() == 1U)
    {
        /* Execute mode 1 */
    }

    return 0;
}

Thay vì cho phép Application thay đổi trực tiếp system_mode, module cung cấp function để kiểm soát việc cập nhật.

Ví dụ trên còn cho phép module kiểm tra giá trị đầu vào trước khi cập nhật trạng thái.

7.3. Chỉ công bố Global Variable khi thực sự cần thiết

Nếu nhiều module thực sự cần truy cập một dữ liệu dùng chung, có thể sử dụng global variable với extern. Tuy nhiên, cần giới hạn số lượng module có quyền ghi dữ liệu.

Ví dụ: 

/* system.h */

#ifndef SYSTEM_H
#define SYSTEM_H

extern unsigned int system_status;

#endif
/* system.c */

#include "system.h"

unsigned int system_status = 0U;

Trong cách tổ chức này, chúng ta cần có quy ước rõ ràng về:

  • Module nào chịu trách nhiệm cập nhật variable.
  • Module nào chỉ được phép đọc variable.
  • Những thời điểm được phép thay đổi dữ liệu.
  • Cách đồng bộ nếu có nhiều execution context cùng truy cập.

Tuy nhiên, nếu không có yêu cầu đặc biệt, việc cung cấp function để đọc và cập nhật dữ liệu thường giúp kiểm soát interface tốt hơn.

7.4. Sử dụng Pointer để cung cấp quyền truy cập có kiểm soát

Trong một số thiết kế, module có thể cung cấp pointer đến dữ liệu hoặc nhận pointer từ module khác. Tuy nhiên, cần xác định rõ quyền đọc và ghi đối với vùng nhớ đó. 

/* sensor.h */

#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

void Sensor_GetData(uint16_t *data);

#endif
/* sensor.c */

#include "sensor.h"

static uint16_t sensor_data = 0U;

void Sensor_GetData(uint16_t *data)
{
    if (data != 0)
    {
        *data = sensor_data;
    }
}

Trong ví dụ này, module không trả về địa chỉ của biến nội bộ. Thay vào đó, nó sao chép dữ liệu vào vùng nhớ do bên gọi cung cấp.

Cách làm này giúp module kiểm soát tốt hơn dữ liệu nội bộ và tránh việc bên ngoài trực tiếp thay đổi vùng nhớ của module.

8. Kết hợp Encapsulation và Static trong một Embedded Module

Để tổng hợp kiến thức, chúng ta sẽ xây dựng một module quản lý trạng thái hệ thống đơn giản.

Yêu cầu:

  • Module quản lý trạng thái hoạt động của hệ thống.
  • Trạng thái được lưu trong một variable nội bộ.
  • Application có thể đọc và cập nhật trạng thái thông qua interface.
  • Giá trị trạng thái phải được kiểm tra trước khi cập nhật.
  • Các function hỗ trợ nội bộ không được công bố cho module khác.

8.1. Định nghĩa Interface

/* system_manager.h */

#ifndef SYSTEM_MANAGER_H
#define SYSTEM_MANAGER_H

typedef enum
{
    SYSTEM_STATE_IDLE,
    SYSTEM_STATE_RUNNING,
    SYSTEM_STATE_ERROR
} System_StateType;

void SystemManager_Init(void);

void SystemManager_SetState(
    System_StateType state
);

System_StateType SystemManager_GetState(void);

#endif

Header file công bố:

  • System_StateType: Kiểu dữ liệu biểu diễn trạng thái hệ thống.
  • SystemManager_Init(): Khởi tạo module.
  • SystemManager_SetState(): Cập nhật trạng thái.
  • SystemManager_GetState(): Đọc trạng thái hiện tại.

8.2. Triển khai Implementation

/* system_manager.c */

#include "system_manager.h"

static System_StateType system_state =
    SYSTEM_STATE_IDLE;

static unsigned char SystemManager_IsValidState(
    System_StateType state
)
{
    if ((state == SYSTEM_STATE_IDLE) ||
        (state == SYSTEM_STATE_RUNNING) ||
        (state == SYSTEM_STATE_ERROR))
    {
        return 1U;
    }

    return 0U;
}

void SystemManager_Init(void)
{
    system_state = SYSTEM_STATE_IDLE;
}

void SystemManager_SetState(
    System_StateType state
)
{
    if (SystemManager_IsValidState(state) != 0U)
    {
        system_state = state;
    }
}

System_StateType SystemManager_GetState(void)
{
    return system_state;
}

Trong implementation:

  • system_state là static variable ở file scope.
  • SystemManager_IsValidState() là static function nội bộ.
  • Chỉ những function được khai báo trong header file mới là interface chính thức.
  • Module chịu trách nhiệm kiểm tra giá trị trước khi cập nhật trạng thái.

8.3. Application sử dụng module

/* main.c */

#include "system_manager.h"

int main(void)
{
    System_StateType current_state;

    SystemManager_Init();

    SystemManager_SetState(SYSTEM_STATE_RUNNING);

    current_state = SystemManager_GetState();

    if (current_state == SYSTEM_STATE_RUNNING)
    {
        /* Execute application */
    }

    return 0;
}

Application chỉ sử dụng interface được cung cấp. Nó không cần biết:

  • Variable trạng thái được lưu như thế nào.
  • Function kiểm tra trạng thái hoạt động ra sao.
  • Những bước xử lý nội bộ trước khi cập nhật dữ liệu.

Nhờ đó, System Manager có thể thay đổi implementation mà không cần thay đổi Application nếu interface và hành vi được công bố vẫn giữ nguyên.

8.4. Sơ đồ tổ chức module

+-----------------------------+
|         Application         |
|                             |
|   main.c                    |
|                             |
|   SystemManager_Init()      |
|   SystemManager_SetState()  |
|   SystemManager_GetState()  |
+--------------+--------------+
               |
               | Include system_manager.h
               v
+-----------------------------+
|       System Manager        |
|                             |
|  Public Interface:          |
|    - Init                   |
|    - SetState               |
|    - GetState               |
|                             |
|  Internal Implementation:  |
|    - system_state           |
|    - IsValidState()         |
+-----------------------------+

Đây là ví dụ điển hình của việc kết hợp Encapsulation, Static Function và Static Variable trong một module C.

9. Một số lưu ý khi sử dụng static và Global Variable trong Embedded C

Trong hệ thống Embedded, việc lựa chọn phạm vi và thời gian tồn tại của dữ liệu có thể ảnh hưởng đến khả năng bảo trì, kiểm thử và hoạt động của chương trình.

9.1. Không sử dụng static chỉ vì muốn giữ giá trị

Static local variable có thể hữu ích khi function cần lưu trạng thái giữa các lần gọi. Tuy nhiên, nếu sử dụng quá nhiều, trạng thái của chương trình có thể trở nên khó theo dõi. 

void Sensor_Process(void)
{
    static unsigned int sample_count = 0U;

    sample_count++;

    /* Process sensor data */
}

Khi sử dụng static local variable, cần xác định rõ:

  • Variable có thực sự cần giữ giá trị giữa các lần gọi không?
  • Có cần reset variable khi module được khởi tạo lại không?
  • Function có được gọi từ nhiều execution context không?
  • Việc giữ trạng thái bên trong function có làm code khó kiểm thử không?

9.2. Không nhầm static với volatile

Hai từ khóa static và volatile giải quyết những vấn đề khác nhau.

Keyword Vai trò chính
static Kiểm soát linkage hoặc storage duration tùy theo vị trí khai báo.
volatile Thông báo cho compiler rằng việc truy cập object cần tuân theo các quy tắc volatile access của ngôn ngữ.

Ví dụ: 

static volatile unsigned int system_flag = 0U;

Trong trường hợp này:

  • static giúp giới hạn linkage nếu variable được khai báo ở file scope.
  • volatile thể hiện rằng các lần truy cập variable có ý nghĩa volatile đối với compiler.

Tuy nhiên, volatile không tự đảm bảo atomicity, thread safety hoặc synchronization.

9.3. Cẩn thận với dữ liệu được chia sẻ giữa ISR và Main Loop

Trong một hệ thống không sử dụng RTOS, dữ liệu có thể được chia sẻ giữa Interrupt Service Routine và main loop.

Ví dụ minh họa: 

static volatile unsigned int event_flag = 0U;

void Timer_ISR(void)
{
    event_flag = 1U;
}

int main(void)
{
    while (1)
    {
        if (event_flag != 0U)
        {
            event_flag = 0U;

            /* Process timer event */
        }
    }
}

Ví dụ trên minh họa một cách sử dụng flag để thông báo sự kiện từ ISR đến main loop. Trong hệ thống thực tế, cần kiểm tra thêm kích thước dữ liệu, tính atomic của thao tác đọc/ghi, quy tắc của compiler và kiến trúc MCU.

Việc khai báo volatile không đảm bảo rằng chuỗi thao tác đọc rồi xóa flag luôn an toàn trước mọi tình huống interrupt. Nếu cần bảo vệ một thao tác không thể bị xen ngang, cần sử dụng cơ chế đồng bộ phù hợp với hệ thống.

9.4. Hạn chế sử dụng quá nhiều Global State

Một hệ thống có quá nhiều global variable để lưu trạng thái của từng module sẽ khiến việc theo dõi luồng dữ liệu trở nên khó khăn.

Thay vì để nhiều module cùng thay đổi một biến trạng thái, nên xác định module chịu trách nhiệm quản lý dữ liệu và cung cấp interface phù hợp cho các thành phần khác.

9.5. Tuân thủ coding convention của dự án

Trong các dự án Embedded lớn, cách đặt tên và quản lý phạm vi của function, variable thường được quy định trong coding convention.

Ví dụ: 

/* Public function */
void Sensor_Init(void);

/* Internal function */
static void Sensor_ResetHardware(void);

/* Internal file-scope variable */
static unsigned int sensor_state = 0U;

/* Static local variable */
void Sensor_Update(void)
{
    static unsigned int update_count = 0U;
}

Việc thống nhất cách đặt tên giúp người đọc nhận biết vai trò và phạm vi của các thành phần trong module dễ dàng hơn.

10. Checklist khi sử dụng Encapsulation, static và Global Variable

Khi thiết kế hoặc review một module C, chúng ta có thể sử dụng checklist sau:

  • Module có phân biệt rõ public interface và internal implementation không?
  • Những function chỉ được sử dụng nội bộ có được khai báo static không?
  • Những variable chỉ phục vụ một module có được giới hạn bằng internal linkage không?
  • Có variable nào đang được công bố ra bên ngoài nhưng không thực sự cần thiết không?
  • Global variable có được định nghĩa tại đúng một source file không?
  • Các declaration sử dụng extern có được tổ chức thống nhất trong header file không?
  • Có nhiều module cùng thay đổi một global variable không?
  • Có thể thay thế việc truy cập trực tiếp bằng Getter và Setter function không?
  • Static local variable có thực sự cần giữ giá trị giữa các lần gọi không?
  • Đã phân biệt rõ scope, storage duration và linkage chưa?
  • Dữ liệu chia sẻ giữa ISR, task hoặc main loop có được bảo vệ phù hợp không?
  • Việc sử dụng volatile có đúng mục đích và không bị nhầm với atomic operation không?
Góc nhìn Automotive Embedded Software: Trong một ECU có nhiều SWC, BSW module và driver, việc giới hạn quyền truy cập vào dữ liệu nội bộ giúp giảm dependency giữa các thành phần. Những trạng thái quan trọng nên được quản lý bởi module chịu trách nhiệm, thay vì cho phép nhiều thành phần tùy ý thay đổi trực tiếp.

11. Tổng kết

Trong bài học này, chúng ta đã tìm hiểu cách sử dụng Encapsulation, từ khóa static và các kỹ thuật quản lý Global Variable trong C.

  • Encapsulation: Tổ chức dữ liệu và function trong module, đồng thời kiểm soát cách truy cập.
  • Static Function: Function có internal linkage, chỉ được sử dụng trong translation unit tương ứng.
  • Static File-scope Variable: Variable có static storage duration và internal linkage.
  • Static Local Variable: Variable có block scope, static storage duration và giữ giá trị giữa các lần gọi function.
  • Scope: Phạm vi source code mà identifier có thể được sử dụng.
  • Storage Duration: Khoảng thời gian object tồn tại trong chương trình.
  • Linkage: Quy định mối liên hệ giữa các khai báo identifier.
  • Global Variable: Có thể được chia sẻ giữa các module nhưng cần kiểm soát quyền truy cập và cập nhật.
  • Getter và Setter: Cung cấp cách đọc và cập nhật dữ liệu thông qua interface.
  • Concurrency: Cần chú ý synchronization khi dữ liệu được chia sẻ giữa nhiều execution context.

Có thể ghi nhớ nguyên tắc cốt lõi của bài học:

Chỉ công bố những function và dữ liệu mà module khác thực sự cần sử dụng. Những thành phần phục vụ nội bộ nên được giữ trong phạm vi module, đồng thời hạn chế việc chia sẻ và cập nhật Global Variable không kiểm soát.
