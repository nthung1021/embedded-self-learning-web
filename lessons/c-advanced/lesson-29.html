Bài 29: Modular Programming – Interface vs Implementation

Trong các bài trước, chúng ta đã tìm hiểu cách tổ chức chương trình C thành nhiều source file, biên dịch từng file riêng biệt và liên kết các object file để tạo thành chương trình hoàn chỉnh.

Khi một dự án chỉ có một vài source file, việc tổ chức code có thể tương đối đơn giản. Tuy nhiên, khi dự án phát triển với nhiều chức năng, peripheral và module khác nhau, chúng ta cần một cách tổ chức rõ ràng hơn để kiểm soát sự phụ thuộc giữa các thành phần.

Đây là lúc Modular Programming trở nên quan trọng. Thay vì viết toàn bộ chức năng trong một hoặc một vài file lớn, chúng ta chia chương trình thành các module có nhiệm vụ riêng biệt. Mỗi module cung cấp một giao diện để những thành phần khác có thể sử dụng, đồng thời giữ phần triển khai bên trong module.

Hai khái niệm quan trọng trong cách tổ chức này là:

  • Interface: Phần giao diện mô tả những gì module cung cấp và cách sử dụng module.
  • Implementation: Phần triển khai chứa logic thực tế để thực hiện các chức năng đó.

Trong C, chúng ta thường sử dụng header file (.h) để khai báo interface và source file (.c) để triển khai implementation.

Mục tiêu bài học:
  • Hiểu khái niệm Modular Programming và vai trò của module trong dự án C.
  • Phân biệt Interface và Implementation.
  • Biết cách tổ chức header file và source file cho một module.
  • Hiểu vai trò của public declarations và internal definitions.
  • Biết cách thiết kế API đơn giản cho một module Embedded.
  • Hiểu High Cohesion và Low Coupling trong thiết kế module.
  • Biết cách quản lý dependency giữa các module.

1. Tổng quan về Modular Programming

Modular Programming là phương pháp thiết kế phần mềm bằng cách chia một chương trình lớn thành nhiều thành phần nhỏ hơn, được gọi là module.

Mỗi module thường chịu trách nhiệm cho một nhóm chức năng cụ thể. Các module có thể hoạt động tương đối độc lập và giao tiếp với nhau thông qua những interface đã được định nghĩa.

Ví dụ, trong một ứng dụng Embedded có chức năng đọc cảm biến và điều khiển LED, chúng ta có thể chia chương trình thành: 

Application
    |
    +-- Sensor Module
    |       |
    |       +-- Đọc dữ liệu cảm biến
    |       +-- Kiểm tra trạng thái cảm biến
    |
    +-- LED Module
    |       |
    |       +-- Bật LED
    |       +-- Tắt LED
    |       +-- Đảo trạng thái LED
    |
    +-- GPIO Driver
            |
            +-- Cấu hình GPIO
            +-- Đọc và ghi GPIO

Trong cấu trúc trên:

  • Application chịu trách nhiệm điều phối hoạt động của chương trình.
  • Sensor Module quản lý các chức năng liên quan đến cảm biến.
  • LED Module quản lý logic điều khiển LED.
  • GPIO Driver cung cấp các thao tác ở mức phần cứng.

Thay vì để Application trực tiếp xử lý toàn bộ thao tác GPIO, chúng ta có thể yêu cầu LED Module thực hiện thông qua một interface. Application chỉ cần quan tâm đến chức năng cần sử dụng, không cần biết chi tiết phần cứng được điều khiển như thế nào.

1.1. Tại sao cần Modular Programming?

Khi không tổ chức code theo module, một chương trình có thể dần trở thành một tập hợp các function và biến nằm rải rác trong nhiều file. Các thành phần có thể phụ thuộc trực tiếp vào nhau và khó thay đổi độc lập.

Modular Programming giúp giải quyết những vấn đề này:

Vấn đề Vai trò của Modular Programming
Source file quá lớn Chia chương trình thành các module có nhiệm vụ rõ ràng.
Khó tìm kiếm và bảo trì code Các chức năng liên quan được tổ chức trong cùng module.
Code bị phụ thuộc quá nhiều Module giao tiếp thông qua interface thay vì truy cập trực tiếp implementation.
Khó tái sử dụng chức năng Module có thể được sử dụng lại trong những phần khác của dự án.
Khó kiểm thử riêng lẻ Module có thể được kiểm thử độc lập thông qua interface của nó.
Nhiều người cùng phát triển Các thành viên có thể làm việc trên những module khác nhau.

1.2. Một module thường bao gồm những gì?

Trong C, một module thông thường có thể được tổ chức thành ít nhất hai file: 

led/
    |
    +-- led.h
    |
    +-- led.c

Trong đó:

  • led.h: Khai báo các function, type, constant mà module cung cấp cho bên ngoài.
  • led.c: Chứa phần định nghĩa function và logic triển khai của module.

Một module lớn hơn có thể có thêm các file nội bộ, file cấu hình hoặc file chứa dữ liệu riêng. Tuy nhiên, nguyên tắc cơ bản vẫn là phân biệt rõ phần giao diện và phần triển khai.

2. Interface và Implementation

Trong thiết kế module, Interface và Implementation là hai phần có vai trò khác nhau nhưng liên kết chặt chẽ với nhau.

2.1. Interface là gì?

Interface là giao diện mà một module cung cấp để những thành phần khác có thể sử dụng chức năng của nó.

Interface trả lời câu hỏi:

Module này cung cấp những chức năng gì và tôi cần gọi chúng như thế nào?

Trong C, interface thường được thể hiện thông qua các khai báo trong header file. 

/* led.h */

#ifndef LED_H
#define LED_H

void LED_Init(void);
void LED_On(void);
void LED_Off(void);
void LED_Toggle(void);

#endif

Header file trên khai báo bốn function mà LED Module cung cấp:

  • LED_Init(): Khởi tạo LED.
  • LED_On(): Bật LED.
  • LED_Off(): Tắt LED.
  • LED_Toggle(): Đảo trạng thái LED.

Khi sử dụng module này, Application chỉ cần biết những khai báo trên. Application không cần biết các function được triển khai bằng cách nào.

2.2. Implementation là gì?

Implementation là phần triển khai thực tế của module. Nó chứa code thực hiện những chức năng đã được công bố trong interface.

Trong C, implementation thường được đặt trong source file tương ứng. 

/* led.c */

#include "led.h"

void LED_Init(void)
{
    /* Configure LED GPIO */
}

void LED_On(void)
{
    /* Set LED GPIO to active level */
}

void LED_Off(void)
{
    /* Set LED GPIO to inactive level */
}

void LED_Toggle(void)
{
    /* Toggle LED GPIO state */
}

Ví dụ trên sử dụng comment để minh họa vị trí triển khai logic. Trong chương trình thực tế, các function sẽ gọi GPIO Driver hoặc truy cập lớp phần cứng phù hợp để điều khiển LED.

2.3. So sánh Interface và Implementation

Tiêu chí Interface Implementation
Mục đích Công bố cách sử dụng module. Thực hiện chức năng của module.
Vị trí thường gặp Header file .h. Source file .c.
Nội dung Function prototype, type, constant, macro cần thiết. Function definition và logic xử lý.
Đối tượng sử dụng Các module khác cần sử dụng chức năng. Compiler và module đang triển khai.
Mức độ chi tiết Chỉ cung cấp thông tin cần thiết để sử dụng. Chứa chi tiết thực hiện bên trong.
Thay đổi Cần thận trọng vì có thể ảnh hưởng đến các module sử dụng. Có thể thay đổi nội bộ nếu không làm thay đổi hành vi interface.

2.4. Vì sao cần tách Interface và Implementation?

Giả sử Application muốn bật một LED. Nếu Application trực tiếp thao tác với các thanh ghi GPIO, nó sẽ phải biết nhiều chi tiết phần cứng như:

  • Địa chỉ thanh ghi GPIO.
  • Bit cấu hình chế độ Input hoặc Output.
  • Bit điều khiển mức logic của chân GPIO.
  • Chân GPIO nào được kết nối với LED.
  • LED sử dụng mức Active-High hay Active-Low.

Nếu những chi tiết này được đặt trực tiếp trong Application, việc thay đổi phần cứng có thể khiến Application phải sửa đổi theo.

Ngược lại, nếu Application chỉ sử dụng: 

LED_On();
LED_Off();

thì phần triển khai bên trong LED Module có thể thay đổi mà Application không cần quan tâm, miễn là interface vẫn giữ nguyên và hành vi của function không thay đổi.

Nguyên tắc quan trọng: Thành phần sử dụng module nên phụ thuộc vào interface mà module công bố, thay vì phụ thuộc vào các chi tiết triển khai bên trong module.

3. Header File và Source File trong thiết kế module

Trong ngôn ngữ C, header file và source file thường được sử dụng để tổ chức interface và implementation. Việc phân chia hợp lý giúp các module giao tiếp với nhau mà không cần đưa toàn bộ code triển khai vào nơi sử dụng.

3.1. Header File – Khai báo giao diện

Header file thường chứa những thành phần cần thiết để module khác có thể sử dụng chức năng được cung cấp.

Ví dụ:

/* sensor.h */

#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

typedef enum
{
    SENSOR_STATUS_OK,
    SENSOR_STATUS_ERROR
} Sensor_StatusType;

void Sensor_Init(void);

Sensor_StatusType Sensor_ReadTemperature(
    uint16_t *temperature
);

#endif

Header file trên cung cấp:

  • Sensor_StatusType: Kiểu dữ liệu biểu diễn trạng thái hoạt động.
  • Sensor_Init(): Function khởi tạo sensor.
  • Sensor_ReadTemperature(): Function đọc giá trị nhiệt độ.

Các module khác chỉ cần include sensor.h để sử dụng những thành phần được khai báo.

3.2. Source File – Triển khai chức năng

Source file chứa phần định nghĩa các function đã được khai báo trong header file. 

/* sensor.c */

#include "sensor.h"

void Sensor_Init(void)
{
    /* Initialize sensor hardware */
}

Sensor_StatusType Sensor_ReadTemperature(
    uint16_t *temperature
)
{
    if (temperature == 0U)
    {
        return SENSOR_STATUS_ERROR;
    }

    /* Read temperature from sensor */

    *temperature = 25U;

    return SENSOR_STATUS_OK;
}

Trong ví dụ này, Application không cần biết cách đọc dữ liệu từ cảm biến được thực hiện như thế nào. Nó chỉ cần gọi function và kiểm tra kết quả trả về.

3.3. Application sử dụng module thông qua header file

Một source file khác có thể sử dụng Sensor Module bằng cách include header file của module. 

/* main.c */

#include <stdio.h>
#include "sensor.h"

int main(void)
{
    uint16_t temperature = 0U;

    Sensor_Init();

    if (Sensor_ReadTemperature(&temperature) == SENSOR_STATUS_OK)
    {
        printf("Temperature: %u\n", temperature);
    }

    return 0;
}

Application chỉ sử dụng những function và type đã được công bố trong sensor.h. Nó không cần include hoặc truy cập trực tiếp vào các chi tiết triển khai bên trong sensor.c.

3.4. Cấu trúc thư mục của một module

Trong một dự án có nhiều module, chúng ta có thể tổ chức thư mục như sau: 

Embedded_Project/
|
+-- Application/
|   |
|   +-- main.c
|
+-- Drivers/
|   |
|   +-- GPIO/
|   |   |
|   |   +-- gpio.h
|   |   +-- gpio.c
|   |
|   +-- UART/
|       |
|       +-- uart.h
|       +-- uart.c
|
+-- Modules/
|   |
|   +-- LED/
|   |   |
|   |   +-- led.h
|   |   +-- led.c
|   |
|   +-- Sensor/
|       |
|       +-- sensor.h
|       +-- sensor.c
|
+-- Config/
    |
    +-- project_config.h

Trong cấu trúc này:

  • Application: Chứa logic điều phối chương trình.
  • Drivers: Chứa các thành phần giao tiếp trực tiếp với phần cứng.
  • Modules: Chứa các module cung cấp chức năng ở mức cao hơn.
  • Config: Chứa các thông tin cấu hình dùng chung của dự án.

Cách tổ chức thư mục cụ thể có thể khác nhau tùy theo kiến trúc dự án. Điều quan trọng là mỗi module cần có phạm vi trách nhiệm rõ ràng và cách giao tiếp được xác định.

Lưu ý: Việc đặt file .h và .c trong cùng một thư mục không phải yêu cầu bắt buộc của C. Đây là quy ước tổ chức source code giúp người phát triển dễ quản lý interface và implementation của từng module.

4. Public Interface và Internal Implementation

Không phải tất cả function, type hoặc dữ liệu trong một module đều cần được cung cấp cho các module khác.

Một thiết kế module tốt chỉ nên công bố những thành phần thực sự cần thiết. Các chi tiết phục vụ triển khai nội bộ nên được giữ bên trong module.

4.1. Public Interface

Public Interface là tập hợp những khai báo mà module cho phép các thành phần bên ngoài sử dụng.

Ví dụ, một LED Module có thể chỉ công bố các function: 

/* led.h */

#ifndef LED_H
#define LED_H

void LED_Init(void);
void LED_On(void);
void LED_Off(void);

#endif

Những function này là các điểm giao tiếp chính thức giữa LED Module và những thành phần sử dụng nó.

Application không cần biết module có sử dụng một function nội bộ để kiểm tra trạng thái GPIO hay không.

4.2. Internal Implementation

Internal Implementation là những thành phần chỉ phục vụ quá trình thực hiện chức năng bên trong module.

Ví dụ, trong led.c, module có thể chứa những function phục vụ xử lý nội bộ: 

/* led.c */

#include "led.h"

static void LED_SetPinHigh(void)
{
    /* Set GPIO output to HIGH */
}

static void LED_SetPinLow(void)
{
    /* Set GPIO output to LOW */
}

void LED_Init(void)
{
    /* Configure GPIO */
}

void LED_On(void)
{
    LED_SetPinHigh();
}

void LED_Off(void)
{
    LED_SetPinLow();
}

Trong ví dụ trên:

  • LED_Init(), LED_On() và LED_Off() là các function được công bố.
  • LED_SetPinHigh() và LED_SetPinLow() phục vụ triển khai bên trong module.
  • Application chỉ cần biết các function được khai báo trong led.h.

Từ khóa static được sử dụng để giới hạn phạm vi liên kết của hai function nội bộ trong source file. Nội dung về static, encapsulation và quản lý global variable sẽ được tìm hiểu sâu hơn ở Bài 30.

4.3. Vì sao không nên công bố mọi thứ?

Nếu một module công bố quá nhiều function, biến và cấu trúc dữ liệu, các module khác có thể bắt đầu phụ thuộc vào những chi tiết vốn chỉ nên tồn tại bên trong implementation.

Điều này tạo ra một số vấn đề:

  • Khó thay đổi cách triển khai mà không ảnh hưởng đến module khác.
  • Các thành phần bên ngoài có thể sử dụng những function không nên được gọi trực tiếp.
  • Interface trở nên phức tạp và khó hiểu.
  • Việc bảo trì và kiểm soát dependency trở nên khó khăn hơn.

Vì vậy, khi thiết kế interface, chúng ta nên đặt câu hỏi:

Thành phần bên ngoài thực sự cần biết những gì để sử dụng module này?

5. High Cohesion và Low Coupling

Khi chia chương trình thành các module, chỉ việc tạo nhiều file chưa đủ để đảm bảo kiến trúc phần mềm tốt. Chúng ta còn cần quan tâm đến cách tổ chức trách nhiệm và mức độ phụ thuộc giữa các module.

Hai nguyên tắc thường được sử dụng trong thiết kế module là:

  • High Cohesion: Mỗi module nên tập trung vào một nhóm chức năng có liên quan chặt chẽ.
  • Low Coupling: Các module nên hạn chế sự phụ thuộc trực tiếp vào chi tiết của nhau.

5.1. High Cohesion – Tính gắn kết cao

Cohesion thể hiện mức độ liên quan giữa các chức năng bên trong cùng một module.

Một module có High Cohesion thường có trách nhiệm rõ ràng, và các function bên trong đều phục vụ cho trách nhiệm đó.

Ví dụ về một LED Module có trách nhiệm rõ ràng:

LED Module
    |
    +-- LED_Init()
    +-- LED_On()
    +-- LED_Off()
    +-- LED_Toggle()
    +-- LED_SetBrightness()

Những function trên đều liên quan đến việc điều khiển LED, vì vậy chúng có thể được tổ chức trong cùng một module.

Ngược lại, nếu LED Module còn chứa những chức năng không liên quan: 

LED Module
    |
    +-- LED_On()
    +-- LED_Off()
    +-- UART_SendData()
    +-- CAN_ReceiveMessage()
    +-- Sensor_ReadTemperature()

thì module đã có quá nhiều trách nhiệm khác nhau. Điều này khiến việc hiểu, kiểm thử và bảo trì module trở nên khó khăn.

5.2. Low Coupling – Mức độ phụ thuộc thấp

Coupling thể hiện mức độ phụ thuộc giữa các module. Khi hai module có coupling cao, việc thay đổi một module có thể khiến module còn lại phải thay đổi theo.

Ví dụ, nếu Application trực tiếp truy cập các thanh ghi GPIO: 

/* main.c */

#define GPIO_PORT_REG   (*(volatile unsigned int *)0x40020000U)

int main(void)
{
    GPIO_PORT_REG |= (1U << 5U);

    while (1)
    {
        /* Main loop */
    }
}

Application đang phụ thuộc trực tiếp vào:

  • Địa chỉ thanh ghi phần cứng.
  • Cách cấu hình GPIO.
  • Vị trí bit điều khiển LED.

Nếu chuyển LED sang một chân GPIO khác hoặc thay đổi MCU, Application có thể cần sửa đổi.

Một cách tổ chức khác là để Application sử dụng LED Module: 

/* main.c */

#include "led.h"

int main(void)
{
    LED_Init();

    while (1)
    {
        LED_On();

        /* Other application tasks */
    }

    return 0;
}

Lúc này, Application chỉ phụ thuộc vào interface của LED Module. Những thay đổi liên quan đến cách truy cập GPIO có thể được xử lý bên trong module hoặc driver tương ứng.

5.3. So sánh High Cohesion và Low Coupling

Khái niệm Phạm vi quan tâm Mục tiêu
High Cohesion Bên trong một module Các chức năng trong module có liên quan chặt chẽ với nhau.
Low Coupling Giữa các module Giảm sự phụ thuộc trực tiếp giữa các module.

Có thể ghi nhớ đơn giản:

High Cohesion: Những gì thuộc về cùng một trách nhiệm nên được tổ chức cùng nhau.
Low Coupling: Những module khác nhau nên giao tiếp thông qua interface rõ ràng thay vì phụ thuộc vào chi tiết nội bộ của nhau.
Góc nhìn Embedded: High Cohesion và Low Coupling đặc biệt hữu ích trong dự án có nhiều peripheral và driver như GPIO, UART, SPI, I2C, CAN. Mỗi module nên có nhiệm vụ cụ thể và cung cấp interface phù hợp để Application hoặc module khác sử dụng.

6. Dependency giữa các module

Trong một dự án C, các module thường cần sử dụng chức năng của nhau. Mối quan hệ này được gọi là Dependency.

Ví dụ, Application cần sử dụng LED Module để điều khiển LED, trong khi LED Module cần sử dụng GPIO Driver để thao tác phần cứng.

6.1. Ví dụ về dependency trong Embedded Project

Application
     |
     | uses
     v
 LED Module
     |
     | uses
     v
 GPIO Driver
     |
     | accesses
     v
 MCU Hardware

Luồng phụ thuộc này thể hiện:

  • Application sử dụng các chức năng được cung cấp bởi LED Module.
  • LED Module sử dụng GPIO Driver để điều khiển chân GPIO.
  • GPIO Driver thực hiện thao tác với phần cứng MCU.

Nhờ phân chia theo từng lớp, Application không cần trực tiếp xử lý các chi tiết thanh ghi GPIO.

6.2. Dependency thông qua header file

Trong C, một module thường thể hiện dependency bằng cách include header file của module khác.

Ví dụ:

/* led.c */

#include "led.h"
#include "gpio.h"

void LED_Init(void)
{
    GPIO_InitOutput(5U);
}

void LED_On(void)
{
    GPIO_WritePin(5U, 1U);
}

void LED_Off(void)
{
    GPIO_WritePin(5U, 0U);
}

Trong trường hợp này:

  • led.c include led.h để có các khai báo của chính module.
  • led.c include gpio.h để sử dụng các function của GPIO Driver.
  • LED Module không cần biết toàn bộ chi tiết triển khai của GPIO Driver.

6.3. Hạn chế dependency không cần thiết

Một lỗi thiết kế thường gặp là để một module include quá nhiều header file, kể cả những header không thực sự cần thiết.

Ví dụ: 

/* application.c */

#include "led.h"
#include "gpio.h"
#include "uart.h"
#include "can.h"
#include "sensor.h"
#include "memory.h"
#include "timer.h"

Nếu Application chỉ cần điều khiển LED, việc include tất cả các header trên có thể tạo ra dependency không cần thiết.

Thay vào đó, chỉ nên include những interface mà source file thực sự sử dụng: 

/* application.c */

#include "led.h"

void Application_Init(void)
{
    LED_Init();
}

Việc giảm dependency không cần thiết giúp:

  • Giảm sự phụ thuộc giữa các thành phần.
  • Hạn chế lỗi phát sinh khi thay đổi header file.
  • Giúp source file dễ đọc và dễ bảo trì hơn.
  • Giảm nguy cơ tạo ra dependency vòng giữa các module.

6.4. Circular Dependency – Phụ thuộc vòng

Circular Dependency xảy ra khi hai hoặc nhiều module phụ thuộc lẫn nhau theo một vòng khép kín.

Ví dụ:

Module A
    |
    | depends on
    v
Module B
    |
    | depends on
    v
Module A

Trong C, một tình huống tương tự có thể xuất hiện khi:

  • module_a.h include module_b.h.
  • module_b.h lại include module_a.h.

Header guard có thể ngăn việc include lặp lại gây ra một số lỗi trong quá trình preprocessing, nhưng không tự động giải quyết vấn đề thiết kế dependency vòng.

Một cách xử lý là xem xét lại trách nhiệm của từng module, chuyển phần giao tiếp chung sang một header riêng, hoặc sử dụng forward declaration khi phù hợp. 

/* common_types.h */

#ifndef COMMON_TYPES_H
#define COMMON_TYPES_H

typedef unsigned int Module_IdType;

#endif

Những module cần sử dụng kiểu dữ liệu chung có thể include common_types.h thay vì phụ thuộc trực tiếp vào header của nhau.

Lưu ý: Không phải mọi dependency giữa hai module đều là lỗi. Vấn đề nằm ở việc dependency có hợp lý, cần thiết và được tổ chức rõ ràng hay không.

7. Thiết kế một Embedded Module hoàn chỉnh

Để hiểu rõ hơn cách áp dụng Modular Programming, chúng ta sẽ xây dựng một ví dụ đơn giản gồm LED Module và Application.

Yêu cầu của chương trình:

  • LED Module cung cấp các function để khởi tạo, bật và tắt LED.
  • Application sử dụng interface của LED Module.
  • Chi tiết điều khiển GPIO được đặt bên trong implementation của module.
  • Application không trực tiếp thao tác với thanh ghi GPIO.

7.1. Cấu trúc chương trình

LED_Project/
|
+-- main.c
|
+-- led.h
|
+-- led.c
|
+-- gpio.h
|
+-- gpio.c

Trong ví dụ này, chúng ta có bốn thành phần chính:

File Vai trò
main.c Application, điều phối hoạt động chương trình.
led.h Interface của LED Module.
led.c Implementation của LED Module.
gpio.h và gpio.c Interface và implementation minh họa của GPIO Driver.

7.2. GPIO Driver Interface

Trước tiên, chúng ta định nghĩa interface của GPIO Driver. 

/* gpio.h */

#ifndef GPIO_H
#define GPIO_H

#include <stdint.h>

void GPIO_InitOutput(uint8_t pin);
void GPIO_WritePin(uint8_t pin, uint8_t value);

#endif

GPIO Driver cung cấp hai function:

  • GPIO_InitOutput(): Cấu hình chân GPIO thành Output.
  • GPIO_WritePin(): Ghi mức logic ra chân GPIO.

7.3. GPIO Driver Implementation

Tiếp theo, chúng ta triển khai hai function trong gpio.c. 

/* gpio.c */

#include "gpio.h"

void GPIO_InitOutput(uint8_t pin)
{
    /* Hardware-specific GPIO configuration */
    (void)pin;
}

void GPIO_WritePin(uint8_t pin, uint8_t value)
{
    /* Hardware-specific GPIO output operation */
    (void)pin;
    (void)value;
}

Đây là implementation minh họa. Trong một dự án thực tế, phần code bên trong sẽ được thay thế bằng thao tác phù hợp với MCU hoặc GPIO Driver đang sử dụng.

7.4. LED Module Interface

Chúng ta định nghĩa những chức năng mà LED Module cung cấp cho Application. 

/* led.h */

#ifndef LED_H
#define LED_H

void LED_Init(void);
void LED_On(void);
void LED_Off(void);
void LED_Toggle(void);

#endif

Application chỉ cần include file này để sử dụng LED Module.

7.5. LED Module Implementation

Trong led.c, chúng ta triển khai các function thông qua GPIO Driver. 

/* led.c */

#include "led.h"
#include "gpio.h"

#define LED_PIN 5U

static unsigned char led_state = 0U;

void LED_Init(void)
{
    GPIO_InitOutput(LED_PIN);

    led_state = 0U;
    GPIO_WritePin(LED_PIN, 0U);
}

void LED_On(void)
{
    GPIO_WritePin(LED_PIN, 1U);

    led_state = 1U;
}

void LED_Off(void)
{
    GPIO_WritePin(LED_PIN, 0U);

    led_state = 0U;
}

void LED_Toggle(void)
{
    if (led_state == 0U)
    {
        LED_On();
    }
    else
    {
        LED_Off();
    }
}

Trong ví dụ này:

  • LED Module sử dụng GPIO Driver để điều khiển phần cứng.
  • LED_PIN xác định chân GPIO được sử dụng.
  • led_state lưu trạng thái logic hiện tại của LED.
  • Các function được khai báo trong led.h là những chức năng Application có thể sử dụng.

Biến led_state và cách quản lý trạng thái nội bộ sẽ được phân tích kỹ hơn trong bài học về Encapsulation và Global Variable Management.

7.6. Application sử dụng LED Module

Cuối cùng, Application chỉ cần include led.h và gọi những function đã được công bố. 

/* main.c */

#include "led.h"

int main(void)
{
    LED_Init();

    while (1)
    {
        LED_On();

        /* Application tasks */

        LED_Off();

        /* Application tasks */
    }

    return 0;
}

Điểm quan trọng là main.c không cần include gpio.h và cũng không cần biết chân GPIO nào đang được sử dụng.

Application chỉ làm việc với interface của LED Module. LED Module chịu trách nhiệm xử lý những chi tiết liên quan đến GPIO Driver.

7.7. Sơ đồ giao tiếp giữa các thành phần

+--------------------------+
|       Application        |
|                          |
|       main.c             |
+------------+-------------+
             |
             | Include led.h
             | Call LED_Init()
             | Call LED_On()
             | Call LED_Off()
             v
+--------------------------+
|        LED Module        |
|                          |
|  Interface: led.h        |
|  Implementation: led.c   |
+------------+-------------+
             |
             | Include gpio.h
             | Call GPIO functions
             v
+--------------------------+
|       GPIO Driver        |
|                          |
|  Interface: gpio.h       |
|  Implementation: gpio.c  |
+------------+-------------+
             |
             v
+--------------------------+
|       MCU Hardware       |
+--------------------------+

Sơ đồ cho thấy mỗi thành phần có một phạm vi trách nhiệm riêng. Application không cần biết implementation của LED Module, và LED Module không cần đưa chi tiết GPIO vào interface của Application.

7.8. Biên dịch chương trình

Vì chương trình được chia thành nhiều source file, chúng ta cần biên dịch và liên kết các file tương ứng. 

gcc main.c led.c gpio.c -o led_project

Hoặc có thể biên dịch từng source file riêng biệt: 

gcc -c main.c -o main.o
gcc -c led.c -o led.o
gcc -c gpio.c -o gpio.o

gcc main.o led.o gpio.o -o led_project

Đây là nội dung đã được tìm hiểu ở Bài 28. Trong bài này, chúng ta sử dụng lại quy trình đó để xây dựng một chương trình có kiến trúc module rõ ràng.

Ghi nhớ: Modular Programming không chỉ là việc chia code thành nhiều file. Điều quan trọng là mỗi module có trách nhiệm rõ ràng, cung cấp interface phù hợp và hạn chế phụ thuộc vào implementation của các module khác.

8. Thay đổi Implementation mà không ảnh hưởng Application

Một trong những lợi ích lớn nhất của việc tách interface và implementation là chúng ta có thể thay đổi cách triển khai bên trong module mà không cần sửa đổi các thành phần đang sử dụng nó.

8.1. Implementation ban đầu

Giả sử LED Module ban đầu sử dụng GPIO Driver: 

/* led.c */

#include "led.h"
#include "gpio.h"

#define LED_PIN 5U

void LED_On(void)
{
    GPIO_WritePin(LED_PIN, 1U);
}

Application sử dụng: 

LED_On();

8.2. Thay đổi Implementation

Sau này, dự án có thể thay đổi cách điều khiển LED, chẳng hạn chuyển sang sử dụng một hardware abstraction layer khác hoặc một driver mới. 

/* led.c */

#include "led.h"
#include "board_gpio.h"

#define LED_PIN 5U

void LED_On(void)
{
    BoardGPIO_SetOutput(LED_PIN);
}

Mặc dù implementation đã thay đổi từ GPIO_WritePin() sang BoardGPIO_SetOutput(), Application vẫn có thể giữ nguyên lời gọi: 

LED_On();

Lý do là interface của LED Module không thay đổi. Application vẫn sử dụng cùng function prototype và cùng cách gọi.

8.3. Lợi ích của việc ổn định Interface

  • Giảm số lượng source file cần sửa khi thay đổi implementation.
  • Giúp Application ít phụ thuộc vào phần cứng cụ thể.
  • Hỗ trợ thay thế driver hoặc thư viện bên dưới module.
  • Giúp kiểm thử module độc lập dễ dàng hơn.
  • Giảm ảnh hưởng dây chuyền giữa các thành phần trong dự án.
Lưu ý: Việc thay đổi implementation chỉ không ảnh hưởng đến Application khi interface và hành vi mà Application dựa vào vẫn được giữ ổn định. Nếu thay đổi ý nghĩa của function, tham số, kiểu dữ liệu hoặc cách trả về, các thành phần sử dụng module vẫn có thể phải sửa đổi.

9. Những lỗi thường gặp khi thiết kế module

Khi bắt đầu áp dụng Modular Programming, có một số lỗi thiết kế thường xuất hiện trong các dự án C.

9.1. Đưa quá nhiều implementation vào header file

Header file nên tập trung vào những khai báo cần thiết để sử dụng module. Nếu đưa quá nhiều logic triển khai vào header, các thành phần khác có thể bị phụ thuộc vào những chi tiết không cần thiết.

Ví dụ không nên tổ chức như sau:

/* led.h */

#ifndef LED_H
#define LED_H

#define LED_PIN 5U

void LED_Init(void);

void LED_On(void)
{
    /* Detailed LED implementation */
}

#endif

Với một function thông thường được định nghĩa trong header và được include ở nhiều source file, chương trình có thể phát sinh lỗi multiple definition trong quá trình linking.

Thay vào đó, nên khai báo function trong header: 

/* led.h */

#ifndef LED_H
#define LED_H

void LED_Init(void);
void LED_On(void);

#endif

Và đặt phần định nghĩa trong source file: 

/* led.c */

#include "led.h"

void LED_On(void)
{
    /* LED implementation */
}

9.2. Công bố quá nhiều function không cần thiết

Một module không nên đưa tất cả function nội bộ vào header file. Chỉ những function thực sự cần thiết cho module khác mới nên được công bố trong public interface.

Nếu một function chỉ được sử dụng bên trong module, hãy cân nhắc giữ nó ở phạm vi nội bộ thay vì đưa vào header.

9.3. Một module có quá nhiều trách nhiệm

Nếu một module vừa xử lý LED, vừa quản lý UART, vừa đọc sensor và xử lý CAN message, module đó có thể đang đảm nhận quá nhiều nhiệm vụ không liên quan.

Nên xem xét tách thành các module riêng biệt để mỗi module có trách nhiệm rõ ràng hơn.

9.4. Application phụ thuộc trực tiếp vào chi tiết phần cứng

Nếu Application trực tiếp truy cập register hoặc sử dụng các function cấp thấp của driver để thực hiện mọi thao tác, mức độ phụ thuộc vào phần cứng sẽ tăng lên.

Nên tổ chức các lớp trung gian phù hợp để Application sử dụng chức năng thông qua interface có ý nghĩa ở mức ứng dụng.

9.5. Tạo dependency vòng giữa các module

Việc để hai module include header của nhau có thể là dấu hiệu cho thấy trách nhiệm của các module chưa được phân chia hợp lý.

Hãy xem xét tách những khai báo dùng chung sang một module riêng hoặc thay đổi hướng dependency để kiến trúc dễ hiểu hơn.

10. Checklist khi thiết kế Modular Programming

Khi thiết kế hoặc review một module trong dự án C, chúng ta có thể sử dụng checklist sau:

  • Module đã có trách nhiệm cụ thể và dễ mô tả chưa?
  • Các function trong module có liên quan đến cùng một nhóm chức năng không?
  • Interface đã công bố đầy đủ những chức năng cần thiết chưa?
  • Header file có tránh chứa những chi tiết implementation không cần thiết không?
  • Source file có triển khai đúng những function đã khai báo trong header không?
  • Những function chỉ phục vụ nội bộ có được giữ ngoài public interface không?
  • Module khác có đang phụ thuộc trực tiếp vào implementation không cần thiết không?
  • Có dependency nào không cần thiết giữa các module không?
  • Có xảy ra circular dependency giữa các header file hoặc module không?
  • Interface có đủ ổn định để implementation có thể thay đổi độc lập không?
  • Module có thể được kiểm thử thông qua interface của nó không?
  • Cấu trúc thư mục và cách đặt tên có nhất quán với dự án không?
Góc nhìn Automotive Embedded Software: Trong một dự án ECU, chương trình có thể chứa nhiều module như Lighting, Door Lock, Window Control, Wiper, Sensor và Communication. Việc thiết kế interface rõ ràng giúp các thành phần giao tiếp với nhau theo quy tắc thống nhất, giảm dependency không cần thiết và hỗ trợ quá trình tích hợp, kiểm thử cũng như bảo trì phần mềm.

11. Tổng kết

Trong bài học này, chúng ta đã tìm hiểu cách tổ chức chương trình C theo Modular Programming, tập trung vào sự phân chia giữa Interface và Implementation.

  • Modular Programming: Chia chương trình thành các module có trách nhiệm riêng biệt.
  • Interface: Công bố những chức năng và kiểu dữ liệu mà module cung cấp.
  • Implementation: Chứa logic triển khai thực tế của module.
  • Header File: Thường được sử dụng để khai báo interface.
  • Source File: Thường chứa phần implementation.
  • Public Interface: Những thành phần được phép sử dụng từ bên ngoài module.
  • Internal Implementation: Những chi tiết chỉ phục vụ hoạt động bên trong module.
  • High Cohesion: Các chức năng trong cùng module nên có mối liên hệ chặt chẽ.
  • Low Coupling: Hạn chế sự phụ thuộc không cần thiết giữa các module.
  • Dependency: Thể hiện mối quan hệ sử dụng giữa các module.

Có thể ghi nhớ nguyên tắc cốt lõi của bài học:

Một module tốt cần có trách nhiệm rõ ràng, cung cấp interface đơn giản và giữ những chi tiết triển khai bên trong module. Các thành phần khác nên sử dụng module thông qua interface thay vì phụ thuộc trực tiếp vào implementation.
