Bài 28: Separate Compilation & Linking

Trong các bài trước, chúng ta đã tìm hiểu về C Preprocessor, Header File, Macro và những kỹ thuật tổ chức code ở mức cơ bản. Tuy nhiên, khi một dự án C phát triển lớn hơn, việc đặt toàn bộ chương trình trong một file duy nhất sẽ khiến source code trở nên khó quản lý và bảo trì.

Trong thực tế, một dự án Embedded thường được chia thành nhiều module. Ví dụ, chương trình có thể bao gồm Application, GPIO Driver, UART Driver, CAN Driver và các module xử lý dữ liệu riêng biệt.

Để xây dựng một chương trình từ nhiều source file, C sử dụng cơ chế Separate Compilation và Linking. Mỗi source file có thể được biên dịch độc lập thành một object file. Sau đó, Linker kết hợp các object file và library cần thiết để tạo ra chương trình hoàn chỉnh.

Mục tiêu bài học:
  • Hiểu khái niệm Separate Compilation.
  • Phân biệt Source File, Header File và Object File.
  • Hiểu vai trò của Compiler và Linker trong quá trình build.
  • Biết cách chia một chương trình C thành nhiều source file.
  • Hiểu Symbol, External Linkage và Undefined Reference.
  • Biết cách biên dịch và liên kết nhiều file bằng GCC.
  • Hiểu cách Separate Compilation được áp dụng trong Embedded Project.

1. Separate Compilation là gì?

Separate Compilation là phương pháp biên dịch chương trình bằng cách chia source code thành nhiều translation unit và biên dịch từng translation unit độc lập.

Trong C, một source file sau khi được xử lý cùng các header file được include sẽ tạo thành một translation unit. Compiler có thể xử lý translation unit này mà không cần biên dịch lại toàn bộ các source file khác trong dự án.

Ví dụ, thay vì viết toàn bộ chương trình trong một file main.c, chúng ta có thể chia thành: 

Project/
│
├── main.c
├── uart.c
├── gpio.c
│
├── uart.h
└── gpio.h

Trong đó:

  • main.c: Chứa chương trình chính và gọi các module khác.
  • uart.c: Chứa phần implementation của UART module.
  • gpio.c: Chứa phần implementation của GPIO module.
  • uart.h: Khai báo interface mà module UART cung cấp.
  • gpio.h: Khai báo interface mà module GPIO cung cấp.

Mỗi file .c sẽ được biên dịch riêng thành một object file: 

main.c  → main.o
uart.c  → uart.o
gpio.c  → gpio.o

Sau đó, Linker kết hợp các object file để tạo ra executable: 

main.o + uart.o + gpio.o
              |
              v
         Executable

Đây chính là ý tưởng cơ bản của Separate Compilation.

Điểm cần nhớ: Separate Compilation cho phép mỗi source file được biên dịch độc lập. Khi một module thay đổi, thông thường chỉ cần biên dịch lại module đó và thực hiện linking lại chương trình.

2. Source File, Header File và Object File

Để hiểu rõ Separate Compilation, trước tiên cần phân biệt vai trò của các loại file thường xuất hiện trong một dự án C.

2.1. Source File (.c)

Source file là file chứa phần implementation của chương trình. Đây là nơi chúng ta định nghĩa function, variable và các logic xử lý.

Ví dụ file uart.c:

#include "uart.h"

void UART_Init(void)
{
    /* UART initialization */
}

void UART_SendByte(unsigned char data)
{
    /* Send one byte through UART */
}

File này chứa phần triển khai hai function: UART_Init() và UART_SendByte().

2.2. Header File (.h)

Header file thường chứa những khai báo cần được chia sẻ giữa các source file. Ví dụ: 

#ifndef UART_H
#define UART_H

void UART_Init(void);
void UART_SendByte(unsigned char data);

#endif

Khi một source file muốn sử dụng function được cung cấp bởi UART module, nó chỉ cần include header file: 

#include "uart.h"

Header file giúp compiler biết được function tồn tại và cách gọi function đó, thông qua function prototype.

Tuy nhiên, việc include header file không tự động cung cấp phần implementation của function. Phần implementation vẫn nằm trong uart.c và cần được liên kết trong quá trình build.

2.3. Object File (.o hoặc .obj)

Object file là kết quả của quá trình compiler và assembler xử lý một translation unit.

Object file thường chứa:

  • Machine code được tạo từ source code.
  • Thông tin về các symbol được định nghĩa.
  • Thông tin về các symbol chưa được giải quyết.
  • Relocation information phục vụ quá trình linking.
  • Các section và metadata liên quan đến object file.

Ví dụ: 

gcc -c uart.c -o uart.o

Lệnh này biên dịch uart.c thành uart.o nhưng chưa tạo executable hoàn chỉnh.

2.4. So sánh các loại file

Loại file Vai trò Ví dụ
Source File Chứa phần implementation của chương trình. main.c, uart.c
Header File Chứa declaration và interface dùng chung. uart.h, gpio.h
Object File Chứa code và thông tin cần thiết cho linking. main.o, uart.o
Executable Chương trình đã được liên kết hoàn chỉnh. firmware.elf, app.exe

3. Quy trình Separate Compilation và Linking

Một chương trình C được xây dựng từ nhiều source file thường trải qua các bước chính sau:

  1. Preprocessing.
  2. Compilation.
  3. Assembly.
  4. Linking.

3.1. Tổng quan luồng xử lý

             Source Files
             ┌───────────┐
             │  main.c   │
             │  uart.c   │
             │  gpio.c   │
             └─────┬─────┘
                   |
                   v
             Preprocessing
                   |
                   v
              Compilation
                   |
                   v
                Assembly
                   |
                   v
             Object Files
             ┌───────────┐
             │  main.o   │
             │  uart.o   │
             │  gpio.o   │
             └─────┬─────┘
                   |
                   v
                Linking
                   |
                   v
              Executable
                firmware.elf

3.2. Preprocessing

Ở bước đầu tiên, Preprocessor xử lý các chỉ thị như:

  • #include
  • #define
  • #if, #ifdef, #ifndef
  • Các macro expansion khác.

Ví dụ: 

#include "uart.h"

#define BAUDRATE 9600U

void UART_Init(void)
{
    /* Configuration */
}

Sau Preprocessing, nội dung header được đưa vào translation unit và macro được thay thế theo quy tắc của Preprocessor.

Có thể sử dụng GCC để chỉ thực hiện bước này: 

gcc -E uart.c -o uart.i

3.3. Compilation

Sau Preprocessing, compiler phân tích source code đã được xử lý, kiểm tra cú pháp, kiểu dữ liệu và chuyển code thành dạng trung gian hoặc mã assembly tùy theo toolchain.

Ví dụ: 

gcc -S uart.i -o uart.s

File uart.s chứa mã assembly được tạo ra từ translation unit.

3.4. Assembly

Assembler chuyển mã assembly thành machine code và tạo object file. 

gcc -c uart.c -o uart.o

Lệnh trên thực hiện các bước cần thiết để tạo object file uart.o, nhưng không thực hiện linking.

3.5. Linking

Sau khi các source file được biên dịch riêng thành object file, Linker sẽ kết hợp chúng lại.

Trong quá trình này, Linker thực hiện các công việc như:

  • Đọc symbol được định nghĩa trong các object file.
  • Tìm definition tương ứng cho những symbol được tham chiếu.
  • Giải quyết external references.
  • Thực hiện relocation theo bố trí địa chỉ.
  • Kết hợp các section theo quy tắc của linker và linker script.
  • Tạo executable hoặc firmware image theo cấu hình build.

Ví dụ: 

gcc main.o uart.o gpio.o -o firmware

Sau khi linking thành công, chương trình hoàn chỉnh sẽ được tạo ra với tên firmware.

Lưu ý: Trong Embedded Development, output thường là file ELF như firmware.elf. Từ file này, toolchain có thể tiếp tục tạo file HEX hoặc BIN để nạp vào MCU.

4. Ví dụ thực tế: Chia chương trình thành nhiều file

Để hiểu rõ hơn, chúng ta sẽ xây dựng một chương trình đơn giản gồm ba source file và hai header file.

4.1. Cấu trúc project

EmbeddedProject/
│
├── main.c
│
├── uart.c
├── uart.h
│
├── gpio.c
└── gpio.h

Mỗi module chịu trách nhiệm cho một chức năng riêng:

  • Main: Điều phối hoạt động của chương trình.
  • UART: Cung cấp các function giao tiếp UART.
  • GPIO: Cung cấp các function điều khiển GPIO.

4.2. File uart.h

#ifndef UART_H
#define UART_H

void UART_Init(void);
void UART_SendByte(unsigned char data);

#endif

Header file khai báo các function mà UART module cung cấp.

4.3. File uart.c

#include "uart.h"
#include <stdio.h>

void UART_Init(void)
{
    printf("UART Initialized\n");
}

void UART_SendByte(unsigned char data)
{
    printf("UART Send: %c\n", data);
}

File này chứa implementation của các function được khai báo trong uart.h.

4.4. File gpio.h

#ifndef GPIO_H
#define GPIO_H

void GPIO_Init(void);
void GPIO_SetHigh(void);
void GPIO_SetLow(void);

#endif

4.5. File gpio.c

#include "gpio.h"
#include <stdio.h>

void GPIO_Init(void)
{
    printf("GPIO Initialized\n");
}

void GPIO_SetHigh(void)
{
    printf("GPIO Output: HIGH\n");
}

void GPIO_SetLow(void)
{
    printf("GPIO Output: LOW\n");
}

4.6. File main.c

#include "uart.h"
#include "gpio.h"

int main(void)
{
    UART_Init();
    GPIO_Init();

    UART_SendByte('A');

    GPIO_SetHigh();
    GPIO_SetLow();

    while (1)
    {
        /* Main loop */
    }

    return 0;
}

Trong main.c, chúng ta không cần biết chi tiết implementation của UART và GPIO. Chương trình chỉ cần include header file để sử dụng các function được module cung cấp.

4.7. Quá trình build

Đầu tiên, biên dịch từng source file thành object file: 

gcc -c main.c -o main.o
gcc -c uart.c -o uart.o
gcc -c gpio.c -o gpio.o

Sau đó, liên kết các object file: 

gcc main.o uart.o gpio.o -o firmware

Cuối cùng, chạy chương trình: 

./firmware

Output minh họa: 

UART Initialized
GPIO Initialized
UART Send: A
GPIO Output: HIGH
GPIO Output: LOW

Như vậy, mặc dù chương trình được chia thành nhiều file, các function vẫn có thể gọi lẫn nhau thông qua declaration và linking.

5. Symbol và External Reference

Để hiểu cách Linker kết nối các object file, chúng ta cần tìm hiểu khái niệm Symbol.

Symbol là tên được sử dụng để đại diện cho một thực thể trong chương trình, chẳng hạn như function hoặc variable có thể được tham chiếu ở cấp độ object file.

Ví dụ: 

void UART_Init(void)
{
    /* Implementation */
}

int system_status = 0;

Trong object file tương ứng, các symbol có thể bao gồm:

  • UART_Init: Symbol đại diện cho function.
  • system_status: Symbol đại diện cho variable global.

5.1. Defined Symbol

Defined Symbol là symbol đã có definition trong object file.

Ví dụ trong uart.c: 

void UART_Init(void)
{
    /* Implementation */
}

Khi biên dịch thành uart.o, object file sẽ cung cấp symbol UART_Init.

5.2. Undefined Symbol

Undefined Symbol là symbol được tham chiếu trong một object file nhưng chưa có definition tại object file đó.

Ví dụ trong main.c: 

int main(void)
{
    UART_Init();

    return 0;
}

Khi biên dịch main.c thành main.o, compiler biết rằng UART_Init() là function được gọi, nhưng phần implementation không nằm trong translation unit của main.c.

Vì vậy, object file main.o sẽ chứa một external reference cần được giải quyết trong quá trình linking.

5.3. Linker giải quyết symbol như thế nào?

Giả sử:

  • main.o tham chiếu đến symbol UART_Init.
  • uart.o định nghĩa symbol UART_Init.

Khi Linker xử lý hai object file này, nó sẽ tìm definition tương ứng và kết nối lời gọi function trong main.o với implementation trong uart.o. 

main.o                         uart.o
┌─────────────────┐           ┌─────────────────┐
│                 │           │                 │
│ Call UART_Init  │ ────────> │ UART_Init()     │
│                 │           │ Implementation │
│ Undefined       │           │ Defined         │
│ Symbol          │           │ Symbol          │
└─────────────────┘           └─────────────────┘
                 \             /
                  \           /
                   v         v
                      Linker
                         |
                         v
                 Resolved Reference

Đây là một trong những nhiệm vụ quan trọng nhất của Linker.

6. External Linkage và Internal Linkage

Trong C, linkage xác định cách một tên có thể được liên kết với những khai báo khác trong các translation unit.

Hai loại linkage quan trọng khi làm việc với Separate Compilation là:

  • External Linkage.
  • Internal Linkage.

6.1. External Linkage

Một function hoặc variable có External Linkage có thể được tham chiếu từ các translation unit khác thông qua khai báo phù hợp.

Ví dụ:

/* uart.c */

int uart_status = 0;

void UART_Init(void)
{
    uart_status = 1;
}

Trong một source file khác: 

/* main.c */

extern int uart_status;

void UART_Init(void);

int main(void)
{
    UART_Init();

    if (uart_status == 1)
    {
        /* UART is initialized */
    }

    return 0;
}

Từ khóa extern ở đây khai báo rằng variable uart_status được định nghĩa ở nơi khác.

Tương tự, function prototype UART_Init() cho phép translation unit của main.c tham chiếu đến function được định nghĩa trong uart.c.

6.2. Internal Linkage

Khi sử dụng từ khóa static ở phạm vi file cho function hoặc variable, tên đó có Internal Linkage. 

/* uart.c */

static int uart_internal_status = 0;

static void UART_ResetInternalState(void)
{
    uart_internal_status = 0;
}

void UART_Init(void)
{
    UART_ResetInternalState();
}

Trong trường hợp này:

  • uart_internal_status chỉ được truy cập thông qua tên này trong translation unit hiện tại.
  • UART_ResetInternalState() chỉ có thể được gọi bằng tên này trong translation unit hiện tại.
  • UART_Init() không được khai báo static, nên có thể được cung cấp cho module khác.

Internal Linkage giúp giới hạn phạm vi sử dụng của các thành phần không cần công khai ra bên ngoài module.

6.3. So sánh External Linkage và Internal Linkage

Tiêu chí External Linkage Internal Linkage
Phạm vi liên kết Có thể được tham chiếu từ translation unit khác. Chỉ có ý nghĩa trong translation unit hiện tại.
Từ khóa thường gặp Không khai báo static ở file scope. static.
Mục đích Cung cấp interface cho module khác. Ẩn implementation nội bộ.
Ví dụ UART_Init() UART_ResetInternalState()
Góc nhìn Embedded: Một driver thường chỉ cần cung cấp một số function public như UART_Init(), UART_Send() hoặc UART_Receive(). Các helper function phục vụ implementation nội bộ nên được khai báo static khi phù hợp để tránh làm lộ quá nhiều symbol ra bên ngoài.

7. Các lỗi thường gặp khi Linking

Khi build một chương trình C gồm nhiều source file, một số lỗi có thể xuất hiện ở bước linking thay vì compilation. Đây là điểm cần phân biệt khi debug build error.

7.1. Undefined Reference

Đây là lỗi xảy ra khi Linker không tìm thấy definition tương ứng cho một symbol được tham chiếu.

Ví dụ:

/* main.c */

void UART_Init(void);

int main(void)
{
    UART_Init();

    return 0;
}

Nếu chỉ biên dịch và linking main.c mà không cung cấp object file chứa implementation của UART_Init(), Linker sẽ không tìm thấy function đó.

Lệnh: 

gcc main.c -o firmware

Có thể dẫn đến lỗi tương tự: 

undefined reference to `UART_Init'

Cách khắc phục là bổ sung source file chứa implementation: 

gcc main.c uart.c -o firmware

7.2. Multiple Definition

Lỗi Multiple Definition xảy ra khi nhiều object file cùng cung cấp definition cho một symbol có External Linkage, trong khi chương trình không cho phép các definition đó tồn tại đồng thời.

Ví dụ sai:

/* main.c */

int system_status = 0;
/* uart.c */

int system_status = 1;

Cả hai source file đều định nghĩa một global variable có cùng tên system_status. Khi linking, Linker có thể báo lỗi Multiple Definition.

Cách tổ chức phù hợp hơn là chỉ định nghĩa variable ở một source file: 

/* system.c */

int system_status = 0;

Các source file khác chỉ khai báo: 

/* system.h */

#ifndef SYSTEM_H
#define SYSTEM_H

extern int system_status;

#endif

Khi cần sử dụng: 

/* main.c */

#include "system.h"

void update_system(void)
{
    system_status = 1;
}

7.3. Function Declaration và Definition không khớp

Một lỗi khác là khai báo function trong header file không khớp với implementation trong source file.

Ví dụ:

/* uart.h */

void UART_SendByte(unsigned char data);
/* uart.c */

void UART_SendByte(unsigned int data)
{
    /* Implementation */
}

Hai khai báo trên không có cùng function type. Điều này có thể gây ra diagnostic hoặc lỗi liên kết tùy trường hợp và toolchain.

Vì vậy, cần bảo đảm function declaration và definition thống nhất về tên, kiểu trả về và danh sách tham số.

7.4. Quên thêm source file vào build system

Trong một project thực tế, source file có thể đã tồn tại trong thư mục nhưng chưa được thêm vào cấu hình build.

Ví dụ, project có: 

main.c
uart.c
gpio.c

Nhưng build command chỉ bao gồm: 

gcc main.c uart.c -o firmware

Nếu main.c gọi function trong gpio.c, Linker sẽ không tìm thấy implementation của function đó.

Cần kiểm tra danh sách source file trong Makefile, CMake, IDE project hoặc build configuration tương ứng.

8. Separate Compilation với GCC

Chúng ta có thể thực hành Separate Compilation bằng GCC thông qua một số lệnh cơ bản.

8.1. Biên dịch từng source file

gcc -c main.c -o main.o
gcc -c uart.c -o uart.o
gcc -c gpio.c -o gpio.o

Tùy chọn -c yêu cầu GCC biên dịch source file thành object file mà không thực hiện bước linking.

8.2. Linking các object file

gcc main.o uart.o gpio.o -o firmware

Lệnh này sử dụng Linker để kết hợp các object file thành executable.

8.3. Biên dịch và linking trong một lệnh

Nếu muốn thực hiện toàn bộ quá trình bằng một lệnh, có thể viết: 

gcc main.c uart.c gpio.c -o firmware

GCC sẽ gọi các công cụ cần thiết để thực hiện Preprocessing, Compilation, Assembly và Linking.

Mặc dù cách viết này ngắn gọn, việc biên dịch riêng từng source file giúp chúng ta dễ kiểm soát quá trình build và tận dụng lại những object file chưa thay đổi.

8.4. Kiểm tra symbol trong object file

GCC toolchain cung cấp công cụ nm để xem symbol được định nghĩa hoặc được tham chiếu trong object file. 

nm main.o
nm uart.o

Ví dụ, output có thể chứa các thông tin: 

                 U UART_Init
0000000000000000 T main

Trong đó:

  • U: Symbol được tham chiếu nhưng chưa được định nghĩa trong object file hiện tại.
  • T: Symbol được định nghĩa trong text section.

Các ký hiệu cụ thể có thể khác nhau tùy loại symbol, object format và toolchain.

8.5. Xem các section trong object file

Có thể sử dụng objdump để xem thông tin object file: 

objdump -h uart.o

Công cụ này có thể hiển thị những section như:

  • .text: Chứa mã lệnh.
  • .data: Chứa dữ liệu được khởi tạo.
  • .bss: Chứa dữ liệu chưa được khởi tạo tường minh.
  • .rodata: Thường chứa dữ liệu chỉ đọc.
Lưu ý: Đây là các công cụ phổ biến trong GCC toolchain. Với Embedded Toolchain, tên công cụ có thể có tiền tố theo kiến trúc, ví dụ arm-none-eabi-nm hoặc arm-none-eabi-objdump.

9. Incremental Build – Chỉ biên dịch lại phần thay đổi

Một ưu điểm quan trọng của Separate Compilation là khả năng hỗ trợ Incremental Build.

Thay vì phải biên dịch lại toàn bộ source code mỗi khi có thay đổi, build system có thể xác định những file cần được biên dịch lại.

9.1. Ví dụ

Giả sử project có: 

main.c
uart.c
gpio.c

Sau khi build lần đầu, chúng ta có: 

main.o
uart.o
gpio.o

Nếu chỉ thay đổi nội dung trong uart.c, build system có thể chỉ biên dịch lại: 

uart.c → uart.o

Sau đó thực hiện linking lại các object file: 

main.o + uart.o + gpio.o
              |
              v
          firmware

Không cần biên dịch lại main.c và gpio.c nếu chúng không bị ảnh hưởng bởi thay đổi.

9.2. Vai trò của Build System

Các công cụ như Make, CMake hoặc build system tích hợp trong IDE có thể quản lý quá trình này.

Chúng theo dõi quan hệ phụ thuộc giữa source file, header file và object file để xác định những thành phần cần được cập nhật.

Ví dụ một Makefile đơn giản: 

CC = gcc
CFLAGS = -Wall -Wextra

TARGET = firmware

OBJS = main.o uart.o gpio.o

$(TARGET): $(OBJS)
	$(CC) $(OBJS) -o $(TARGET)

main.o: main.c uart.h gpio.h
	$(CC) $(CFLAGS) -c main.c -o main.o

uart.o: uart.c uart.h
	$(CC) $(CFLAGS) -c uart.c -o uart.o

gpio.o: gpio.c gpio.h
	$(CC) $(CFLAGS) -c gpio.c -o gpio.o

clean:
	rm -f $(OBJS) $(TARGET)

Trong Makefile trên:

  • CC xác định compiler được sử dụng.
  • CFLAGS chứa các compiler options.
  • OBJS liệt kê các object file.
  • $(TARGET) là executable được tạo ra.
  • Các dependency giúp Make xác định file nào cần được build lại.
  • clean xóa các file được tạo trong quá trình build.

Đây là ví dụ cơ bản để hiểu cách build system quản lý nhiều source file. Trong dự án lớn, Makefile hoặc CMake thường có cấu trúc phức tạp hơn với nhiều thư mục, compiler options và library dependencies.

10. Separate Compilation trong Embedded Project

Trong dự án Embedded thực tế, Separate Compilation được sử dụng để tổ chức firmware thành các module độc lập.

Ví dụ, một hệ thống điều khiển có thể được chia thành: 

Firmware/
│
├── Application/
│   ├── main.c
│   ├── app.c
│   └── app.h
│
├── Drivers/
│   ├── UART/
│   │   ├── uart.c
│   │   └── uart.h
│   │
│   ├── GPIO/
│   │   ├── gpio.c
│   │   └── gpio.h
│   │
│   └── CAN/
│       ├── can.c
│       └── can.h
│
└── Config/
    └── system_config.h

Mỗi module có thể được biên dịch riêng và cung cấp các object file tương ứng cho quá trình linking.

10.1. Application Layer

Application Layer chứa logic của ứng dụng. Module này thường sử dụng các interface do driver hoặc service module cung cấp.

10.2. Driver Layer

Driver Layer chứa implementation liên quan đến việc giao tiếp với phần cứng. Ví dụ:

  • UART Driver.
  • GPIO Driver.
  • CAN Driver.
  • SPI Driver.
  • I2C Driver.

10.3. Linking trong Firmware Build

Sau khi các module được biên dịch thành object file, Linker kết hợp chúng cùng các thành phần cần thiết của toolchain để tạo firmware ELF.

Trong Embedded Development, quá trình linking còn liên quan đến Linker Script để xác định vị trí các section trong bộ nhớ MCU.

Ví dụ:

  • .text thường được đặt trong vùng Flash.
  • .rodata thường được đặt trong vùng Flash.
  • .data có vị trí lưu trữ ban đầu trong Flash và được khởi tạo vào RAM khi startup.
  • .bss thường được đặt trong RAM và được khởi tạo về 0 khi startup.

Sau khi tạo ELF, toolchain có thể chuyển đổi firmware thành file HEX hoặc BIN để nạp vào vi điều khiển.

Liên hệ với AUTOSAR: Trong dự án AUTOSAR, các module như RTE, BSW và Application Software cũng được tổ chức thành nhiều source file và object file. Build system sẽ biên dịch và liên kết các thành phần này theo cấu hình của ECU và toolchain được sử dụng.

11. Checklist khi kiểm tra Separate Compilation và Linking

Khi gặp lỗi build trong một dự án C hoặc Embedded C, có thể kiểm tra theo các bước sau:

  • Source file cần thiết đã được thêm vào build configuration chưa?
  • Header file đã được include đúng chưa?
  • Function prototype có khớp với function definition không?
  • Global variable có bị định nghĩa nhiều lần không?
  • Symbol được tham chiếu đã có definition tương ứng chưa?
  • Function hoặc variable có bị khai báo static ngoài dự kiến không?
  • Object file cần thiết đã được đưa vào linker command chưa?
  • Library dependency đã được cấu hình đúng chưa?
  • Linker Script có được sử dụng đúng với kiến trúc MCU không?
  • Địa chỉ và section trong linker output có phù hợp với memory layout không?
Góc nhìn khi debug: Nếu compiler báo lỗi cú pháp hoặc kiểu dữ liệu, hãy kiểm tra source code, header file và compiler diagnostics. Nếu Linker báo undefined reference hoặc multiple definition, hãy kiểm tra symbol và danh sách object file được đưa vào quá trình linking.

12. Tổng kết

Trong bài học này, chúng ta đã tìm hiểu cách xây dựng một chương trình C từ nhiều source file thông qua Separate Compilation và Linking.

  • Separate Compilation: Cho phép biên dịch từng translation unit độc lập.
  • Source File (.c): Chứa implementation của module.
  • Header File (.h): Chứa các declaration và interface dùng chung.
  • Object File (.o): Chứa machine code và thông tin cần thiết cho linking.
  • Linker: Kết hợp object file, giải quyết symbol và thực hiện relocation.
  • External Linkage: Cho phép symbol được tham chiếu từ translation unit khác.
  • Internal Linkage: Giới hạn symbol trong translation unit hiện tại.
  • Undefined Reference: Xảy ra khi Linker không tìm thấy definition tương ứng.
  • Multiple Definition: Xảy ra khi có nhiều definition xung đột cho cùng một symbol.
  • Incremental Build: Cho phép chỉ biên dịch lại những thành phần bị thay đổi.

Có thể ghi nhớ quy trình cơ bản:

Source File → Preprocessing → Compilation → Assembly → Object File → Linking → Executable/Firmware.

Bài học tiếp theo

Ở bài tiếp theo, chúng ta sẽ tìm hiểu sâu hơn về cách tổ chức chương trình thành các module có cấu trúc rõ ràng thông qua Modular Programming – Interface vs Implementation. Chúng ta sẽ phân biệt phần interface mà module cung cấp với phần implementation nội bộ, từ đó xây dựng chương trình dễ mở rộng, tái sử dụng và bảo trì hơn.
